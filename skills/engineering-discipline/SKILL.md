# Инженерная дисциплина

Применяй к каждой правке кода. Ревьюер проверяет PR по этим же пунктам.

## 1. Сначала — чтобы заработало
- **Минимум:** самая маленькая правка, которая решает задачу. Одно решение живёт в одном месте.
- **Сначала форма данных,** потом логика. Недопустимое состояние должно быть невозможно выразить типами.
- **Тест первым.** Напиши падающий тест, убедись, что он падает по ожидаемой причине, потом минимально почини. Если честный тест невозможен — не пиши плохой, а напиши в PR, как проверено.
- **Убери, прежде чем добавить.** Сложность сначала вычитается.
- **Проверка на входе:** внешние данные разбираются и проверяются один раз, где входят. Внутри им доверяем. Бизнес-логика — в чистых функциях.
- **Идемпотентность:** повторный запуск или запуск после падения на полпути приходит к тому же состоянию.
- **Не глуши компилятор:** никаких `as any`, `@ts-ignore` и `!` ради зелёного typecheck.
- **Перепроектирование — только если задача этого требует.** Не раздувай объём мелкой задачи.

## 2. Потом — чтобы было правильно
- **Чини причину.** Воспроизведи и найди причину. Заплатка, которая прячет падение (try/except вокруг, лишняя проверка на null, ретрай), — не исправление.
- **Если две правки с одной посылкой провалили одну и ту же проверку,** выпиши эту посылку одной фразой и проверь её, прежде чем делать третью.
- **Тест проверяет поведение, а не реализацию:** вызывает код так, как его вызывает пользователь, и проверяет то, что пользователь увидит. Если тест прошёл бы, когда функции возвращают пустоту, — он не годится.
- **Ожидания тестов не подгоняются под фактический вывод.** Если тест падает, сначала реши, кто неправ — код или тест, — и напиши это в PR.
- **Рефакторинг:** зафиксируй поведение тестом, меняй структуру, докажи, что поведение не изменилось.
- **По желанию** — отчёт по изменённым файлам на сборочном сервере: сложность и покрытие (crapper, CRAP < 10 на функцию), дубли (dryer). Мутационные тесты — только по указанию лида.

## 3. Практика
- **Мелкие проверяемые шаги:** закончил кусок, проверил, потом следующий.
- **До пуша** — `typecheck` и тесты затронутого пакета на сборочном сервере. На ревью — только зелёный CI.
- **Коммиты** маленькие и упорядоченные. В каждом: зачем, что изменено, чем проверено.
- **Только ветка `bot/OPE-…` → PR → ревью → вливание автоматикой.** Никогда не пушь в main.
- **Журнал в задаче:** что сделано, почему и чем проверено. Итог — одним комментарием.
- **Рабочие копии:** незакоммиченное не удаляй. Закрытые копии убирает `myr-ws close`.
- **Миграции БД перед сдачей PR (30.10, OPE-10067):** если PR добавляет новую миграцию в `packages/db/src/migrations/`, перед сдачей обязательно влить свежий `main` (`git fetch origin main && git merge origin/main`) и проверить номер миграции скриптом guard (`node scripts/myrmidon/ci/migration-guard.mjs`). Если номер уже занят в `main` или в параллельном открытом PR, перенумеровать одной командой: `pnpm db:renumber <старый_номер>` (или `pnpm db:renumber <старый_номер> <новый_номер>`).

## Ревьюеру: отставание от main — не причина отклонять (29.10)
Если CI на голове PR зелёный и GitHub показывает MERGEABLE (без конфликтов), статус BEHIND (ветка отстаёт от main) — НЕ повод для REQUEST CHANGES. Оценивай код и одобряй (метка `review-approved`), если код верен. Актуальность относительно main проверяет автовливание: оно перепроверяет CI на свежем main перед слиянием. REQUEST CHANGES — только за дефекты кода, тестов или красный CI. При конфликте (CONFLICTING) — вернуть исполнителю на rebase.

## Ревьюеру: одобрение доводишь до метки сам (29.10)
После вердикта `APPROVE PR #N <SHA>` на доске сам ставишь метку на PR:
1. `gh pr view N -R <repo> --json headRefOid` — голова должна совпадать с SHA из вердикта. Не совпадает — не ставь метку, пересмотри новую голову.
2. `gh pr edit N -R <repo> --add-label review-approved`.
3. Проверь, что метка встала (`gh pr view N --json labels`), и напиши в задаче одной строкой: «метка review-approved поставлена на <SHA>».
4. Включи автовливание GitHub: `gh pr merge N -R <repo> --auto --squash`. GitHub сам вольёт PR, когда обязательные проверки (`CI result`, `hot files review`) зелёные — защита ветки main включена 29.10. Не используй `--admin` и не вливай вручную в обход проверок.

## Ревьюеру: после вердикта закрой рабочую копию (29.10)
Рабочая копия для ревью — полная копия репозитория (~0,5 ГБ). После вердикта (APPROVE или REQUEST CHANGES) закрой её: `myr-ws close OPE-NNNN`. Для повторного ревью копия откроется заново. 29.10 копии ревьюеров заняли 20 ГБ тома ботов.

## Всем: `permittedActions` и `inspect_run` — кнопки оператора, а не твои права (30.10)
В ответе доски о прогоне (`execution`) поле `permittedActions` (`inspect_run`, `inspect_recovery`) — это кнопки оператора в интерфейсе. Фаза `reconnecting` — диагностика доски. Твоих прав ни то ни другое не ограничивает.

Комментарий, вердикт ревью, смену статуса и исполнителя, правку PR делай как обычно. Если доска действительно запрещает действие, она ответит ошибкой 4xx с текстом — тогда процитируй этот текст в задаче.

30.10 из-за неверного чтения этого поля 47 ревью застряли на ревьюерах, и половина инженеров простаивала. Поле переименуют в `operatorActions` (OPE-9972, PR #2023).

## Ревьюеру: как вернуть задачу на доработку (30.10)
Вердикт «вернуть» записывается одним запросом `PATCH /api/issues/<id>` от тебя, участника этапа: `{"status":"in_progress","comment":"REQUEST CHANGES PR #N <SHA>: …замечания…\"}`. Комментарий обязателен **в том же запросе** — прежние комментарии доска не учитывает. Доска сама вернёт задачу автору и запишет решение этапа.

Одобрение — как в разделе выше: вердикт `APPROVE PR #N <SHA>` в комментарии, метка `review-approved` и автовливание. Задача закроется после слияния.

`POST /issues/:id/stalled-review-decision` — маршрут оператора доски. Агенту он всегда отвечает 403, не используй его. Если `PATCH` ответил 4xx — процитируй текст ошибки в задаче.

## Ревьюеру: CI ещё идёт — это не повод для REQUEST CHANGES (30.10)
Если итоговая проверка `CI result` на голове PR ещё не завершилась (в очереди или идёт), вердикта не выноси. REQUEST CHANGES ставится только за дефекты кода и тестов или за упавший `CI result`.

Закончи прогон с комментарием «жду CI на <SHA>». С rc.19 доска сама ждёт CI: задача не блокируется, и тебя разбудят, когда CI завершится.

Упавшие необязательные проверки (`freeze`, `hot files review` в ожидании одобрения) — тоже не вердикт.

## Ревьюеру: не делай checkout задачи на ревью (30.10)
`checkout` (`POST /api/issues/<id>/checkout`, в MCP — `paperclipCheckoutIssue`) переводит задачу в `in_progress`. На задаче в `in_review` это выбивает её из ревью: этап висит, доска считает её взятой в работу и будит тебя по кругу (`idle_pickup`).

Ревью делается без checkout: прочитай задачу и PR, проверь `CI result` на текущей голове, запиши вердикт по разделам выше. Если checkout уже сделан, верни задачу в `in_review` запросом `PATCH {"status":"in_review","comment":"…"}` — этап ревью сохранится.
