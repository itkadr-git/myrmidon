# Инварианты платформы Myrmidon

> Источник: OPE-56 «Целевая архитектура» (v2.4), раздел 0 «Инварианты».
> Владелец документа: Alex. **Раздел меняет только владелец** (решение 09.10.2026, «давай так»).
> Изменение любого пункта — через ADR (`docs/architecture/adr/`) с явной ссылкой на заменяемый инвариант.

Инварианты — то, что должно оставаться верным в любом релизе. Каждый из них имеет номер,
автоматическую проверку в CI (fitness function) и ADR-обоснование. Нарушение любого инварианта —
красный CI, PR не идёт в ревью.

## Прецеденты разъездов 09.10 (финал 1.6.5), закрываемые инвариантами

- Пилот жил в коде после решения его убрать → INV-12.
- Два разных правила остывания (#1042 и #1070) → единая реализация очереди, INV-11.
- Две модели порядка очереди роя («приоритет × ожидание» #1075 и «сила феромона» #1047) столкнулись при слиянии → INV-11, ADR-0003.
- Дубли номеров миграций (#1047/#1003/#1096) → INV-13, ADR-0005.
- Документация на несуществующий код (#1088) → ADR обязательны к привязке к реальным модулям; PR-шаблон спрашивает «какой ADR реализует или меняет этот PR».

## Как добавить инвариант

1. Владелец формулирует решение (дословная формулировка фиксируется в ADR как цитата).
2. ADR в `docs/architecture/adr/ADR-00XX-<slug>.md` (статус accepted).
3. Если инвариант проверяется кодом — тест в `docs/architecture/invariants/` рядом с остальными; тест обязан иметь «красную сторону»: fixture, на котором проверка падает.
4. Строка в таблице выше.
