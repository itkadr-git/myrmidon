# Настройки в интерфейсе

> English version: [Settings-in-the-interface](Settings-in-the-interface)

Где делается повседневная настройка доски. В боковом меню настроек компании UI 2.0
сейчас доступны «Общие», «Участники», «Доступ», «Секреты», «Бюджеты»,
«Автономия» и «Касты агентов», а также разделы, реализованные в таблице
маршрутов UI 2.0. «Guardrails» намеренно не показывается: экран и маршрут для
него в этом выпуске ещё не реализованы. Источники: раздел «Настройка»
[README](https://github.com/itkadr-git/myrmidon/blob/main/README.ru.md) и
руководства оператора в
[`docs/myrmidon/guides/`](https://github.com/itkadr-git/myrmidon/tree/main/docs/myrmidon/guides).

## Карта одним абзацем

Модели и агенты настраиваются в их карточках; матрица автономии и список
участников — в **настройках компании**; оболочка UI 2.0 — в **настройках
инстанса → Experimental**; язык доски (RU/EN) — у каждого пользователя на
экране «Язык и форматы» интерфейса 2.0. Переключатели функций, которые всё
ещё переменные окружения (`MYRMIDON_*`, все по умолчанию выключены),
перечислены в
[SETTINGS.ru.md](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/SETTINGS.ru.md).

## Лимиты запусков (инстанс)

**Instance → General → секция «Run limits»** — меняются вживую, без
перезапуска сервера и без прерывания идущих прогонов
([run-limits](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/run-limits.ru.md)):

| Настройка | Что ограничивает | По умолчанию |
|---|---|---|
| `maxConcurrentRuns` | Сколько прогонов сервер держит в воздухе одновременно | выкл. |
| `maxStartsPerMinute` | Рампа старта: сколько прогонов может начаться за скользящую минуту | `5` (с 1.6.2) |
| `minFreeMemoryMb` | Свободная память в cgroup сервера, нужная для старта прогона | выкл. |
| `runMemoryEstimateMb` | Бюджет памяти одного прогона | `300` |
| `minFreeHostMemoryMb` | Свободная память хоста (`MemAvailable`), нужная для старта прогона | `15360` (15 ГБ, с 1.6.2) |

У каждого поля видно, откуда взялось действующее значение — сохранённая
настройка, переменная окружения или встроенное умолчание.

## Позиция и приоритет в очереди прогонов

На карточке queued-прогона в чате показываются место в очереди, её размер и
причина ожидания, если сервер передал эти данные. Интерфейс сначала берёт
метаданные прогона, а недостающие поля дополняет через endpoint позиции; пока
место неизвестно, endpoint опрашивается раз в 30 секунд. Если сервер пока не
обслуживает endpoint, строка не отображается — интерфейс не выдумывает данные.

В **Instance → General → Run queue priority** оператор может менять веса
ролей review, release, lead, engineer и docs, надбавку для текущего релиза,
шаг и предел aging очереди. У каждого поля показан источник: сохранённая
настройка, окружение сервера или значение по умолчанию. Изменения применяются
на следующем проходе допуска без перезапуска сервера. Если endpoint ещё не
доступен, панель сообщает об этом и не создаёт впечатления, что настройки
сохранены.

## Хаб доступов

Хаб находится в **Настройки компании → Доступы**. При включённом модуле
маршруты списка возвращают массивы доступов и хостов. При выключенном они
отвечают HTTP 200 с `enabled: false` и пустыми массивами. Вместо списка UI
показывает уведомление «пока недоступно». Это состояние выключенной функции,
а не сбой API. Проверьте `GET /api/myrmidon/access-hub/status` и
`MYRMIDON_ACCESS_HUB_ENABLED`. Если статус сообщает, что модуль включён, но
запрос списка завершается ошибкой или возвращает некорректные данные,
исследуйте проблему API/сервиса.

Подробности: [руководство оператора хаба доступов](../myrmidon/guides/access-hub.ru.md).

## Параллельные ходы агента

### Изоляция `hermes_local`

Изоляция настраивается в карточке агента в `adapterConfig` адаптера Hermes,
а не в настройках инстанса. По умолчанию она выключена. Задайте
`filesystemScope: "workspace"` для границы Bubblewrap только на workspace;
при необходимости задайте `filesystemSandboxCommand` (по умолчанию `bwrap`)
и `filesystemExtraPaths`. Изоляция сети независима: `networkScope: "deny"` отключает сеть, а `"allowlist"` использует
`networkAllowlist` для разрешённых
хостов/origin. Bubblewrap должен быть установлен на хосте агента. Подробности
в [справочнике оператора](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/SETTINGS.ru.md#изоляция-процесса-hermes_local).

В карточке агента, раздел **Container**: политика планирования
(`runtimeConfig.heartbeat.maxConcurrentRuns`) задаёт, сколько прогонов этого
агента может быть активно одновременно; доска нормализует значение в
диапазон 1–50 и записывает его в конфиг шлюза бота. Карточка сравнивает то,
что просит доска, с тем, что реально применил шлюз бота, и помечает
расхождение
([bot-container-card](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/bot-container-card.ru.md)).

Рядом: **WIP-лимит** ограничивает, сколько задач агент держит в работе —
**Настройки компании → WIP limit**, живое значение видно в строке каждого
агента
([wip-limit](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/wip-limit.ru.md)).
Параметры самоорганизации роя (стартовая сила феромона по приоритетам,
надбавка за ожидание, штраф за неудачный прогон без изменений задачи,
срок аренды, потолок активных задач на агента, вытеснение P0)
правятся вживую в **Instance → General → Self-organization (swarm)** — рой по
умолчанию выключен, включается переключателем «Enable the swarm»; остывание
задачи после пустого прогона (база 30 минут, потолок 24 часа) задаёт
охранник побудок (`general.swarm.cooldownBaseMin` / `cooldownCeilingHours`);
как включить рой и
проверить его работу за три действия —
[swarm-self-organization](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/swarm-self-organization.ru.md).
Низкоуровневые детали очередей —
[swarm-claim-settings](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/swarm-claim-settings.ru.md).

## Параллельные помощники

Агенты могут раздавать задачу параллельным субагентам-помощникам
(`delegate_task`). В карточке агента с адаптером `hermes_gateway` секция
**Parallel helpers** включает помощников и задаёт лимит на агента, модель
помощника и необязательный бюджет ходов на помощника; **Instance → General
→ секция «Parallel helpers»** задаёт потолок компании (по умолчанию `10`,
встроенного верхнего предела нет со времён HELPERS-NO-CAP (1.6.1) —
сохранённый потолок выше 50 лишь показывает жёлтое предупреждение
о нагрузке на хост) и умолчание на агента (`2`), а также показывает
подсказку о ёмкости, сравнивающую разрешённые лимиты со слотами сборки
сервера. Очистка любого поля ёмкости с сохранением отправляет `null` в PATCH
и удаляет сохранённую подсказку. Изменение применяется на следующем тике
сверки каждого бота, без перезапуска. Подробности:
[parallel-helpers](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/parallel-helpers.ru.md).

## Касты агентов (справочник ролей компании)

**Настройки компании → Agent castes** — собственный справочник ролей агентов
компании. Он начинается с двенадцати встроенных каст, а дальше владелец может
создавать, править и удалять касты; роль в карточке агента — это ключ из
этого справочника, и изменения видны рою сразу, без перезапуска
([custom-castes](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/custom-castes.ru.md)).

## Бюджеты (лимиты расхода по уровням)

**Настройки компании → Бюджеты** (`/company/settings/budgets`) — место, где
владелец задаёт лимиты расхода по уровням иерархии агентов: вся компания или
один проект (гнездо), каста, проход фуражировки или отдельная задача. Лимит
отвечает, сколько скоуп может тратить за период (календарный месяц UTC или
за всё время) и что происходит на лимите — жёсткий отказ или мягкая пауза с
карточкой владельцу. В строке виден расход против лимита (например
`$600.00 / $500.00 (120% израсходовано)`, пометка **Сверх лимита**), правка
идёт на месте: «Сохранить», «Создать» и «Удалить» уходят прямо в работающий
API — без перезапуска и без перезагрузки страницы. Переключатель вверху —
глобальный режим «только сигнал»: пока он включён, пересечение лимита лишь
сигналит и ничего не блокирует; экран показывает, откуда взято значение
(умолчание, выбор владельца или переменная окружения
`MYRMIDON_BUDGET_LIMITS_SIGNAL_ONLY`, которая блокирует переключатель).
Нижняя таблица — дополняемый журнал изменений: кто, когда и что менял, новые
записи сверху; удалённый лимит сохраняет свои строки. Чтение — участникам
компании, каждая мутация — только актору доски. Подробности:
[лимиты расхода](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/budget-limits.ru.md)
(API и хранение) и
[экран владельца](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/budget-limits-ui.ru.md).

## Бэкапы

Политика хранения бэкапов БД живёт в общих настройках инстанса
(`instance_settings.general.backupRetention`): тиры день/неделя/месяц и — с
1.6.5 — необязательный флаг **«Хранить только последний бэкап»** на странице
общих настроек инстанса. Когда он включён, прогон бэкапа потоково
верифицирует новый дамп и только после этого удаляет прежние; дамп, не
прошедший верификацию, удаляется, старые бэкапы сохраняются, а прогон
завершается ошибкой с причиной
([журнал изменений](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/CHANGELOG.ru.md),
1.6.5 BACKUP-KEEP-LAST).

Прогоны бэкапа и восстановления не ограничены базовым `statement_timeout`:
с 1.6.5 каждое соединение, которое открывает бэкап или восстановление,
ставит сессионный `statement_timeout` в `0` — то есть без лимита —
(параметр подключения JavaScript-клиента и
`PGOPTIONS="-c statement_timeout=0"` для процессов pg_dump/psql), поэтому
длинный `COPY` по большой таблице не обрывается базовым лимитом, заданным
через `ALTER DATABASE ... SET statement_timeout`. Остальные соединения
доски сохраняют базовый лимит без изменений
(1.6.5 BACKUP-STATEMENT-TIMEOUT).

## Окна ленты внимания

**Instance → General → «Лента внимания»** — два окна ленты внимания,
меняются вживую и применяются при следующей сборке ленты, без перезапуска:

| Настройка | Что ограничивает | Умолчание |
|---|---|---|
| Горизонт упавших прогонов | На сколько дней назад лента ищет неразрешённый упавший или превысивший таймаут прогон | `7` дней |
| TTL кэша ленты | Сколько секунд лента переиспользует собранный по компании снимок | `45` с |

Горизонт принимает целые дни от `1` до `365`; TTL — целые секунды от `0` до
`300`, где `0` выключает кэш (лента собирается заново при каждом чтении).
Каждое поле показывает свои границы, встроенное умолчание и откуда взято
действующее значение — из сохранённой строки настроек или из умолчания.

Панель читает и сохраняет через `GET`/`PATCH`
`/api/myrmidon/attention-feed`, за которыми стоит строка настроек инстанса
(`attentionFailedRunHorizonDays`, `attentionFeedCacheTtlSeconds` в блоке
general). Сохранение — частичная запись: пишется только изменённое окно, и
изменение попадает в аудит по каждой компании. Ни у одного из окон нет
переменной окружения, поэтому единственный источник — сохранённая строка (а
затем умолчание); значение, поправленное руками и не являющееся целым числом
в границах, читается как умолчание — тот же откат, что применяет сама лента.

- **Сторож зависших прогонов** — секция «Run stall detection» на странице
  Instance → General (с 1.6.5) правит сторож вживую, без перезапуска:
  интервал прохода (`checkIntervalSec`, 15 с – 24 ч) и размер страницы скана
  (`pageSize`, 1–200). Выключатель и порог тишины показаны только для
  чтения со ссылкой на секцию Team liveness — им они принадлежат
  (`runStallEnabled`, `runStallThresholdSec` на
  `/api/myrmidon/team-liveness`). У каждого значения виден источник —
  сохранённая строка настроек (`instance_settings.general.runStall`),
  окружение развёртывания (`MYRMIDON_RUN_STALL_*`) или встроенное
  умолчание. Пишет администратор инстанса через `GET`/`PATCH` на
  `/api/myrmidon/run-stall`.
- **Состав процессов доски** (с 1.6.6) — сколько HTTP-процессов (`api`) и
  сколько планировщиков (`worker`) запускает развёртывание; читается один
  раз при старте из ключа настроек инстанса `general.processes`. Ключа нет —
  это `{ api: 1, worker: 0 }`, одиночный процесс, как раньше; нечитаемая
  строка отказывает старту и называет исправление в журнале. При нескольких
  процессах их готовность отдают эндпоинт готовности процесса
  `GET /internal/ready` и агрегат `GET /healthz` (200, только когда готовы
  все api-процессы) для балансировщика.
- **Контекст долгих задач** — задача, чья история больше не помещается в
  окно модели, сбрасывается автоматически, а не роняет прогон на сжатии
  контекста: сессия, дошедшая до `resetPct` (умолчание — 70 %) окна модели,
  сбрасывается до того, как следующий прогон её продолжит, а история в
  payload побудки ограничена не только по числу записей, но и по объёму.
  Настраивается переменными `MYRMIDON_LONG_TASK_CONTEXT_*` и
  `MYRMIDON_CONTINUATION_*` (с 1.6.6) — подробности в руководстве
  [long-task-context](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/long-task-context.md)
  и в
  [SETTINGS.ru.md](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/SETTINGS.ru.md).

## Ещё в интерфейсе

- **Порог диска хоста** — Instance → General, «Host disk» (по умолчанию
  85 %); доска меряет заполнение диска хоста на каждом тике планировщика и
  поднимает сигнал внимания.
- **Квоты диска на бота** — панель «Per-bot disk quota» на странице общих
  настроек инстанса, с переопределениями в карточке агента.
- **Режим бюджетов** — только сигнал, пауза с карточкой владельцу или
  жёсткий отказ новых прогонов; ставится вживую на инстанс
  ([budget-enforcement](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/budget-enforcement.ru.md)).
- **Окна ленты внимания** — панель «Лента внимания» в настройках инстанса
  (Instance → General, с 1.6.6) задаёт, на сколько дней назад лента внимания
  ищет неразрешённый упавший или превысивший таймаут прогон (1–365 дней,
  умолчание 7) и сколько секунд собранная лента переиспользуется для
  компании (0–300 секунд, умолчание 60; `0` выключает кэш; снимок старше TTL, но не старше двух TTL, отдаётся сразу, пока одна фоновая пересборка обновляет его). У каждого поля
  видны границы, встроенное умолчание и пометка, откуда взято действующее
  значение — из сохранённой строки настроек или из умолчания. Сохранение
  применяется без перезапуска: лента подхватывает новое значение при
  следующей сборке. Читает любой участник доски, пишет администратор
  инстанса через `GET`/`PATCH /api/myrmidon/attention-feed` (значения
  хранятся как `attentionFailedRunHorizonDays` и
  `attentionFeedCacheTtlSeconds` в настройках инстанса).

## Модель прогона шлюза

В деталях прогона на странице агента указана модель, которая фактически
ответила. Для прогонов `hermes_gateway` значение берётся по цепочке
приоритетов: модель из ответа шлюза, затем `model_group` LiteLLM, на которую
был направлен запрос, затем модель, заданная в конфигурации запуска. Пустые
значения и сентинел `unknown` на каждом шаге отбрасываются, поэтому поле
либо содержит реальное имя модели, либо отсутствует.
## Runtime-настройки поведения (behavior-settings API)

Начиная с Myrmidon 1.7 (SETTINGS-TO-UI), настройки поведения можно читать и изменять на лету без перезапуска сервера:
- `GET /api/myrmidon/behavior-settings/definitions` — список всех определений настроек, их scope, типов и значений по умолчанию.
- `GET /api/myrmidon/behavior-settings` (а также `?key=:key` или `/key/:key`) — чтение действующих настроек инстанса и источников значений (`ui`, `env`, `default`).
- `PATCH /api/myrmidon/behavior-settings` (и алиас `PUT`) — изменение настроек уровня инстанса (только для администраторов инстанса).
- `GET|PATCH /api/myrmidon/behavior-settings/company/:companyId` — чтение и обновление настроек уровня компании (требуются права доступа к компании).

Строго соблюдается изоляция scope: маршруты инстанса отклоняют ключи компании, а маршруты компании отклоняют ключи инстанса с ошибкой HTTP 400. Страница Agents обновляет данные активных прогонов каждые 60 секунд. Если данные нужны немедленно, используйте ручное обновление страницы.
