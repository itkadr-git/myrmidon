# Агенты и роли

> English version: [Agents-and-castes](Agents-and-castes)

Myrmidon выполняет работу как команда агентов. У каждого агента есть запись
на доске: его роль, модель, инструкции, бюджет и состояние — а в
контейнерном режиме и собственная изолированная среда запуска.

## Что такое агент

Агент — это запись на доске плюс среда запуска. В записи хранятся:

- **роль** (ключ касты, например `coder` или `reviewer`): она решает, из
  какой очереди агент берёт работу, какие классы действий к нему применяет
  [матрица автономии](Safety-and-guardrails.ru) и какую долю бюджета
  компании он может тратить;
- **модель**, на которой работают его запуски (из зарегистрированных в
  компании провайдеров — см. [Модели и бюджеты](Models-and-keys.ru));
- **пакет инструкций** — файлы, которые агент читает при каждом запуске
  (входной файл и сопутствующие документы);
- **банк памяти** (необязательно), собственный ключ API и секреты.

Карточка агента — окно оператора во всю эту работу: на её вкладках видны
состояние, память, инструкции, контейнер и стоимость последних запусков.

Страница «Агенты» позволяет смотреть агентов всей компании или отдельного
проекта. Выберите область вкладками компании и проекта; выбранный проект
сохраняется в URL, а список и оргструктура фильтруются по его участникам.
Результаты можно дополнительно сузить по роли и модели. API списка также
поддерживает `q` (поиск без учёта регистра по имени, роли или должности),
`status` (один статус или список через запятую), точное совпадение `role` и
`reportsTo` (ID руководителя или `none` для корневых агентов). Фильтры
объединяются через AND и применяются после проверки доступа; неизвестные
параметры запроса по-прежнему дают HTTP 400. Подробности — в
[руководстве по флоту](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/ui2-agents-fleet.md).

## Экран «Флот агентов»

В UI-2 доступен общий для компании экран «Флот агентов» по адресу
`/{company}/agents`. Он группирует агентов по связям подчинения, показывает
состояние каждого агента и последний активный прогон, а также ведёт на
страницу карточки/чата агента. Данные агентов обновляются каждые 30 секунд,
прогонов — каждые 15 секунд; статус приостановленного агента остаётся
отдельным. Подробности — в
[руководстве по флоту](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/guides/ui2-agents-fleet.md).

## Контейнерная среда

Агент с адаптером `hermes_gateway` может работать внутри Docker-контейнера,
которым управляет доска. Раздел **Container** карточки хранит настройки
контейнера и показывает его живое состояние. Контейнер бота:

- имеет ровно один записываемый том для своих данных, с дисковой квотой на
  бота — один «сбежавший» клон не заполнит диск хоста;
- монтирует общие read-only кэши (пакеты pnpm, модули Go, объекты git), так
  что загрузки хранятся один раз на хост, а не по разу на бота;
- выходит на доску через собственный ключ шлюза, а наружу — через прокси
  хост-сервера (см. [Обслуживание](Server-maintenance.ru)).

### Защита архивов bot-disk

Хостовый писатель архивов `botd` создаёт bundle- и tar-файлы с правами
`0640`, приватные patch-файлы и манифесты — `0600`, а каталоги архивов —
`0750` независимо от унаследованного umask процесса. Файлы disk-state и
кэша attention/cooldown создаются с правами `0640`. Это защищает единственную
копию незапушенной работы бота от других процессов на общем хосте. Уже
созданные архивы не переписываются; их состав и политика хранения не меняются.

### Необязательная централизованная память fleetd

Хостовый демон `fleetd` может проксировать запросы централизованной памяти,
если в его JSON-конфигурации задан блок `memory` с `enabled: true`, URL по
HTTP(S) и непустой `bank`. Необязательные bearer-токен `token` и `timeoutMs`
(100–120000; по умолчанию 15000) задают параметры запросов к апстриму.
Без включённого блока маршруты памяти по умолчанию выключены: они отвечают
`503 centralized_memory_disabled` и не обращаются к апстриму. Проверка
`--check-config` отклоняет пустой банк, URL не по HTTP(S) и URL со встроенными
учётными данными. Клиент использует только HTTP(S), не путь файловой системы
хоста и не Docker socket. Для этих маршрутов действует обычная bearer-
аутентификация fleetd. См. [описание изменения fleetd](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/changes/fleetd-centralized-memory-client.md).

## Инструкции с историей

Каждое изменение пакета инструкций агента — добавление файла, удаление,
правка пакета — сохраняется как полная ревизия. Любую раннюю ревизию можно
восстановить через API, и само восстановление тоже становится ревизией:
ничего не теряется. [Матрица автономии](Safety-and-guardrails.ru) решает,
может ли агент менять инструкции сам или только с одобрения.

## Память

Вкладка **Memory** карточки агента показывает записи его банка памяти — того
самого банка, куда агент пишет во время запусков. Со вкладки оператор может
просмотреть записи, выгрузить весь банк в JSON, удалить одну запись или
очистить банк целиком.

## Восстановление вместо ручного надзора

Доска следит за агентами и чинит то, что сломалось:

- агента, оставшегося в статусе `error` после сбойного запуска, доска
  возобновляет сама, с нарастающей паузой (1, 5, 15 минут); если
  возобновления не помогают, карточка попадает на стол внимания — к
  оператору;
- запуск, чей прогресс не двигался дольше порога залипания (по умолчанию 20
  минут), доска прерывает, задачу возвращает в `todo`, а исполнителя будит
  заново — доска не ждёт жёсткого таймаута, чтобы заметить зависший
  запуск.

## Жизненный цикл: завершение (terminate) vs удаление (delete) и история затрат

Жизненный цикл агента включает приостановку, возобновление, сброс ошибки, завершение и удаление:

- **Завершение** (`POST /api/agents/:id/terminate`): безвозвратно деактивирует агента. Запуски прекращаются, но запись агента, выполненные задачи, логи и финансовая история сохраняются для аудита.
- **Удаление** (`DELETE /api/agents/:id`): полностью удаляет запись агента из базы. Для гарантии целостности финансовой истории агент с записанными расходами (`cost_events`) не может быть удалён: API возвращает `HTTP 409 Conflict` с кодом `agent_has_cost_events` и пояснением о необходимости использовать `terminate`. При наличии ссылок из других таблиц нарушение внешних ключей возвращает `HTTP 409 Conflict` с кодом `agent_referenced` вместо ошибки 500.

Для агентов с карточкой контейнера (bot container) на локальной или удалённой площадке завершение и удаление вызывают очистку контейнера (`POST /v1/bots/{botKey}/cleanup` или `DELETE /v1/bots/{botKey}`) для остановки, удаления контейнера и удаления каталога данных на хосте до изменения базы данных. Эта очистка fail-closed: если удалённая площадка недоступна или очистка завершилась ошибкой, операция завершения/удаления прерывается, сохраняя запись агента в базе для повторной попытки и предотвращая появление забытых (orphaned) контейнеров.

## Образ среды OMP

Самостоятельный образ `agent-runtime-omp` запускает `omp` непосредственно на
Bun 1.4.3 с закреплённой версией `@oh-my-pi/pi-coding-agent` 18.9.2. Он
работает с uid/gid 1000, использует собственные `HOME` и каталоги
XDG/сессий и не использует shim базового образа. При сборке выполняются
smoke-check: точные версии Bun и OMP, наличие `omp` в `PATH`, команды
`omp --help` и `omp models ls`; обращений к провайдеру модели нет.

Цель bake `omp` рассчитана на `linux/amd64`. CI настроен на сборку,
публикацию и подпись digest через cosign keyless OIDC. Перед использованием
тега проверьте запуск workflow и digest в registry: конфигурация не
подтверждает успешную публикацию. Инструкции сборки/запуска и scope CI — в
[семействе образов среды агента](../../docker/agent-runtime/README.ru.md).
