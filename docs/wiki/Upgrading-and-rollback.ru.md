# Обновление и откат

> English version: [Upgrading-and-rollback](Upgrading-and-rollback)

## Обновление установщиком (обычный путь)

На сервере, поставленном однострочной командой, обновление — та же команда
ещё раз:

```sh
curl -fsSL https://github.com/itkadr-git/myrmidon/releases/download/myr-v1.6.5-rc.5/install.sh | sudo bash
```

Пока выпуск 1.6.5 не стал финальным, команда ставит текущего кандидата:
установщик приложен к выпускам начиная с 1.6.5, и постоянная ссылка
`releases/latest/download/install.sh` пока отдаёт 404 — она заработает вместе
с финальным выпуском. Установщик находит выпуск, **снимает копию базы данных
до любых изменений**, переключается на новый выпуск и ждёт ответа доски. Если
новая доска не поднялась, установщик **сам возвращается на прежний выпуск**,
а копия базы остаётся. Конкретный выпуск: `install.sh --version myr-vX.Y.Z`.
Когда короткая ссылка `latest` заработает, она по-прежнему ведёт только на
последний **стабильный** выпуск, а RC ставится только по точному тегу.

## Обновление через deploy.sh (ручной поток)

На серверах, которыми управляют руками, путь — скрипт выката, см.
[Ручной выкат](Manual-deployment.ru). Заметки оператора по каждому выпуску
живут в
[`docs/myrmidon/deploy.ru.md`](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/deploy.ru.md),
а журнал изменений называет выпуск, в который вошло каждое изменение.

## Обновление

Остаток страницы описывает ручной поток `deploy.sh` для серверов под ручным
управлением — полная процедура в [Ручном выкате](Manual-deployment.ru);
здесь — справочник оператора.

Обновление идёт тем же скриптом, что и установка:

```sh
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --digest sha256:<новый digest>
```

или, для опубликованного выпуска, с резолвом digest из манифеста релиза
(`release-components.json`, загружается вложением выпуска):

```sh
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --release myr-vX.Y.Z
```

Что делает выкат, по порядку:

1. **Гейт «только из CI»** — до любых действий (до `docker pull`, дампа,
   обслуживания): проходит только образ, собранный CI из `main` или тега
   `myr-v*`. Флага обхода нет.
2. **Дамп БД** — `DUMP_COMMAND` в `DUMP_DIR`; отсутствующий или слишком
   маленький файл прерывает выкат.
3. **Проверка на копии базы** (`MYRMIDON_PREDEPLOY_CHECK=1`, по умолчанию) —
   дамп разворачивается в одноразовый Postgres, на копии поднимаются новая
   доска и новый dockergate того же релиза, `/api/health` должен ответить
   `ok` с версией и коммитом нового образа, пройденные маршруты должны
   отвечать. Любой сбой останавливает выкат **до** окна обслуживания: бой
   не трогается.
4. **Одно окно обслуживания** — доска, dockergate, fleetd и список образов
   ботов катятся вместе. Компонент, уже работающий на образе релиза, не
   перезапускается.
5. **Доказательство здоровья** — доска по `/api/health` (версия и коммит),
   dockergate по журналу (`self-check ok` / `config_reloaded` называют
   версию нового бинаря и хеш конфига), fleetd — пробой здоровья.
6. **Всё или ничего** — сбой любого компонента внутри окна откатывает
   изменённые компоненты, конфиг dockergate и доску вместе
   (`MYRMIDON_COMPONENT_AUTO_ROLLBACK=1`, по умолчанию). Карточки ботов
   переключаются пачками не больше 5, каждый бот — только пока его агент на
   паузе или простаивает: ни один запуск не прерывается.

## Кандидаты и финальные выпуски (с 1.6.5)

Выпуск проходит пробный прогон, прежде чем стать **Latest** на GitHub:

1. **Тег-кандидат.** `myr-vX.Y.Z-rc.N` собирает все образы компонентов как
   `X.Y.Z-rc.N`; публикация уходит GitHub **pre-release** и метку `latest`
   не трогает.
2. **Выкат кандидата.** `deploy.sh --release myr-vX.Y.Z-rc.N` работает как
   обычный выпуск — выкат RC и есть пробный прогон релизного потока.
3. **Проверка на бою.** Здоровье на `X.Y.Z-rc.N`, список внимания без новых
   повреждений, агенты берут задачи, образы ботов применились.
4. **Финальный тег.** Когда кандидат признан годным, на ТОМ ЖЕ коммите
   ставится `myr-vX.Y.Z` — без пересборки; workflow образов дотегирует те же
   образы, публикуется финальный релиз, всё ещё без `latest`.
5. **Перевод в Latest — отдельным шагом**, только когда финальный релиз
   работает на бое и прошёл smoke:

   ```sh
   scripts/myrmidon/release/promote-latest.sh --tag myr-vX.Y.Z \
     --health-url https://<доска>/api/health --health-token-file <файл-ключа-доски>
   ```

   Команда отказывает, если тег — кандидат, релиз — pre-release, коммит
   релиза не на `main` или доска отвечает любой другой версией, кроме
   `X.Y.Z`.

## Откат

```sh
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env                          # на предыдущий образ
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --to sha256:<64 hex>
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --local                  # на локальный образ, без pull (с 1.6.0)
```

- Откат возвращает образ и проверяет health по меткам старого образа. **БД
  не восстанавливается** по умолчанию; восстановление — отдельный явный путь
  (`--restore-dump` с `RESTORE_COMMAND`, скрипт просит напечатать
  `RESTORE`).
- Откату не нужна живая доска, и он **не блокируется** проверкой «только из
  CI»: это аварийный путь.
- Откат доски не откатывает компоненты, откат компонента не трогает доску.
- **Автоматический откат по здоровью** (`AUTO_ROLLBACK=1`, по умолчанию с
  1.4.0): когда выкат, запущенный из интерфейса доски, проваливает проверку
  здоровья, хостовой исполнитель немедленно запускает `rollback.sh` на
  образ, который выкат запомнил перед переключением.
