# Обновление и откат

> English version: [Upgrading-and-rollback](Upgrading-and-rollback)

## Обновление установщиком (обычный путь)

На сервере, поставленном однострочной командой, обновление — та же команда
ещё раз:

```sh
curl -fsSL https://github.com/itkadr-git/myrmidon/releases/latest/download/install.sh | sudo bash
```

Установщик находит последний выпуск, **снимает копию базы данных до любых
изменений**, переключается на новый выпуск и ждёт ответа доски. Если новая
доска не поднялась, установщик **сам возвращается на прежний выпуск**, а
копия базы остаётся. Конкретный выпуск: `install.sh --version myr-vX.Y.Z`.
Предрелизы (RC) однострочная команда не ставит: она всегда идёт за последним
**стабильным** выпуском, а RC ставится только по его точному тегу.

## Обновление через deploy.sh (ручной поток)

На серверах, которыми управляют руками, путь — скрипт выката, см.
[Ручной выкат](Manual-deployment.ru). Заметки оператора по каждому выпуску
живут в
[`docs/myrmidon/deploy.md`](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/deploy.ru.md),
а журнал изменений называет выпуск, в который вошло каждое изменение.

## Обновление

Остаток страницы описывает ручной поток `deploy.sh` для серверов под ручным
управлением — полная процедура в [Ручном выкате](Manual-deployment.ru);
здесь — справочник оператора.

Обновление идёт тем же скриптом, что и установка:

```sh
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --digest sha256:<новый digest>
```

или, для опубликованного выпуска, с резолвом digest из манифеста релиза
(`release-components.json`, загружается asset'ом релиза):

```sh
scripts/myrmidon/deploy/deploy.sh --config /path/to/deploy.env --release myr-vX.Y.Z
```

Что делает выкат, по порядку:

1. **Гейт «только из CI»** — до любых действий (до `docker pull`, дампа,
   обслуживания): проходит только образ, собранный CI из `main` или тега
   `myr-v*`. Флага обхода нет.
2. **Дамп БД** — `DUMP_COMMAND` в `DUMP_DIR`; отсутствующий или слишком
   маленький файл прерывает выкат.
3. **Проверка на копии базы** (`MYRMIDON_PREDEPLOY_CHECK=1`, по умолчанию) —
   дамп разворачивается в одноразовый Postgres, на копии поднимаются новая
   доска и новый dockergate того же релиза, `/api/health` должен ответить
   `ok` с версией и коммитом нового образа, пройденные маршруты должны
   отвечать. Любой сбой останавливает выкат **до** окна обслуживания: бой
   не трогается.
4. **Одно окно обслуживания** — доска, dockergate, fleetd и список образов
   ботов катятся вместе. Компонент, уже работающий на образе релиза, не
   перезапускается.
5. **Доказательство здоровья** — доска по `/api/health` (версия и коммит),
   dockergate по журналу (`self-check ok` / `config_reloaded` называют
   версию нового бинаря и хеш конфига), fleetd — пробой здоровья.
6. **Всё или ничего** — сбой любого компонента внутри окна откатывает
   изменённые компоненты, конфиг dockergate и доску вместе
   (`MYRMIDON_COMPONENT_AUTO_ROLLBACK=1`, по умолчанию). Карточки ботов
   переключаются пачками не больше 5, каждый бот — только пока его агент на
   паузе или простаивает: ни один запуск не прерывается. Применение образа
   асинхронно: выкат ждёт задачу применения и затем подтверждает контейнер на
   образе релиза. Отказ применения (409), занятый бот, таймаут или успешная
   задача, чей контейнер остался на старом образе, — всё это «отложено», а не
   сбой: их доделает периодический обход. Сбой или откладывание одного бота
   никогда не останавливает прогон: доходят все оставшиеся боты, и прогон
   заканчивается строкой `WARNING`, когда есть отложенные, и `DEGRADED` —
   только когда хотя бы один реально не переключился.

Выкат также управляет настройками сервера PostgreSQL (с 1.6.5, DB-TUNING):
декларативный источник лежит в репозитории
(`scripts/myrmidon/deploy/db-tuning.sql`), выкат применяет его через
`DB_TUNE_COMMAND` и затем проверяет каждую пару `DB_TUNE_EXPECTED` через
`SHOW` — расхождение означает неудачный выкат, и прежние значения
(записанные до первого управляемого применения) возвращаются сразу. Откат
возвращает настройки через `DB_TUNE_ROLLBACK_COMMAND` и проверяет их по
записанным прежним значениям. Все четыре настройки `DB_TUNE_*`
необязательны; при пустой `DB_TUNE_COMMAND` шаг пропускается, и база
остаётся с теми настройками, что у неё есть. Значения, порядок проверки и
запрос `pg_stat_statements` для замера «до/после» — в
[`docs/myrmidon/deploy.md`](https://github.com/itkadr-git/myrmidon/blob/main/docs/myrmidon/deploy.ru.md).

## Кандидаты и финальные выпуски (с 1.6.5)

Выпуск проходит пробный прогон, прежде чем стать **Latest** на GitHub:

1. **Тег-кандидат.** `myr-vX.Y.Z-rc.N` собирает все образы компонентов как
   `X.Y.Z-rc.N`; публикация уходит GitHub **pre-release** и метку `latest`
   не трогает.
2. **Выкат кандидата.** `deploy.sh --release myr-vX.Y.Z-rc.N` работает как
   обычный выпуск — выкат RC и есть пробный прогон релизного потока.
3. **Проверка на бою.** Здоровье на `X.Y.Z-rc.N`, список внимания без новых
   повреждений, агенты берут задачи, образы ботов применились.
4. **Финальный тег.** Когда кандидат признан годным, на ТОМ ЖЕ коммите
   ставится `myr-vX.Y.Z` — без пересборки; workflow образов дотегирует те же
   образы, публикуется финальный релиз, всё ещё без `latest`.
5. **Перевод в Latest — отдельным шагом**, только когда финальный релиз
   работает на бое и прошёл smoke:

   ```sh
   scripts/myrmidon/release/promote-latest.sh --tag myr-vX.Y.Z \
     --health-url https://<доска>/api/health --health-token-file <файл-ключа-доски>
   ```

   Команда отказывает, если тег — кандидат, релиз — pre-release, коммит
   релиза не на `main` или доска отвечает любой другой версией, кроме
   `X.Y.Z`.

## Откат

```sh
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env                          # на предыдущий образ
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --to sha256:<64 hex>
scripts/myrmidon/deploy/rollback.sh --config /path/to/deploy.env --local                  # на локальный образ, без pull (с 1.6.0)
```

- Откат возвращает образ и проверяет health по меткам старого образа. **БД
  не восстанавливается** по умолчанию; восстановление — отдельный явный путь
  (`--restore-dump` с `RESTORE_COMMAND`, скрипт просит напечатать
  `RESTORE`).
- Откату не нужна живая доска, и он **не блокируется** проверкой «только из
  CI»: это аварийный путь.
- Откат доски не откатывает компоненты, откат компонента не трогает доску.
- **Автоматический откат по здоровью** (`AUTO_ROLLBACK=1`, по умолчанию с
  1.4.0): когда выкат, запущенный из интерфейса доски, проваливает проверку
  здоровья, хостовой исполнитель немедленно запускает `rollback.sh` на
  образ, который выкат запомнил перед переключением.

## Доска на общем сервере PostgreSQL 18 (с 1.6.5)

Всё, что описано на этой странице, работает без изменений, когда база доски
живёт на общем сервере PostgreSQL 18, а не во встроенном контейнере (см.
[Установку](Installation.ru)): скрипт выката обращается к базе только через
команды из файла настроек, поэтому достаточно направить эти команды на общий
сервер.

**Клиентские программы.** `pg_dump`, `pg_restore` и `psql` на хосте выката
должны быть из клиентского пакета PostgreSQL **18** или новее: PostgreSQL
отказывается снимать дамп клиентом старше сервера (`pg_dump: aborting
because of server version mismatch`). В Ubuntu/Debian актуальный клиент
ставится из репозитория PostgreSQL
(`sudo apt-get install postgresql-client-18`).

**Команды резервной копии и восстановления** для файла настроек — та же
форма, что описана в `deploy.env.example`, направленная на общий сервер
строкой подключения и всегда называющая **только собственную базу доски**
(соседние базы других программ доску не касаются):

```sh
# Строка подключения к базе доски на общем сервере; пароль не попадает ни в
# файл, ни в список процессов (PGPASSWORD, строка в .pgpass или локально
# проброшенный сокет). USER, HOST и DATABASE вам даёт администратор.
DATABASE_URL='postgres://USER@HOST:5432/DATABASE'

DUMP_COMMAND='pg_dump "$DATABASE_URL" -Fc -f "$DUMP_FILE"'
RESTORE_COMMAND='pg_restore "$DATABASE_URL" --clean --if-exists --no-owner --no-acl < "$DUMP_FILE"'
```

`pg_dump` и `pg_restore` берут хост, логин и базу прямо из строки
подключения, поэтому отдельные ключи `-h`/`-U`/`-d` не нужны. Важны две
детали:

- `--no-owner --no-acl`: дамп несёт владельцев и права тех ролей, с которыми
  он был снят; при восстановлении их место занимает собственная роль доски
  на общем сервере, иначе `pg_restore` остановится на ролях, которые
  существуют только там, где дамп снимали.
- После восстановления обновите статистику планировщика — `pg_restore`
  загружает строки, но не статистику, и пока она не обновлена, запросы могут
  работать заметно медленнее обычного:

  ```sh
  psql "$DATABASE_URL" -c ANALYZE
  ```

**Проверка перед выкатом на копии базы** (`MYRMIDON_PREDEPLOY_CHECK=1`)
требует только образа: задайте
`MYRMIDON_PREDEPLOY_POSTGRES_IMAGE=pgvector/pgvector:pg18` (или другой
образ PostgreSQL 18 с расширением pgvector), чтобы одноразовая копия
совпадала с мажорной версией общего сервера и несла расширение, нужное базе
доски, — `pg_restore` отказывается загружать дамп в более старый сервер, а
проверка понятно завершается ошибкой, когда в копии нет нужного расширения.
Проверка по-прежнему разворачивает дамп в собственном одноразовом
контейнере, никогда — в общий сервер, и её команда восстановления по
умолчанию уже несёт `--no-owner --no-acl` и после загрузки выполняет
`ANALYZE`.

**Перенос существующей боевой базы на общий сервер** — разовая задача,
которую оператор доски выполняет **логической репликацией, без простоя**;
сознательно вне объёма этих скриптов. (Решение держать один общий сервер
PostgreSQL 18 для доски, шлюза языковых моделей, трассировки и памяти
агентов — хозяйское решение по хранилищам; у каждой программы на нём своя
база и своя роль.)
