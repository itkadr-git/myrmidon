# Этап проверки выполнения (VERIFY-ON-PROD)

> English version: [Verify-execution-stage](Verify-execution-stage)

Этап проверки выполнения (`verify`) гарантирует, что изменения, поставляемые задачами выпуска, проверены на реальной выкаченной версии перед окончательным закрытием задачи. Он обеспечивает автоматический гейт качества между ревью кода/слиянием PR и завершением задачи (OPE-12995).

## Обзор

В модели execution policy Myrmidon после завершения работы задача проходит через структурированные этапы. Если этап `review` проверяет качество кода до слияния, а этап `approval` обеспечивает согласование лидом или стейкхолдером, то этап `verify` валидирует фактическое поведение системы в развернутом окружении (staging или production).

| Тип этапа | Назначение | Когда применяется |
|---|---|---|
| `review` | Ревью кода и согласование pull request | До слияния PR |
| `verify` | Операционная проверка на выкаченной версии выпуска | После выката / перед `done` |
| `approval` | Авторизация руководителем / стейкхолдером | Финальное согласование |

## Настройка этапа

Этап проверки настраивается в массиве `executionPolicy.stages` задачи:

```json
{
  "mode": "normal",
  "stages": [
    {
      "type": "review",
      "approvalsNeeded": 1,
      "participants": [{ "type": "agent", "agentId": "d674a53a-3abd-43fe-8f49-696a04937323" }]
    },
    {
      "type": "verify",
      "approvalsNeeded": 1,
      "participants": [{ "type": "agent", "agentId": "07555686-c5f7-4536-ac2b-c9ab1027e89f" }],
      "requirements": {
        "deployVersion": true,
        "checkMethod": true,
        "skip": false
      }
    }
  ]
}
```

### Поля схемы этапа

- **`type`**: Должно быть `"verify"`.
- **`approvalsNeeded`**: В настоящее время `1`.
- **`participants`**: Список участников-проверяющих (`agent` или `user`).
- **`requirements`**: Необязательный объект настроек подтверждений и пропуска:
  - **`deployVersion`** (`boolean`): Если `true`, проверяющий обязан указать проверенную версию выкачки.
  - **`checkMethod`** (`boolean`): Если `true`, проверяющий обязан зафиксировать способ или команду проверки.
  - **`skip`** (`boolean`): Если `true`, явно разрешает пропуск этапа проверки для задач без кода (документация, настройки).

## Независимость проверяющего

Для обеспечения объективности проверки рантайм принудительно соблюдает правило `REVIEW-INDEPENDENCE`:
- Проверяющий участник **обязан отличаться** от исполнителя задачи (`assignee`, `returnAssignee` или агент, сдавший задачу).
- Исполнитель не может подтвердить свой собственный этап проверки. Попытка автора/исполнителя вынести решение verify возвращает `422 Unprocessable Entity`.
- При пробуждении назначенного проверяющего рантайм отправляет wake payload с `wakeRole: "verifier"` и причиной `execution_verify_requested`.

## Обязательные свидетельства при подтверждении

Когда проверяющий завершает проверку, переводя задачу в статус `done`, комментарий к решению обязан содержать требуемые свидетельства проверки:

1. **Версия выкачки (Deploy Version)**: Должна указывать проверенную версию сборки или коммит.
   - Распознается регистронезависимыми шаблонами: `deploy version: <значение>`, `deploy_version: <значение>`, `version: <значение>`.
2. **Способ проверки (Check Method)**: Должен описывать примененный метод проверки или команду.
   - Распознается регистронезависимыми шаблонами: `check method: <значение>`, `check_method: <значение>`, `method: <значение>`.

### Пример комментария к решению

```text
Проверка на выкаченном окружении пройдена успешно.
Deploy version: 2026.11.14-rc.3
Check method: Ручной смоук-тест интерфейса доски и проверка health-эндпоинта API.
Все критерии приемки подтверждены на живом инстансе.
```

### Автоматическое применение для выпускных задач

Для задач выпуска (задачи, название которых соответствует соглашению выпуска через `isReleaseTask`), требования `deployVersion` и `checkMethod` **обязательны по умолчанию**, даже если они опущены в явной конфигурации этапа в задаче. Если какое-либо поле отсутствует в комментарии подтверждения, API отклоняет переход с кодом `422 Unprocessable Entity`, указывая на недостающее требование.

## Возврат исполнителю при отказе (Changes Requested)

Если в ходе проверки выявлен дефект или регрессия:

1. Проверяющий переводит задачу в `in_progress` (или другой активный не-`done` статус) с комментарием, подробно описывающим причину отказа.
2. Рантайм фиксирует исход решения как `changes_requested`.
3. Задача автоматически переназначается обратно исходному исполнителю (`returnAssignee`).
4. Исполнитель пробуждается с причиной `execution_changes_requested` и ролью `executor`.
5. После устранения замечаний и повторной сдачи исполнителем (`PATCH status: "in_review"`) рантайм направляет задачу напрямую на активный этап проверки назначенному проверяющему.

## Семантика пропуска (`requirements.skip`)

Некоторые задачи выпуска не содержат изменений кода или выкатов (например, обновление документации, вики или изменение настроек). В таких случаях:

- Указание `requirements: { "skip": true }` на этапе verify явно сообщает рантайму, что проверка на бою не требуется.
- Когда `skip` равен `true`, гейт-проверки пропускаются, позволяя задаче успешно перейти в `done` без нарушения политик выпуска.
- Этап verify без `skip: true` никогда не пропускается автоматически.

## Гейт закрытия (Done Gate) для задач выпуска

Рантайм блокирует любую попытку перевести задачу выпуска с кодовыми рабочими продуктами напрямую в `done`, если:
1. В `executionPolicy.stages` не настроен этап `verify`, И
2. Ни один этап verify не содержит `requirements.skip: true`.

Попытка закрыть непроверенную задачу выпуска отклоняется:
```text
HTTP 422 Unprocessable Entity: Cannot mark release task done without a verify execution stage. A release task requires an independent verification stage with deploy version and check method, or an explicit skip configuration.
```
