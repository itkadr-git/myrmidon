# Повторы при deployment cooldown и HTTP 429 (ограниченный бэкофф и подавление немедленных пробуждений)

> English version: [Deployment-cooldown-retries](Deployment-cooldown-retries)

Когда пул моделей вышестоящего провайдера исчерпан или находится под лимитом запросов, маршрутизаторы (например, LiteLLM) возвращают ошибки cooldown пула деплойментов (*«No deployments available»*, *«all deployments in cooldown»*, *«all deployments are in cooldown»*, *«All deployments for selected model are in cooldown»*) либо HTTP 429 Too Many Requests.

Ранее подобные сбои могли вызывать немедленные повторные пробуждения продолжения задачи и формировать тугие циклы перезапуска (например, 141 упавший подряд прогон при недоступности пула моделей), что приводило к сжиганию лимитов и перегрузке очередей.

Для предотвращения холостых циклов система использует распознавание сигнатур cooldown и 429, приоритет подсказки `Retry-After`, ограниченный экспоненциальный бэкофф с потолком и джиттером, а также исключение немедленных пробуждений.

## 1. Распознавание и классификация ошибок

Классификация сбоев распределена между адаптером исполнения и политикой повторов доски:

### Уровень адаптера (Hermes Gateway)
- **Deployment pool cooldown:** Проверяется регулярным выражением `LITELLM_DEPLOYMENT_COOLDOWN_RE`:
  - `No deployments available`
  - `all deployments in cooldown`
  - `all deployments are in cooldown`
  - `All deployments for selected model are in cooldown`
  - `deployments in cooldown`
  При совпадении адаптер присваивает `errorFamily: "provider_quota"`, выставляет флаг `resultJson.cooldown: true` и извлекает метку `retryNotBefore` из тела ошибки или заголовков.
- **Обычный HTTP 429 (Rate Limit):** Если 429 вернулся без специфической сигнатуры cooldown деплойментов, он классифицируется как `errorFamily: "transient_upstream"`. Подсказка `Retry-After` сохраняется в `retryNotBefore`, но флаг `resultJson.cooldown` остаётся неопределённым.

### Уровень политики повторов (`server/src/myrmidon/run-retry-policy`)
- Регулярное выражение `TRANSIENT_ERROR_MESSAGE_RE` распознаёт формулировки cooldown деплойментов, `HTTP 429`, `too many requests` и `rate_limit_error`.
- Сбой классифицируется как `classification: "transient"` (`reason: "transient_error_message"`), что даёт право на ограниченный автоматический повтор.

## 2. Приоритет подсказки Retry-After

При планировании отложенного повтора в `heartbeat.scheduleBoundedRetry`:

1. **Высший приоритет — точная подсказка:** Если в результате прогона присутствует `retryNotBefore` (извлечённый из заголовка `Retry-After` или ответа шлюза) и это время находится в будущем:
   ```
   dueAt = retryNotBefore
   ```
   Доска выдерживает паузу, явно запрошенную upstream-провайдером, без угадывания задержки.
2. **Резервный путь — экспоненциальный бэкофф:** Если подсказка `retryNotBefore` отсутствует, задержка вычисляется по формуле бэкоффа:
   ```
   задержка(попытка) = min(MYRMIDON_RUN_RETRY_MAX_DELAY_SEC, MYRMIDON_RUN_RETRY_BASE_DELAY_SEC × (MYRMIDON_RUN_RETRY_MULTIPLIER ^ (попытка - 1))) ± джиттер
   ```

## 3. Ограниченный бэкофф, джиттер и потолок

Параметры повтора настраиваются переменными окружения и настройками инстанса:

| Переменная / Настройка | По умолчанию | Описание |
|---|---|---|
| `MYRMIDON_RUN_RETRY_ENABLED` | `true` | Главный выключатель автоповторов упавших прогонов. |
| `MYRMIDON_RUN_RETRY_MAX_ATTEMPTS` | `3` | Максимальное количество попыток для временных сбоев. |
| `MYRMIDON_RUN_RETRY_BASE_DELAY_SEC` | `60` | Базовая задержка первой попытки (в секундах). |
| `MYRMIDON_RUN_RETRY_MULTIPLIER` | `2` | Множитель экспоненциального роста задержки на каждой попытке. |
| `MYRMIDON_RUN_RETRY_MAX_DELAY_SEC` | `1800` | Верхний предел (потолок) задержки (30 минут). |
| `MYRMIDON_RUN_RETRY_JITTER_PERCENT` | `0` | Процент симметричного случайного джиттера (`±N%`) против одновременного перезапуска. |

## 4. Отсутствие немедленного пробуждения

Для предотвращения шторма пробуждений:
- Задача **не** ставится в очередь исполнения немедленно.
- В базе создаётся ровно одна запись прогона со статусом `scheduled_retry`, у которой `dueAt` выставлен на время окончания окна задержки.
- Задача остаётся в статусе `in_progress`, а поле `executionRunId` указывает на запланированный повтор.
- Новые бессобытийные пробуждения для этой задачи во время ожидания подавляются.
- При наступлении `dueAt` планировщик переводит прогон в статус `queued`.
- При успешном восстановлении пула моделей задача продолжает выполнение. Если лимит попыток исчерпан, прогон завершается с ошибкой и требует внимания оператора.
