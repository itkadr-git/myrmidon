# Удалённые площадки исполнения

> English version: [Remote-execution-sites](Remote-execution-sites)

Удалённые площадки исполнения запускают контейнеры ботов Myrmidon на
выделенных хостах вне центральной доски. Доска остаётся единой плоскостью
управления — база данных, очередь задач, планировщик, хранилище секретов,
журнал событий, аудит, — а агент площадки (`fleetd`) выполняет только
зачисленные контейнерные операции. Возможность появляется в 1.6.6.

Авторитетная версия — руководство оператора
`docs/myrmidon/guides/remote-execution-sites.ru.md`
(английская: `.md`);
детали VM-exec агента площадки — в
`docs/myrmidon/fleetd-vmexec.ru.md`.
Эта страница вики сжимает их до обзора.

## Односторонняя плоскость управления

Управляющие соединения идут строго в одну сторону — от доски к площадке — по
частной сети IPsec/WireGuard. Агент площадки не хранит администраторских
токенов доски, не имеет доступа к базе и обратных доступов в хост доски. Он
слушает частный интерфейс (например, `fleetd.internal:9100`), обращается
только к локальному сокету Docker и выполняет запросы жизненного цикла
контейнеров строго в рамках зачисленных квот на бота (память, CPU, pids) и
списка разрешённых образов.

Каждый запрос несёт bearer-заголовок авторизации; боевые развёртывания
добавляют mTLS с клиентским сертификатом, выпущенным CA площадки. Тела
запросов и ответов — JSON (`Content-Type: application/json; charset=utf-8`).

## API агента площадки

Контракт определяет 13 маршрутов:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/v1/health` | Снимок здоровья, текущая эпоха, ёмкость, активные аренды |
| `GET` | `/v1/bots` | Список статусов контейнеров, управляемых на площадке |
| `POST` | `/v1/bots` | Создать спецификацию контейнера (создан, но остановлен) |
| `GET` | `/v1/bots/{botKey}/status` | Статус, состояние, хеши, выделенный `gatewayPort` |
| `POST` | `/v1/bots/{botKey}/template-drift` | Сверить контейнер с желаемой спецификацией |
| `PUT` | `/v1/bots/{botKey}/profile` | Записать собранные файлы профиля (`0600`/`0644`) |
| `POST` | `/v1/bots/{botKey}/recreate` | Пересоздать контейнер при обнаружении дрейфа |
| `POST` | `/v1/bots/{botKey}/start` | Запустить контейнер (только после записи профиля) |
| `POST` | `/v1/bots/{botKey}/restart` | Перезапустить шлюз контейнера |
| `POST` | `/v1/bots/{botKey}/stop` | Остановить шлюз контейнера |
| `GET` | `/v1/bots/{botKey}/logs?tail=N` | Получить ограниченные, вычищенные от секретов логи |
| `POST` | `/v1/leases/claim` | Получить или продлить аренду исполнения с ограждением по эпохе |
| `POST` | `/v1/leases/release` | Освободить аренду исполнения по завершении задачи |

Снимок здоровья несёт `siteId`, монотонно растущую `epoch`, `status`,
`capacity`, текущие резервы `allocated`, необязательную проверку исходящих
соединений `egressCheck`, `activeLeases` и версию `version` fleetd. Каждая
аренда ограждена эпохой площадки: когда эпоха сдвигается, старые аренды
больше не могут менять контейнеры.

## Состояния здоровья площадки

- `healthy` — сердцебиения каждые 30 с, резервы в пределах зачисленной
  ёмкости, проба исходящих соединений проходит; можно размещать новую работу.
- `degraded` — 1–2 промаха пробы или деградация задержки исходящих
  соединений; текущая работа продолжается, планировщик перестаёт выделять
  площадке новые пакеты задач.
- `unavailable` — 3 промаха пробы подряд (90 с); доска помечает площадку
  как осушаемую, новые запуски отклоняются или удерживаются.
- `fenced` — связь отсутствует больше 10 минут или площадка вручную отведена
  оператором; доска наращивает `siteEpoch`, что обнуляет активные аренды, а
  агент площадки отказывает в новых арендах, пока эпохи не синхронизируются.
- `recovering` — площадка переподключилась; проверяются дайджесты
  контейнеров и целостность томов, устаревшие осиротевшие контейнеры
  вычищаются, затем площадка возвращается в `healthy`.

Каждый ответ с ошибкой использует однострочные коды причин без секретов —
например, `invalid_token`/`bad_certificate` (401), `bot_not_enrolled`,
`limit_exceeds_enrollment`, `image_not_allowed`, `mount_not_allowed` (403),
`lease_conflict`, `epoch_stale`, `site_fenced` (409), `capacity_exhausted`
(429), `docker_unreachable` (502). Полная таблица — в руководстве оператора.

## Внедрение

1. Подготовьте выделенный Linux-хост (XFS с проектными квотами под тома
   ботов), частный туннель и случайный bearer-токен, сохранённый как секрет
   компании на доске.
2. Настройте агента площадки в `/etc/myrmidon/fleetd.json` (`0600`):
   идентичность площадки — `siteId` и стартовый `epoch` (валидируются;
   используются для ограждения аренд) — плюс адрес слушателя, токен, сокет
   Docker и зачисленных ботов с их квотами. Порт 9100 не должен быть
   доступен извне.
3. Зарегистрируйте площадку через API доски; не редактируйте БД и не
   добавляйте mTLS-площадку в `MYRMIDON_FLEET_HOSTS` (устаревший путь
   начальной загрузки принимает только HTTP и не передаёт клиентский
   сертификат). Сохраните bearer-токен и клиентский сертификат/ключ доски в
   секретах компании, затем выполните enroll через
   `POST /api/companies/{companyId}/fleet/sites`. Создавать и удалять площадки
   могут только владелец/администратор компании или администратор экземпляра.
   В запросе указываются частный HTTPS URL, ссылки на секреты, CA площадки,
   ёмкость и профиль; значения секретов в запрос не передаются. Шаги выпуска
   PKI через OpenSSL и точный пример запроса приведены в руководстве
   оператора §4.1–4.3. Необязательно закрепите `caFingerprint`: доска проверяет
   подпись клиентского сертификата CA и отказывает в соединении, если CA
   позже отличается от закреплённого отпечатка. Список площадок возвращает
   `GET /api/companies/{companyId}/fleet/sites`. Удаляйте через
   `DELETE /api/companies/{companyId}/fleet/sites/{name}` только после
   переноса всех ботов (`204` при успехе, `409`, пока боты остаются на площадке).
4. Проверьте `GET /v1/health` локально, затем перенесите канареечного бота:
   включите контейнер в карточке агента и укажите хост площадки.
   Сверщик проводит бота через окно обслуживания (пауза → осушение →
   запись профиля → старт), а агент площадки выделяет порт шлюза.
5. Проверьте на канарейке продолжение сессии, припоминание памяти и
   маршрутизацию вебхуков, затем переносите остальных ботов волнами.
6. Откат снимает хост площадки с карточки (или отключает контейнер); тома
   с данными на диске при откате никогда не удаляются. Снятие площадки
   означает сперва осушение её аренд и ботов.

Доска терминирует вебхуки Telegram и пересылает ходы на шлюз бота по его
`apiBaseUrl`, поэтому маршрутизация вебхуков переживает миграцию без потерь.
