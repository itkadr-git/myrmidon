# Миграция с Paperclip на Myrmidon

> English version: [migration-from-paperclip.md](migration-from-paperclip.md)

Руководство показывает, как скопировать один экземпляр Paperclip (базу, файлы и секреты) в чистую
установку Myrmidon командой `myrmidon:migrate`. Команда никогда не меняет источник. Если источник
или ключ не подходят, она останавливается, ничего не записав в цель.

Прочитайте руководство целиком до начала: раздел об откате важен **до** переключения.

## 1. Что поддерживается

| Что | Поддержка |
|---|---|
| Источник | Один из релизов Paperclip: `v2026.916.1` (278 миграций), `v2026.1001.0` (282), `v2026.1005.0` (292), `v2026.1012.0` (304). Совместимость определяют **хэши** применённых миграций: список источника должен точно, по порядку, совпасть со списком ровно одного из этих релизов. Строки версий и номер последней миграции ничего не решают. Пробный прогон называет распознанный релиз (`source.vendorRelease`). |
| Старее, новее или незнакомый | Отказ до любой записи в цель с причиной (`older-than-supported-release`, `newer-than-supported-release`, `hash-mismatch`) и списком поддерживаемых релизов. Сначала приведите источник к одному из них. Адаптеров нет. |
| Данные возможностей Paperclip, которых нет в Myrmidon | Не переносятся; см. следующий раздел. Если они не пусты, нужен `--accept-vendor-only-data`. |
| Доступ к источнику | URL PostgreSQL (снимок только для чтения) или файл `pg_dump` в **plain-формате**. |
| Секреты | `local_encrypted` (конверты `local_encrypted_v1`) в любом JSON-столбце. |
| Файлы | Каталог хранилища `local_disk`. |
| Цель | Новая пустая база PostgreSQL и пустой (или отсутствующий) каталог, выделенные под Myrmidon. |

Не входит намеренно: секреты во внешнем провайдере (например, облачном хранилище секретов)
копируются как ссылки — значения остаются на месте, и цель Myrmidon должна до них дотягиваться;
объекты в объектном хранилище (S3 и подобные) не переносятся, переносятся только строки;
таблицы вне схемы `public` не переносятся; состояние Paperclip вне базы и каталога хранилища
(рабочие каталоги агентов, сессии адаптеров на диске, переменные окружения сервиса) переносите
сами.

### Возможности Paperclip, которых нет в Myrmidon

Релизы Paperclip после `v2026.916.1` добавили таблицы и столбцы, которых в Myrmidon нет (например,
запуски browser-use, клиенты MCP OAuth, chat-endpoints, внешний вид агента). Это не ошибка, но эти
данные **не** копируются. Пробный прогон перечисляет их в `vendorOnlyData`: таблица или столбец,
число строк с данными (для столбца: не null и не просто значение по умолчанию) и релиз, в котором
это появилось.

- Если в чём-то из этого есть данные, настоящий запуск останавливается **до первой записи** и
  говорит об этом. Посмотрите список, решите, что без них можно обойтись (они остаются в источнике,
  который не меняется), и запустите снова с `--accept-vendor-only-data`.
- Пустые таблицы и столбцы исключаются без флага и перечисляются в отчёте.
- Любое другое расхождение схемы источника и цели по-прежнему ошибка.
- Проверка до первой записи делается по одному только релизу источника, поэтому флаг может
  потребоваться и для таблицы, которая в цели на самом деле есть. Что в итоге оставлено, показывает
  поле `vendorOnlyData` итогового результата.
- Число в более широком типе, чем в цели (например, `assets.byte_size` в источнике `bigint`, в
  цели `integer`), проверяется на помещаемость до копирования строк; не помещающееся значение
  останавливает прогон ошибкой `value-out-of-range-in-target`. Столбец, который новый релиз Paperclip
  убрал (`user.keyboard_shortcuts`), цели не нужен.

## 2. Требования

- CLI `paperclipai` сборки Myrmidon с этой командой (`paperclipai myrmidon:migrate --help`).
- Node 24+ на машине, где запускается команда, с сетевым доступом к исходной и целевой базам.
- Роль целевой базы с правом создавать таблицы. Быстрее и точнее всего загрузка идёт с ролью,
  которой разрешено менять `session_replication_role` (суперпользователь или PostgreSQL 15+ с
  выданным правом на этот параметр); без неё команда упорядочивает таблицы по внешним ключам и
  отказывается, если ключи образуют цикл.
- Для `--source-dump`: `psql` на машине и пустая временная база (см. 5.2).
- Доступ к **ключу источника** и **ключу цели** (32 байта: base64, 64 hex-символа или строка из
  32 символов). Ключи передаются путём к файлу или именем переменной окружения — никогда
  значением в командной строке.
- Свободное место под полную копию каталога хранилища и под резервную копию (раздел 3).

Во всех командах ниже — заглушки. Настоящие URL и ключи держите в файлах с правами `0600` или в
переменных окружения; команда вычищает URL и ключи из ошибок и JSON-вывода.

## 3. Подготовка и резервная копия (до любых изменений)

1. **Остановите пишущих.** Остановите сервер Paperclip и всё, что пишет в его базу или
   хранилище (агенты, планировщики). Перенос читает согласованный снимок, но всё записанное в
   источник позже **не** переносится, а проверка в конце прогона не пройдёт, если источник
   изменился за время работы.
2. **Сделайте копию источника**, все три части, в место вне обоих хостов:
   - базу: `pg_dump --format=plain --no-owner --no-privileges "$SOURCE_DB_URL" > source.sql`
   - каталог хранилища (копию с содержимым файлов; символические ссылки перенос отвергает);
   - файл мастер-ключа (или значение переменной окружения) и файл конфигурации экземпляра. Без
     ключа секреты из копии не прочитать.
3. **Подготовьте цель**: пустую базу (`CREATE DATABASE myrmidon_target;`), пустой каталог
   хранилища (или никакого — команда создаст), каталог состояния вне целевого каталога и
   **новый** мастер-ключ цели (32 случайных байта, base64). Ключ цели лучше сделать отличным от
   ключа источника: перенос перешифровывает каждый секрет им.
4. **Перенесите настройки сервиса**, которых нет в базе: например, провайдер секретов и место
   ключа новой установки, а также `BETTER_AUTH_SECRET` / `AGENT_JWT_SECRET`, если хотите, чтобы
   прежние браузерные сессии и токены агентов продолжили работать. Новую установку направьте на
   **ключ цели**.

## 4. Пробный прогон (без записи)

```sh
paperclipai myrmidon:migrate --dry-run \
  --source-url-env SOURCE_DB_URL \
  --source-files /path/to/paperclip/storage \
  --source-key-file /secure/source-master.key \
  --target-url-env TARGET_DB_URL \
  --target-dir /path/to/myrmidon/storage \
  --target-key-file /secure/target-master.key \
  > dry-run.json
```

(`--source-dump ./source.sql --scratch-url-env SCRATCH_DB_URL` заменяет `--source-url-env`; см. 5.2.)

Пробный прогон доказывает, что источник можно переносить, и печатает полный JSON-инвентарь. В
источник, целевую базу и целевой каталог он ничего не пишет. Проверьте поля:

- `source.vendorRelease` и `source.chain`: распознанный релиз и
  `{ "expected": 304, "applied": 304, "matches": true }` (числа этого релиза). Иначе прогон
  кончается сообщением `Unsupported source schema (<причина>)`.
- `vendorOnlyData`: данные возможностей Paperclip, которых нет в Myrmidon (`withData`, `empty`,
  `requiresFlag`). Если `requiresFlag` истинно, настоящему запуску нужен `--accept-vendor-only-data`.
- `inventory.tables[]`: каждая таблица с `rows` и дайджестом содержимого `digest`;
  `secretCarrierColumns` — столбцы с зашифрованным материалом.
- `inventory.secretCarriers`: общее число найденных зашифрованных значений по таблицам и
  столбцам и `externalProviderSecrets` — секреты, значения которых лежат во внешнем провайдере и
  **не** перешифровываются.
- `inventory.files`: манифест файлов (путь, размер, sha256), строки assets, ссылающиеся на
  файлы, и `problems` (отсутствующие или изменённые файлы assets). Проблемы останавливают
  прогон, если не указан `--allow-missing-files` — указывать его стоит только осознанно.
- `inventory.exclusions`: что не переносится и почему (таблица журнала миграций, таблицы вне
  `public`, assets на нелокальном провайдере).
- `target.state`: `fresh` для нетронутой цели.

Команда останавливается с сообщением, и ничего не записывается, если: история источника не
совпадает с цепочкой поддерживаемого релиза; в источнике есть данные возможностей, которых нет в Myrmidon, а `--accept-vendor-only-data` не указан; ключ источника не расшифровывает какое-либо зашифрованное
значение; зашифрованное значение лежит в обычном текстовом столбце (безопасно перешифровать
нельзя); нет файлов assets; целевая база или каталог не пусты и не созданы прошлым запуском
этого инструмента.

## 5. Перенос

### 5.1 Из URL базы

```sh
paperclipai myrmidon:migrate \
  --source-url-env SOURCE_DB_URL \
  --source-files /path/to/paperclip/storage \
  --source-key-file /secure/source-master.key \
  --target-url-env TARGET_DB_URL \
  --target-dir /path/to/myrmidon/storage \
  --target-key-file /secure/target-master.key \
  --state-dir /path/to/migration-state \
  > migrate.json
```

### 5.2 Из файла pg_dump

Снимайте дамп в plain-формате без владельцев и прав (`pg_dump --format=plain --no-owner
--no-privileges`). Архивы в custom-формате отвергаются. Команда разворачивает дамп через `psql` в
**пустую временную базу**, которую даёте вы, читает источник оттуда и оставляет временную базу
вам на удаление:

```sh
paperclipai myrmidon:migrate --source-dump ./source.sql --scratch-url-env SCRATCH_DB_URL \
  --source-files ... --source-key-file ... --target-url-env ... --target-dir ... \
  --target-key-file ... --state-dir ...
```

Инструмент восстановления получает URL временной базы аргументом, поэтому берите одноразовую
базу и учётные данные, которые исчезнут вместе с ней.

### 5.3 Что происходит

Фазы пишутся в журнал в `--state-dir` (вместе с блокировкой и, в конце, `report.json`):

1. **Проверки** — ключи, цепочка источника, инвентарь, пустота цели (записи в цель ещё нет).
2. **schema** — целевая база получает миграции Myrmidon; цепочка цели должна содержать
   вендорскую цепочку точным префиксом.
3. **data** — все строки копируются **одной транзакцией** в порядке внешних ключей, зашифрованные
   значения по пути перешифровываются; последовательности выравниваются, внешние ключи
   перепроверяются. Ложится либо всё, либо ничего. Индексы к этой фазе уже есть от фазы schema:
   загрузка — обычная пакетная вставка, а не загрузка без индексов.
4. **files** — сначала в журнал записывается намерение (список файлов, новые каталоги), затем
   каждый файл копируется через временное имя и проверяется по sha256. Существующий файл с
   другим содержимым никогда не перезаписывается.
5. **verify** — см. раздел 6; прогон считается `complete`, только если проверка прошла.

Если запуск прерван или упал, журнал показывает `failed` и достигнутую фазу. **Запустите ту же
команду ещё раз**: завершённые фазы пропускаются, прерванное копирование файлов продолжается, а
загрузка данных, успевшая зафиксироваться перед обрывом, узнаётся по содержимому и не
повторяется. Дублей нет. Повторный запуск после успеха сообщает `already-migrated` и ничего не
пишет.

Другой (или изменившийся) источник при уже начатой цели отвергается: сначала откат.

## 6. Проверка

Собственная проверка команды (`verification` в выводе) сообщает факты, а не «ошибок нет»:

- `countsAndContentMatch` и `tables[]`: число строк и дайджесты содержимого по таблицам,
  источник против цели;
- `foreignKeyViolations`: пусто;
- `secrets`: `decryptWithTargetKey` true, `plaintextParity` true (каждый расшифрованный секрет
  цели равен секрету источника, сравнение по хэшу), `oldKeyRejected` true (ключ источника цель
  не открывает; `null` — ключи совпадают);
- `filesVerified` и `fileProblems`: каждый файл манифеста перехэширован в цели;
- `sourceUnchanged`: дайджест снимка источника, снятый заново после прогона, равен первому.

Совпадение одних счётчиков не гарантирует отсутствия потерь: оно охватывает перенесённые
таблицы и файлы, но не данные вне них (см. раздел 1).

Затем проверьте в приложении: запустите новую установку на **целевой** базе, каталоге и ключе:

1. Войдите существующим пользователем.
2. Откройте компанию, затем задачу с комментариями и вложенным документом или файлом, откройте
   файл.
3. Откройте агента и его конфигурацию; разрешите один секрет (запуск, который его использует,
   или экран секретов).
4. Запустите один прогон агента и дождитесь окончания.

Не направляйте агентов и интеграции на новую установку, пока эти проверки не пройдены.

## 7. Переключение и пределы возврата

Старую установку держите остановленной, но не удалённой, пока не приняли новую. С момента, когда
пользователи и агенты **пишут в цель**, источник этих изменений не содержит. Откат после этого
момента их теряет; автоматического слияния обратно нет.

Под «откатом» понимают две разные вещи:

- **Отменить перенос** (`--rollback`, ниже): очищает то, что команда создала в цели. Применять
  до переключения — если проверка не прошла или вы хотите начать заново.
- **Вернуться на старую установку**: запустить старый Paperclip на старых базе, хранилище и
  ключе (оригиналах или восстановленных из копии раздела 3). **Один лишь старый образ** данные не
  возвращает: состояние возвращает восстановление из резервной копии. После переключения это
  вернёт состояние на момент копии, без всего, что записали в Myrmidon с тех пор.

Внешние сервисы продолжают указывать туда, куда вы их направили: боты, вебхуки, адреса
перенаправления OAuth и внешние провайдеры секретов переключаете (и возвращаете) вы.

## 8. Откат переноса

```sh
paperclipai myrmidon:migrate --rollback \
  --target-url-env TARGET_DB_URL --target-dir /path/to/myrmidon/storage \
  --state-dir /path/to/migration-state
```

Нужны журнал запуска и та же целевая база (проверяется по её идентификатору). Откат удаляет
таблицы, типы, функции и представления, которых не было до запуска (расширения и прежние
объекты остаются), схему миграций, а также файлы и каталоги, добавленные запуском; файл,
содержимое которого с тех пор изменилось, остаётся и указывается в `filesKeptBecauseChanged`.
Источник не затрагивается. После отката журнал показывает `rolled-back`, и ту же цель можно
использовать для нового запуска.

`--rollback` — не восстановление из резервной копии: если после переноса в цель кто-то писал,
откат удалит и эти данные.

## 9. Справка

Флаги (`paperclipai myrmidon:migrate --help`):

| Флаг | Смысл |
|---|---|
| `--source-url <url>` / `--source-url-env <имя>` | База источника (форма с переменной не пускает URL в список процессов). |
| `--source-dump <путь>` + `--scratch-url` / `--scratch-url-env` | Plain-дамп pg_dump, разворачиваемый в пустую временную базу. |
| `--source-files <каталог>` | Каталог хранилища источника. Обязателен, если в базе есть assets `local_disk`. |
| `--source-key-file <путь>` / `--source-key-env <имя>` | Мастер-ключ источника. |
| `--target-url` / `--target-url-env` | Целевая база (пустая, выделенная). |
| `--target-dir <каталог>` | Каталог хранилища цели (пустой или отсутствует). Обязателен, если есть файлы. |
| `--target-key-file` / `--target-key-env` | Мастер-ключ цели. |
| `--state-dir <каталог>` | Журнал, блокировка и отчёт; вне целевого каталога. Обязателен без `--dry-run`. |
| `--dry-run` | Только инвентарь. |
| `--rollback` | Отменить созданное прошлым запуском. |
| `--allow-missing-files` | Продолжить, если файлы assets отсутствуют или изменены (будет в отчёте). |
| `--accept-vendor-only-data` | Продолжить, если в источнике есть данные возможностей Paperclip, которых нет в Myrmidon; они попадут в отчёт и не переносятся. |

Вывод всегда JSON в stdout (`--json` принимается для совместимости); ошибки идут в stderr с
ненулевым кодом возврата. Поля верхнего уровня: `command`, `contractVersion` (1), `mode`
(`dry-run`, `migrate`, `rollback`), `status` (`ok`, `already-migrated`, `rolled-back`),
`writesPerformed`, `source`, `inventory`, `vendorOnlyData`, `target`, а для настоящего запуска ещё
`phases`, `load` и `verification`.

Известные ограничения: источник должен быть точно одним из поддерживаемых релизов; один запуск переносит один
экземпляр; загрузка идёт одной транзакцией, поэтому очень большой базе нужен соответствующий
запас; столбцы с зашифрованным материалом не сравниваются по содержимому (их проверяют
расшифровкой каждого значения); данные в таблицах вне `public`, во внешних объектных хранилищах
и внешних провайдерах секретов не переносятся.
