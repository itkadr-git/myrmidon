# Execution Policy: рабочие процессы ревью и приёмки

Система execution policy в Myrmidon гарантирует, что задачи завершаются с нужным уровнем контроля. Вместо того чтобы полагаться на память агентов при передаче работы на ревью, рантайм **принудительно** применяет этапы ревью и приёмки автоматически.

## Обзор

Execution policy — необязательный структурированный объект на задаче, который определяет, что должно произойти после того, как исполнитель закончил работу. Он поддерживает три уровня принуждения:

| Уровень | Назначение | Область действия |
|---|---|---|
| **Обязательный комментарий** | Каждое агентское выполнение должно оставить комментарий к задаче | Инвариант рантайма (всегда включён) |
| **Этап ревью** | Ревьюер проверяет качество/корректность и может запросить изменения | На задачу, необязательный |
| **Этап приёмки** | Руководитель/заинтересованное лицо даёт финальную подпись | На задачу, необязательный |

Уровни сочетаются. У задачи может быть только ревью, только приёмка, обе стадии последовательно или ни одной (тогда остаётся только обязательный комментарий).

## Модель данных

### Execution Policy (поле задачи: `executionPolicy`)

```ts
interface IssueExecutionPolicy {
  mode: "normal" | "auto";
  commentRequired: boolean;       // всегда true, принуждается рантаймом
  stages: IssueExecutionStage[];  // упорядоченный список этапов ревью/приёмки
}

interface IssueExecutionStage {
  id: string;                                 // автоматически генерируемый UUID
  type: "review" | "approval";                // вид этапа
  approvalsNeeded: 1;                         // несколько приёмок пока не поддерживается
  participants: IssueExecutionStageParticipant[];
}

interface IssueExecutionStageParticipant {
  id: string;
  type: "agent" | "user";
  agentId?: string | null;    // заполняется, когда type — "agent"
  userId?: string | null;     // заполняется, когда type — "user"
}
```

Участники могут быть агентами или пользователями доски. У каждого этапа может быть несколько участников; рантайм выбирает первого подходящего, предпочитая явно запрошенного ответственного и исключая исходного исполнителя.

### Execution State (поле задачи: `executionState`)

Отслеживает, на каком шаге workflow-процесса задача находится сейчас:

```ts
interface IssueExecutionState {
  status: "idle" | "pending" | "changes_requested" | "completed";
  currentStageId: string | null;
  currentStageIndex: number | null;
  currentStageType: "review" | "approval" | null;
  currentParticipant: IssueExecutionStagePrincipal | null;
  returnAssignee: IssueExecutionStagePrincipal | null;
  completedStageIds: string[];
  lastDecisionId: string | null;
  lastDecisionOutcome: "approved" | "changes_requested" | null;
}
```

### Решения execution (таблица: `issue_execution_decisions`)

Аудиторский след каждого действия ревью/приёмки:

```ts
interface IssueExecutionDecision {
  id: string;
  companyId: string;
  issueId: string;
  stageId: string;
  stageType: "review" | "approval";
  actorAgentId: string | null;
  actorUserId: string | null;
  outcome: "approved" | "changes_requested";
  body: string;              // обязательный комментарий с объяснением решения
  createdByRunId: string | null;
  createdAt: Date;
}
```

## Workflow

### Счастливый путь: ревью + приёмка

```
┌──────────┐    исполнитель   ┌───────────┐   ревьюер    ┌───────────┐  приёмщик   ┌──────┐
│  todo     │───завершает───▶│ in_review  │───одобряет───▶│ in_review │───одобряет──▶│ done │
│ (Кодер)  │    работу       │ (QA)      │               │ (CTO)     │             │      │
└──────────┘                 └───────────┘               └───────────┘             └──────┘
```

1. **Задача создана** с `executionPolicy`, задающим этап ревью (например, QA) и этап приёмки (например, CTO).
2. **Исполнитель работает** над задачей в статусе `in_progress`.
3. **Исполнитель переводит в `done`** — рантайм перехватывает переход:
   - Статус становится `in_review` (не `done`)
   - Задача переназначается первому ревьюеру
   - `executionState` входит в `pending` на этапе ревью
4. **Ревьюер проверяет** и переводит в `done` с комментарием:
   - Создаётся запись решения: `{ outcome: "approved" }`
   - Задача остаётся `in_review`, переназначается приёмщику
   - `executionState` переходит к этапу приёмки
5. **Приёмщик одобряет** и переводит в `done` с комментарием:
   - Создаётся запись решения: `{ outcome: "approved" }`
   - `executionState.status` становится `completed`
   - Задача достигает реального статуса `done`

### Сценарий «запрошены изменения»

```
┌───────────┐  ревьюер запросил  ┌─────────────┐  исполнитель  ┌───────────┐
│ in_review  │────изменения──────▶│ in_progress  │──пересдаёт──▶│ in_review │
│ (QA)      │                    │ (Кодер)      │              │ (QA)      │
└───────────┘                    └──────────────┘              └───────────┘
```

1. **Ревьюер запрашивает изменения**, переводя задачу в любой статус, кроме `done` (обычно `in_progress`), с комментарием о том, что нужно изменить.
2. Рантайм автоматически:
   - Ставит статус `in_progress`
   - Переназначает на исходного исполнителя (сохраняется в `returnAssignee`)
   - Ставит `executionState.status` в `changes_requested`
3. **Исполнитель вносит изменения** и снова переводит в `done` или пересдаёт обратно в `in_review`.
4. Рантайм возвращает задачу на **тот же этап ревью** (не с начала), тому же ревьюеру. Продолжение ревью выводится из существующей execution policy задачи, поэтому повторный PATCH не обязан заново передавать payload `executionPolicy`, а решение recovery action (`POST /api/issues/:id/recovery-actions/resolve`) применяет переход по policy до валидации пути ревью — типизированное продолжение ревьюера распознаётся сразу, без ошибки `422 missing review_path`.
5. Цикл продолжается, пока ревьюер не одобрит.

### Варианты policy

**Только ревью** (без этапа приёмки):
```json
{
  "stages": [
    { "type": "review", "participants": [{ "type": "agent", "agentId": "qa-agent-id" }] }
  ]
}
```
Исполнитель завершает → ревьюер одобряет → done.

**Только приёмка** (без этапа ревью):
```json
{
  "stages": [
    { "type": "approval", "participants": [{ "type": "user", "userId": "manager-user-id" }] }
  ]
}
```
Исполнитель завершает → приёмщик подписывает → done.

**Несколько ревьюеров/приёмщиков:**
Каждый этап поддерживает нескольких участников. Рантайм выбирает одного действующего, исключая исходного исполнителя, чтобы предотвратить само-ревью.

## Обязательный комментарий

Независимо от этапов ревью каждое агентское выполнение по задаче обязано оставить комментарий. Это принуждается на уровне рантайма:

1. **Выполнение завершено** — рантайм проверяет, оставил ли агент комментарий по этому выполнению.
2. **Комментария нет**: `issueCommentStatus` ставится в `retry_queued`, агент будится ещё раз с причиной `missing_issue_comment`.
3. **Комментария снова нет**: `issueCommentStatus` ставится в `retry_exhausted`. Дальнейших повторов нет, отказ фиксируется.
4. **Комментарий оставлен**: `issueCommentStatus` ставится в `satisfied` и связывается с ID комментария.

Это предотвращает «тихие» завершения, когда агент закончил работу, но не оставил следа.

### Поля отслеживания на уровне выполнения

| Поле | Описание |
|---|---|
| `issueCommentStatus` | `satisfied`, `retry_queued` или `retry_exhausted` |
| `issueCommentSatisfiedByCommentId` | Ссылка на комментарий, закрывший требование |
| `issueCommentRetryQueuedAt` | Момент планирования повторной побудки |

## Права доступа

- Только **активный ревьюер/приёмщик** (`currentParticipant` в execution state) может продвинуть или отклонить текущий этап.
- Неучастник, пытающийся перевести задачу, получает ошибку `422 Unprocessable Entity`.
- И одобрения, и запросы изменений **требуют комментарий** — пустые комментарии (или только из пробелов) отклоняются.
- Комментарий с решением должен быть передан в том же запросе `PATCH /api/issues/{issueId}`, что и смена статуса. Отдельный `POST /api/issues/{issueId}/comments` остаётся обычным обсуждением и не закрывает защиту решения ревью/приёмки.

## Использование API

### Запись решений ревью или приёмки

```bash
PATCH /api/issues/{issueId}
{ "status": "done", "comment": "Решение ревьюера: одобрить — реализация и тесты в порядке." }
```

Чтобы запросить изменения, передайте целевой статус, отличный от `done`, вместе с объяснением:

```bash
PATCH /api/issues/{issueId}
{ "status": "in_progress", "comment": "Решение ревьюера: запросить изменения — покройте краевой случай ретрая." }
```

Не разбивайте решение на `POST /comments` и последующий PATCH только статуса; рантайм записывает решение только из поля `comment` того же обновления статуса.

### Задание execution policy при создании задачи

```bash
POST /api/companies/{companyId}/issues
{
  "title": "Реализовать фичу X",
  "assigneeAgentId": "coder-agent-id",
  "executionPolicy": {
    "mode": "normal",
    "commentRequired": true,
    "stages": [
      {
        "type": "review",
        "participants": [
          { "type": "agent", "agentId": "qa-agent-id" }
        ]
      },
      {
        "type": "approval",
        "participants": [
          { "type": "user", "userId": "cto-user-id" }
        ]
      }
    ]
  }
}
```

ID этапов и участников генерируются автоматически, если не указаны. Дубликаты участников внутри этапа автоматически удаляются. Этапы без валидных участников удаляются. Если валидных этапов не осталось, policy ставится в `null`.

### Обновление execution policy существующей задачи

```bash
PATCH /api/issues/{issueId}
{
  "executionPolicy": { ... }
}
```

Если policy снята (`null`), пока ревью идёт, execution state очищается, а задача возвращается исходному исполнителю.

### Продвижение этапа (ревьюер/приёмщик одобряет)

Активный ревьюер или приёмщик переводит задачу в `done` с комментарием:

```bash
PATCH /api/issues/{issueId}
{
  "status": "done",
  "comment": "Проверено — реализация корректна, тесты проходят."
}
```

Рантайм определяет, завершает ли это workflow или переводит к следующему этапу.

### Запрос изменений

Активный ревьюер переводит задачу в любой статус, кроме `done`, с комментарием:

```bash
PATCH /api/issues/{issueId}
{
  "status": "in_progress",
  "comment": "Кнопки съехали на мобильной раскладке. Исправьте flex-контейнер."
}
```

Рантайм автоматически переназначает задачу исходному исполнителю.

## Интерфейс

### Диалог новой задачи

При создании новой задачи рядом с выбором исполнителя появляются кнопки **Ревьюер** и **Приёмщик**. Нажатие любой открывает выбор участника:
- «Без ревьюера» / «Без приёмщика» (очистить)
- «Я» (текущий пользователь)
- Полный список агентов и пользователей доски

Выбор автоматически собирает массив `executionPolicy.stages`.

### Панель свойств задачи

Для существующих задач панель свойств показывает редактируемые поля **Ревьюер** и **Приёмщик**. На каждый этап можно добавить нескольких участников. Изменения сохраняются в `executionPolicy` задачи через API.

## Принципы дизайна

1. **Принуждается рантаймом, а не промптом.** Агентам не нужно помнить о передаче на ревью. Рантайм перехватывает смены статусов и маршрутизирует сам.
2. **Итеративно, а не терминально.** Ревью — это цикл (запрос изменений → доработка → повторное ревью), а не одноразовые ворота. Система возвращается на тот же этап при пересдаче.
3. **Гибкие роли.** Участники могут быть агентами или пользователями. Далеко не в каждой организации есть «QA» — паттерн ревьюер/приёмщик достаточно общий для peer review, подписи руководителя, комплаенс-проверок или любого многостороннего процесса.
4. **Аудируемо.** Каждое решение записывается с актором, исходом, комментарием и ID выполнения. Вся история ревью запрашивается по задаче.
5. **Инвариант одиночного выполнения сохранён.** Побудки ревью и повторы комментариев уважают существующее ограничение: только одно агентское выполнение может быть активным по задаче в каждый момент.
