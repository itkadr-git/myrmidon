# Очередь слияний

> English version: [merge-queue.md](merge-queue.md)

GitHub merge queue для `main`. Она появилась потому, что 06.10 `main` дважды краснел от сшивки
PR, зелёных по отдельности: между «CI зелёный на PR» и «слияние в `main`» `main` уезжал вперёд.
Очередь закрывает это окно (задача OPE-5500).

## Как это работает

`main-protection` по-прежнему требует на голове PR: `CI result` и `hot-files-review`. Зелёной
головы PR мало для входа в очередь — те же проверки перезапускаются на **кандидатском
коммите**: `main` плюс все PR, стоящие в очереди раньше твоего. Только зелёный кандидат
GitHub пушит в `main` — и тут же начинает проверять следующую группу уже с твоим коммитом
в составе `main`. Слияния идут последовательно, и `main` остаётся зелёным.

Очередь настраивается в настройках репозитория (ветка `main`, способ слияния — **merge
commit**; правила очереди задаёт владелец в разделе Settings → Merge queue). Очередь ставит
PR в порядок сама и собирает кандидатские коммиты; в `main` она пишет обычные merge-коммиты,
поэтому история `main` остаётся пригодной для штатного разбора (`git log main`) — ни один
гейт выпуска не завязан на то, что у каждого коммита `main` ровно один родитель.

## Что делает CI на событии очереди

- В `myrmidon-ci.yml` есть триггер `merge_group: types: [checks_requested]`. Шаг `plan` на
  событии merge-group считает diff `merge_group.base_sha..head_sha` — тот же diff, что
  проверялся на PR, но поверх свежего `main`; ярус и подбор тестов работают как для PR.
  Проверки на кандидате те же, что на PR (`plan`, `typecheck`, `build`, `tests-affected`,
  `ci-result`), и имена проверок — те же имена джобов, поэтому требования ruleset
  `main-protection` выполняются на кандидате. Если до завершения проверок в `main` влилась
  предыдущая группа, GitHub перезапрашивает проверки на новом кандидате — тот же код, новая
  база.
- Прогон CI на `merge_group` **не отменяется автоматически**: группа конкурентности для него
  фиксирована (`myrmidon-ci-refs/heads/gh-readonly-queue/main/pr-<n>-<sha>`, по одной на
  запись — у события merge_group, в отличие от pull, `github.run_id` в группе конкурентности
  недоступен) и `cancel-in-progress` выключен. Отменённый прогон очереди выкидывает группу
  из очереди, так что отмена сама была бы потерей; голова PR и предыдущий кандидат всё равно
  отменяются штатно.
- `myrmidon-hot-files-review.yml` тоже срабатывает на `merge_group`, но ревью обеспечивается
  на PR: джоб просто выставляет коммит-статус `hot-files-review` = success на кандидатский
  коммит и выходит, чтобы гейт не тормозил очередь.

## Процесс: ревьюер и стюард

1. **Ревьюер** (adm-dev-review или мейнтейнер) читает diff, проверяет, что тест падает без
   изменения, и ставит PR метку `review-approved` (для hot-файлов именно она зелёнит
   `hot-files-review` — см. [CONVENTIONS.md](CONVENTIONS.md), раздел 6). Новый пуш снимает
   метку, ревью начинается заново.
2. **Стюард** (роль, которая мержит) отправляет одобренный PR с зелёным CI на голове в
   очередь:

   ```bash
   gh pr merge --auto --merge <PR>
   ```

   `--auto` ставит в очередь, а не мержит сразу; момент и кандидата подбирает GitHub.
3. GitHub перепроверяет кандидата поверх свежего `main`. Зелёный — PR смержен в `main` и
   закрыт. Красный — PR выпадает из очереди и возвращается в состояние `open`.

## Если PR выпал из очереди

PR возвращается автору с упавшими проверками на кандидате:

1. Открыть упавший `CI result` / прогон события `merge_group` и посмотреть, какая ланка
   легла (формат тот же, что у PR CI — см. [ci.md](ci.md)).
2. Воспроизвести локально: ребейзнуть ветку на текущий `main` и прогнать затронутые ланки.
   Столкновение двух соседних PR — не «флейк»: чинит тот, кто вошёл в очередь позже.
3. Запушить фикс, дождаться зелёного CI на PR, перевставить метку `review-approved`
   (пуш снимает её), и стюард снова ставит PR в очередь: `gh pr merge --auto --merge`.

Если очередь встала (проверки кандидатов не стартуют) — сначала проверить триггер
`merge_group` в `myrmidon-ci.yml` и имя проверки `CI result`, затем настройки очереди ветки
`main` в настройках репозитория.
