# Многопроцессный режим доски

> English version: [multi-instance.md](multi-instance.md)

По умолчанию доска Myrmidon работает одним процессом ОС: он отдаёт
HTTP-интерфейс на порту 3100, и в нём же крутятся все фоновые таймеры (побудки
агентов, сверки, дампы БД). Многопроцессный режим (внутреннее имя
BOARD-PROCESSES, выходит в 1.6.6) превращает этот единственный процесс в
процесс-*worker* и один или несколько процессов *api*: worker ведёт всю
фоновую работу, api только обслуживают HTTP. Смысл в том, чтобы медленный
выкат, всплеск HTTP-нагрузки или упавший обработчик запроса не прерывали
фоновую работу доски.

На этой странице — что это за режим, когда его включать, как настроить и как
за ним наблюдать.

## Текущее состояние в 1.6.6

Режим выкатывается по частям. Сейчас в доске уже есть:

- **реестр процессов**: каждые 10 секунд каждый процесс доски добавляет в
  таблицу `board_processes` строку о себе (роль, pid, имя хоста, версия,
  аптайм, задержка цикла событий, занятая память). Строки старше 2 минут
  считаются мёртвыми и удаляются;
- **панель «Процессы»** в интерфейсе доски (Instance → General), которая
  показывает этот реестр вживую;
- **`GET /internal/ready`** — готовность одного процесса (HTTP 200, когда он
  может принимать трафик, иначе 503) с тремя дешёвыми проверками: `database`
  (один `SELECT 1` с ограничением в 1 секунду), `migrations` (фаза загрузки) и
  `bus` (подписка на шину событий; пока процесс шиной не пользуется, проверка
  отвечает `not_applicable`);
- **`GET /healthz`** — сводный ответ для балансировщика. Пока доска работает
  одним процессом, ответ описывает только его (`scope: "process"`). Когда
  появится супервизор процессов, ответ будет 200, только если готовы **все**
  api-процессы (`scope: "supervisor"`, со счётчиками
  `api: {desired, ready, starting}`, состоянием супервизора и машиночитаемым
  полем `reason`).

Что ещё **ожидается в релиз-кандидате** (в main не слито; ниже — как задумано
в дизайн-документе BOARD-PROCESSES):

- **супервизор процессов** — worker порождает дочерние api-процессы, они делят
  порт 3100 через `SO_REUSEPORT`, и доска переключается между одиночным и
  разделённым режимом **на ходу, без перезапуска контейнера**;
- **ключ настроек `processes`** (`instance_settings.general.processes`) и его
  API `GET`/`PATCH /api/myrmidon/processes`;
- **метка `role` на всех семействах метрик** и эндпоинт
  **`GET /internal/procs`** на роутере метрик.

Разделы про ещё не слитые в main части помечены «ожидается в rc».

## Когда включать

Оставайтесь на одиночном процессе, если доска обслуживает небольшую команду и
процессор хоста не перегружен. Один процесс проще для понимания, и ничто на
этой странице не меняет его поведение: умолчание побайтово совпадает с
сегодняшней доской.

Разделение имеет смысл, когда:

- важна задержка ответов по HTTP во время выкатов: когда один порт делят
  несколько api-процессов, перезапуск одного дочернего процесса не роняет
  интерфейс;
- фоновая работа (побудки, сверки, дампы) должна продолжаться, даже когда
  HTTP-слой перегружен или перезапускается;
- на хосте есть свободные ядра: режим рассчитан на контейнер с 4 ядрами — один
  worker и два api-процесса; три api-процесса — рекомендуемая верхняя граница.

## Роли и порты

| Роль | Что делает | Слушает |
|---|---|---|
| `all` (умолчание) | Всё: HTTP и вся фоновая работа | `0.0.0.0:3100` |
| `worker` | Все фоновые таймеры; применяет миграции БД; управляет дочерними api-процессами | приложение доски на внутреннем loopback `127.0.0.1:3101` |
| `api` | Только HTTP — ни одного фонового таймера; миграции сам не применяет, а ждёт, пока их применит worker | `0.0.0.0:3100` (порт делится между api-процессами через `reusePort`) |

Роль процесса задаёт переменная окружения `PAPERCLIP_PROCESS_ROLE` (`all` /
`worker` / `api`); не заданное или неизвестное значение считается равным
`all`, и при запуске в журнал пишется предупреждение. Задавать её вручную
обычно не нужно: в управляемом режиме worker сам порождает дочерние
api-процессы и прописывает им `PAPERCLIP_PROCESS_ROLE=api` (и
`PAPERCLIP_PARENT_BOOT_ID`).

## Настройка (ожидается в rc)

Разделение настраивается из интерфейса доски — **Instance → General →
«Процессы доски»** — или через API. Значения хранятся в
`instance_settings.general.processes`:

| Ключ | Значения | Умолчание | Смысл |
|---|---|---|---|
| `mode` | `single`, `split` | `single` | Либо один процесс делает всё, либо worker и api-процессы |
| `apiCount` | 1–4 | 1 | Сколько api-процессов поднимает `split` |
| `leaderLeaseTtlSec` | 5–600 | 30 | TTL аренды лидера фоновой роли |
| `liveEventsBus` | `local`, `pg` | `local` | Как события реального времени передаются между процессами |
| `admissionStore` | `memory`, `db` | `memory` | Где решается допуск прогонов |
| `singletonProxy` | boolean | `true` | Не-лидер проксирует однопроцессные маршруты лидеру |

Прочитать действующие значения и источник каждого (`settings` / `env` /
`default`), а также режим, который эта сборка действительно применяет:

```sh
curl -s http://localhost:3100/api/myrmidon/processes
```

Сменить режим (только администратор инстанса; применяется сразу, без
перезапуска контейнера):

```sh
curl -s -X PATCH http://localhost:3100/api/myrmidon/processes \
  -H 'Content-Type: application/json' \
  -d '{"mode": "split", "apiCount": 2}'
```

**Аварийный выход.** Переменная `PAPERCLIP_PROCESS_MODE=single` в окружении
сильнее сохранённой настройки: она читается при запуске, ещё до обращения к
базе. Если сохранённое значение когда-нибудь уронит доску, запустите контейнер
с этой переменной — доска поднимется одним процессом, и настройку можно будет
исправить из интерфейса. Пока переменная задана, страница настроек показывает
принудительный режим с источником `env`.

## Наблюдение за процессами

### Панель «Процессы»

Instance → General показывает каждый живой процесс доски: boot id (строка
процесса, который отдал страницу, помечена «self»), роль, pid и имя хоста, id
контейнера, api-порт, версию, аптайм, возраст пульса, задержку цикла событий и
занятую память. Панель опрашивает реестр с той же частотой, поэтому умерший
процесс желтеет в течение одного такта пульса (10 с) и исчезает в течение окна
устаревания (2 минуты).

### API реестра

Те же данные через API (читать может любой участник доски):

```sh
curl -s http://localhost:3100/api/myrmidon/board-processes
```

В ответе — `pulseSeconds`, `staleAfterSeconds` и по записи на процесс со
`status: "live" | "stale"`.

### /internal/procs (ожидается в rc)

На роутере метрик появляется `GET /internal/procs`, защищённый тем же
bearer-токеном, что и эндпоинт метрик (`MYRMIDON_METRICS_TOKEN` или секрет
компании из `MYRMIDON_METRICS_TOKEN_SECRET`). Эндпоинт отдаёт список
процессов доски из реестра — роль, pid, `startedAt`, `uptimeSeconds`, `ready`
— и называет роль процесса, который отвечает:

```sh
curl -s -H "Authorization: Bearer $MYRMIDON_METRICS_TOKEN" \
  http://localhost:3100/internal/procs
```

Если реестр прочитать не удалось, ответ всё равно остаётся HTTP 200, только
список пуст: при недоступной базе поллер получает корректные данные, а не
страницу ошибки.

### Метрики по ролям (ожидается в rc)

Каждая строка-образец в любом семействе метрик несёт метку
`role="api|worker|all"`, которая вычисляется так же, как в реестре процессов
(`PAPERCLIP_PROCESS_ROLE`, умолчание `all`). Имена метрик не меняются;
единственная конфликтная метка семейства очередей переименована из `role` в
`assignee_role`. Сбор метрик по ролям отвечает на вопрос «тормозит HTTP-слой
или планировщик?», не заглядывая в журналы.

### Пробы готовности для балансировщика

Направьте балансировщик или рантайм контейнера на:

- `GET /healthz` — сводный ответ: 200, только когда доска целиком может
  принимать трафик. Пока идёт переход в split
  (`supervisorState: "startingSplit"`), ответ по определению 503, так что
  балансировщик ждёт готовности всех дочерних api-процессов, а не шлёт трафик
  в полусобранную схему;
- `GET /internal/ready` — отчёт одного процесса о себе; используйте для
  проверок по каждому процессу (роль, boot id, детали каждой проверки), когда
  разбираетесь с проблемой.

Оба эндпоинта выставляют `Cache-Control: no-store`, не читают учётные данные и
не раскрывают данные компаний.

## Выкаты и drain (ожидается в rc)

Смена режима не требует перезапуска контейнера — супервизор переключает доску
на ходу:

- **single → split**: worker порождает дочерние api-процессы, но сам
  продолжает обслуживать порт 3100, пока *каждый* из них не пришлёт `ready` по
  IPC. Дочерний процесс сообщает о готовности только после того, как поднял
  свой слушатель и выполнил `SELECT 1`. Затем worker закрывает свой публичный
  слушатель. Весь переход `/healthz` отвечает 503 с
  `reason: "split_starting"`.
- **split → single**: worker снова открывает порт 3100 (с `reusePort`, поэтому
  дочерние процессы продолжают обслуживать трафик) и затем по одному выводит
  их из работы (*drain*).
- **Масштабирование** (смена `apiCount`) идёт через ту же проверку готовности.

Drain — это вывод дочернего процесса из работы без потери запросов:

1. Worker шлёт `drain` по IPC.
2. Дочерний процесс перестаёт принимать новые соединения (`server.close()`),
   закрывает простаивающие, а клиентам websocket-подписки на события посылает
   `close(1012)`, чтобы они переподключились к уцелевшему процессу.
3. Через 30 секунд ожидания он закрывает всё оставшееся
   (`closeAllConnections()`) и корректно завершается.

Обработка падений: умерший дочерний api-процесс перезапускается с нарастающим
бэкоффом (1 с, удвоение до 30 с). Если 15 секунд нет ни одного живого
api-процесса, worker сам открывает порт 3100 (*аварийный возврат в single*) и
подаёт сигнал внимания — доска продолжает работать, даже если сломались все
дочерние процессы. Каждому дочернему api-процессу ставится потолок кучи 1 ГБ
(`--max-old-space-size`), чтобы разогнавшийся обработчик запросов не оставил
worker без памяти.

Выкаты контейнера: оставьте health-check контейнера на `/healthz`. Пока split
стартует или идёт drain, сводный ответ — 503, поэтому оркестратор, который
учитывает эту пробу, не переключит трафик на новый контейнер, пока новая схема
действительно не начнёт обслуживать запросы, и не остановит старый контейнер
посреди drain.
