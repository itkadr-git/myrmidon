# Многопроцессный режим доски

> English version: [multi-instance.md](multi-instance.md)

По умолчанию доска Myrmidon работает одним процессом ОС: он отдаёт
HTTP-интерфейс на порту 3100 и в нём же крутятся все фоновые таймеры
(побудки агентов, сверки, дампы БД). Многопроцессный режим — внутреннее имя
BOARD-PROCESSES, выходит в 1.6.6 — разделяет этот процесс на процесс-*worker*,
который ведёт всю фоновую работу, и один или несколько процессов *api*,
которые только обслуживают HTTP. Цель: медленный выкат, всплеск HTTP-нагрузки
или упавший обработчик запроса не должны прерывать фоновую работу доски.

На этой странице — что это за режим, когда его включать, как настроить и как
за ним наблюдать.

## Текущее состояние в 1.6.6

Режим выкатывается по частям. Сейчас в доске уже есть:

- **реестр процессов**: каждый процесс доски раз в 10 секунд пишет о себе
  строку в таблицу `board_processes` (роль, pid, имя хоста, версия, аптайм,
  лаг цикла событий, занятая память). Строки старше 2 минут считаются
  мёртвыми и подметаются;
- **панель «Процессы»** в интерфейсе доски (Instance → General), которая
  показывает этот реестр вживую;
- **`GET /internal/ready`** — готовность одного процесса (HTTP 200, когда он
  может принимать трафик, иначе 503) с тремя дешёвыми проверками: `database`
  (один `SELECT 1` с дедлайном 1 секунда), `migrations` (фаза загрузки) и
  `bus` (подписка на шину событий; до тех пор, пока процесс шину не
  использует, проверка отвечает `not_applicable`);
- **`GET /healthz`** — сводный вердикт для балансировщика. На сегодняшнем
  одиночном процессе он описывает только этот процесс (`scope: "process"`).
  Когда появится супервизор процессов, ответ будет 200 только если готовы
  **все** api-процессы (`scope: "supervisor"`, со счётчиками
  `api: {desired, ready, starting}`, состоянием супервизора и машиночитаемым
  `reason`).

Что ещё **ожидается в релиз-кандидате** (в main не слито; ниже описано по
постановке дизайн-документа BOARD-PROCESSES):

- **супервизор процессов** — worker форкает api-детей, они делят порт 3100
  через `SO_REUSEPORT`, и доска переходит между одиночным и разделённым
  режимом **на живую, без перезапуска контейнера**;
- **ключ настроек `processes`** (`instance_settings.general.processes`) и его
  API `GET`/`PATCH /api/myrmidon/processes`;
- **метка `role` на всех семействах метрик** и эндпоинт
  **`GET /internal/procs`** на роутере метрик.

Разделы про ещё не слитые части помечены «ожидается в rc».

## Когда включать

Оставайтесь на одиночном процессе, если доска обслуживает небольшую команду и
хост не упирается в процессор. Один процесс проще для понимания, и ничто на
этой странице не меняет его поведение — умолчание побайтово совпадает с
сегодняшней доской.

Разделение имеет смысл, когда:

- важна HTTP-латентность во время выкатов: при нескольких api-процессах на
  одном порту перезапуск одного ребёнка не роняет интерфейс;
- фоновая работа (побудки, сверки, дампы) должна продолжаться, даже когда
  HTTP-полоса перегружена или перезапускается;
- на хосте есть свободные ядра: дизайн ориентируется на контейнер с 4 ядрами —
  один worker плюс два api-процесса; три api-процесса — рекомендуемая верхняя
  граница.

## Роли и порты

| Роль | Что делает | Слушает |
|---|---|---|
| `all` (умолчание) | Всё: HTTP и вся фоновая работа | `0.0.0.0:3100` |
| `worker` | Все фоновые таймеры; применяет миграции БД; руководит api-детьми | приложение доски на внутреннем loopback `127.0.0.1:3101` |
| `api` | Только HTTP — ни одного фонового таймера; ждёт, пока worker применит миграции, сам базу не мигрирует | `0.0.0.0:3100` (порт делится между api-процессами через `reusePort`) |

Роль процесса задаётся переменной окружения `PAPERCLIP_PROCESS_ROLE`
(`all` / `worker` / `api`); пустое или неизвестное значение откатывается к
`all` с предупреждением в журнале при старте. Руками её обычно ставить не
нужно: в управляемом варианте worker сам форкает api-детей и выставляет им
`PAPERCLIP_PROCESS_ROLE=api` (и `PAPERCLIP_PARENT_BOOT_ID`).

## Настройка (ожидается в rc)

Разделение настраивается из интерфейса доски — **Instance → General →
«Процессы доски»** — или через API. Значения живут в
`instance_settings.general.processes`:

| Ключ | Значения | Умолчание | Смысл |
|---|---|---|---|
| `mode` | `single`, `split` | `single` | Один процесс делает всё, либо worker + api-процессы |
| `apiCount` | 1–4 | 1 | Сколько api-процессов поднимает `split` |
| `leaderLeaseTtlSec` | 5–600 | 30 | TTL лидерской аренды фоновой роли |
| `liveEventsBus` | `local`, `pg` | `local` | Как события в реальном времени идут между процессами |
| `admissionStore` | `memory`, `db` | `memory` | Где решается допуск прогонов |
| `singletonProxy` | boolean | `true` | Не-лидер проксирует однопроцессные маршруты лидеру |

Прочитать действующие значения и источник каждого (`settings` / `env` /
`default`), а также режим, который реально исполняет эта сборка:

```sh
curl -s http://localhost:3100/api/myrmidon/processes
```

Сменить режим (только администратор инстанса; применяется на живую, без
перезапуска контейнера):

```sh
curl -s -X PATCH http://localhost:3100/api/myrmidon/processes \
  -H 'Content-Type: application/json' \
  -d '{"mode": "split", "apiCount": 2}'
```

**Аварийный выход.** Переменная `PAPERCLIP_PROCESS_MODE=single` в окружении
сильнее сохранённой настройки и читается при старте, раньше базы: если
сохранённая строка когда-нибудь уронит доску, запустите контейнер с этой
переменной — доска поднимется одним процессом, и настройку можно будет
исправить из интерфейса. Пока переменная выставлена, страница настроек
показывает принудительный режим с источником `env`.

## Наблюдение за процессами

### Панель «Процессы»

Instance → General показывает каждый живой процесс доски: boot id (строка
процесса, который отдал страницу, помечена «self»), роль, pid и имя хоста,
id контейнера, api-порт, версию, аптайм, возраст пульса, лаг цикла событий и
занятую память. Панель опрашивает реестр с его же частотой, поэтому умерший
процесс желтеет в течение одного такта пульса (10 с) и исчезает в течение
окна протухания (2 минуты).

### API реестра

Те же данные через API (читать может любой участник доски):

```sh
curl -s http://localhost:3100/api/myrmidon/board-processes
```

В ответе — `pulseSeconds`, `staleAfterSeconds` и по записи на процесс со
`status: "live" | "stale"`.

### /internal/procs (ожидается в rc)

Роутер метрик получает `GET /internal/procs` под тем же bearer-токеном, что и
эндпоинт метрик (`MYRMIDON_METRICS_TOKEN` или секрет компании, названный в
`MYRMIDON_METRICS_TOKEN_SECRET`). Он отдаёт список процессов доски из
реестра — роль, pid, `startedAt`, `uptimeSeconds`, `ready` — и называет роль
отвечающего процесса:

```sh
curl -s -H "Authorization: Bearer $MYRMIDON_METRICS_TOKEN" \
  http://localhost:3100/internal/procs
```

Неудачное чтение реестра всё равно отвечает HTTP 200 с корректным пустым
списком: поллер во время отказа базы получает тишину в форме данных, а не
страницу ошибки.

### Метрики по ролям (ожидается в rc)

Каждая строка-сэмпл всех семейств метрик несёт метку `role="api|worker|all"`,
разрешённую так же, как в реестре процессов (`PAPERCLIP_PROCESS_ROLE`,
умолчание `all`). Имена метрик не меняются; единственная конфликтовавшая
метка семейства очередей переименована `role` → `assignee_role`. Скрейп по
ролям отвечает на вопрос «тормозит HTTP-полоса или планировщик?» без чтения
журналов.

### Пробы готовности для балансировщика

Направьте балансировщик или рантайм контейнера на:

- `GET /healthz` — сводный ответ: 200 только когда доска целиком может
  принимать трафик. Во время перехода в split (`supervisorState:
  "startingSplit"`) ответ 503 по определению, так что балансировщик ждёт все
  api-дети вместо того, чтобы слать трафик в полусобранную схему;
- `GET /internal/ready` — один процесс о себе; используйте для попроцессных
  проверок (роль, boot id, детали по каждой проверке) при разборе.

Оба эндпоинта ставят `Cache-Control: no-store`, не читают учётных данных и не
раскрывают данных компаний.

## Выкаты и drain (ожидается в rc)

Смена режима не требует перезапуска контейнера — супервизор переводит доску
на живую:

- **single → split**: worker форкает api-детей, но сам продолжает обслуживать
  :3100, пока *каждый* ребёнок не пришлёт `ready` по IPC (ребёнок сообщает о
  готовности только после поднятия listener'а и успешного `SELECT 1`). Затем
  worker закрывает свой публичный listener. Весь переход `/healthz` отвечает
  503 с `reason: "split_starting"`.
- **split → single**: worker заново открывает :3100 (с `reusePort`, поэтому
  дети продолжают обслуживать трафик) и затем *дрейнит* детей по одному.
- **Масштабирование** (смена `apiCount`) проходит через те же ворота
  готовности.

Drain — это вывод ребёнка без потери запросов:

1. Worker шлёт `drain` по IPC.
2. Ребёнок перестаёт принимать новые соединения (`server.close()`), закрывает
   простаивающие, а websocket-клиентам событий шлёт `close(1012)`, чтобы они
   переподключились к выжившему процессу.
3. Через 30 секунд грейса он закрывает всё оставшееся
   (`closeAllConnections()`) и корректно завершается.

Обработка падений: умерший api-ребёнок перезапускается с лестницей бэкоффа
(1 с, удвоение до 30 с). Если 15 секунд нет ни одного живого api-ребёнка,
worker сам открывает :3100 (*аварийный возврат в single*) и поднимает сигнал
внимания — доска остаётся на месте, даже если сломались все дети. Каждый
api-ребёнок получает потолок кучи 1 ГБ (`--max-old-space-size`), чтобы
разогнавшийся обработчик запросов не мог оставить worker без памяти.

Выкаты контейнера: оставьте health-check контейнера на `/healthz`. Так как
сводный ответ — 503, пока split стартует или идёт drain, оркестратор, который
слушается пробы, не переключит трафик на новый контейнер, пока новая схема
реально не обслуживает, и не убьёт старый посреди drain.
