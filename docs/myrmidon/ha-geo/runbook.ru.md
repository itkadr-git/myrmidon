# HA-GEO: инструкция оператора

Это шаблон, а не подтверждение готовности площадки или разрешение на действия. См. [существующий T9 runbook](../../../doc/runbooks/t9-center-standby.md). Исторический порог RPO 900 секунд не доказывает целевой HA-GEO RPO <= 300 секунд. Цель ручного RTO <= 1800 секунд. Реальные работы разрешены только отдельным допуском и в согласованное окно.

## Безопасность и роли

Части A-D остаются pending до подтверждения их владельцами. `geo-check` и `standby-ctl` присутствуют в этой ревизии. Упомянутый в контексте `/api/health/replication` и формат ответа в этой ревизии не подтверждены: не вызывать и не выдумывать JSON; зависимый от него шаг запрещен до сверки исходника релиза. Незаданные адреса, маршруты, секреты, пути, образы, версии, процедура fencing и способ контроля workers блокируют соответствующую операцию. Имя DNS, хранилище секретов и версию не предполагать.

Назначить руководителя инцидента, оператора БД, оператора приложения, оператора инфраструктуры с правом fencing и наблюдателя. Для каждой изменяющей команды записать предпосылки, исполнителя, разрешение и окно, команду, код выхода, проверку результата и действие при отказе. Остановиться при неизвестном состоянии или второй активной копии. Не записывать секреты. Лаборатория использует только синтетические данные и изолированные пути; этот документ не разрешает подключаться к площадкам. Боевой образ приложения только из CI по согласованному digest.

## Инвентаризация

Предпосылки: владельцы A-D и ведомость параметров определены. Оператор: наблюдатель. Окно: лабораторное; для реальной площадки отдельное разрешение на чтение. Проверить ОС, Docker, клиент PostgreSQL, доступность PostgreSQL и LiteLLM, наличие именованных секретов и конфигурацию mirror:

```bash
myrmidon geo-check --json --config <approved-config>
```

Проверка готовности не доказывает репликацию или failover. При ненулевом коде, неполном отчете или неизвестном параметре остановиться. Значения секретов в отчет не копировать.

## Подготовка standby

Предпосылки: инвентаризация пройдена; согласованы endpoint primary, ссылка на учетные данные, каталоги, версия PostgreSQL и политика WAL/слота; состояние данных проверено. Исполнитель: оператор БД. Разрешение: отдельное окно подготовки. Сначала проверить план:

```bash
bash scripts/myrmidon/standby/standby-ctl.sh setup --target all --dry-run
```

После согласования выполнить с защищенным passfile (правила путей см. в T9):

```bash
bash scripts/myrmidon/standby/standby-ctl.sh setup --target all --credentials <approved-passfile>
```

Проверить код 0, обе базы с `pg_is_in_recovery() = 1`, поток, ограниченный слот и отсутствие приложения и workers на холодной площадке. При ошибке preflight остановиться, не применять `--force`; после начала изменения сохранить каталог и передать оператору БД. Не удалять promoted standby.

## Backup и restore

Предпосылки: только изолированная лабораторная копия с синтетическими данными, разрешенные пути и образ, без production volumes и секретов. Обертка по умолчанию использует host network и production-пути: в лаборатории она запрещена. Нужна отдельно проверенная изолированная конфигурация host-mode без production volumes; если ее нет, учение не выполнять. Проверить, что host, port, passfile, новый каталог и переменные среды относятся только к fixture: значения по умолчанию не изолированы. Источник snapshot — 127.0.0.1 на указанном standby-port, а не primary host/port: до запуска независимо убедиться, что этот порт ведет к изолированному standby и не может попасть на боевые данные. Для all выполняется одно учение кластера board с проверкой обеих баз, а не два отдельных кластера. Оператор БД, лабораторное окно. Сначала план, затем выполнение после разрешения:

```bash
bash scripts/myrmidon/standby/standby-ctl.sh rehearse --target all --dry-run
STANDBY_CTL_NO_DOCKER=1 bash scripts/myrmidon/standby/standby-ctl.sh rehearse --target all --pg-runner=host --primary-host=<isolated-primary-host> --primary-port=<isolated-primary-port> --standby-port=<isolated-standby-port> --drill-dir=<isolated-new-drill-dir> --drill-port=<isolated-drill-port> --credentials=<isolated-passfile>
```

Проверить код 0, запуск, promotion, smoke обеих баз, время и удаление каталога учения. При отказе остановить только изолированный экземпляр, сохранить обезличенные журналы и проверить очистку. Любое боевое резервное копирование или восстановление требует отдельного окна и утвержденной процедуры.

## Ручной failover и fencing

Предпосылки: разрешенный инцидент или окно, lag <= 300 секунд, план остановки записи и отката, независимое доказательство fencing, оператор инфраструктуры присутствует. Неизвестный lag или fencing запрещают promotion. Руководитель инцидента координирует; оператор инфраструктуры отключает старый writer; оператор БД выполняет promotion.

1. Остановить запись и дождаться завершения работ; проверить отсутствие второго writer.
2. Изолировать или остановить старый writer на инфраструктурной границе. Записать способ, исполнителя, время и независимое доказательство. Недоступность сети или ping не является fencing.
3. После проверки fencing оператор БД выполняет:

```bash
bash scripts/myrmidon/standby/standby-ctl.sh failover board --fenced="<change-id>: <fencing evidence>"
```

4. Проверить код 0, `pg_is_in_recovery() = 0`, сохранение fencing старого writer и единственность нового. Не обходить guard.
5. Оператор приложения запускает холодное приложение по утвержденной процедуре, оставляя scheduler, интеграции и workers выключенными. Маршрутизацию менять только утвержденным методом. Проверить health, базу, интеграции и единственность workers; точный способ остается pending в A-D. Если нет проверки или обнаружены двойные workers, не включать их и остановить переключение.

При отказе после promotion не включать старый writer: оставить его fenced, остановить новые workers, сохранить LSN и передать инцидент оператору БД. Процедура отката не означает второе автоматическое promotion.

## Измерения

Перед инцидентом сохранить код и результаты для обеих целей:

```bash
bash scripts/myrmidon/standby/standby-ctl.sh check-lag --target all --rpo 300
```

Код 0 не подтверждает RPO в более поздний момент отказа. Для реальной приемки записать UTC последней подтвержденной записи primary и последней восстановленной записи согласованного набора; вычесть время восстановленной записи из времени подтвержденной записи primary; разность должна быть от 0 до 300 секунд. Отсутствие маркеров или неопределенность часов означает отказ приемки; время последнего replay на простаивающей БД само по себе не равно lag.

RTO измерять от объявления инцидента до одновременного прохождения health, проверки записи, интеграций и single-active workers. Вычисление разности UTC epoch секунд офлайн (подставить оба значения):

```bash
python3 -c 'print(int("<end_epoch>") - int("<start_epoch>"))'
```

Отрицательное или отсутствующее значение недопустимо; RTO должен быть <= 1800 секунд. Успех изолированного restore drill сам по себе не доказывает полный RTO.

## Failback и rollback

Предпосылки: отдельное окно и разрешение руководителя, резервная копия всех новых записей, старый primary fenced, согласованная процедура синхронизации и проверка идентификатора и timeline. Операторы БД, инфраструктуры и приложения выполняют свои действия.

1. Сохранить LSN текущего writer и восстановить старый узел как standby из текущего writer; проверить recovery и streaming. Не запускать старый узел writer.
2. Остановить запись и workers на текущем узле, проверить ноль workers. Инфраструктурный оператор выполняет fencing текущего writer с независимым подтверждением.
3. Оператор БД выполняет утвержденное promotion синхронизированного standby и проверяет единственный writer. Без подтверждения promotion или fencing маршрутизацию не менять.
4. Оператор приложения переключает маршрут по согласованной процедуре, проверяет базу, health, интеграции и единственный набор workers. Только после подтверждения нового writer оператор БД может перевести бывший активный узел в standby по отдельно разрешенной процедуре.

При ошибке остановиться, сохранить обе копии и evidence LSN; не удалять единственную копию новых записей. При возможном расхождении timeline не объединять их наугад. Маршрут возвращать только к проверенному writer после согласования; не снимать fencing автоматически.

## Доказательства приемки

| Критерий | Лаборатория | Реальная площадка, отдельное окно |
|---|---|---|
| Готовность | `geo-check --json`, полные параметры | Отчет и подтвержденные параметры |
| Standby | Изолированный setup, обе базы в recovery | Streaming, слот, timeline и результат setup |
| RPO <= 300 | Синтетические маркеры и `check-lag --rpo 300` | Последняя подтвержденная и восстановленная записи, время и lag |
| RTO <= 1800 | Время полного сценария, не только restore | UTC начала и конца с health, записью и интеграциями |
| Fencing | Синтетическая изоляция и отказ записи | Независимое инфраструктурное доказательство |
| Single-active | Один writer, нет внешних workers | Один writer и scheduler, нет старых или двойных workers |
| Backup/restore | Smoke и проверенная очистка | ID backup, результат restore и подпись оператора |

Боевое окно требуется для fencing, изменения репликации, учетных данных, слота, каталогов, приложения, маршрутов, интеграций, workers, failback и удаления данных. Пока их владельцы не заполнили параметры и процедуры, соответствующие операции запрещены. Готовность документа не равна готовности площадки.
