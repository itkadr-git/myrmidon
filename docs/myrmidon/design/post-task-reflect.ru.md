# Разбор после задачи: урок в банк памяти роли

> English version: [post-task-reflect.md](post-task-reflect.md)

Редакция от 06.10.2026, для релиза 1.7, пункт POST-TASK-REFLECT эпика
AGENT-EXCHANGE. Документ фиксирует дизайн до нарезки на инженерные части:
какие события порождают «урок», схему записи в банк памяти роли, правила
дедупликации и настройки. Кода по этому документу пока нет; каждый названный
механизм опирается на модули, которые уже есть в `main`.

## 0. Коротко

- После трёх исходов задачи — **возврат с приёмки**, **ошибка прогона**,
  **`blocked`** — доска пишет **ровно одну** запись «урок» в **банк памяти
  роли** (значение `agents.role`) агента, который держал задачу.
- Текст урока даёт короткий разбор **бесплатной моделью** (соединение,
  помеченное `free` в каталоге моделей), а не платной моделью самого
  прогона. Разбор — один вызов, один абзац, без инструментов.
- Запись несёт теги (`lesson`, вид события, ключ задачи), срок годности
  (`expires_at` в метаданных retain) и ссылку на задачу как `document_id`.
- Дедупликация детерминированная: один урок на (задача, вид события, редакция
  исхода) — задача, возвращённая дважды, даёт два урока; повторный проход по
  тому же исходу не даёт ни одного.
- Функция включается и выключается на компанию из интерфейса без перезапуска,
  с настраиваемым сроком годности; оба значения живут в настройках инстанса и
  перечитываются на каждое событие — по прецеденту настроек памяти агента
  (`general.agentMemory`, перечитываются на каждый запрос).

## 1. Почему сначала дизайн-документ

Пункт зависит от двух соседей, чья механика ещё устаканивается: DEBATE-ASYM
(механика ролей и судьи) и BUDGET-CONFIG. Резка сразу в код зафиксировала бы
предположения об адресации «банка роли» и о том, какую модель можно тратить
на разбор. Документ фиксирует только то, что уже истинно в коде (адресация
банков памяти, поверхность retain API, точки подписки на смену статуса), а
остальное помечает открытыми вопросами с названным владельцем решения — чтобы
инженерная нарезка могла начаться со стабильных частей.

## 2. События, порождающие урок

Событие — долговременный переход состояния задачи или прогона, который видит
сервер доски. В объёме три вида:

| Событие | Как его видит доска | Чей это урок |
|---|---|---|
| **Возврат с приёмки** | Статус задачи уходит из `in_review` обратно в `in_progress` (проверяющий или владелец отклонил результат; модуль маршрутизации проверок уже отслеживает возвращаемого исполнителя) | Агент, которому задача возвращается (возвращаемый исполнитель), а не проверяющий |
| **Ошибка прогона** | Прогон heartbeat исполнителя задачи завершается в `error` (модуль auto-resume уже считает такие случаи и эскалирует после исчерпания попыток) | Агент, чей прогон упал |
| **`blocked`** | Статус задачи становится `blocked` с дескриптором разблокировки | Текущий исполнитель задачи |

Вне объёма (урок не пишется):

- успешные завершения и приёмки — урок об успехе идёт по пути кандидата в
  навыки (SKILL-LIFECYCLE), а не по этому;
- отмены, паузы, откладывания окном обслуживания — сигнала отказа нет;
- повторный `error` того же прогона в попытках auto-resume: событие срабатывает
  один раз на **окончательный** отказ (auto-resume сдался или неприменим), а не
  на каждую попытку. Потолок попыток AUTO-RESUME — естественный срез: урок
  пишется в момент, когда доска сдаётся, потому что именно тогда отказ
  становится фактом, достойным запоминания.

Каждое событие потребляется **один раз**, в момент перехода, хуком рядом с
кодом, выполняющим переход (путь патча статуса — для возвратов и блоков; путь
финализации прогона — для ошибок). Хук ставит задание в исходящую очередь;
разбор и вызов retain идут асинхронно, поэтому медленный или лежащий сервис
памяти никогда не задерживает сам переход статуса.

## 3. Запись урока

### 3.1 В какой банк

Запись идёт в **банк роли**: `role-<companyId>-<role>` по досковой роли
исполнителя (`agents.role`). Обоснование:

- урок, выученный одним разработчиком, должен вспоминаться следующим
  разработчиком; банк конкретного агента (`adapterConfig.hindsight.bankId`)
  запер бы урок в нём;
- роль уже является единицей адресации для грантов касты и пулов проверяющих,
  поэтому банки `role-…` переиспользуют существующую, видимую оператору
  систему имён;
- для агентов без роли (роль пуста) урок не пишется — событие логируется и
  пропускается, подобно тому как агент без банка в карточке памяти — это
  состояние, а не ошибка.

Сторона чтения: блок `adapterConfig.hindsight` профиля бота получает банк роли
как дополнительный источник recall (для бота — только чтение), так что уроки
доходят до следующего прогона любого агента с этой ролью. Путь retain остаётся
только на запись со стороны доски; боты уроки напрямую не пишут.

### 3.2 Форма записи

Одна retain-запись на урок, через тот же HTTP API hindsight, что использует
плагин памяти (`POST /v1/default/banks/{bankId}/memories`, одна запись,
`async: true`):

- **content** — текст урока в один абзац от модели разбора (см. §4), на
  английском, от первого лица роли («When a docs PR is returned with “X”,
  check Y before resubmitting»), не более ~500 символов.
- **context** — `"paperclip"` (как уже шлёт плагин), чтобы уроки лежали в той
  же полосе удержания, что и прочие записи доски.
- **document_id** — ссылка на задачу: `issue:<issueId>`. Hindsight группирует
  и дедуплицирует по document id; задача становится якорем, а «все уроки
  задачи X» — запросом в рамках документа.
- **metadata**:
  - `kind: "lesson"` (признак применимости: recall фильтрует по нему),
  - `event`: `review_return` | `run_error` | `blocked`,
  - `issue_key`: человекочитаемый ключ задачи,
  - `role`: роль, которой принадлежит банк,
  - `expires_at`: метка времени ISO-8601 = время события + TTL (§5),
  - `dedup_key`: см. §4.2,
  - `run_id`, когда событие привязано к прогону.
- **tags**: `["lesson", "post-task-reflect", "event:<event>", "role:<role>"]` —
  тот набор тегов, который уже показывает карточка памяти.

Срок годности — рекомендательные метаданные, а не функция hindsight:
ежедневная очистка инвалидирует (`state: invalidated`, причина `ttl-expired`)
записи уроков с прошедшим `expires_at`. Мягкая инвалидация соответствует
семантике удаления в карточке памяти и сохраняет аудит на стороне сервиса.

## 4. Разбор, дедупликация и поведение при сбоях

### 4.1 Вызов разбора

Один вызов бесплатной модели: на входе — заголовок задачи, последний
комментарий проверяющего / сводка ошибки прогона / дескриптор разблокировки
(что бы ни вызвало событие) и не более последних N=5 комментариев треда с
усечением. Промпт просит один абзац: что пошло не так, что делать иначе, в
форме совета роли. Модель выбирается из каталога моделей инстанса среди
соединений, помеченных `free` (флаг каталога, который уже отдаёт модуль
model-providers); если бесплатная модель не настроена, функция деградирует до
**шаблонного урока** (вид события + текст причины, без разбора), а не тратит
платную модель — настройка в §5 управляет тем, допустима ли деградация.

### 4.2 Ровно один раз на исход

Задание исходящей очереди несёт `dedup_key`:

```
<issueId>:<event>:<outcomeRevision>
```

- `review_return`: редакция = число возвратов этой задачи (хранится в
  состоянии исполнения; состояние маршрутизации проверок уже версионирует
  этапы),
- `run_error`: редакция = id упавшего прогона,
- `blocked`: редакция = метка времени перехода в blocked.

Перед retain работник читает банк роли с фильтром по `document_id` задачи и
пропускает запись, если запись с тем же `dedup_key` уже есть (действующая или
инвалидированная). Ключи детерминированные, а не семантическое сходство: два
по-настоящему разных отказа одной задачи дают два урока, один отказ,
обработанный дважды, — один. Критерий приёмки «возврат с приёмки создаёт
ровно одну запись урока» — это тест на этот путь: переход вызван дважды
(второй раз — повторным проходом очистки), утверждается одна запись.

### 4.3 Поведение при сбоях

- Сервис памяти лежит или retain не удался: задание повторяется с backoff в
  рамках тика работника, затем сдаётся и пишет строку в журнал активности
  (`myrmidon.reflect.retain_failed`). Переход статуса, вызвавший событие,
  никогда не откатывается и не ждёт.
- Вызов разбора не удался, или нет бесплатной модели при выключенной
  деградации: тот же повтор в очереди; при окончательном отказе событие
  отбрасывается с той же строкой журнала. Частичных записей нет: retain
  происходит только после успешного разбора.
- Каждый записанный урок и каждый окончательный отказ пишут одну строку в
  журнал активности (конвенция аудита модуля памяти: id банка, ключ задачи,
  ключ дедупликации — никогда текст урока).

## 5. Настройки (интерфейс, без перезапуска)

Новые настройки инстанса под `general.postTaskReflect`, перечитываются на
каждое событие, каждая показывается в интерфейсе с источником значения
(настройка / env / умолчание) — в точности как настройки памяти агента:

| Настройка | Умолчание | Смысл |
|---|---|---|
| `enabled` | `false` | Главный выключатель. Выкл = события не ставятся в очередь, записи не пишутся, без перезапуска (критерий приёмки: выключение на лету останавливает новые записи) |
| `lessonTtlDays` | `90` | Срок годности записи урока, 1–365. Очистка инвалидирует просроченные уроки |
| `allowTemplateFallback` | `true` | При отсутствии бесплатной модели писать шаблонный урок вместо отбрасывания события |
| `maxLessonsPerDay` | `20` | Потолок расхода на вызовы разбора в день на компанию (согласование с BUDGET-CONFIG); на потолке события отбрасываются со строкой журнала до следующего дня |

Переопределения env (`MYRMIDON_POST_TASK_REFLECT_*`) существуют только как
принудительные и проигрывают настройке инстанса — по действующему правилу
настроек. Переключатель живёт в текущем интерфейсе (Instance settings →
General), рядом с панелью памяти агента; экраны нового интерфейса не делаются.

## 6. Критерии приёмки (из постановки, привязка к тестам)

- **Возврат с приёмки создаёт ровно одну запись урока** — тест на путь
  дедупликации (§4.2): переход вызван дважды, одна запись в банке, второй
  проход — холостой.
- **При выключенной настройке записей нет, без перезапуска** — тест: функция
  включена → событие → одна запись; `enabled` переведён в `false` в настройке
  инстанса (без перезапуска процесса); то же событие на другой задаче → новых
  записей нет, задание в очередь не ставится.

## 7. Зависимости и открытые вопросы

- **DEBATE-ASYM** владеет вопросом, является ли вердикт судьи (в отличие от
  возврата человеком/владельцем) четвёртым видом события. Дизайн допускает
  его как ещё одно значение `event` с той же формой записи; инженерная
  нарезка добавит его, когда DEBATE-ASYM приземлится.
- **BUDGET-CONFIG** владеет вопросом, входит ли `maxLessonsPerDay` в общий
  бюджетный конверт вместо отдельного счётчика. Форма настройки выше
  совместима с обоими вариантами.
- **SKILL-LIFECYCLE** остаётся путём для положительных уроков (кандидаты в
  навыки); запись урока, чей текст позже поднят в кандидата навыка,
  инвалидируется с причиной `promoted-to-skill`, чтобы recall оставался
  чистым. Эта связка — отдельный шаг, не часть данного пункта.

## 8. Риски

- **Засорение банка.** Болтливый режим отказов (шаткий инструмент, падающий
  каждый прогон) заполняет банк роли почти одинаковыми уроками. Сдержки в
  дизайне: дедупликация по id прогона тут не помогает, но `maxLessonsPerDay`
  ограничивает поток, очистка по TTL их устаревает, а карточка памяти уже
  позволяет оператору инвалидировать записи. Ограничение темпа по префиксу
  `dedup_key` — задокументированный следующий шаг, если потолок окажется
  слишком грубым.
- **Бесплатная модель не настроена.** При `allowTemplateFallback: false`
  функция молча ничего не делает; строка журнала активности и строка статуса
  в панели настроек — сигнал оператору.
- **Переименование роли.** Банки названы по строке роли; переименование роли
  бросает старый банк (recall смотрит на новое имя). Роли управляются
  оператором и переименовываются редко; карточка памяти конкретного агента не
  затрагивается. Зафиксировано здесь как известное ограничение, в этом пункте
  не решается.
