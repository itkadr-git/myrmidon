# Пилот корпуса знаний: поиск на PostgreSQL + pgvector — результаты и решение

> English version: [corpus-pgvector-pilot.md](corpus-pgvector-pilot.md)

Редакция 08.10.2026. Документ фиксирует итог пилота третьего шага CORPUS-2.0:
может ли корпус знаний платформы (поиск по памяти и документам агентов)
переехать из внешнего сервиса RAGFlow в индекс внутри собственного PostgreSQL
платформы с расширением pgvector. Пилот — это измерение, а не функция
продукта: в поставляемой сборке ничего не меняется, и эта страница — постоянная
запись обоснования рекомендации.

## 0. Коротко

- Поиск на PostgreSQL + pgvector **не хуже RAGFlow** на корпусе пилота и
  быстрее на два порядка: recall@5 — 0.8429 против 0.829 у базовой RAGFlow,
  nDCG@10 — 0.7056 против 0.663; задержка поиска p95 — ~0.1 с против ~15 с.
  Приёмочный порог пилота — p95 < 2 с — пройден с большим запасом.
- Рекомендация для будущего модуля корпуса (реализация — отдельный пункт эпика,
  не этот пилот):
  - эмбеддер: DashScope `text-embedding-v4` с размерностью 1024, вызов через
    шлюз LiteLLM;
  - векторный индекс: HNSW с параметрами `m = 16`, `ef_construction = 64`,
    `ef_search = 64`;
  - гибридный поиск: слияние рангов RRF с `k0 = 60`, `k_candidates = 100`;
    полнотекстовая сторона — индекс GIN по `pg_trgm`.
- Стоимость эмбеддинга по ценам на момент пилота: около **$1.64 за 100 000
  чанков**.

## 1. Контекст

Эпик корпуса заменяет RAGFlow собственным модулем поиска на TypeScript.
Третий шаг эпика — пилот с одним вопросом, на который нужно ответить
измерением: выдержит ли индекс корпуса PostgreSQL + pgvector с качеством и
задержкой не хуже, чем используемый сейчас сервис RAGFlow? Пилот шёл вне
репозитория продукта, во внутреннем репозитории инструментов (стенд, раннер
эмбеддеров и харнес качества в каталоге `corpus-pilot/`), поэтому код и
настройки продукта в этом шаге не менялись.

## 2. Результаты измерений

| Метрика | Стенд pgvector | Базовая RAGFlow |
| --- | --- | --- |
| recall@5 | 0.8429 | 0.829 |
| nDCG@10 | 0.7056 | 0.663 |
| Задержка поиска, p95 | ~0.1 с | ~15 с |

- Масштаб стенда: порядка 100 000 чанков.
- Порог по задержке для пилота: p95 < 2 с — пройден с большим запасом (~0.1 с).

## 3. Рекомендуемая конфигурация

| Компонент | Выбор |
| --- | --- |
| Эмбеддер | DashScope `text-embedding-v4`, размерность 1024, через шлюз LiteLLM |
| Векторный индекс | pgvector HNSW: `m = 16`, `ef_construction = 64`, `ef_search = 64` |
| Слияние в гибриде | Reciprocal rank fusion (RRF), `k0 = 60`, `k_candidates = 100` |
| Полнотекстовая сторона | Триграммный индекс GIN по `pg_trgm` |

Стоимость эмбеддинга по ценам пилота: ~$1.64 за 100 000 чанков.

## 4. Отступление от исходной спецификации

Спецификация шага с самого начала называла эмбеддером `text-embedding-v4`.
Когда этап эмбеддеров стартовал, модель не была заведена в шлюзе LiteLLM
(вызовы отвечали HTTP 400), поэтому этап прошёл на запасном эмбеддере, с
которым был собран раннер. 07.10.2026 модель добавили в шлюз, и полный прогон
качества повторили на `text-embedding-v4` — цифры в разделе 2 относятся к
результатам v4. Раннер пилота выбирает эмбеддер переменной окружения
`EMBED_MODEL`, поэтому переключение не потребовало правки кода.

## 5. Решение

Вопрос пилота закрыт: индекс корпуса может жить в собственном PostgreSQL
платформы с pgvector без потери качества и задержки по сравнению с RAGFlow.
Рекомендация из раздела 3 — вход для пункта эпика, реализующего модуль
корпуса; пока этот пункт не поставлен, RAGFlow остаётся рабочим путём поиска,
а эта страница фиксирует, почему.
