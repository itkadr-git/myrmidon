# Канал через коннектор: Telegram выходит из ядра

> English version: [chat-channel-connector.en.md](chat-channel-connector.en.md)

**Редакция:** 07.10.2026 · **Трек 4** · выпуск **1.6.6**, шаг 1 (проект).

Документ описывает контракт коннектора канала, пошаговый перенос Telegram из ядра без простоя
ботов и совместимость с текущими настройками и данными. **Код по этому документу не пишется до
одобрения проекта.**

Документ продолжает вендорские планы:
`doc/plans/chat-adapters/2026-09-03-chat-adapters-architecture.md` (граница владения, модель
приложений и подключения, модель персистентности, общие контракты, потоки событий, идентичность и
права, фазы поставки) и `doc/plans/2026-09-09-chat-provider-foundation.md` (провайдер и основа
данных). Наши правила правки вендорского кода — [CONVENTIONS.md](../CONVENTIONS.md), раздел 8.

## 0. Коротко

- **Ядро знает только контракт.** Всё, что знает о Telegram, переезжает в коннектор
  `server/src/myrmidon/channel-connectors/telegram/` и в общий слой. В вендорском
  `server/src/services/chat-channels.ts` остаётся **одна** наша вставка — точка подключения хаба.
- **Сейчас вставок 81**, а не 77, как в постановке: `chat-channels.ts` вырос до 38 696 строк, из
  81 вставки `// myrmidon(…)` **66** про Telegram-мост (адресация, удержания, статус в личке,
  топики, голос, уведомления, медиа-лимиты) и **15** общие — переименование продукта (B1, B1b) и
  ускорение БД на горячем пути (D1, D2). Целевое состояние — одна вставка; общие 15 остаются, к
  каналу они не относятся.
- **Коннектор — объект поверх вендорского рантайма.** Вендорский `ChatSdkEndpointRuntime` уже
  поднимает транспорт на endpoint; наш коннектор отвечает за пять областей: жизненный цикл,
  ссылки и учёт, приём, отправка, медиа — и за настройки. Ни одной новой ветки в вендорском
  `switch (provider)` не добавляется.
- **Подключение, настройка и отключение — в интерфейсе** на существующих экранах Chat endpoints
  (`/chat-endpoints*`); подключение и отключение канала не перезапускают сервер: рантайм канала
  создаётся для каждого endpoint, а состояние живёт в базе и в арендах (`chat_endpoint_leases`).
- **Данные и настройки совместимы.** Шаги 1–3 не меняют схему и не перекладывают данные; набор
  настроек и их значения остаются прежними, миграции — только аддитивные и только там, где без
  них не обойтись. Откат образа на новой схеме обязан работать.
- **Перенос — 6 шагов, каждый отдельным PR** и каждый принимается на копии боевой базы:
  контракт и реестр (поведение не меняется) → точка подключения в режиме наблюдения → темы моста
  по одной → выключатель канала в интерфейсе → общий слой доступа пишущих.
- **Не наша цель — вырезать Telegram из вендорских файлов.** 247 сравнений `provider === "…"`,
  92 литерала `"telegram"` и фабрика `@chat-adapter/*` — вендорский код; еженедельный порт
  важнее. Мы убираем из вендорских файлов **свои** вставки, а не вендорскую логику.

## 1. Задача и границы

Что решаем:

1. Каждое обновление вендора конфликтует в `chat-channels.ts`, потому что наш мост врезан в его
   ветки: входящий ход, вейкап, публикация ответа, меню команд, аренды, медиа.
2. Наши функции разбросаны по темам и не собраны в одном месте: адресация `@bot`, удержания
   (CHAT-HOLD), статус в личке, форум-топики, голос, идентичность агента, уведомления.
3. Настройка канала живёт в двух местах (настройки компании и наш блок `channelSettings`), а
   подключение и отключение канала в интерфейсе никак не показаны.

Что не решаем на этом этапе:

| Вне этапа | Почему |
|---|---|
| Переписывание вендорских `chat-telegram-*` и `switch (provider)` | вендорский код, еженедельный порт; см. CONVENTIONS §8 |
| Новые каналы (свой транспорт без вендорского адаптера) | реестр это позволит, реализация — отдельная задача |
| Смена модели данных (свои таблицы вместо вендорских) | рост риска порта и миграций без пользы |
| Изменение пользовательских текстов моста | тексты и язык — [telegram-bridge-locale.md](../guides/telegram-bridge-locale.md) |
| Права и доступ пишущих как таковые | общий слой — отдельная задача выпуска (раздел 9) |

## 3. Контракт коннектора канала

### 3.1 Пять областей

Коннектор — объект на каждый провайдер (`telegram`), создаваемый фабрикой. Все методы вызываются
синхронно и получают контекст (база, компания, журнал, время) — глобального состояния нет.

```ts
// server/src/myrmidon/channel-connectors/contract.ts  (проект, код не пишем)
export interface ChannelConnector {
  readonly provider: ChatProviderName;          // "telegram"

  lifecycle: {
    start(endpoint): Promise<ChannelRuntime>;   // поднять рантайм канала
    stop(endpoint, reason): Promise<void>;      // отключение в интерфейсе
    status(endpoint): Promise<ChannelStatus>;   // disabled | connecting | ready | degraded
  };

  links: {
    conversationKey(event): string;             // устойчивый ключ диалога
    conversationUrl(conversation): string | null;
    route(event): Promise<ChannelRoute | null>; // задача и агент, которым адресован ход
    bind(conversation, route): Promise<void>;   // привязка диалога к задаче и агенту
  };

  inbound: {
    normalize(raw): Promise<ChannelTurn | null>;      // событие транспорта → наш вид
    admit(turn, ctx): Promise<ChannelAdmission>;      // впускать ли: удержания, топик, право писать
    intakeMedia(turn): Promise<MediaIntakeResult>;    // вложения хода, лимиты, причина отказа
  };

  outbound: {
    plan(publication, ctx): Promise<TransportPlan>;   // текст, части, файл, строка статуса
    send(plan, transport): Promise<SendResult>;       // отправка и учёт в outbox
  };

  media: {
    fileLimitBytes: number; captionLimit: number; accepts: readonly MediaKind[];
  };

  settings: {
    keys: readonly ChannelSettingDescriptor[];        // чем настраивается канал
    resolve(ctx): Promise<ResolvedChannelSettings>;   // env → база → умолчание
  };
}
```

Жизненный цикл опирается на то, что уже есть у вендора: эффекты `chat-provider-lifecycle.ts`
(подписка на вебхук, меню команд, приветствие) и аренду endpoint в `chat_endpoint_leases`.
`start`/`stop` не порождают новый процесс: транспорт Telegram — вебхук на endpoint, поэтому
включение и выключение канала — это запись состояния и аренды, а не перезапуск сервера.

### 3.2 Реестр и хаб

```ts
// server/src/myrmidon/channel-connectors/registry.ts
registerChannelConnector("telegram", telegramConnectorFactory);

// server/src/myrmidon/channel-connectors/hub.ts
hub(db, deps);              // единственный объект, который видит ядро
hub.inbound({ endpoint, raw });
hub.outbound({ publication });
hub.lifecycle.start(endpoint) / .stop(endpoint);
hub.settings(endpoint);
```

- Реестр — единственное место, где перечислены наши каналы. Ядро спрашивает хаб по провайдеру
  endpoint и не знает ни одного имени канала.
- Хаб отвечает за порядок: одно входящее событие — один ход; публикация не уходит дважды
  (ключ идемпотентности вендорского outbox сохраняется).
- Провайдера, которого нет в реестре, хаб пропускает насквозь: вендорский путь остаётся
  нетронутым. Это позволяет переносить темы по одной, не ломая остальные каналы.

### 3.3 Границы контракта

- Коннектор не знает о `ChatSdkEndpointRuntime` напрямую, а получает от хаба нормализованное
  событие и адаптер отправки — вендорский рантайм остаётся вендорским.
- Коннектор не пишет SQL к вендорским таблицам напрямую: доступ к данным идёт через один слой
  `channel-connectors/store.ts` поверх существующих таблиц.
- В контракте нет ни UI, ни текстов: тексты (уведомления, удержания, строка статуса) живут в
  ресурсах коннектора и в общем слое карточек.
- Учёт отправленного остаётся вендорским: `chat_publications` и `chat_deliveries` — источник
  истины, коннектор только выбирает план отправки.

## 4. Одна точка подключения в `chat-channels.ts`

Целевая вставка ровно одна:

```ts
// myrmidon(HUB): the only connection between the vendor chat service and our
// channel connectors. Everything channel-specific lives in
// server/src/myrmidon/channel-connectors/.
const channelHub = myrmidonChannelConnectorHub(db, { logger });
```

Через неё проходят четыре потока: входящее событие транспорта, вейкап и маршрутизация,
публикация ответа и жизненный цикл endpoint. Всё остальное (`X8b`, `X9b`, `U1`, `U2`, `CHAT-HOLD`,
`TG-NOTIFY-D`, `VOICE-STT`, `P7`, `X8e`, `TG-LOCALE` — 66 вставок) уезжает в коннектор и общий
слой: в вендорском файле остаётся вызов хаба, а не наша логика между вендорскими ветками.

Общие 15 вставок (`B1`, `B1b`, `D1`, `D2`) перенос не затрагивает: переименование продукта и
типизированные сравнения UUID на горячем пути — не про канал, их место в ядре.

Порядок снятия вставок по шагам (раздел 6) выбран так, чтобы каждый PR был обозримым: одна тема —
один PR, вставки темы удаляются тем же PR, что переносит её код.

### 5.2 Данные

- Схема не меняется на шагах 1–3: ни одной миграции. Коннектор читает и пишет те же таблицы.
- Где без нового поля не обойтись (шаг 4, выключатель канала), поле аддитивное и его номер —
  следующий свободный после вендорских миграций; старое состояние «поля нет» читается как
  «включён», поэтому откат образа на новой схеме работает.
- Данные не перекладываются: `chat_endpoints`, `chat_conversations`, `chat_publications`,
  `chat_endpoint_leases` остаются источником истины, поэтому копия боевой базы подходит для
  приёмки без конвертации.

### 5.3 Что видит пользователь

Ничего нового на шагах 1–3: те же ЛС, те же группы и топики, те же команды, тот же текст
удержания. Шаг 4 добавляет в карточку канала состояние «включён/выключен» и объяснение, почему
канал не отвечает: сейчас этого нет.

## 6. Перенос по шагам

| Шаг | Что | Файлы | Сторожевой тест | Простой | Приёмка |
|---|---|---|---|---|---|
| S1 | Контракт, типы, реестр, хаб — только новые файлы | `server/src/myrmidon/channel-connectors/*` | тесты контракта и реестра | нет | типы и тесты пакета |
| S2 | Точка подключения: одна вставка `HUB`, хаб в режиме наблюдения | `chat-channels.ts` (+1 вставка), хаб | тест «наблюдение не меняет поведение» | нет | копия базы: журнал хаба совпадает с фактическими ходами |
| S3 | Темы моста по одной: топики → уведомления и статус в личке → удержания → адресация и команды → голос → медиа → идентичность | коннектор Telegram + вендорский файл (снятие вставок темы) | существующие `*.myrmidon.test.ts` темы + тест коннектора | нет | сценарии темы на копии базы |
| S4 | Выключатель канала в интерфейсе: состояние, объяснение, отключение и включение | `channel-settings/*`, аддитивное поле, `ui/src/pages/apps/chat/*` | тест «отключённый канал не принимает и не отправляет» | нет | копия базы: отключение и включение без перезапуска |
| S5 | Общий слой доступа пишущих подключается к коннектору и ядру | общий слой + вызов хаба | тесты слоя | нет | сценарии прав на копии базы |
| S6 | Сверка: осталась одна вставка, общие 15 на месте, реестр отличий обновлён фрагментом | `chat-channels.ts`, `docs/myrmidon/changes/*` | тест-счётчик вставок | нет | разбор diff вендорского файла |

**S1 — контракт и реестр.** Ни одной строки в вендорских файлах. Проверка: типы и тесты новых
файлов. Риск нулевой, поведение не меняется.

**S2 — точка подключения в режиме наблюдения.** Хаб создаётся один раз, получает четыре потока и
пишет журнал, но ничего не решает: решения остаются на вендорском пути. Смысл шага — убедиться на
копии боевой базы, что хаб видит все ходы и все публикации, до того как он начнёт что-то решать.
Сторожевой тест: при включённом наблюдении поведение и число публикаций не отличаются от `main`.

**S3 — темы по одной.** Порядок — от «меньше всего видно» к «больше всего видно», внутри темы
сначала переезд кода, потом снятие вставок:

1. форум-топики (`TG-NOTIFY-D`, 7 вставок) — приём и гейт топика;
2. уведомления и статус в личке (`U1`, 8, и модуль `telegram-notify`) — прогресс и уведомления;
3. удержания (`CHAT-HOLD`, 6) — ответ «ход принят, ждёт»;
4. адресация и команды (`X9b` 9, `X8b` 10, `X8e` 2) — `@<alias>`, `/new`, `/model`, `/stop`;
5. голос (`VOICE-STT` 10) — приём голосового и расшифровка;
6. медиа (`P7` 7, лимиты, разбиение длинного) — вложения и подписи;
7. идентичность и маршруты (остаток `X8b`/`U2`) — привязка диалога к задаче и агенту.

Каждая тема — отдельный PR с одним фрагментом реестра; критерий темы: тексты, кнопки и маршруты
не изменились, а её сценарии на копии базы проходят как раньше.

**S4 — выключатель канала.** Коннектор сам объявляет состояние; карточка канала показывает
«включён/выключен», причину простоя и кнопку. Отключение — запись состояния и освобождение
аренды, включение — обратный путь; перезапуска нет.

**S5 — доступ и права пишущих.** Общий слой (раздел 9) подключается одним и тем же способом и к
коннектору, и к ядру: у канала нет своего понятия прав.

**S6 — сверка.** Проверяем, что в `chat-channels.ts` осталась одна наша вставка, 15 общих на
месте и строки реестра отличий добавлены фрагментами. После этого шага каналы живут за
контрактом, и порт вендора трогает только вендорский код.

## 7. Без простоя ботов

- **Рантайм канала живёт на endpoint.** Вендорский рантайм создаётся для каждого endpoint и живёт
  в процессе сервера; `start`/`stop` коннектора — состояние и аренда, а не перезапуск. Отсюда:
  подключение, настройка и отключение канала не требуют перезапуска сервера.
- **За порядок сообщений отвечает вендорский outbox.** `chat_publications` и `chat_deliveries` с
  ключами идемпотентности — источник истины отправки; перенос логики публикации не меняет ключи,
  поэтому повторный заход после сбоя не дублирует сообщение.
- **Шаги 1–3 не меняют маршруты и тексты.** Вендорские ветки остаются работоспособными: пока
  тема не перенесена, работает вендорский путь; после переноса — путь коннектора. Общий путь
  один и тот же (хаб), поэтому «двух правд» не появляется.
- **Наблюдение перед решением.** Шаг S2 идёт раньше, чем хаб начинает что-то решать; ошибки
  коннектора на шагах S3 логируются и уходят на вендорский путь (fail-open), а не оставляют бота
  немым.
- **Выкат — только образом из CI.** Порядок выката и отката — существующий, отдельного
  обслуживания для этого выпуска не требуется.

## 8. Проверка на копии боевой базы

1. **Копия.** Снять дамп боевой базы и поднять стенд на этой копии — приёмка идёт только на ней,
   не на синтетической базе.
2. **Инвентаризация.** Сверить до/после: список endpoint и их провайдеров; связки диалогов с
   задачами и агентами; активные аренды; число публикаций и доставок.
3. **Сценарии хода.** ЛС боту, группа с `@<alias>`, форум-топик, голосовое, вложение больше
   лимита, длинный ответ текстом, `/new`, `/stop`, удержание на паузе — каждый сценарий проходит
   как раньше, отчёт содержит хвосты журнала.
4. **Сценарии настроек.** Изменение настроек компании (диалоги в личке, статус в личке, лимит
   файла, максимум частей) и приоритет env над базой — значения и источник видны как раньше.
5. **Жизненный цикл (начиная с S4).** Отключение и включение канала без перезапуска: входящие не
   принимаются, публикации не уходят, после включения работа возвращается; аренда освобождается.
6. **Наблюдение (S2).** Журнал хаба сверяется с фактическими ходами: пропущенных и лишних нет.

## 9. Общий слой доступа пишущих

Права и доступ пишущих — свойство канала как такового, а не Telegram: «кто может писать в этот
диалог и в какую задачу попадает это сообщение» решается один раз и одинаково для всех каналов.
Поэтому слой живёт не в коннекторе, а рядом с ним, и подключается к хабу и к ядру одним вызовом.
Коннектор сообщает только входные данные (автор, диалог, признак адресации), решение принимает
общий слой. Это позволяет вводить права постепенно, не переписывая коннекторы.

До реализации этого слоя коннектор спрашивает у вендорского кода, впускать ли, и ведёт себя как
сейчас: перенос тем шага S3 от этого не зависит.

## 10. Риски

| Риск | Чем закрываем |
|---|---|
| Хаб начинает решать раньше, чем его проверило наблюдение | шаг S2 отдельным PR с тестом «поведение не изменилось» |
| Тема перенесена, а сценарий потерян | каждая тема — свой PR, свой фрагмент и свои сценарии на копии базы |
| Порт вендора конфликтует во время переноса | каждая тема снимает только свои вставки; общие 15 не трогаем |
| Ошибка коннектора оставляет бота немым | fail-open на вендорский путь на шагах S2–S3, журнал и счётчик ошибок |
| Файл каналов — горячий (нужен `review-approved`) | PR по одному шагу, малый diff, ревью после зелёного CI |
| Настройки расходятся между env и интерфейсом | приоритет env → база → умолчание сохраняется, шаг S4 добавляет только ключ выключателя |

## 11. Открытые вопросы и решения без владельца

**Вопросы владельцу (ответы получены; именно их реализует проект):**

1. Выключатель канала (S4): достаточно ли «включён/выключен» для всего канала, или нужно
   выключать отдельные функции (топики, голос, уведомления) по отдельности? — **Решено: один
   выключатель на весь канал.**
2. Общий слой доступа пишущих: вводим его сразу после S4 или отдельным выпуском, когда
   Telegram уже за контрактом? — **Решено: сразу после S4, в этом выпуске.**
3. Порядок тем в S3 — оставляем «от малого риска к большому» или владелец хочет видеть сначала
   адресацию `@bot` и удержания? — **Решено: оставляем «от малого риска к большому».**

**Решения без владельца (приняты в этом документе):**

- Коннектор — слой поверх вендорского рантайма, а не новый транспорт: минимальное вмешательство в
  вендорский код важнее полноты контракта.
- Провайдер, которого нет в реестре, проходит насквозь: перенос не обязан охватывать все каналы
  сразу.
- Общие вставки (`B1`, `B1b`, `D1`, `D2`) остаются в ядре: они не про канал.
- Порядок тем внутри S3 и состав шагов уточняются при декомпозиции, если владелец не возражает.
