# Общий кэш пакетов и объекты git для контейнеров ботов (1.6.1-BOT-DISK-B, 1.6.2-BOT-DISK-C, BOT-DISK-D, BOT-DISK-F)

Боты разработки снова и снова скачивают одни и те же пакеты pnpm, модули Go и
зависимости Gradle, каждый в свой том. С общим кэшем пакетов каждый бот на
собственном хосте доски монтирует один набор каталогов кэша на запись, и
скачанное хранится один раз.

## Что получает бот

У каждого контейнера бота ровно **одна** привязка для его собственных данных
(весь каталог бота под корнем томов, смонтированный в `/bot`; см.
[Единое монтирование бота](#единое-монтирование-бота)). Когда настройка задана,
локальный драйвер добавляет каждому контейнеру бота на хосте по умолчанию ещё
четыре привязки, после дополнительных монтирований карточки:

| Каталог хоста | Точка монтирования в боте | Переменная в `hermes/.env` |
|---|---|---|
| `<cache>/pnpm` | `/cache/pnpm` | `npm_config_cache_dir` (только кэш загрузок; **хранилище** pnpm здесь не лежит никогда, см. [node_modules на жёстких ссылках](#node_modules-на-жёстких-ссылках)) |
| `<cache>/go-mod` | `/cache/go-mod` | `GOMODCACHE` |
| `<cache>/go-build` | `/cache/go-build` | `GOCACHE` |
| `<cache>/gradle` | `/cache/gradle` | `GRADLE_USER_HOME` |

Переменные пишет компилятор профиля, и они побеждают одноимённое значение из
карточки (предупреждение называет отброшенное). Шлюз загружает `hermes/.env` с
override, поэтому они заменяют умолчания образа, указывающие в том бота.

pip в кэш не входит: образ бота задаёт `PIP_NO_CACHE_DIR`, а он выключает кэш
pip при любом значении, и файл dotenv не может удалить переменную.

Это единственные привязки на запись, которые может иметь бот. Дополнительные
монтирования карточки остаются только для чтения, а пока кэш задан, монтирование
карточки в `/cache` или глубже отклоняется.

## Как задать

Путь — поле `sharedPackageCachePath` настройки экземпляра
`instance_settings.general.botDisk` (тот же ключ и API, что у жизненного цикла
черновых каталогов BOT-DISK A; PATCH с одним полем сохраняет остальные):

- Instance → General, панель «Shared package cache for bots», или
- `GET /api/myrmidon/bot-disk` (любой участник доски) и
  `PATCH /api/myrmidon/bot-disk` с `{"sharedPackageCachePath": "/abs/path"}`
  (только администратор экземпляра, с записью в журнал активности); `null` или
  пустая строка выключают кэш.

Путь — простой абсолютный каталог (без `..`, пустых сегментов и завершающего
слэша). Перезапуск не нужен: локальный драйвер и компилятор профиля перечитывают
настройку на каждом проходе сверки, поэтому на следующем проходе каждый бот
пересоздаётся с новыми привязками и перезапускается с новыми переменными.
Выключение работает так же.

## Шаги оператора

1. Создать четыре подкаталога и отдать их пользователю бота (uid и gid 10001 в
   образе бота); иначе Docker создаст недостающий каталог от root, и бот не
   сможет в него писать:

   ```sh
   install -d -o 10001 -g 10001 /srv/package-cache/{pnpm,go-mod,go-build,gradle}
   ```

2. Задать тот же каталог как `packageCacheRoot` в конфигурации dockergate и
   послать dockergate `SIGHUP` (ключ применяется без перезапуска). Без этого
   dockergate отклоняет каждую привязку кэша с `mount_source_not_allowed`, и
   ошибка сверки называет бота. См. [dockergate.ru.md](dockergate.ru.md).
3. Сохранить путь в настройке экземпляра.

Каталог не должен лежать внутри корня томов ботов.

## Дублирование между клонами (1.6.2-BOT-DISK-C)

Кэш пакетов хранит скачанное один раз, но бот разработки держит в `/workspace`
ещё и несколько полных клонов одних и тех же репозиториев, у каждого своя база
объектов и свой `node_modules`. Это убирают три части.

### Общие объекты git

Доска держит по одному голому зеркалу на каждый репозиторий из списка
`gitMirrorRepos`, в `<cache>/git/<owner>/<repo>.git` на хосте, и обновляет его
`git fetch --prune` (каждое зеркало не чаще раза в `gitMirrorRefreshMs`, одно
обновление за раз, рядом с зеркалом каталог-замок, чтобы второй процесс доски или
ручной запуск не мешали; новое зеркало строится рядом с итоговым путём и
переименовывается на место, так что бот никогда не видит недоделанное). Доска
тянет по https; для приватного репозитория берётся `GITHUB_TOKEN` (или
`GH_TOKEN`) сервера, он передаётся только в окружении процесса git, не в
аргументах и не в конфигурации зеркала.

Боты монтируют `<cache>/git` **только на чтение** в `/cache/git`. Это
намеренно: клон с альтернативой читает объекты зеркала без перепроверки хеша,
поэтому зеркало на запись позволило бы одному боту изменить то, что выгрузит
клон другого. Пишет только доска. Зеркало не теряет ни одного объекта, который
ещё может занимать клон: автоматический gc выключен, gc обновляющего процесса хранит
недостижимые объекты (`gc.pruneExpire=never`), а удалённая в источнике ветка
убирает только ссылку.

В образе разработки первым в `PATH` стоит обёртка `git`
(`/opt/paperclip/bin/git`). Для `git clone https://github.com/<owner>/<repo>[.git]`
(и ssh-/scp-форм GitHub, которые `/etc/gitconfig` уже переписывает в https) она
добавляет `--reference-if-able /cache/git/<owner>/<repo>.git`, если такое
зеркало есть в контейнере: `objects/info/alternates` клона указывает на зеркало,
и клон хранит только то, чего в зеркале нет, — коммиты самого бота и то, что
появилось в источнике после последнего обновления. Больше ничего не меняется:
другие подкоманды, другие хосты, репозитории без зеркала и клоны, уже
выбравшие своё хранение (`--reference`, `--dissociate`, `--shared`, `--local`,
`--mirror`, `--depth`, `--filter`), запускают настоящий git с теми же
аргументами, окружением, потоками и кодом выхода. Помощник учётных данных
(`git-credential-paperclip` в `/etc/gitconfig`) принадлежит настоящему git и не
затронут: клон от зеркала по-прежнему докачивает недостающие объекты через него.
Боту, которому нужен самодостаточный клон, достаточно `git repack -a -d` в нём
или клонирования с `--dissociate`.

Тяжёлые сборки идут через `devbuild` в отдельном контейнере сборки. Клону с
альтернативой для старой истории нужен путь `/cache/git`, а контейнер сборки его
не монтирует: `pnpm install`, `tsc`, `vitest` и подобные историю git не читают,
но шаг сборки, который читает (`git log`, штамп версии), должен сначала выполнить
`git repack -a -d`.

### Единое монтирование бота

link(2) не пересекает точку монтирования (`EXDEV`), даже если два монтирования
взяты с одной файловой системы хоста (в том числе ext4). Контейнер бота раньше
получал три отдельные привязки (`hermes` в `/data/hermes`, `workspace` в
`/workspace`, `scratch` в `/scratch`) и привязки кэша, поэтому жёсткая ссылка из
хранилища pnpm в клон не получалась нигде, pnpm молча переходил на **копирование**,
и `node_modules` каждого клона был полной копией (счётчик ссылок 1; диск бота рос
примерно на 5 ГБ в час).

Теперь у контейнера бота **одна** привязка для записываемых данных: каталог бота
`<корень томов>/<ключ бота>` монтируется в `/bot`, а `hermes/`, `workspace/` и
`scratch/` — каталоги внутри него. Три пути, которые знают боты и инструменты, —
ссылки, сделанные образом, а не монтирования:

| Путь в контейнере | Что это |
|---|---|
| `/data/hermes` (`HERMES_HOME`, `HOME`) | ссылка на `/bot/hermes` |
| `/workspace` (рабочий каталог) | ссылка на `/data/workspace`, а та — на `/bot/workspace` |
| `/scratch` | ссылка на `/data/scratch`, а та — на `/bot/scratch` |

Раскладка на хосте не меняется (`<root>/<key>/{hermes,workspace,scratch}`),
поэтому на диске ничего не переносится. Монтирования кэша только на чтение и общие
остаются отдельными привязками (`/cache/pnpm`, `/cache/go-mod`, `/cache/go-build`,
`/cache/gradle`, `/cache/git`). Профиль, маркер применённого состояния и отчёт
гигиены клонов читаются и пишутся по настоящим путям под `/bot/hermes`.
Вспомогательные контейнеры, готовящие тома и укладывающие профиль, сохраняют три
узкие привязки: они только пишут файлы, и жёсткие ссылки им не нужны. dockergate
принимает тело бота с одной привязкой `<root>/<key>:/bot` и тело помощника с тремя
узкими; `/bot` и `/data` — зарезервированные пути контейнера, монтирование
карточки занять их не может.

**Проход в сам `/bot`.** Всё дерево живёт за корнем бота, поэтому корень должен хотя
бы впускать uid бота `10001`: каталог на хосте, оставленный внешней операцией как
`root:65532 0710` (или любой режим без бита прохода), прячет от бота всё под `/bot`,
и entrypoint тогда падает на нечитаемом `.env`, не называя настоящую причину. При
каждом применении prepare-хелпер получает и привязку корня бота
(`<root>/<key>:/bot`, его четвёртую привязку — gate принимает ровно эти четыре) и
нормализует режим корня в `0711` одним нерекурсивным `chmod`: войти можно, список
прочитать нельзя (нет `r`), владелец остаётся `root`, содержимое не читается, не
пишется и не chown-ится. Исправление идемпотентно — внешнее `0710`/`0700` перестаёт
быть фатальным после ближайшего применения. Если бот всё же стартует на корне, в
который не может войти (его не применяли после внешнего изменения), entrypoint
падает одной строкой, называющей проблему прохода и исправление (пересоздать бота),
а не вводящей в заблуждение ошибкой `API_SERVER_KEY is required`. Участнику общей
области такая строка не нужна: корень его дерева — каталог инстанса, который
prepare-скрипт и так chown-ит на uid `10001` и chmod-ит в `0700`.

### node_modules на жёстких ссылках

pnpm держит одно адресуемое по содержимому хранилище и связывает с ним
`node_modules` каждого проекта жёсткими ссылками. Когда дерево бота — одно
монтирование, хранилище лежит внутри него:

- **Хранилище**: по умолчанию `/workspace/.pnpm-store` (настройка `pnpmStoreDir`;
  любой путь под `/workspace`, `/data`, `/scratch` или `/bot`); задаётся как
  `npm_config_store_dir` в образе, в самопроверке точки входа и в `.env` профиля
  (для ботов с общим кэшем) из той же настройки. Очистка жизненного цикла никогда
  не считает хранилище черновиком. Хранилище вне единого монтирования API
  настроек отклоняет.
- **Способ импорта**: `package-import-method=hardlink` (настройка
  `pnpmImportMethod`, по умолчанию `hardlink`; `clone-or-copy` и `copy` — явный
  отказ от жёстких ссылок). `hardlink` заставляет pnpm пробовать только жёсткие
  ссылки. Он **не** превращает отказ в ссылке в ошибку: pnpm 9 (проверено на 9.15)
  при `EXDEV` от ядра молча переходит на копирование при любом способе. Видят это
  проверка при сборке образа и самопроверка при запуске ниже.
- **`/cache/pnpm` — только источник загрузок**: это кэш метаданных pnpm
  (`npm_config_cache_dir`), но не хранилище. Прежний режим `pnpmStore: "shared"`,
  который клал хранилище туда и копировал на ext4, удалён; сохранённое значение
  `pnpmStore` игнорируется.
- Среда выполнения не пишет `.npmrc`; любой запуск pnpm в контейнере читает
  переменные выше (`ENV` образа, `.env` профиля).

Одна копия каждого пакета на бота связана жёсткими ссылками со всеми его клонами,
в каком бы корне клон ни лежал (`/data/hermes/cache/*`, `/workspace/*`,
`/data/hermes/work/*`, `/scratch/*`). Жёсткая ссылка — это тот же файл: бот,
правящий установленный файл в `node_modules` на месте, правит и копию в
хранилище, и другие свои клоны (проверка целостности хранилища pnpm, включённая по
умолчанию, заметит это при следующей установке). Хранилище у каждого бота своё, так
что между ботами это не проходит.

**Самопроверка при запуске.** При каждом старте контейнера точка входа создаёт файл
в каталоге хранилища pnpm и пробует сделать на него жёсткую ссылку в каждом корне
клонов (`/data/hermes`, `/workspace`, `/scratch`). Сбой пишется в журнал как
`ERROR: hard-link self-check: ...` и в
`/data/hermes/.myrmidon/hardlink-check.json`; отчёт гигиены клонов копирует его в
поле `hardlinkCheck`, а доска поднимает карточку внимания (источник
`bot_disk_lifecycle`, по одной на корень с ошибкой), которая исчезает, когда бот
перезапущен и проверка проходит. Проверка шлюз не останавливает.

`docker/bot-runtime/pnpm-hardlink-check.sh` доказывает поведение из каждого корня
клонов: ставит локальный пакет из tarball без сети в проект под каждым корнем и
печатает счётчик ссылок установленного файла, по строке на корень. Сборка образа
разработки запускает его от uid 10001 на собственном pnpm образа для
`/data/hermes`, `/workspace` и `/scratch` и роняет сборку при копии, а
`scripts/myrmidon/bot-runtime/pnpm-hardlink.test.mjs` запускает его в CI, в том
числе отрицательный случай хранилища на другом монтировании: он виден как копия
(счётчик ссылок 1), хотя установка проходит.

### Перевод работающих ботов на единое монтирование

На хосте ничего не переносится, поэтому боту нужен только новый контейнер. На
каждого бота, пока доска выполняет проход сверки (или вручную):

1. **Приостановить** агента бота на доске (новых запусков нет; дождаться открытых
   ходов).
2. Выкатить новый образ бота и доску (шаблон контейнера меняется: три привязки
   становятся `<root>/<key>:/bot`; проверка дрейфа это видит и пересоздаёт
   контейнер на следующем проходе; нужен и соответствующий dockergate, иначе он
   отклонит новое тело с `binds_mismatch`).
3. **Пересоздать** контейнер (это делает проход сверки; остановленного бота
   пересоздаёт `recreate`).
4. **Проверить**: `docker inspect` показывает одну привязку `...:/bot` и ни одного
   монтирования `/data/hermes`, `/workspace`, `/scratch`; в журнале контейнера
   `hard-link self-check ok`; внутри `stat -c %h` на файле `node_modules`
   существующего клона остаётся 1 (старые установки — копии), а свежий
   `pnpm install` даёт значение больше 1.
5. **Возобновить** агента.

Существующие клоны хранят скопированные `node_modules`, пока их не переустановят
(`rm -rf node_modules && pnpm install`) или не удалит жизненный цикл; хранилище, с
которым они связываются, — каталог `pnpmStoreDir`, создаваемый при первом
использовании. Откат — выкатить прежние образ и dockergate (раскладка на хосте та
же).

### Область изоляции: кто делит диск

По умолчанию у каждого бота свой диск (единое монтирование выше), и он ничем не делится. Для ботов,
которые работают с одним кодом, владелец может для каждого **экземпляра области** выбрать общий
корень (BOT-DISK-F): один каталог с **одним хранилищем pnpm** и подкаталогом на бота, так что
жёсткая ссылка работает внутри бота **и между ботами экземпляра**, а пакет хранится один раз на всех.
Разные экземпляры никогда не делят каталог: разработчики на общем корне не видят дерево
маркетингового бота.

**Откуда берётся область агента.** Семь уровней, самый частный первым; решает первый уровень, у
экземпляра которого есть явная настройка; ничего не задано — по умолчанию (собственный диск агента):

| № | Уровень | Экземпляр области | Чем задаётся |
|---|---|---|---|
| 1 | переопределение агента | один агент | «держать изолированным» у агента (и его собственный выбор между несколькими группами или проектами) |
| 2 | явная именованная группа | группа, в ней любые агенты | id группы |
| 3 | каста | все с одной ролью | `agents.role` (ключ справочника каст компании) |
| 4 | поддерево подчинения | руководитель и все под ним | id руководителя, через `agents.reports_to`; побеждает ближайший настроенный руководитель выше агента |
| 5 | проект | агенты одного проекта | id проекта (агент ведёт проект или состоит в нём) |
| 6 | установленная команда каталога | агенты, установленные из одной команды каталога | `metadata.paperclip.catalogTeam.catalogId` |
| 7 | компания | все | компания |

Экземпляр в режиме **изолирован** — явное «у каждого свой диск», он прекращает поиск (общий уровень
ниже к этим участникам не применяется); **общий корень** даёт участникам один каталог. Резолвер — один
чистый модуль (`packages/shared/src/myrmidon-isolation-scope.ts`), его могут переиспользовать другие
политики со своими настройками: так позже будет сделана область контейнеров.

**Группы** — самостоятельная сущность: создание, переименование, удаление и состав меняются в
настройках экземпляра, «Изоляция дисков ботов», или через API, без перезапуска; на странице группы —
участники и её настройка изоляции (*не задаёт изоляцию*, *изолирован*, *общий корень*). Агент может
быть в нескольких группах, но область изоляции задаёт только одна: если настройка есть у двух и более
групп агента, он помечается **конфликт групп**, и владелец должен выбрать, какая решает. Агент в
нескольких проектах, у каждого из которых есть настройка, помечается **неоднозначный проект**. Пока
выбор не сделан, агент остаётся изолированным (на догадке ничего не делится) и применить его нельзя.
Конфликт, который уже решает уровень выше (переопределение агента, либо группа, каста или поддерево подчинения, когда речь о проектах),
не показывается.

**Раскладка на хосте.** Общий экземпляр — каталог `<общий корень>/<kind>-<id>/` с одним хранилищем pnpm
(`.pnpm-store`) и подкаталогом на каждого бота-участника:

```
<общий корень>/caste-<company>-engineer/
  .pnpm-store/
  <botKey-1>/{hermes,workspace,scratch}
  <botKey-2>/{hermes,workspace,scratch}
```

Общий корень — `MYRMIDON_BOT_SCOPE_ROOT` (по умолчанию `<корень томов>/.scopes`: ключ бота не
начинается с `.`; держите его на **той же файловой системе**, что и корень томов, тогда перенос — это
rename). id касты и команды каталога уникальны только внутри компании, поэтому в именах их каталогов есть
id компании.

**В контейнере.** У участника ОДНА привязка — каталог экземпляра в `/bot-scope`, и нет `/bot`. tmpfs
поверх `/data` хранит три ссылки `/data/hermes`, `/data/workspace`, `/data/scratch`, которые entrypoint
направляет в `/bot-scope/<botKey>/...` (ключ бота приходит в единственной несекретной переменной
`MYRMIDON_BOT_SCOPE_SUBDIR`); `/workspace` и `/scratch` остаются ссылками через `/data`. Профиль пишет
`npm_config_store_dir=/bot-scope/.pnpm-store` каждому участнику (с общим кэшем пакетов и без него);
самопроверка при старте идёт из этого хранилища в три корня участника. Образ должен объявлять метку
`myrmidon.bot-runtime.scope=1` (этот образ объявляет; его `WORKDIR` теперь `/`, потому что `/workspace`
не разрешается, пока нет ссылок): драйвер отказывается создавать участника из образа без неё.

**Нужен перезапуск.** Изменение группы, настройки или выбора агента сразу меняет то, к чему агент
*разрешается*, но доска держит контейнер на раскладке, которую владелец **применил** последней. Разница
видна у агента как **нужен перезапуск**. Сам ничего не перезапускается: владелец нажимает *Применить и
перезапустить* (на агенте) или *Применить ко всем*, после чего проход согласования видит разницу привязок
как дрейф шаблона и пересоздаёт контейнер через окно обслуживания.

**Смена области агента (что происходит при перезапуске, по порядку).**

1. *Пауза*: проход согласования открывает окно обслуживания агента и ждёт открытые прогоны.
2. *Проверка*: план переноса считается по привязкам живого контейнера (где он сейчас) и применённой
   раскладке (куда идёт). Три каталога переносятся целиком (`rename`) в **отсутствующий или пустой**
   целевой; целевой с данными, источник-ссылка или файл, либо корень томов, которого доска не видит,
   **отклоняют всю смену до остановки чего-либо**, и бот продолжает работать на старой раскладке. Ничего
   не удаляется и не сливается. Прерванный прежний запуск распознаётся (источника нет, цель есть) и
   дорабатывается.
3. *Подготовка* томов новой раскладки (помощник подготовки передаёт и каталог экземпляра uid бота) и
   *создание* замены с новыми привязками, **пока старый контейнер ещё работает**: отказ dockergate или
   демона (бот не записан, нет образа) ничего не меняет. Затем *остановка* старого контейнера, *перенос*
   каталогов (упавший шаг откатывает предыдущие, старый контейнер запускается снова) и подмена
   заменой.
4. *Самопроверка*: новый контейнер при старте проверяет жёсткие ссылки из хранилища; сбой поднимается
   карточкой внимания, как любой другой.
5. *Возобновление*: окно обслуживания закрывается, агент снова работает.

Старое личное хранилище pnpm бота (`workspace/.pnpm-store`) переезжает вместе с workspace и остаётся
неиспользуемым; удалите вручную, когда удобно (перенос ничего не удаляет). Если доска не видит тома
(обычный боевой вариант), перенесите вручную при приостановленном и остановленном боте:
`mkdir -p <общий корень>/<экземпляр>/<botKey>`, затем `mv <корень томов>/<botKey>/{hermes,workspace,scratch}`
туда (или обратно), запустите бота и примените смену на доске.

**dockergate.** Шлюз принимает привязку общего экземпляра только для бота, записанного на этот экземпляр
(`bots[].scopeInstances`), и только собственный каталог экземпляра, не корень и не соседа; см.
[dockergate.ru.md](dockergate.ru.md#участники-общей-области-изоляции-bot-disk-f). Записывайте ботов
**до** применения.

**Компромиссы: прочитайте перед общим корнем.** Участники экземпляра работают с одним uid, и каждый
контейнер монтирует весь каталог экземпляра, поэтому бот может читать и писать `hermes/` (профиль, `.env`
с ключами), `workspace` и `scratch` **каждого другого участника**. Делитесь только между ботами, которые
доверяют друг другу в этом (смысл уровней в том, что маркетинговый бот в другом экземпляре, чем
разработчики). Жёсткая ссылка — тот же файл: правка установленного файла в `node_modules` на месте
правит копию в хранилище и каждый клон каждого участника (проверка целостности pnpm заметит при
следующей установке). В общее хранилище пишут несколько ботов одновременно; хранилище pnpm рассчитано
на параллельную запись. Сбой диска или переполнение тома теперь касаются всего экземпляра.

**Откуда берутся проекты агентов.** В доске нет таблицы «агент — проект»; агент в проекте, если ведёт его
или у него есть принятая строка `project_memberships` с его id.

**API.** `GET /api/myrmidon/companies/:companyId/bot-scopes` (агенты с эффективной областью, источником,
проблемами, применённой раскладкой и `restartRequired`; группы; настроенные экземпляры); запись требует прав
администратора экземпляра: `POST|PATCH|DELETE .../bot-scopes/groups[/:groupId]`, `PUT|DELETE
.../bot-scopes/settings/:kind/:scopeId` (`{"mode":"isolated"|"shared"}`), `PUT .../bot-scopes/agents/:agentId`
(`isolate`, `groupId`, `projectId`), `POST .../bot-scopes/agents/:agentId/apply` и `POST
.../bot-scopes/apply-all`. Таблицы: `myrmidon_scope_groups`, `myrmidon_scope_group_members`,
`myrmidon_scope_settings`, `myrmidon_scope_agent_prefs` (миграция `0300_bot_isolation_scope`).

### Гигиена клонов в жизненном цикле черновиков

Жизненный цикл BOT-DISK A удалял любой верхнеуровневый элемент томов `workspace` и
`scratch` бота, простаивающий дольше TTL, по mtime каталога. Для клона это
неверно в обе стороны: правка отслеживаемого файла или коммит mtime каталога не
меняют, так что занятой клон выглядел простаивающим, а merged-работу от
незапушенной ничто не отличало. Элемент, который является git-репозиторием или
содержит его (до трёх уровней вниз), теперь судится по каждому репозиторию:

- **Удаляется**, если отчёт самого бота говорит, что он чистый (нет изменённых,
  проиндексированных и неотслеживаемых файлов — игнорируемые не считаются; нет
  слияния, rebase, cherry-pick или bisect в процессе; нет stash) и **полностью
  запушен** (каждый коммит `HEAD` и каждой локальной ветки есть на какой-то
  удалённо-отслеживаемой ссылке, что покрывает «ветка влита в основную ветку
  origin» и «запушено, локальных изменений нет»), он не база связанных worktree и
  не альтернатива другого клона, и дольше TTL в нём ничего не менялось.
- **Остаётся с сигналом внимания** (очередь Attention, источник
  `bot_disk_lifecycle`, одна карточка на клон с ботом, путём клона, веткой и
  причиной), если в нём есть незапушенная работа — незафиксированные изменения,
  операция в процессе, stash или коммиты, которых нет ни на одном remote, — и он
  простаивает дольше TTL. Карточка исчезает, когда работа запушена или выброшена,
  клона коснулись или он удалён. Такой клон никогда не удаляется.
- **Остаётся молча** в остальных случаях: недавно активен, отчёта ещё нет или
  осмотр не удался.

**Где это работает.** У сервера доски нет монтирования томов ботов (хостовые
монтирования убраны из неё в 1.3.0), поэтому он не может ни осмотреть, ни удалить
клон: серверная очистка BOT-DISK A не находит корня томов, пишет одно предупреждение
и ничего не делает — освобождено было ноль байт. Поэтому удаление выполняется внутри
каждого контейнера бота, где файлы видны. `bot-clone-hygiene` образа разработки
(запускается entrypoint, раз в 15 минут, с `nice`, от пользователя бота) применяет
политику сам: компилятор профиля пишет в `.env` бота `MYRMIDON_CLONE_IDLE_TTL_SEC`
(TTL простоя жизненного цикла, `0` при выключенном), файл перечитывается на каждом
проходе, так что изменение настроек применяется без перезапуска. В том же проходе,
что осмотрел репозиторий, он удаляет его, только если тот чистый, полностью запушен,
не база worktree и не альтернатива, и дольше TTL в нём ничего не менялось
(`node_modules` не заходится, файл с жёсткими ссылками судится по mtime, так как
другая ссылка меняет его ctime). Также удаляется верхнеуровневый каталог `/workspace`
без репозитория, простаивающий дольше TTL, если в нём нет метки `.heartbeat` и его имя
не начинается с точки (хранилище pnpm). Путь удаления должен быть настоящим каталогом
внутри корня без символьных ссылок. Политика пишется только ботам с ролями из
`sharedCacheRoles`; бот на образе без этой программы просто никогда не теряет клон.
Доска только читает отчёт (драйвер забирает
`/data/hermes/.myrmidon/clone-hygiene.json` из работающего контейнера; git в каталоге
бота доска не запускает — конфигурация репозитория может называть исполняемые
программы) и поднимает карточки внимания. Если доска не видит корень томов и 24 часа не
получает ни одного отчёта, она поднимает одну карточку «Lifecycle not effective».

Один случай остаётся, а не удаляется: ветка, влитая **squash**, у которой потом
удалили и вычистили удалённую ветку, имеет коммиты, которых нет ни на одной
удалённо-отслеживаемой ссылке, и значится незапушенной работой, пока оператор или
бот не выбросит клон. Fetch без prune оставляет ссылку и считается запушенным.

## Настройки

Все ключи лежат в `instance_settings.general.botDisk` и применяются на
следующем проходе сверки или такте обслуживания без перезапуска (`GET` и
`PATCH /api/myrmidon/bot-disk` или Instance → General, «Shared package cache for
bots»); PATCH с одним ключом сохраняет остальные, `null` возвращает ключ к
умолчанию:

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `sharedPackageCachePath` | не задан | Каталог общего кэша (выше) |
| `gitMirrorRepos` | `[]` | Имена `owner/repo` для зеркал; пусто — ни зеркал, ни монтирования `/cache/git`. Нужен `sharedPackageCachePath` |
| `gitMirrorRefreshMs` | `900000` (15 мин) | Как часто обновляется каждое зеркало, от 1 мин до 24 ч |
| `pnpmStoreDir` | `/workspace/.pnpm-store` | Хранилище pnpm, путь под `/workspace`, `/data`, `/scratch` или `/bot` (выше) |
| `pnpmImportMethod` | `hardlink` | `hardlink`, `clone-or-copy` или `copy` (выше) |
| `sharedCacheRoles` | `engineer`, `reviewer`, `devops`, `release`, `qa` | Роли, чьи боты получают монтирования кэша и зеркал; остальные не получают и не пересоздаются при включении кэша |
| `idleTtlMs`, `enabled` | 6 ч, вкл. | Жизненный цикл черновиков BOT-DISK A, которому следует гигиена клонов |

## Включение зеркал git (шаги оператора)

1. Шаги общего кэша выше выполнены (`packageCacheRoot` в dockergate).
2. Создать каталог зеркал с владельцем — пользователем **доски** (зеркала пишет
   она) и доступный всем на чтение, чтобы боты (uid 10001) читали его через
   монтирование только на чтение. Иначе Docker создаст отсутствующий источник
   привязки от root, и доска не сможет в него писать:

   ```sh
   install -d -o <пользователь доски> -m 0755 /srv/package-cache/git
   ```

   Процесс доски должен видеть тот же путь (он читает и пишет каталог кэша
   напрямую); доске в контейнере нужно монтирование по тому же пути.
3. Нового ключа dockergate не требуется: подкаталог `git` в `packageCacheRoot`
   принимается как привязка **только на чтение** в `/cache/git`, привязка на
   запись отклоняется. `SIGHUP` нужен, только если менялся сам корень.
4. Перечислить репозитории: `PATCH /api/myrmidon/bot-disk` с
   `{"gitMirrorRepos": ["owner/repo"]}` (или панель). Для приватного
   репозитория дать серверу `GITHUB_TOKEN` с правом чтения.
5. Первое обновление идёт на ближайшем такте обслуживания (один раз клонирует
   весь репозиторий). Боты пересоздаются с новой привязкой на следующем проходе
   сверки; их следующий `git clone` указанного репозитория берёт зеркало. Проверка:
   `ls /srv/package-cache/git/<owner>/<repo>.git/myrmidon-fetched-at` на хосте и
   `cat .git/objects/info/alternates` в свежем клоне.
6. Существующие клоны остаются как есть. Чтобы убрать их дубли объектов, бот
   может заклонировать заново или после ручного добавления альтернативы выполнить
   `git repack -a -l -d`.

Выключение: `{"gitMirrorRepos": null}` (привязка исчезает на следующем проходе).
**Не удаляйте зеркало, пока из него заимствует клон** — клон потеряет объекты;
очистите настройку, дайте клонам ботов удалиться или пересоздайтесь, затем
удалите каталог.

## Ожидаемая экономия

Для бота разработки с несколькими клонами одного репозитория (база объектов этого
репозитория около 1,7 ГиБ в упакованном виде):

- **Объекты:** первый клон не меняется, пока зеркала нет; каждый следующий, у
  любого бота хоста, хранит только свои объекты, поэтому *N* клонов стоят одно
  зеркало (около 1,7 ГиБ один раз на хосте) плюс несколько мегабайт на клон вместо
  *N* × 1,7 ГиБ. Четыре клона у каждого из десяти ботов — около 68 ГиБ баз
  объектов до и около 2 ГиБ после.
- **node_modules:** копия на клон становится жёсткой ссылкой на файл, что стоит
  запись каталога и inode, а не содержимое: содержимое хранится один раз на бота
  (`workspace`) или один раз на хост (`shared` на файловой системе с reflink).
  Экономия на дополнительный клон — размер его `node_modules` (для монорепозитория
  такого размера обычно от одного до нескольких ГиБ; здесь не измерено).
- **Возврат места:** чистые, запушенные, простаивающие клоны удаляются, не
  дожидаясь человека, а удаление клона с `node_modules` на жёстких ссылках
  освобождает только записи, не разделяемые с другим клоном или хранилищем.

Экономия — оценка по приведённым размерам объектов и пакетов; проверка в
рантайме — тест жёстких ссылок и тест alternates при `git clone` в CI.

## Компромиссы зеркал и хранилища в workspace

Объекты git разделяются только на чтение: ни один бот не может изменить историю
другого. Зеркалу доверяют как собственному fetch доски (оно так же надёжно, как
источник и токен). Клон с альтернативой зависит от каталога зеркала ради своей
истории, поэтому зеркало никогда не чистится. При хранилище по умолчанию внутри монтирования бота
оно принадлежит одному боту и растёт с его установками; собственный
`store prune` pnpm (через `devbuild`) возвращает пакеты, которые не использует
ни один клон.


## Боты на хосте fleetd

Бот, чья карточка называет хост fleetd, кэш не получает: fleetd строит свой
шаблон контейнера без привязок кэша, а путь называет каталог на хосте доски.
Компилятор не пишет таким ботам переменные, а драйвер fleetd один раз пишет в
журнал, что кэш там не применяется. То же верно для зеркал git (нет монтирования
`/cache/git`, клон там полный) и для переменных хранилища pnpm. (Бот на fleetd строит свой контейнер вне этой раскладки с единым монтированием.)

## Компромиссы общего кэша

Все боты хоста делят кэш на запись, поэтому один бот может изменить то, что
другой потом из него прочитает. pnpm проверяет целостность того, что берёт из
своего хранилища, а кэш сборки Go и кэши Gradle принимаются как есть. Включайте
кэш только для ботов, которые и так доверяют друг другу (боты разработки одной
команды); где боты должны быть изолированы, держите его выключенным.
