# Метрики цели не собираются

Runbook тревоги «скрейп цели падает». Ключ runbook: `metrics-scrape-failing`, владелец — роль
`devops`.

Prometheus не может снять метрики с цели. Дальше всё ослепляет: дашборд флота пустеет, а тревоги
по метрикам перестают приходить — молчание метрик опаснее громкой тревоги, поэтому задача на роль
`devops` приходит с шагами ниже.

## Когда срабатывает

Тревога, имя триггера которой содержит `scrape`, `prometheus`, `target down` или `метрики`.

## Метрика проверки

Две вещи: цель в Prometheus снова `UP = 1`, и сам эндпоинт отвечает кодом 200
(`/api/myrmidon/monitoring/selfcheck` у доски). Снятая тревога без живого эндпоинта — обман.

## Шаги восстановления

1. Проверить эндпоинт цели вручную:
   `curl -sS -o /dev/null -w '%{http_code}\n' http://<target>:3100/api/myrmidon/monitoring/selfcheck`.
2. Проверить, что сама доска жива: `curl -sS http://<target>:3100/api/health`.
3. Посмотреть страницу Prometheus → Targets: текст ошибки скрейпа (таймаут, 401, 404).
4. Проверить токен и сеть между Prometheus и целью: адрес, порт, TLS, заголовок авторизации.
5. Проверить нагрузку на цель: таймаут скрейпа лечится таймаутом опроса, а не его учащением.
6. Проверить метрику: цель снова UP, тревога снята.

## Если не помогло

- Эндпоинт отвечает 200, а Prometheus всё равно видит цель мёртвой — проблема в конфигурации
  Prometheus (правило, лейбл, сеть сервера мониторинга): задача оператору доски.
- Цель отвечает только под нагрузкой ниже обычной — это симптом утечки ресурсов самой доски:
  заведи задачу на разбор и оставь в ней графики за последний час.

## Интерпретация счётчиков continuation dedupe

На `/metrics` доступны `myrmidon_continuation_created_total` и
`myrmidon_continuation_deduped_total`. Первый считает уникальные continuation
keys, впервые принятые claim-путём; второй — claims уже принятого ключа,
подавленные дедупликацией. Это процесс-локальные счётчики: каждый процесс
начинает с нуля после рестарта. Сравнивайте их с учётом метки `role` и scrape
target/instance: одной метки `role` недостаточно для различения нескольких
процессов одной роли. Не суммируйте значения как глобальный реестр событий.

Continuation key не является меткой. В метриках нет значения ключа или меток
по ключу: это сохраняет малую кардинальность и не раскрывает идентификаторы
continuation. При чтении сравнивайте прирост created и deduped на одном процессе;
рост deduped показывает, что повторные claims были подавлены.

## Интерпретация метрик knowledge-on-change

На `/metrics` доступны `myrmidon_knowledge_on_change_share` (gauge) и
`myrmidon_knowledge_revision_delay_seconds` (summary, quantile 0.5/0.95).
Обе метрики читаются из базы доски и покрывают последние 7 дней.

`myrmidon_knowledge_on_change_share` — доля системно изменённых задач, у
которых есть запись вики. Знаменатель — задачи со статусом `done` или
`cancelled`, закрытые за окно, с work product `pull_request` в статусе
`merged`. Числитель — те из них, на которые ссылается ревизия вики
(`knowledge_sources` kind=`task`, ref=`issues.identifier`). Задачи без
слитого PR в знаменатель не входят. Значение `null` (HELP/TYPE без
сэмплов) означает, что за окно не закрыто ни одной системно изменённой
задачи. Падение доли со временем — сигнал, что правило «вики при каждом
изменении» перестали соблюдать.

`myrmidon_knowledge_revision_delay_seconds` — задержка между слиянием PR
и появлением ревизии вики, ссылающейся на этот PR. Сопоставление идёт по
`externalId` или `url` work product (`knowledge_sources` kind=`pr`).
Отрицательные и неразличимые задержки отбрасываются; оба квантиля —
линейно интерполированные перцентили. Значение `null` означает, что ни
один PR за окно не получил ревизии вики. Рост p95 показывает, что
ревизии вики запаздывают относительно слияний.

Обе метрики собираются guarded-коллектором: ошибка чтения из БД не роняет
скрейп, а только прячет сэмплы. Метка `role` у каждого сэмпла различает
процессы `api` и `worker`; сравнивайте значения на одном процессе.

## Как закрывается задача

Шаги выполнены → тревога снимается в источнике → задача закрывается сама, когда тревога
продержится снятой заданное число минут (по умолчанию 10). Повторная тревога в пределах окна
возврата (по умолчанию 60 минут) возвращается в эту же задачу.
