# External Nest Provisioning and Isolation Runbook (OPE-10548 PR-1)

> Версия на русском языке: [external-nest-runbook.ru.md](external-nest-runbook.ru.md)

Wave-1 operational runbook for provisioning, configuring, verifying isolation, and revoking access for an external client nest (OPE-10548, epic OPE-3799 item 1) on the Myrmidon control plane.

---

## 1. Architectural Principles and Isolation Boundaries

1. **Isolation Unit — Tenant Company (`company`)**:
   - The external client is isolated at the company level in the owner's single shared PostgreSQL database. A separate database or isolated instance is **not created** (contract architecture decision OPE-10548 §1).
   - All platform resources (tasks, projects, agents, secrets, channels, budgets) are strictly scoped by `company_id`.
2. **Actor Model**:
   - **Board Owner (`adm`)**: performs administrative provisioning via the owner API/UI (company creation, castes, agents, budget limits, nest assignment).
   - **Host Operator**: manages container environments and host secrets.
   - **Client**: end-user connecting via external channels (Telegram chat, web widget); has no direct access to Myrmidon API or board UI (board UI is not exposed externally).
3. **Execution Isolation**:
   - The external bot agent is restricted to client projects using `agent_nests`. An agent with nests is physically prevented from picking up tasks from other projects or companies (`agentNestAllowsProject`).

---

## 2. Preconditions

Before provisioning an external nest, verify:
- The Myrmidon server is healthy (`GET /api/health` returns `status: "ok"`).
- Board owner credentials are ready (`MYRMIDON_API_KEY` with instance admin privileges).
- Client parameters are determined: company name, spend limits (`budgetMonthlyCents`), project token quotas. The issue prefix (`issuePrefix`) is automatically generated by the platform based on company name.

---

## 3. Step-by-Step Provisioning Sequence

### Step 1. Create the Tenant Company
The company is provisioned via the instance-admin API. Per `createCompanySchema` (`packages/shared/src/validators/company.ts`), the allowed fields are `name`, `description`, `budgetMonthlyCents`, and `defaultResponsibleUserId`:

```http
POST /api/companies
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "name": "Acme External Client",
  "description": "Tenant company for external client Acme",
  "budgetMonthlyCents": 50000
}
```

**Expected Response:** HTTP 201 Created with the company object:
```json
{
  "id": "c1000000-0000-0000-0000-000000000001",
  "name": "Acme External Client",
  "description": "Tenant company for external client Acme",
  "issuePrefix": "ACME",
  "budgetMonthlyCents": 50000,
  "status": "active"
}
```

**Invariants:**
- `issuePrefix` is not accepted in the creation payload; it is automatically derived by the platform (`createCompanyWithUniquePrefix`, fallback default `PAP`). If `ACME` is already taken, the platform allocates a unique suffix (e.g. `ACME1`).
- The actual allocated prefix should be read from the creation response or verified via `GET /api/companies/:companyId`.
- The audit log records the `company.created` activity event.
- `budgetMonthlyCents` establishes the hard monthly spending ceiling for the company in cents.

---

### Step 2. Create the External Bot Caste
Register a dedicated caste within the tenant company. The `color` parameter must belong to `CASTE_COLORS` (`packages/shared/src/myrmidon-castes.ts`: `primary`, `muted`, `blue`, `amber`, `green`, `violet`, `red`, `gray`):

```http
POST /api/myrmidon/companies/:companyId/castes
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "key": "external-bot",
  "nameRu": "Внешний бот",
  "nameEn": "External Bot",
  "description": "External client bot caste with nest isolation",
  "color": "violet"
}
```

**Expected Response:** HTTP 201 Created with the registered caste object.

**Invariants:**
- Castes are strictly scoped within `companyId` (test `castes.db.myrmidon.test.ts: company A's castes are invisible to company B`). Caste `external-bot` in company Acme does not collide with other tenants.

---

### Step 3. Create the Client Project with `defaultCasteKey`
Create the client project, setting the default caste key:

```http
POST /api/companies/:companyId/projects
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "name": "Acme Support Bot",
  "defaultCasteKey": "external-bot"
}
```

**Expected Response:** HTTP 201 Created containing project attributes including `defaultCasteKey: "external-bot"`.

**Invariants:**
- Project issues automatically resolve to this caste via `resolveTaskCaste(db, { companyId, issueId })` (`server/src/myrmidon/castes/resolve.ts`) when no caste is explicitly set on the issue.
- The platform validates that the specified caste exists within the company (`assertProjectDefaultCasteExists`).

---

### Step 4. Create External Bot Agent and Bind Nests (`agent_nests`)

#### 4.1. Create Agent
Per `createAgentSchema` (`packages/shared/src/validators/agent.ts`), `capabilities` is a string (`z.string().optional().nullable()`), and `role` accepts the caste key:

```http
POST /api/companies/:companyId/agents
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "name": "acme-bot",
  "role": "external-bot",
  "title": "Acme Support Agent",
  "adapterType": "process",
  "capabilities": "chat, customer-support",
  "budgetMonthlyCents": 20000
}
```

**Expected Response:** HTTP 201 Created with generated `id` (`agentId`).

#### 4.2. Assign Project Nests
```http
PUT /api/myrmidon/companies/:companyId/agents/:agentId/nests
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "projectIds": [
    "<projectId-from-step-3>"
  ]
}
```

**Expected Response:** HTTP 200 OK with the array of bound `projectIds`.

**Invariants:**
- Stored in table `agent_nests(company_id, agent_id, project_id)`.
- The route rejects project IDs belonging to other companies with HTTP 400 (`server/src/myrmidon/castes/nests-api.myrmidon.test.ts: another company's project is unknown (400)`).
- The scheduler restricts task eligibility to the agent's bound nests (`agentNestAllowsProject` in `packages/shared/src/myrmidon-agent-nests.ts`).

---

### Step 5. Configure Budget Limits and Token Quotas

#### 5.1. Configure Nest Spend Limits (`budget_limits`)
The platform contract (`packages/shared/src/myrmidon-budget-limits.ts`, `server/src/myrmidon/budget-limits/routes.ts`) provides hierarchical limits at the `nest` level (where `ref` is the project UUID):

```http
PUT /api/myrmidon/companies/:companyId/budget-limits/limits/nest/:projectId
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "amountCents": 15000,
  "period": "calendar_month_utc",
  "mode": "hard",
  "isActive": true
}
```

**Expected Response:** HTTP 200 OK with the saved limit object (`BudgetLimitView`).

**Invariants:**
- `mode: "hard"`: on limit overrun, task admission is strictly refused (`refuse`).
- `mode: "soft"`: on limit overrun, the agent is paused (`pause`) and a notification card is generated for the owner.
- `period`: valid options are `"calendar_month_utc"` and `"lifetime"`.
- Live usage is readable via `GET /api/myrmidon/companies/:companyId/budget-limits/usage`.
- Every limit mutation is audited in `GET /api/myrmidon/companies/:companyId/budget-limits/journal` (table `budget_limit_changes`).

#### 5.2. Configure Daily and Weekly Token Quotas (`project_token_quotas`)
The project token quota endpoint (`server/src/myrmidon/project-token-quota/routes.ts`, `packages/shared/src/myrmidon-project-token-quota.ts`) uses the singular route:

```http
PUT /api/myrmidon/companies/:companyId/projects/:projectId/token-quota
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "dailyTokenLimit": 500000,
  "weeklyTokenLimit": 2500000
}
```

*(Setting `null` removes the cap for that window).*

**Expected Response:** HTTP 200 OK with quota configuration and status.

**Invariants:**
- Quota status and window usage counters are retrieved via `GET /api/myrmidon/companies/:companyId/projects/:projectId/token-quota`.
- When token limits are exceeded, the scheduler skips task execution with system reason `project.token_quota_exceeded` (`PROJECT_TOKEN_QUOTA_SKIP_REASON`), and records the event in `project_token_usage_events`. This is an internal task skip, not an HTTP 429 response to callers.

---

### Step 6. Provision Company Secrets
Secrets are created in the tenant company scope via `POST /api/companies/:companyId/secrets` (`packages/shared/src/validators/secret.ts`, `server/src/routes/secrets.ts`). The `provider` field identifies the secure storage mechanism (`SECRET_PROVIDERS = local_encrypted | aws_secrets_manager | gcp_secret_manager | vault`), not the LLM service brand:

```http
POST /api/companies/:companyId/secrets
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "name": "OPENAI_API_KEY",
  "value": "<SECRET_KEY_VALUE>",
  "description": "Acme provider API key",
  "provider": "local_encrypted"
}
```

**Expected Response:** HTTP 201 Created with secret metadata (field `value` is omitted from the API response).

**Invariants:**
- Secret values are encrypted at rest and never exposed via `GET /api/companies/:companyId/secrets`.
- Secret access is granted solely through server-side `secret-ref` resolution within the same `company_id`.
- All decryption and read events are recorded in `secret_access_events`.

---

### Step 7. Configure Chat Inbound Endpoint (`chat_endpoints`)
Register an external chat endpoint matching `createChatEndpointSchema` (`packages/shared/src/validators/chat-channels.ts`):

```http
POST /api/chat-endpoints
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "provider": "telegram",
  "assignedAgentId": "<agentId>",
  "name": "Acme Support Bot"
}
```

**Expected Response:** HTTP 201 Created with endpoint object (`id` = `endpointId`, status `draft`).

Credential provisioning and endpoint activation are handled via the lifecycle configuration route `POST /api/chat-endpoints/:endpointId/configure`:

```http
POST /api/chat-endpoints/:endpointId/configure
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "action": "configure",
  "credentials": {
    "botToken": "<TELEGRAM_BOT_TOKEN>"
  }
}
```

**Invariants and Scope Separation:**
- Inbound routing dispatches messages to `assignedAgentId`, which is confined by its project nests.
- In wave 1, external chat membership gating (`enforceChatMembership`, `allowedChatIds` whitelist) is not part of the `chat_endpoints` REST API schema. Gating is enforced manually by the operator via external messenger privacy settings (private bot or restricted group); programmatic source validation is deferred to connector PR-3 (OPE-10550).

## 4. Rollback and Revocation Sequence

When terminating a client contract or responding to security incidents:

### Step R1. Pause or Remove Chat Endpoint
Stop inbound traffic by setting the endpoint action to `pause`:

```http
POST /api/chat-endpoints/:endpointId/configure
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "action": "pause"
}
```

To permanently remove the endpoint:
```http
POST /api/chat-endpoints/:endpointId/configure
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "action": "remove"
}
```
*(There is no direct `DELETE /api/chat-endpoints/:id` or `PATCH status` route; state transitions are handled exclusively through `configure`).*

### Step R2. Force-Pause or Terminate Agent
Cancel active runs and prevent wakeups:

```http
POST /api/agents/:agentId/pause
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "reason": "Client contract terminated",
  "cancelActive": true
}
```

For complete agent decommissioning:
```http
POST /api/agents/:agentId/terminate
Authorization: Bearer $MYRMIDON_API_KEY
Content-Type: application/json

{
  "reason": "Client contract terminated"
}
```

### Step R3. Invalidate and Delete Secrets
```http
DELETE /api/secrets/:secretId
Authorization: Bearer $MYRMIDON_API_KEY
```
*(Or rotate to invalid values via secrets management).* Future resolution attempts fail closed.

### Step R4. Project Nest Access Revocation
> **WARNING! CRITICAL SECURITY INVARIANT:**
> Never execute `PUT /api/myrmidon/companies/:companyId/agents/:agentId/nests` with an empty array `{"projectIds": []}` to revoke access!
> Under `agent_nests` semantics (`packages/shared/src/myrmidon-agent-nests.ts`, `agentNestAllowsProject`), an empty array means the agent is a citizen of the entire company, making it eligible for **all** projects. Sending an empty array widens access instead of revoking it.

To safely revoke project access:
1. Terminate or permanently pause the agent (Step R2).
2. If the agent remains active for other client projects, issue `PUT nests` containing only the remaining permitted `projectIds` (omitting the revoked project).
3. To isolate an agent without terminating, rebind it to a dedicated archived or dummy project rather than passing an empty array.

### Step R5. Audit Trail Verification
The operator inspects audit trails:
1. Budget limits audit history: `GET /api/myrmidon/companies/:companyId/budget-limits/journal`
2. Secret access logs: `GET /api/secrets/:secretId/access-events`
3. Company activity events: `GET /api/companies/:companyId/activity`

## 6. Implementation Readiness Boundaries

For implementation transparency, capabilities are categorized into three distinct layers:

### Implemented in Platform Core (Myrmidon main 1.6.5/1.6.6)
- Shared PostgreSQL with strict tenant data isolation by `company_id`.
- Company creation with automated `issuePrefix` allocation and `budgetMonthlyCents`.
- Company-scoped castes (`/myrmidon/companies/:companyId/castes`).
- Project `defaultCasteKey` resolution via `resolveTaskCaste`.
- Agent-to-project binding via `agent_nests` with cross-company rejection.
- Nest-level budget limits (`PUT .../budget-limits/limits/nest/:projectId`) with `hard`/`soft` modes and journal `GET .../budget-limits/journal`.
- Project token quotas (`PUT .../projects/:projectId/token-quota`) with `project.token_quota_exceeded` skip logging.
- Tenant secrets with `local_encrypted` / `vault` backends, server-side binding, and `secret_access_events` auditing.
- External chat registry `chat_endpoints` with lifecycle actions (`pause`, `resume`, `remove`).

### Manual Operator Procedures
- Provisioning tenant company records via owner API/UI.
- Setting initial budget ceilings and token quotas during client onboarding.
- Entering model provider API credentials into encrypted company secrets storage.
- Configuring external chat platform access (private group/bot privacy) prior to automated membership gates.
- Executing revocation and teardown sequences upon contract conclusion.

### Deferred Capabilities (Beyond PR-1 Scope)
1. **OPE-10549**: Ephemeral secrets with TTL (dynamic Vault leasing, automated key expiration).
2. **OPE-9131**: Embedded `myrmidon.personal-bot` UI components (in-board client/operator secret management).
3. **PR-3 / PR-4 (OPE-10548, OPE-10550)**: Native chat connectors with automated membership checks (`enforceChatMembership`) and website widget with Origin/domain authorization.
4. **PR-5 (OPE-10548)**: Client dialogue history export and retention controls.
