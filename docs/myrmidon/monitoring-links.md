# Связующие звенья: сервисные ключи и самопроверка «я живой» (1.6.6 MONITORING E)

Runbook для оператора доски. Отвечает на два вопроса: как выдать каждому связующему
звену свой ключ с минимальными правами и как доска замечает, что звено ослепло.

Повод: 02–06.10.2026 агрегатор High был слеп четыре дня — ключ звена умер
(протух/отозван), все запросы звена получали 401, и никто об этом не узнал.

## 0. Что такое звено

Связующее звено — внешний участник, который пишет на доску, но не управляет ею:

- агрегатор Zabbix,
- вебхук Alertmanager,
- сборщики (collectors).

Звену нужен один ключ доски со скоупом `monitoring_link`. Это самый узкий скоуп
доски: он умеет ровно три вещи — создать задачу, обновить задачу и отправить пульс
о том, что звено живо. Он не читает компании, агентов и секреты, не создаёт
приглашения, не ставит задачу на обслуживание и не удаляет задачи.
**Общий операторский ключ (`full`) звену не выдаётся никогда.**

## 1. Выдать звену ключ

1. Settings → Instance settings → Board API keys → Create, вид скоупа —
   `monitoring_link`. Заполнить:
   - `linkKey` — короткое имя звена (`zabbix-aggregator`, `alertmanager-webhook`,
     `collector-runners`), уникальное в компании: по нему звено узнаётся в пульсе
     и в тексте тревоги;
   - `companyId` — компания, на которую звено пишет;
   - `staleAfterSec` — порог тишины, по умолчанию `480` (8 минут), см. п.3;
   - `alertAssigneeAgentId` — необязательный исполнитель тревоги (обычно роль
     observability компании; если не задан, доска ищет observability-агента сама).
2. Токен показывается один раз — сразу положить его держателю звена.
3. Проверить живым использованием: задача создаётся, задача обновляется, чужое
   действие звена даёт 403 `Board API key scope 'monitoring_link' does not allow
   this action`.
4. Отозвать прежний общий ключ звена, если он был (ротация по
   `docs/myrmidon/board-key-rotation.md`, п.1).

## 2. Пульс «я живой»

Звено раз в минуту (или чаще) подтверждает, что живо и что ключ принят:

```
POST /api/myrmidon/companies/{companyId}/monitoring/links/pulse
Authorization: Bearer <ключ звена со скоупом monitoring_link>
```

Тело не требуется, и это намеренно: звено называет себя самим ключом. Токен звена
привязан к своей `linkKey` и своей компании — ключ агрегатора Zabbix не назовётся
вебхуком Alertmanager и не запишет пульс в чужую компанию (такая попытка — 403).

Ответ `200` и есть признак жизни: доска ответила «слышу тебя» и записала время
пульса. Пульс фиксируется слоем аутентификации доски, а не обработчиком: любой
аутентифицированный запрос звена обновляет `last_used_at` его ключа, поэтому
«пропал пульс» и «ключом давно не пользовались» — одно и то же событие, и второго
хранилища пульсов, которое могло бы разойтись с первым, нет.

401/403 на пульсе — это и есть отказ ключа: звено обязано считать это симптомом
слепоты (в идеале — сразу позвать в Zabbix), но обнаруживать слепоту доска должна
сама, не полагаясь на честность звена (см. п.3).

## 3. Как доска замечает слепоту

Проход сторожа (`server/src/myrmidon/monitoring/links/watchdog.ts`) идёт на тике
планировщика сердцебиения (по умолчанию 30 секунд) со своим шагом 60 секунд. Проход
читает строки `board_api_keys` со скоупом `monitoring_link` и для каждого звена
выносит вердикт:

| Вердикт | Условие | Что значит |
|---|---|---|
| `key_revoked` | `revokedAt` заполнен | ключ звена отозвали — звено слепо немедленно |
| `key_expired` | `expiresAt` наступил | ключ протух — ровно случай 02–06.10 |
| `no_pulse` | от последнего пульса прошло больше `staleAfterSec` | звено молчит |
| `healthy` | ключ жив и пульс свежий | норма |

Если вердикт не `healthy`, сторож открывает **одну задачу High** на пару
(ключ, причина) с исполнителем observability — и это единственная задача по этой
паре: повторные проходы находят её по ключу идемпотентности и не плодят дубли.
Когда звено вернулось в строй, сторож закрывает свои тревоги с комментарием
«звено снова на связи». Если человек закрыл тревогу, а звено всё ещё слепо, сторож
её переоткрывает — слепота не гасится вручную.

**Бюджет обнаружения.** Протухший ключ или пропавший пульс видны не позднее чем
через 10 минут: `staleAfterSec` (480 с) + шаг прохода (60 с) + тик планировщика
(30 с) = 570 с. Поэтому порог тишины по умолчанию 480 с, а не больше; тест
`server/src/myrmidon/monitoring/links/monitoring-links.test.ts` проверяет эту
арифметику и оба сценария (ключ протух на ходу; звено замолчало) на сжатых часах.

## 4. Посмотреть состояние звеньев

```
GET /api/myrmidon/companies/{companyId}/monitoring/links          # лента всех звеньев компании
```

Ответ: `{ generatedAt, links: [...] }`. Лента сортирована по `linkKey` и по каждому
звену отдаёт `keyState`, `lastPulseAt`, `pulseAgeSec`, `staleAfterSec`, `verdict` и
`unhealthy`. Ключ звена видит только свою компанию; операторский ключ и сессия UI —
все.

Отдельного фильтра по звену нет намеренно: лента компании — это один короткий
список, и оператору в момент разбора нужен весь он, а не одна строка.

## 5. Признаки проблем

- Задача High «ключ протух» — выдать звену новый ключ (п.1), тревога закроется
  сама на следующем проходе.
- Задача High «пропал пульс» — проверить само звено: процесс жив? адрес доски
  доступен? Пульс настраивается в звене, ключ трогать не нужно.
- Звено получает 403 на легитимном действии — скоуп уже, чем потребность звена:
  выдать ключ с нужным видом, сообщить команде (см. `board-key-rotation.md`, п.5).
