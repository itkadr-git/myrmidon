# Корпус посева базы знаний (1.6.6 KNOWLEDGE-2.0 K-8)

> English version: [knowledge-seed.md](knowledge-seed.md)

Новое гнездо начинается пустым. Посев знаний
(`server/src/myrmidon/knowledge/seed.ts`, релиз 1.6.6, OPE-5961) наполняет папки
`decisions/` и `product/` из выверенного корпуса под контролем git, чтобы агенты
открывали базу знаний и видели решения владельца и продуктовое направление, а не
пустую страницу. Эта страница — справочник по корпусу: откуда берётся содержимое,
как запустить посев, с какими полномочиями он действует и что означают его
итоговые счётчики.

Четыре product-страницы:

- `product/open-core` — модель open core и лицензирование модулей.

Каждая запись решения несёт, кто решил, дату, дословную цитату владельца и
указатель источника обратно на запись реестра, чтобы агенты читали решения как
датированные записи, а не как документ на 204 КБ. Решения пишутся как элементы
`kind=wiki` с `decided_by` / `date` / цитатой во front-matter контента;
product-страницы — `kind=note`.

Четыре решения отменяют более раннее (цепочки `supersedes`, например решение
FORAGING вариант-2, отменённое «включить сейчас»). Цепочки применяются через
`store.supersede` **вторым проходом**, когда обе записи уже существуют, поэтому
порядок данных не важен; отменённое решение сохраняет свою историю и остаётся
доступным — superseded это состояние, а не удаление.

## Как запустить

`seedKnowledgeBase` — **только библиотечный экспорт**. Ни CLI-команды, ни
HTTP/MCP-эндпоинта, запускающего посев, нет: точка импорта одна —
`server/src/myrmidon/knowledge/seed.ts` и индекс модуля
`server/src/myrmidon/knowledge/index.ts`; в `routes.ts` и `mcp.ts` поверхности
посева нет. Чтобы выполнить посев, вызовите функцию из кода или скрипта с
подключением к базе:

```ts
import { seedKnowledgeBase } from "@myrmidon/server/src/myrmidon/knowledge/index.js";

const result = await seedKnowledgeBase(db, companyId, nestId);
// result: { created, skipped, superseded, errors }
```

Параметры:

- `db` — `Db` из `@myrmidon/db` (`createDb(connectionString)`).
- `companyId` — компания (дерево гнёзд), к которой относится знание.
- `nestId` — гнездо, владеющее папками `decisions/` и `product/`.
- `options.now?` — переопределение часов для детерминированных тестов; в обычном
  запуске не указывается.

Поведение приёмки закреплено тестом на встроенном Postgres
`server/src/myrmidon/knowledge/knowledge-seed.db.myrmidon.test.ts`.

## Полномочия публикации

Каждая созданная запись сразу **публикуется** (`store.publish`), а не остаётся
черновиком — тест приёмки требует `status = "published"` и непустой
`deliveredRevisionId` для каждой неотменённой записи. Посев действует от имени
системного актора:

```ts
export const SEED_ACTOR: KnowledgeActor = { actorType: "system", actorId: null };
```

Это свёрнутый в один программный шаг обычный путь «куратор готовит черновик →
оператор публикует»: сам корпус ревьюится в git (seed-data.ts / seed-product.ts),
поэтому публикация происходит под ревью слияния этого кода, а не постранично в
интерфейсе. Системный актор не обозначает человека-автора — происхождение
посеянных записей зафиксировано в `sources` (`OPE-401` для решений, `OPE-2913`
для product-страниц).

Замечание: запуск посева — операция над **данными** живого гнезда. Поставка кода
корпуса его нигде не запускает; в 1.6.6 ничего не исполняет посев автоматически
на бою.

## Идемпотентность и частичные отказы

Посев идемпотентен: повторный запуск **пропускает** записи, чей slug уже есть в
гнезде (доменная ошибка `slug_conflict` от `create()` трактуется как «уже
есть»), а не дублирует строки. Тест приёмки это закрепляет: второй прогон даёт
`created = 0`, `skipped = first.created`, `errors = []`, количество записей не
меняется.

**Общей транзакции на корпус и отката нет.** Записи создаются по одной, поэтому
сбой посреди прогона (недоступная база, некорректные данные) оставляет на месте
успешно созданный префикс. Это сделано осознанно: повторный запуск безопасен —
существующие slug пропускаются, и прогон продолжается с места остановки. Цепочки
supersedes, уже находящиеся в целевом состоянии, считаются успешным пропуском
(`superseded` повторно не растёт; тест требует `second.superseded = 0`).

После прогона сверьте счётчики с ожидаемыми суммами:

- `created + skipped` должно равняться **50** (46 решений + 4 product-страницы)
  на свежем гнезде, `skipped = 50` при повторном запуске.
- `superseded` должно равняться **4** на свежем гнезде (четыре цепочки
  `supersedes`), `0` при повторном запуске.
- `errors` должен быть пуст. Ошибка `knowledge_not_found` называет отсутствующую
  цель `supersedes`; доменные ошибки supersede тоже попадают в `errors`. Любая
  недоменная ошибка прерывает прогон.

## Чего посев не делает

- Не создаёт и не меняет пользователей, роли, гнёзда и компании — только записи
  знаний внутри одного существующего гнезда.
- Не импортирует и не переносит вики старого плагина; это
  [knowledge-migrate.md](knowledge-migrate.md) (K-6).
- Не трогает записи со slug вне `decisions/` и `product/`; существующее знание в
  гнезде остаётся как есть.
- Не запускается по расписанию или из интерфейса; без вызывающего корпус
  остаётся только в репозитории.
