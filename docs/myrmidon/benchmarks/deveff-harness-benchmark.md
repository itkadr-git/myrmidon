# Benchmark обвязок разработки: Hermes, Claude Code, Codex CLI, Antigravity

- **Задача**: OPE-10093 (1.7 DEVEFF: зафиксировать benchmark обвязок Hermes/Claude/Codex/Antigravity на 5 задачах)
- **Родительская задача**: OPE-9995 (1.7 DEVEFF: анализ инструментов агентной разработки (kodik и аналоги) — что перенести к нам для эффективности разработки)
- **Релиз**: 1.7
- **Статус бенчмарка**: Манифест и preflight зафиксированы для релиза 1.7; массовый прогон НЕ запускался согласно ограничению задачи.

---

## 1. Цель и контекст

В рамках анализа эффективности агентной разработки (OPE-9995) и подготовки релиза 1.7 зафиксирован компактный и детерминированный бенчмарк для сравнения четырёх инструментальных обвязок:
1. **Hermes Agent** (текущий стандартный агентный контур доски)
2. **Claude Code** (адаптер `claude_local` / CLI `@anthropic-ai/claude-code`)
3. **OpenAI Codex CLI** (адаптер `codex_local` / CLI `@openai/codex`)
4. **Antigravity CLI / Local** (адаптер `antigravity_local` / CLI `agy`)

Вместо неизмеримых синтетических тестов бенчмарк строится на **5 реальных закрытых задачах 1.6.x** с изолированными оракулами верификации (`node:test`), не требующими тяжеловесных контейнеров или долгих CI-очередей.

### Детализация задач и требования оракула

#### Задача 1: OPE-9679 — DevFlow auto-merge protection
- **Проблема**: Автоматическое слияние (`review-approve-label.mjs`) по вердикту ревьюера при красном `main` ломало очередь и приводило к каскадным сбоям CI.
- **Требования**: Проверять статус последнего CI в `main`. При падении `main` вешать метку одобрения, но блокировать включение auto-merge и применять экспоненциальный backoff. При отсутствии/очереди CI PR не разрешать auto-merge. Возобновлять слияние только после позеленения `main`.
- **Оракул**: 36 unit-тестов проверяют парсинг вердиктов, алгоритм backoff, матрицу решений `decideApproveLabel` и идемпотентность `runOnce`.

#### Задача 2: OPE-9072 — Escalation of stranded runs to agents
- **Проблема**: Завершившиеся успехом, но зависшие без передачи управления прогоны эскалировались на людей (Alex и операторов доски), создавая шум и нарушая автономность.
- **Требования**: Эскалировать дескриптор разблокировки строго по цепочке руководства агентов: менеджер исполнителя -> тимлид проекта -> системный агент `adm`. Запрещено передавать задачи человеку (`userId`).
- **Оракул**: 7 тестов проверяют корректность иерархии руководителей, fallback, защиту от пустой цепочки, фильтрацию и режим dry-run.

#### Задача 3: OPE-7773 — /tmp hygiene & host profile janitor
- **Проблема**: Профили браузера, дампы и остаточные файлы в `/tmp` забивали диск хоста и несли риски утечки данных между прогонами.
- **Требования**: Реализовать fail-closed скрипт очистки `myrmidon-tmp-janitor.sh` с валидацией TTL, рекурсивной проверкой занятых дескрипторов процессов (`lsof` / `/proc`), защитой белого списка активных профилей и запретом перехода по симлинкам.
- **Оракул**: 16 тестов проверяют удаление просроченных директорий, сохранение активных процессов, запрет удаления живых профилей, fail-closed поведение при ошибке проверок.

#### Задача 4: OPE-9185 — Legacy blocked classifier without speculation
- **Проблема**: Задачи зависали в статусе `blocked` из-за неточных или устаревших комментариев в тредах; агенты простаивали без работы.
- **Требования**: Реализовать строгий табличный классификатор `classify.ts`, опирающийся только на явные факты (активные тикеты-блокеры, ожидание решений, открытые PR). Конфликтующие или устаревшие формулировки безопасно классифицировать как `unknown`.
- **Оракул**: 19 тестов покрывают консервативную матрицу классификации всех видов блокировок и граничные случаи противоречивых комментариев.

#### Задача 5: OPE-8844 — Brand release audit with exact allowlist
- **Проблема**: Выпуск релиза требовал гарантированного отсутствия упоминаний вендора во внешних интерфейсах и пакетах при сохранении легальных атрибуций и внутренних контуров совместимости.
- **Требования**: Реализовать статический аудит `brand-release-audit.mjs`, проверяющий ссылки в `package.json`, запрещающий пользовательские упоминания вендора, требующий точных (non-glob) записей в allowlist и защищающий от утечек масок.
- **Оракул**: 10 утверждений проверяют блокировку некорректных метаданных, пропуск разрешённых атрибуций, отказ при glob-масках в allowlist.

## 3. Preflight четырёх обвязок

### 1. Hermes Agent
- **Версия**: `Hermes Agent v0.21.5 (2026.9.24)` на Python 3.13.18, OpenAI SDK 2.24.0.
- **Тип интеграции на доске**: Адаптер `hermes_gateway` / `hermes`, автономный контейнер `myrmidon-bot-<id>`.
- **Инструментарий**: Встроенный типизированный набор (`read_file`, `write_file`, `patch`, `terminal`, `search_files`, `browser_exec`, `memory`).
- **Автономный / Headless режим**: Нативный. Управляется через API сервера Myrmidon, поддерживает фоновые прогоны и таймауты.
- **Целевая модель**: `antigravity/gemini-3.8-flash-medium` через пул LiteLLM (`http://localhost:4000/v1`), fallback `chatgpt-pool/gpt-6-sol`.
- **Плюсы**: Высокая стабильность в нашем контуре, отсутствие проблем с экранированием терминала при работе с файлами, низкие накладные расходы на вызов.
- **Риски**: Склонность к холостым циклам при повторяющихся ошибках инструментов без вмешательства оператора.

### 2. Claude Code
- **Версия / Пакет**: `@anthropic-ai/claude-code` (npm).
- **Тип интеграции на доске**: Адаптер `claude_local` (`packages/adapters/claude-local`).
- **Движок**: Поддержка двух режимов: `engine: "acp"` (Agent Client Protocol via `@agentclientprotocol/claude-agent-acp`) и `engine: "cli"` через PTY.
- **Автономный / Headless режим**: Требует обязательной передачи флага `--dangerously-skip-permissions` (в CLI) или `nonInteractivePermissions: "deny"` (в ACP), иначе зависает на интерактивном подтверждении в терминале.
- **Целевая модель**: `nghi-claude-sonnet-5` (или `claude-3-7-sonnet-20250219`).
- **Плюсы**: Высокое качество сложного архитектурного рассуждения, отличная способность к самостоятельной локализации регрессий.
- **Риски**: Значительно более высокая стоимость токенов и задержка ответа; требование PTY/ACP окружения.

### 3. OpenAI Codex CLI
- **Версия / Пакет**: `@openai/codex` (npm).
- **Тип интеграции на доске**: Адаптер `codex_local` (`packages/adapters/codex-local`).
- **Движок**: CLI в интерактивном псевдотерминале (`codex exec "..." --sandbox workspace-write` или `--sandbox danger-full-access`).
- **Автономный / Headless режим**: Выполняется командой `codex exec` в один проход, автоматически одобряет модификацию файлов внутри workspace.
- **Целевая модель**: `chatgpt-pool/gpt-6-sol` / `openai-gpt-5.6-sol` через LiteLLM.
- **Плюсы**: Быстрая генерация кода, строгое следование TypeScript-типам.
- **Риски**: Категорически отказывается работать вне git-репозитория; в контейнерах песочница `bwrap` может конфликтовать с namespaces (требуется флаг `danger-full-access`).

### 4. Antigravity CLI / Local
- **Версия / Пакет**: `agy 0.2.0` / адаптер `antigravity_local` на доске.
- **Тип интеграции на доске**: Локальный запуск на хосте доски без отдельного контейнера; проверка серверной лицензии модуля `antigravity`.
- **Автономный / Headless режим**: В документации CLI (`cli-docs.md`) поддерживаются флаги `--sandbox`, `--dangerously-skip-permissions`, `proceed-in-sandbox`. Без них CLI переходит в интерактивный режим запроса прав.
- **Целевая модель**: `antigravity/gemini-3.8-flash-medium` / `kie-gemini-3.1-pro`.
- **Плюсы**: Сверхнизкая задержка генерации, огромный контекст (1M+ токенов), минимальная стоимость токенов; модель уже используется как основной бэкенд в пуле LiteLLM.
- **Риски**: Необходимость лицензирования модуля `antigravity` на сервере для штатного адаптера доски; закрытый характер бинарных сборок.

## 5. Критерии успеха и метрики

1. **Pass@1 Oracle Rate (Главный критерий приёмки)**:
   - Решение задачи считается успешным тогда и только тогда, когда оракул задачи завершается с кодом `0`, `fail = 0`, `pass = total`.
2. **Чистота изменений (Clean Diff)**:
   - Отсутствие побочных изменений вне области задачи; отсутствие временных файлов, логов, ключей и секретов.
3. **Число шагов (Turns to Completion)**:
   - Общее число вызовов модели до завершения задачи.
4. **Доля пустых ходов (Empty Turn Rate)**:
   - Доля ходов без продуктивных действий (опросы статуса, повторные чтения без изменений, холостые циклы). Допустимый порог: 0%.
5. **Время выполнения (Wall-Clock Duration)**:
   - Физическое время от инициализации рабочего каталога до финального коммита.

### Правила принудительной остановки (Stop Rules)
- **Петля инструментов**: 3 последовательных вызова с идентичными ошибками приводят к немедленному прерыванию.
- **Лимит ходов**: Жёсткий останов на 15 ходах на задачу.
- **Таймаут**: Останов по истечении 600 секунд (10 минут) на задачу.

## 7. Протокол запуска (инструкция оператору)

В соответствии с прямым указанием в задаче («не запускать массовый прогон»), автоматический прогон всех 20 комбинаций в рамках этого тикета не производился.

Для последующего запуска испытаний оператор выполняет:
1. Создание изолированного worktree на родительском коммите задачи:
   ```bash
   git worktree add /tmp/bench/<TASK_ID> <BASE_COMMIT_SHA>
   ```
2. Передачу задачи соответствующей обвязке (Hermes / Claude / Codex / Antigravity) с текстом постановки задачи из манифеста.
3. Запуск команды оракула после завершения работы обвязки:
   ```bash
   cd /tmp/bench/<TASK_ID> && <ORACLE_COMMAND>
   ```
4. Фиксацию результатов в матрицу `pass@1 / turns / tokens / duration`.
