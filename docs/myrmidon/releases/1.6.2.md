# Release 1.6.2 — operator notes

> Russian version: [1.6.2.ru.md](1.6.2.ru.md)

This page is for the operator upgrading a board to 1.6.2: what changed, what
is on by default, and what needs a switch or a host step. Every entry is
traced to the changelog ([../CHANGELOG.md](../CHANGELOG.md)) and the linked
guides; the full deploy procedure is [../deploy.md](../deploy.md).

## At a glance

| Change | On by default? | Operator action |
|---|---|---|
| Run admission: host free-memory floor and start ramp | Yes (floor 15360 MB, ramp 5 starts/min) | Optional: adjust the values; none needed to keep the defaults |
| Bot language servers by role | Yes (new policy applies at upgrade) | Optional: tune the policy or pin a mode per agent |
| Shared package cache for development bots | No | Host directories + dockergate `packageCacheRoot` + instance setting (steps below) |
| A board unblock lifts a settled replay hold | Yes (behavior fix) | None |

| Gateway spend attributed through per-bot secret references | Yes (hotfix) | None |
| Plugin bridge: invocation-scope attribution (PLS2) | Yes (compatibility fix) | None |
| Plugin entitlement keys | Yes (the gate exists; with no keys, entitled plugins stay inactive) | Optional: accept keys for `requiresEntitlement` plugins |
| Release publish waits for the tag's own image runs | Yes (CI fix) | None |

Details per change follow.

## Stability and fixes (no settings change)

These land with the upgrade itself; there is nothing to switch on.

- **A blocked task stuck by an old recovery decision wakes again.** A task
  whose closed recovery record held `"replay": "blocked"` stayed stuck: every
  automatic wake was parked, and idle pickup treated that parked wake as
  covering the task. Now a board member moving a task out of `blocked` (or
  reassigning a workable one) clears its settled replay holds in the same
  transaction, and a parked wake no longer counts as covering the task.
- **Chats are never held.** A chat (a bridged Telegram DM thread or a board
  Agent Chat) is a conversation, not a work ticket: recovery no longer marks
  it `blocked` and records no replay hold; a new message from a person always
  wakes it. If a message cannot start at once (the previous turn is winding
  down, an open question, a paused agent, an exhausted budget, the host memory
  gate), the chat is told why, in plain language, with a time estimate where
  one is known. Guide: [../guides/telegram-dm-status.md](../guides/telegram-dm-status.md).
- **Gateway spend is attributed per bot again.** The cost sweep wrote no
  rows: bot cards carry the gateway key as a `secret_ref` binding, and the
  lookup understood only an inline value or the one shared secret. The lookup
  now resolves the card's secret reference, so spend rows are attributed to
  the agent and its run. The model-fallback signal, which reuses the lookup,
  is fixed by the same change.
- **Plugins built on the old SDK work through the bridge again.** The plugin
  bridge attributed an un-echoed worker call only to an in-flight plugin API
  route, so nested calls from `onEvent`/`performAction`/`getData`/
  `executeTool` handlers were refused with "missing, expired, or unknown
  invocation scope" (an empty page list, pages that would not open, failing
  wiki-write tools). Attribution now covers any in-flight host-issued
  invocation. The safety guard is unchanged: attribution applies only while
  every in-flight invocation belongs to one company.
- **Release publish waits for the tag's own image runs.** The publish gate
  matched workflow runs by the tag commit's `head_sha` only, so it saw the
  already-green `main` run of the same commit instead of the tag's image run
  and the digest probe failed. The gate also filters by `head_branch` now,
  and accepts a green same-commit main run for the CI lane (`myrmidon-ci.yml`
  has no tag trigger). A manual re-run from `main` no longer overrides the
  typed tag.

## Run admission: host free-memory floor and start ramp (on by default)

Before 1.6.2 the free-memory check measured the server cgroup and could not
see bot containers: 23 concurrent runs once exhausted a host while the server
looked healthy. Two changes fix that:

- **Host floor.** A new run (whatever woke it) starts only while the host's
  `MemAvailable`, minus the budget of runs started in the last 30 s, stays at
  or above `minFreeHostMemoryMb` — default **15360 MB** (15 GB). Otherwise the
  run stays `queued` and is retried every 15 s. Host memory is read from
  `/proc/meminfo`; a container-scoped meminfo (lxcfs) is detected and refused
  — mount the host's file read-only and point `MYRMIDON_HOST_MEMINFO_PATH` at
  it.
- **Start ramp.** `maxStartsPerMinute` now defaults to **5** (was off). An
  instance that already saved its run limits keeps its saved value.

Where to change: Instance → General, "Run limits" section (also Settings →
"Runs & queue"), or `PATCH /api/myrmidon/runtime-limits`. Environment
overrides: `MYRMIDON_MIN_FREE_HOST_MEMORY_MB` (15360),
`MYRMIDON_MAX_RUN_STARTS_PER_MINUTE` (5); `0`/`off` switches a limit off.
Changes apply without a restart.

How to check it works:

- Lower the floor below the host's free memory and back: queued runs start
  within a minute, no restart.
- When the floor holds runs back for more than 10 minutes, the attention desk
  shows "Runs held: host memory" with the current free memory and the floor;
  the card disappears with the first admitted run.

Guide: [../guides/run-limits.md](../guides/run-limits.md); settings rows in
[../SETTINGS.md](../SETTINGS.md).

## Bot language servers by role (on by default)

Each language server for a TypeScript worktree costs about 1 GB of heap, and
most bots never write code. Since 1.6.2 the mode is decided per bot:

- Roles that write code (by default `engineer`, `qa`, `devops`, `reviewer`,
  `release`) run **limited**: one TypeScript server per worktree, no automatic
  typings download, a 1024 MB heap cap, a 120 s idle timeout.
- Every other bot runs **none** (`lsp.enabled: false`).

No opt-in is needed: the policy applies at upgrade (one restart per container
bot, under its pause). The monorepo typecheck is unaffected — it goes through
the build server.

Where to change: the instance policy on Instance → General → "Bot language
servers" (`GET`/`PATCH /api/myrmidon/bot-lsp`): which roles write code, the
mode for coding and other roles (`off` / `limited` / `full`), the idle
timeout, the memory cap, excluded workspace roots. One agent can pin its own
mode in the "Language servers" section of its card. Changes apply without a
server restart, on the next reconcile tick.

How to check it works: the policy panel shows how many bots run in each mode;
after a change, the bot's `config.yaml` `lsp` block updates on the next
reconcile pass.

Guide: [../guides/bot-lsp.md](../guides/bot-lsp.md); field reference in
[../SETTINGS.md](../SETTINGS.md).

## Shared package cache for development bots (off by default)

Development bots download the same pnpm packages, Go modules and Gradle
dependencies again and again, each into its own volume. With the shared
package cache, every bot on the board's host mounts one set of cache
directories read-write, and downloads are kept once:

| Host directory | Mount point in the bot | Variable written to the bot profile |
|---|---|---|
| `<cache>/pnpm` | `/cache/pnpm` | `npm_config_store_dir` |
| `<cache>/go-mod` | `/cache/go-mod` | `GOMODCACHE` |
| `<cache>/go-build` | `/cache/go-build` | `GOCACHE` |
| `<cache>/gradle` | `/cache/gradle` | `GRADLE_USER_HOME` |

pip is not covered (the image's `PIP_NO_CACHE_DIR` cannot be unset). Bots on a
fleetd host do not get the cache.

Steps to enable (all three are required):

1. Create the four subdirectories and give them to the bot user (uid and gid
   10001 in the bot image) — Docker would otherwise create a missing one as
   root and the bot could not write to it:

   ```sh
   install -d -o 10001 -g 10001 /srv/package-cache/{pnpm,go-mod,go-build,gradle}
   ```

2. Set the same directory as `packageCacheRoot` in the dockergate
   configuration and send dockergate `SIGHUP` (applied without a restart).
   Without it dockergate refuses every cache bind with
   `mount_source_not_allowed`, and the reconcile error names the bot. See
   [../dockergate.md](../dockergate.md).
3. Save the path in the instance setting: Instance → General, panel "Shared
   package cache for bots", or `PATCH /api/myrmidon/bot-disk` with
   `{"sharedPackageCachePath": "/srv/package-cache"}` (instance admins only).
   `null` or an empty string turns the cache off.

No server restart is needed: the local driver and the profile compiler re-read
the setting on every reconcile pass, so on the next pass every bot is
recreated with the new binds and restarted with the new variables. The
directory must be a plain absolute path and must not be inside the bot volume
root.

How to check it works:

- After a reconcile pass, a bot's container has the four `/cache/*` binds and
  its `hermes/.env` points the four variables at them.
- A cache bind with `packageCacheRoot` unset is refused with
  `mount_source_not_allowed` in the dockergate log — that refusal names the
  bot whose reconcile tried.

Trade-off: all bots on the host share the cache read-write, so turn it on only
for bots that already trust each other (the same team's development bots).
Full guide: [../bot-disk-cache.md](../bot-disk-cache.md).

## Plugin entitlement keys (the gate is on; keys are yours to add)

A plugin whose manifest sets `requiresEntitlement: true` stays unactivated —
no worker process, no UI slots, hidden from menus and settings — until the
instance admin accepts a valid entitlement key for its exact plugin id. Where:
the "Plugin keys" block on the instance settings page, or
`GET`/`POST`/`DELETE /api/myrmidon/plugin-entitlement/keys`. The gate re-reads
the settings on every activation pass, so accepting or removing a key takes
effect without a restart. With no keys registered, nothing changes for
plugins that do not opt in. Guide:
[../guides/plugin-entitlement-keys.md](../guides/plugin-entitlement-keys.md).

## Heavy builds blocked in the dev bot image (on by default, dev image only)

The development variant of the bot image no longer relies on convention to
keep heavy builds off the bot container: `pnpm`, `tsc`, `vitest`, `gradle` and
`go` shims (first on `PATH`) refuse every non-trivial invocation with exit 1
and a message naming the exact `devbuild …` replacement. Light probes keep
working locally (`pnpm --version`, `pnpm config …`, bare `--version`/`--help`),
and `git`, `node`, `cargo`, `gh`, `docker` are not wrapped. To build:
`devbuild pnpm install`, `devbuild pnpm exec tsc --noEmit`,
`devbuild pnpm vitest run`, `devbuild go build ./...` — the workspace is
mounted into a build container on the build host and the same command runs
there. See `docker/bot-runtime/README.md`, section "Heavy builds are blocked
at the image level".

## Maintenance: asynchronous exit and the post-deploy fleet check

Leaving maintenance mode is asynchronous: the `exit` call returns as soon as
the window is marked `leaving`, and the tail (resuming the queued wake
backlog, the exit hook, retiring the window) runs on the maintenance tick
(`MYRMIDON_MAINTENANCE_TICK_SEC`, default 5 s). The deploy polls the
maintenance state until the window is `off`, bounded by
`MAINTENANCE_EXIT_WAIT_SEC` (default 120 s).

The deploy ends with a read-only post-deploy fleet check (step 9): with
`BOARD_API_URL` and `BOARD_COMPANY_ID` set it asks the board for issues that
are `blocked` with an update since the deploy started and re-reads the
maintenance state; a hit ends the run with `DEPLOY DEGRADED` — a verdict, not
a failure of an already switched and healthy deploy. Without the two settings
the check is skipped. Set them in the deploy environment to enable it.

## Budget enforcement modes (default keeps prior behavior)

What a crossed spend budget does is now a mode, not a fixed stop:
`signal_only` (the default — the incident and the owner signal appear, runs
start), `soft` (pause plus the "raise the budget or keep paused" card),
`hard` (new runs of the over-limit scope are refused). One mode for the whole
instance, changed live from Instance → General or
`PATCH /api/myrmidon/budget-enforcement`; the environment override is
`MYRMIDON_BUDGET_ENFORCEMENT_MODE`. With the default, behavior matches the
previous release. Guide:
[../guides/budget-enforcement.md](../guides/budget-enforcement.md).

## WIP limit (counting on; limits optional)

The per-agent work-in-progress limit: a company-wide default and per-agent
overrides edited on the "WIP limit" screen in Company Settings. Each agent's
live `in progress + in review` load shows in the screen's table, as a
`wip/limit` badge on the agents page, and in the attention feed. Without a
saved limit the load is still counted and shown, but nothing signals. Guide:
[../guides/wip-limit.md](../guides/wip-limit.md).

## Automatic rollback by health: operator guide (docs only)

The existing behavior (a failed post-deploy health check rolls the board back
to the remembered previous image) gets its operator guide: when the rollback
fires, the job and report phases, where the failure reason is recorded, what
the owner sees when a rollback fails, and the settings of both halves of the
switch. No code change. Guide:
[../guides/deploy-auto-rollback.md](../guides/deploy-auto-rollback.md).

## Voice STT, server core (off by default)

The server-side speech-to-text core ships with the `dashscope` (through the
shared LiteLLM gateway) and `deepgram` backends and the `transcribeAudio`
contract with stable error codes. Off by default: without
`MYRMIDON_STT_ENABLED` the path makes no outbound request. Backend keys are
company secrets referenced by name only. See [../SETTINGS.md](../SETTINGS.md),
the VOICE-STT section.
