# Release 1.6.6 — operator notes

> Russian version: [1.6.6.ru.md](1.6.6.ru.md)

This page is for the operator upgrading a board to 1.6.6: what changed, what is on by default, and what needs a switch or a host step. The changelog section
([../CHANGELOG.md](../CHANGELOG.md), "1.6.6") has about three hundred entries; here are the ones that change what the operator sees or does, each traced to
its entry and the linked guides. The full deploy procedure is [../deploy.md](../deploy.md); every setting named below is listed with defaults in
[../SETTINGS.md](../SETTINGS.md).

## At a glance

| Change | On by default? | Operator action |
|---|---|---|
| Deploy preflight counts the incoming release images and a reserve for the database copy; image retention keeps the current release plus N previous | Yes | Check free space on the deploy host; optional `MYRMIDON_DEPLOY_DB_DUMP_RESERVE_GB` (5), `MYRMIDON_DEPLOY_IMAGE_KEEP`, `MYRMIDON_PREDEPLOY_IO_DEVICE` / `MYRMIDON_PREDEPLOY_IO_RATE` |
| Board database image with pgvector (`pgvector/pgvector:0.8.7-pg17`) | Fresh installs only | An existing board on `postgres:17-alpine` keeps its image; enable pgvector by [../runbooks/pgvector-extension.md](../runbooks/pgvector-extension.md) before turning the corpus on |
| 61 database migrations (`0389` … `0462`) | Yes, at the deploy | `0401` repairs duplicate wake keys first; `0462` backfills pull-request work products. After the rollout the release operator reconciles `.deployed.json` ([../deploy.md](../deploy.md), "Production migration registry") |
| Idle bot containers are stopped after 30 minutes and woken on demand | Yes (since OPE-7898; see below) | Per bot: "On demand" / "Always on"; switch off with `MYRMIDON_IDLE_STOP_ENABLED=false` or in Instance settings |
| An agent in "container not started" gets its container started automatically | Yes | None |
| Public self-registration is closed | Yes | `MYRMIDON_AUTH_DISABLE_SIGN_UP=false` to allow it |
| A task cannot enter `blocked` without a reason (422 `blocked_requires_reason`) | Yes | `scripts/myrmidon/unblock-reasonless.mjs` returns existing reasonless blocked tasks to `todo` (dry run by default, `--apply`) |
| Code issues can be assigned to engineers only (422 `issue_requires_engineer`) | Yes | None |
| An issue with linked pull requests cannot go to `done` before they are merged (`issue_done_pull_request_gate`) | Yes | None |
| Run guard: call-limit continuations get their own ceiling; a final guard stop wakes the manager; wider read-only limits for code roles | Yes | Optional `runtimeConfig.heartbeat.runGuardContinuation.*`, `MYRMIDON_RUN_GUARD_*` |
| A run over the agent's daily run limit is deferred to the reset instead of being cancelled | Yes | None |
| The board merges an approved pull request itself once its head is green and mergeable | Yes (`boardMerge.enabled` = `true`) | `boardMerge.baseBranches` defaults to `["main"]`: add the release base (for example `rel/1.6.6`) if the board should merge into it; `boardMerge.maxMergesPerPass` (3) |
| Bot runtime: `state.db` VACUUM by free pages, input-token economy, stable conversation key, tool lists per role | Yes, with the next bot image rollout | Bot containers are recreated by the rollout; the first VACUUMs follow about an hour after each start |
| Knowledge corpus and knowledge module | Corpus: off (`MYRMIDON_CORPUS_ENABLED` = 0) | Needs pgvector, a parser URL and an embedder; see "Optional features" |
| Board processes (api + worker split) | No: the default is the single process | `general.processes` in the instance settings |
| Remote execution sites | No: `MYRMIDON_SITE_HEALTH=1` and `MYRMIDON_SITE_SCHEDULER=1` | Register sites through the board API / Fleet screen |
| Monitoring alerts webhook (Zabbix, Alertmanager) | Needs configuration | `MYRMIDON_ALERTS_WEBHOOK_TOKEN_REF` and `MYRMIDON_ALERTS_COMPANY_ID`; without them the webhook answers 503 |
| Comment wakes of one task collected into one run | No | `MYRMIDON_WAKE_BATCH_WINDOW_MS` (10000 recommended) |
| CLI renamed `myrmidon` | Yes | `paperclipai` keeps working and prints a deprecation line |
| Final tag needs the database audit report | Yes, in the publish gate | Commit `releases/<version>-db-audit.md` before the final tag |

Details per change follow.

## What changes at the deploy

- **Disk preflight.** `deploy_disk_precheck` adds the registry size of every release image that is not on the host to the required free space before the first pull or the maintenance window, and refuses a deploy that cannot fit (cleanup candidates are printed; it also refuses when an image size cannot be read from the registry, while `--dry-run` only warns). The reserve for the predeploy database copy is `MYRMIDON_DEPLOY_DB_DUMP_RESERVE_GB` (default 5); it applies to full deploys that declare `MYRMIDON_DEPLOY_IMAGE_REFS`, while `bot-image-rollout.sh` and `rollout-component.sh` keep the plain `MYRMIDON_DEPLOY_MIN_FREE_GB` threshold. The throwaway database copy is throttled at the Docker data device (`MYRMIDON_PREDEPLOY_IO_DEVICE`, `MYRMIDON_PREDEPLOY_IO_RATE`; PREDEPLOY-IO).
- **Image retention.** The retention step counted its window over the images no container uses and so kept two superseded generations of every bot image on top of the running one. It now keeps the current release plus `MYRMIDON_DEPLOY_IMAGE_KEEP` previous ones.
- **Installer.** The one-command installer names the machine's host names and global IPv4 addresses in the board allow-list (`MYRMIDON_ALLOWED_HOSTNAMES`; `MYRMIDON_ALLOWED_HOSTS`, comma-separated, overrides the detected list), refuses a processor below the x86-64-v2 baseline before touching the machine, wires the dockergate service, and starts the database from the pgvector image and enables the extension before the board starts (a version other than `0.8.7` fails the installation).
- **Release publish.** A notes section over GitHub's 125000-character limit is published as the list of entry headings with a pointer to the full changelog; the tag-CI wait budget is 80 minutes; the release cut fails when the changelog has no `## X.Y.Z` section.
- **Bot image rollout.** A bot's memory, CPU or pids limits reach the running container with a live update and no restart; skill changes reach a running container without a restart; the rollout waits for an interrupted run to finalise (the drain poll grace is 120 s).
- **Database.** 61 migrations (`0389` … `0462`). `0401_wakeup_key_partial_unique_indexes` repairs duplicate `pause_resume:` / stranded-retry wake keys first (the most meaningful run-backed wake keeps the key, running work is never cancelled). `0462_pull_request_work_product_url_backfill` fills `url` / `external_id` of pull-request work products from their metadata. `0404_install_identity` stores the installation id (see Licensing).

## Behavior that changes without a switch

- **Idle containers are stopped (IDLE-STOP, OPE-7898).** A bot container without an active heartbeat run for 30 minutes (`MYRMIDON_IDLE_STOP_AFTER_SEC`, default 1800, minimum 60) is stopped; before a claimed run starts the board starts it and waits up to 7 minutes (`MYRMIDON_IDLE_START_HEALTH_TIMEOUT_MS`, default 420000) for it to become healthy, otherwise the run is cancelled with a journal error. Per-bot modes "On demand" and "Always on" are on the agent card and in a bot list under Instance settings. With nothing stored in the instance settings the switch follows `MYRMIDON_IDLE_STOP_ENABLED` (any value except `false`, `0`, `no`, `off` keeps it on).
- **Auto-resume of "container not started".** The sweep starts the bot container first (four attempts, 15 minutes apart, then one critical alert card), then resumes the agent as usual.
- **Sign-up is closed by default** (`MYRMIDON_AUTH_DISABLE_SIGN_UP`, default `true`).
- **`blocked` needs a reason.** A transition into `blocked` is refused (422 `blocked_requires_reason`) unless the task has an open blocker, a `blockerMetadata.blockReason`, or an `unblockDescriptor` with an owner and an action. A `cancelled` blocker now counts as resolved everywhere, like `done`. When the last open blocker closes and nothing else holds the dependent, it returns to `todo`.
- **Engineers only for code issues.** Creating or reassigning a code issue (label `needs-engineer`, engineer caste, a live checkout needed) to an agent whose role is not `engineer` answers 422 `issue_requires_engineer`; humans can still be assigned.
- **Done gate.** An issue linked to pull-request work products cannot go to `done` until every linked pull request is verified merged (conflict `issue_done_pull_request_gate`; a closed pull request is accepted only when `metadata.replacementPullRequestUrl` names a valid replacement).
- **Guarded hand-off.** `PATCH /api/issues/{id}` accepts optional `expectedAssigneeAgentId` and `expectedStatusVersion`; when both are present and the assignee changes, the update is a compare-and-set.
- **Run guard.** A call-limit stop of a run that made changes continues in a follow-up run with its own ceiling (`runtimeConfig.heartbeat.runGuardContinuation.maxAttempts`, default 6, at most 20); a final guard stop wakes the assignee's manager (`run_guard_stop_needs_input`). The default limits of the read-only stops are 100 / 5 for the roles `engineer`, `reviewer`, `lead`, `architect` and 40 / 3 for the others; a run stopped by `no_progress_exploration` is continued once. Automatic retry of a failed run is one policy: the failure is classified `transient`, `permanent` or `unknown`; a transient failure is retried with exponential backoff up to an attempt limit, a permanent one never, an unclassified one keeps the single-attempt treatment.
- **Daily run limit.** A queued run refused under `heartbeat.daily_run_limit` is deferred to the end of the day window (plus up to 5 minutes of jitter) instead of being cancelled; a zero limit, the daily cost limit and a user's manual wake still cancel.
- **Review routing.** The board merges an approved pull request itself (`boardMerge.enabled`, default `true`; base branches default to `["main"]`) once its head is green and mergeable (squash, through the shared GitHub App identity), at most `boardMerge.maxMergesPerPass` per pass; the merge is bound to the approved head and the required check `CI result` must be `success` on it. A review return on the same head, or only on infrastructure checks, no longer wakes the executor; an exhausted review wake series is escalated once and re-armed after 6 hours.
- **Wakes.** A continuation wake carries a summary, not the task history three times; continuation wakes go only to actionable assigned issues, with a real attempt cap; an agent no longer wakes itself with its own PATCH or comment bookkeeping; a stale delivery no longer starts a turn (the wake guard also checks the issue version).
- **Issue list.** `GET /api/companies/:companyId/issues` honours `page` (`offset = (page - 1) * limit`); `page=0` or a non-numeric value answers 400.

## Bot runtime (arrives with the bot image rollout)

- **`state.db` compaction.** The `state.db` of a bot is vacuumed when more than 25% of its pages are free and `sessions.min_vacuum_interval_days` (30) have passed; it waits for a quiet moment and for room, and the temporary copy goes to `$HERMES_HOME/.sqlite-tmp` on the bot's volume instead of tmpfs. Verify by the gateway log line `state.db VACUUM: … MB -> … MB`.
- **Input tokens.** The runtime keeps the provider prompt cache (it rewrites nothing in the middle of a session and bounds what is new); requests carry a stable conversation key so the pool's cache can hit; the per-role default tool lists drop unused tool schemas; the Myrmidon skill core is compact with details on demand. `context_economy.stale_wakes` (rewriting superseded wake messages) is off by default.
- **Gateway slots.** The board frees the gateway slot of every run it finishes, and gateway runs survive a board restart (the result stays visible). A lost connection to the model gateway no longer moves a run to the fallback model.
- **Tools.** `execute_code` receives `PAPERCLIP_API_KEY` / `PAPERCLIP_API_URL` through `terminal.env_passthrough` (the profile changes, so bot containers are recreated by the maintenance window). Bots also read the board key and address as `MYRMIDON_API_KEY` / `MYRMIDON_API_URL` (`PAPERCLIP_*` remain synonyms).

## Optional features (off by default or need configuration)

- **Knowledge corpus and knowledge module (KNOWLEDGE-2.0, CORPUS-2.0).** The corpus is off (`MYRMIDON_CORPUS_ENABLED` = 0); every corpus route answers 503 `corpus_disabled` until it is switched on. It needs pgvector (above), the parser URL (`MYRMIDON_CORPUS_PARSER_BASE_URL`) and an embedder; search is hybrid (full-text plus vector, HNSW with an iterative scan); documents can be added by address with a refresh period; bots search through the `corpus_*` MCP tools; `corpus_search` returns document titles, ranks globally across datasets and accepts dataset names. The knowledge module adds REST and MCP behind one set of rights, rules, a distiller, a nightly Git export, an evals gate and screens in the current interface.
- **Board processes (BOARD-PROCESSES).** The board can run as `api` processes plus a `worker`; the composition is the instance setting `general.processes`, and an absent key means `{ api: 1, worker: 0 }`, today's single process. Readiness is `GET /internal/ready` per process and the aggregate `/healthz`.
- **Remote execution sites (REMOTE-SITES).** Sites are registered through the board API and managed on the Fleet screen; the `site-monitor` lane (health probes, automatic drain and failover) and the `site-scheduler` lane (bot moves between sites) are off until `MYRMIDON_SITE_HEALTH=1` / `MYRMIDON_SITE_SCHEDULER=1`; fleetd gets a mutual-TLS listener for the site API.
- **Licensing.** The installation id is stored in the board database (`myrmidon_install_identity`) and never changes; it is `MYR_LICENSE_INSTANCE_ID` if set, else the same formula as before, so licenses already issued stay valid. Settings → Instance → Licenses shows the id, the request line, the state of every closed module's license and an install form; the installation pulls the issuer's signed deny-list of revoked licenses.
- **Monitoring.** Alerts webhook for Zabbix and Alertmanager (an alarm becomes a task of the owning role with the runbook steps and is closed on recovery); fleet dashboard data from VictoriaMetrics and Zabbix; `myrmidon_auth_401_burst_*` metrics (`MYRMIDON_AUTH_401_BURST_THRESHOLD`, default 20, `…_WINDOW_SEC`, default 60); OOM losses classified as `resource.oom`; engineer idle and unblocked-task gauges; live-run phase gauges with a reconnecting watchdog.
- **Settings screens.** Instance → Features (registry of fork features with live health), the bot-disk lifecycle, run priority, model fallback signal, workspace hygiene, attention windows, execution policy badge, typed adapter settings and the Browsers screen are editable in the interface. The bot's `/model` menu is a group tree the owner edits (MODEL-MENU).
- **Money and quotas.** Project token quotas (daily / weekly, refused at enqueue); provider key and account usage with a warning before a package or window runs out; Codex OAuth lifecycle for pool accounts.
- **Secrets by reference.** OAuth client secrets of tools and cloud connectors, application module credentials and the telemetry export token can come from a secret reference.
- **Telegram and channel connectors.** The channel connector contract, registry and hub, and a Telegram connector over that contract land as an installation flag with no traffic switch; the bridge seam is off while `MYRMIDON_CHANNEL_CONNECTOR_BRIDGE` is unset, and then behaves byte for byte as before.
- **Migration from Paperclip.** `myrmidon:migrate` accepts Paperclip releases `v2026.916.1`, `v2026.1001.0`, `v2026.1005.0` and `v2026.1012.0` (dry run prints the inventory and writes nothing).
- **Comment batching.** `MYRMIDON_WAKE_BATCH_WINDOW_MS` (off, 10000 recommended) makes the comments of one task inside the window start one run.
