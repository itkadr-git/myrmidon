# Аудит базы доски 1.6.8 (db-audit)

Правило владельца 08.10.2026: финальный тег, без суффикса `-rc`, выходит только с принятым аудитом базы. Отчёт лежит в `docs/myrmidon/releases/<версия>-db-audit.md`, то есть здесь. Гейт — `scripts/myrmidon/release/db-audit-gate.sh`.

## 1. Происхождение

- Автоотчёт модуля datastore-care (DBC-4): `POST /api/myrmidon/datastores/board/audit-reports` и экспорт `GET /api/myrmidon/audit-reports/6508d1cc-f141-4bb1-9f22-5a57832dfb16/export`. Сформирован 2026-11-13T05:26:52Z на бою 1.6.7-rc.30 (коммит `4e84921b0d`), запустил оператор вручную перед финальным тегом.
- База: PostgreSQL 18.6, объём 27.6 GiB (перед 1.6.7 — 22.4 GiB).
- Снимок только на чтение. Мутаций при подготовке файла не было.

## 2. Вердикт гейта

`db-audit-gate.sh --report <отчёт> --mode warn`: норма 11, внимание 8, нарушение 0, нет данных 0. Отчёту 0 часов. Режим предупреждения (правило 1.6.5): выпуск не блокируется.

Нарушение `backup-freshness` из аудитов 1.6.6 и 1.6.7 закрыто: критерий теперь учитывает внешнее покрытие (`vm-pbs`, ночной снимок ВМ) и даёт «норма».

## 3. Рост базы на 5,2 GiB за пять дней — причина найдена и устранена в 1.6.8

С 10.11 таблица `secret_access_events` получала 1,5–3,6 млн строк в сутки вместо примерно 200 тыс. (6,2 GiB с индексами на момент аудита). Причина — сверка слотов шлюза, пришедшая с 1.6.7-rc.17: на каждом проходе она опрашивала до 64 завершённых прогонов агента и для каждого опроса заново разрешала секреты агента, по строке аудита на секрет. Исправление OPE-12890 входит в 1.6.8: секреты разрешаются один раз за проход, подтверждённо закрытые прогоны повторно не опрашиваются.

Факт на бою: до исправления 2500–8500 строк в минуту, после выката 1.6.7-rc.29 — 40–170 в минуту, через 10 минут после выката 1.6.7-rc.30 — 523 строки за 10 минут.

Штатная очистка по сроку хранения (30 дней) за таким потоком не успевала; после исправления она догонит сама. Место в файлах таблицы само не вернётся — контрольный замер и возврат места в OPE-12979.

## 4. Предупреждения

| Критерий | Значение | Порог | Что делаем |
|---|---|---|---|
| db-size | 27.6 GiB | ≤ 8.0 GiB | причина роста устранена (раздел 3); возврат места и сроки хранения — OPE-12979 |
| growth-24h | +8.80 % (920 KiB за 0.0 ч) | ≤ 5 %/сутки | ложное: окно измерения нулевой длины сразу после перезапуска доски (раздел 5) |
| cache-hit | 94.9 % | ≥ 99 % | следствие размера базы; вместе с ним — OPE-12979 |
| unused-indexes | 658 из 1208 (54.5 %), 410 MiB | ≤ 20 %, ≤ 512 МиБ | объём уже в пороге (перед 1.6.7 — 628 MiB); удаление миграцией продолжается — OPE-12580 |
| dead-tuples | execution_workspaces: 16.4 % | ≤ 10 % | причина и настройка autovacuum по таблице — OPE-12979 |
| autovacuum-vacuum / analyze | 0.2 / 0.1 | ≤ 0.05 | настройки базы — через предложение и окно обслуживания, OPE-12979 |
| work-mem | 32.0 MiB | ≤ 16 МиБ | пересмотреть значение сервера или порог критерия — OPE-12979 |

Ни одно предупреждение выпуск не блокирует: гейт в режиме предупреждения, правило 1.6.5.

## 5. Замечания к самому автоотчёту

- Критерий `growth-24h` сразу после перезапуска доски считает рост по окну нулевой длины («920 KiB за 0.0 ч») и даёт предупреждение после каждого выката. Нужен минимум окна — OPE-12979.
- Единицы `work_mem`, отмеченные в аудите 1.6.7, исправлены: значение показано как 32.0 MiB.
- Критерий `pgvector-indexed`, ошибавшийся в 1.6.7, исправлен: «1 из 1».

## 6. Вывод

Аудит принят оператором: нарушений нет, предупреждения выпуск не блокируют. Главная находка — рост базы из-за записи аудита секретов — исправлена в самом выпуске 1.6.8 и подтверждена замером на бою. Финальный тег `myr-v1.6.8` разрешён.
