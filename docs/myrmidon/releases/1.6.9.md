# Release 1.6.9 — operator notes

> Russian version: [1.6.9.ru.md](1.6.9.ru.md)

This page is for the operator upgrading a board to 1.6.9, a fix release after 1.6.8. It describes the release built from the code of candidate 1.6.9-rc.5 (tag `myr-v1.6.9-rc.5`, release branch `rel/1.6.6-fixes`): what changed, what is on by default, and what needs a switch or a check. The changelog section
([../CHANGELOG.md](../CHANGELOG.md), "1.6.9") has 60 entries; here is what changes what the operator sees or does, each traced to its entry
(task number or label in brackets). The full deploy procedure is [../deploy.md](../deploy.md); the board's environment variables named below are listed with defaults in
[../SETTINGS.md](../SETTINGS.md). Almost all of the release is one thing: on the first day after 1.6.8 the board spent a large share of its runs on wakes that
changed nothing (pickups of a task the agent kept handing back, reviewers woken onto an unfinished or red CI, tasks returned from review on the first finished job). 1.6.9 closes those paths. Candidate rc.4 added eleven fixes for defects found on rc.2 and rc.3 (an agent card edit under a running run, the pause and resume of agents, the age of a queued run after a pause, the CI summary of a replaced run, the review stage in the task context, a blocked reply of the content filter). Candidate rc.5 adds 36 more entries: a plan gate and a run cap for engineering tasks, an optional starter-pack scout, review hand-off fixes, handling of closed tasks, bot-disk and git-mirror settings, a shorter host clone cleanup, and omp runner fixes. All of it is in the sections below.

## Operator actions at the update

Do these in addition to the usual deploy.

1. **Deploy as usual, all components from one tag**
   ([../deploy.md](../deploy.md), "Deploy the board and the release components together"). The entries of this release name no new required setting and, for the CI-delivery change (EMPTY-RUNS-3), no database migration. The one host-side change is the cleanup of closed-task clones (item 5).
2. **Check what you tuned on 1.6.8.** If you raised or lowered `general.swarm.cooldownCeilingHours` to work around repeated pickups, review it: the task cooling now
   also catches a task that its agent keeps handing back (EMPTY-RUNS-1), and the default ceiling is 24 hours.
3. **Expect bots to switch images after their runs.** Agent card edits that need a gateway restart or a recreated bot container, and an image roll-out by `bot-image-rollout.sh`, now wait for a bot's running run to end (BOT-PROFILE-NO-RUN-INTERRUPT); the content-filter retry (CONTENT-FILTER-RETRY, and its per-call counting CONTENT-FILTER-RETRY-PER-CALL) is part of the bot image (hermes patch 36) and works for a bot only after its image is rolled out. The `myr-handoff` command (PF-HANDOFF-REVIEW) is added to the bot-runtime image, and the neutralised RFC 2119 line (OMP-PROMPT-AGY-429), the orphan reaper (OPE-13105) and the `--reference` clone wrapper (OPE-13113) are in the omp runner images, so they reach a runner only with a rolled-out image.
4. **Know the new defaults that change what agents do.** The plan gate (PF-PLAN-GATE, OPE-13081) holds `size:M` / `size:L` engineering tasks without a `plan` document in planning mode until the plan is approved. A task is blocked after 4 consecutive runs without a new commit (`general.processes.taskRunsWithoutCommitLimit`, `0` = off; PF-RUN-CAP-NO-COMMIT). Developers' task sessions now resume between runs (OPE-13087). The starter-pack scout is off until `general.starterPackAgentId` is set (OPE-13095).
5. **Check the host cleanup schedule.** The default clone TTL of the host cleanup (`CLONE_TTL_HOURS`, `--clone-ttl`) is now 3 hours and its systemd timer runs every 30 minutes, `OnCalendar=*-*-* *:10/30:00` (OPE-13104). The changelog entry does not say how an already installed timer unit is replaced; check the timer on the host after the deploy.
6. **After the deploy, run the checks in "How to check after the update"** below. The first one matters most: the GitHub App wake of a finished CI had been
   dropped in the api processes and begins to work for the first time.

## CI results and returns from review

- **Final result only (EMPTY-RUNS-3).** The GitHub App events used to treat every finished job as a finished CI: the task monitor was disarmed, the assignee woken
  (`ci_completed`) and a task in review went back to its executor on the first job that ended. On 13.11 that was 48 returns from review, 45 of them on a single
  `check_run`; one such run made 139 model calls to answer "main is red, nothing to change". Now only the delivery with the final result of the current head counts: the
  finished `CI result` check (cancelled, skipped or stale does not count) or, for a pull request without that check, the moment GitHub shows every check finished.
  A job that ends changes nothing. The result is recorded as `lastCompletedCi`, announces a possible merge when green, disarms the monitor and wakes the assignee
  once per result; the same result delivered again wakes nobody, and a result of an older head decides nothing.
- **Red main (EMPTY-RUNS-3).** A task in a pending review stage goes back to its executor on a failed final result, with the failed checks named in the comment. A failed
  result with `main-green` red on the head is a failure on a red base branch: the task stays in review, the executor is not woken, a system note says why and the
  `ci_infra_retry_needed` row is written, once per head. When main is green again the "Main green gate" workflow re-runs `main-green` on open pull requests; a head
  that is still red is then returned with the instruction to re-run the failed jobs first. A head on which only `CI result` failed is held the same way. When GitHub
  cannot be read, a failed final result returns the task without the list of checks.
- **Wakes now reach the queue (EMPTY-RUNS-3).** The App webhook is served by the api processes, and the event service there had been given a stub instead of a
  wake function: not one `ci_completed` wake was recorded for 54 returns from review. An api process now enqueues the wake through a heartbeat service of its own role,
  and every wake of a delivery is sent after the transaction of the delivery has committed.
- **Deadlocks (EMPTY-RUNS-3).** A dozen jobs of one pull request finishing within a second killed each other's deliveries (`deadlock detected`, 15 times in an hour, 14 answers
  500 of `POST /api/myrmidon/github-app/webhook`, the event lost). Deliveries of one pull request now run one after another; a transaction rolled back for a
  deadlock (`40P01`) or a serialization failure (`40001`) runs again, up to four runs in all. The reason of a failed query (the Postgres code and text) is now in the
  request log and in the delivery's `lastError`.
- **One wake per result (EMPTY-RUNS-3B).** A head that has a `CI result` check counts only when it is finished and not skipped, cancelled or stale; a partial run (a label event, an auxiliary workflow) whose `CI result` is skipped no longer wakes anyone. The "every check finished" fallback is used only for a head with no `CI result` at all. One result of one head wakes once whatever event carries it (`check_run`, `check_suite`, `workflow_run`): the handled result is kept as `ciVerdictHandled` and, unlike `lastCompletedCi`, is not cleared when a job starts; a failed result clears it, so a green one after a re-run is news again. The `ci_completed` wake of a task in review goes to the participant of its pending review stage, not to the assignee; a task in review without a pending stage wakes nobody.
- **Cancelled checks of a replaced run (CI-SNAPSHOT-CANCELLED).** Adding the `full-ci` label or re-running used to replace a running CI, and the cancelled checks of the old run made the CI summary that the board gives agents (`ciResult`, `pullRequestsCi`) show a false FAILURE. Now each check name is counted by its latest record on the head, and the last finished record with a verdict represents it. A check whose latest record is `cancelled` and has no replacement is reported as "cancelled, not a test failure": the conclusion is `cancelled` (neither `failure` nor `success`) and the check is listed in the new field `cancelledJobs`; `failedJobs` keeps only real `failure`, `timed_out` and `action_required`. A later `skipped`, `neutral` or `cancelled` record never hides an earlier verdict of the same check: a real failure stays FAILURE. A successful `CI result` with no real failures gives `success` and absorbs only the cancelled checks of its own workflow run; a cancelled required check of another run keeps the summary `cancelled`. Agents now see the cancelled checks listed separately in the task text.
- **Switches.** `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED=off` brings back the old handling (and, in an api process, the dropped wake); `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED=off` removes the
  holds, so every failed final result returns the task; `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` without `main-green` removes the base-branch hold.

## Fewer empty wakes

- **A parked task (EMPTY-RUNS-1).** On 13.11 a third of all runs (258 of 780 in eight hours) were `swarm_matched` / `idle_pickup` pickups and 217 of them changed nothing:
  the agent took its own `todo` task, wrote "no new data" and handed it back. The rewake throttle no longer counts that hand-back (the move `in_progress` → `todo` and the
  comment next to it) as progress, and the task cooling no longer takes "advanced" as proof for a task in `todo`. After two such runs the pause grows; after six
  the task is frozen and the lead is asked. The cooling steps are 30 minutes, then 60, 120 and so on up to `general.swarm.cooldownCeilingHours`; the cooling list shows the
  reason `no_progress`. A user or another agent moving the task lifts the cooling; tasks in `in_progress`, `in_review` and `blocked` are judged as before.
- **Monitor waiting for a pull request (EMPTY-RUNS-4).** When CI of the current head had finished and the agent had seen it, the monitor still woke the agent with `no_signal` every
  30 minutes. That state is now `settled`: the monitor re-arms silently (`issue.monitor_deferred`, reason `pr_wait_unchanged`) with a growing interval, capped at 60 minutes.
  The agent is still woken at once for news (merged or closed, a review submitted, a merge conflict, CI completed again) and, as a last backstop, after 6 quiet hours. A pull request the board holds no check data for is still woken after 30 minutes.
- **Queued run (EMPTY-RUNS-6).** A run older than `general.processes.queuedRunStaleAfterSec` (30 minutes) used to be cancelled and, after two such cancellations in a row, the
  task was frozen with "2 runs without progress" although no run had started. A run that waits only because of its own agent's concurrency ceiling (wait reason
  `agent_concurrency`, the agent has a run in `running`) now stays in the queue and starts when a slot frees. A reassigned or closed task still cancels it; other waits expire as before. (EMPTY-RUNS-6B) The protection used to end the second the agent's last run ended: the age sweep then cancelled the waiting run with `queued_run_stale_timeout` and a replacement started with that reason instead of the original wake reason (on 13.11 a `ci_completed` wake was replaced this way after a 48-minute wait). The wait is now counted from the end of the agent's last started run when that is later than its start, so a run whose slot freed just now is kept and starts with its own wake reason and data. A slot that has been free for the whole threshold without the run starting is a lost start and expires as before. Limit of 6B: the protection held only while the wait reason stayed `agent_concurrency`. (EMPTY-RUNS-6C) In the pass that frees the slot the start sweep takes the heaviest waiting run and renames the wait of the agent's other ready runs to `priority`; the age sweep of the same second then cancelled them with `queued_run_stale_timeout` and the replacements lost the original reason (`pause_resume`, `execution_changes_requested`) and context. Now `priority` counts as the same wait for the agent's own slot: such a run is kept while the agent has a `running` run and for the threshold after the end of any started run of the agent (succeeded, failed or cancelled), and starts with its own wake reason and data. A run that does not start with a free slot for the whole threshold, and every other cancellation reason (reassignment, closed task), are unchanged. A wait that a start pass changes to `agent_fair_share` or `higher_priority_ready` is still not protected. The start order is by priority weight, not first come first served; that is unchanged.
- **Reviewer wakes (EMPTY-RUNS-2, EMPTY-RUNS-2B).** The hand-off to review does not wake a reviewer while the head is not green. Two paths ignored that. The executor's closing
  comment, posted seconds after the hand-off, woke the reviewer past the gate; it is now held back (an `issue.review_comment_wake_deferred` row is written, the comment stays in the thread) when the task is
  in a pending review stage, the author is the agent that handed it over, the "Review CI wait" monitor is armed and the head is not admitted. A person's comment, an @-mention, a critical task, a green head and any
  comment after the reviewer was admitted wake as before. And the "Review CI wait" monitor woke the reviewer onto the same red head ten minutes later; it now re-arms
  while the finished head is red (`issue.monitor_deferred`, reason `review_head_red`, next check in ten minutes), bounded by the CI-wait budget of a review stage
  (18 ticks), after which the reviewer is woken as before. `MYRMIDON_REVIEW_COMMENT_WAKE_GATE_ENABLED=off` turns the comment gate off. (EMPTY-RUNS-2C) The idle pickup of a review participant had checked only a stored pending or unknown CI state; it now reads the CI of the head as it is and applies the same admission rule: while the head CI is unfinished, unreadable or red the reviewer is not picked up (a critical task is). A failed read wakes as before; the same switch turns it off.
- **Gateway slot reconcile (OPE-12984).** When the gateway is unreachable, the pass of `gateway-slot-reconcile` ended only after probing up to 64 finished runs one by one (a timeout each) and the
  start of a run waited for all of them. The first `unreachable` answer now ends the pass.

## Agent cards, pauses and content filter

- **A card edit under a running run (BOT-PROFILE-NO-RUN-INTERRUPT).** An edit that has to stop a bot gateway (a restart-class profile change, an image or resource drift) used to open a maintenance window, wait for the agent's run to drain and, at the deadline, interrupt it ("Interrupted by maintenance mode"). Now, with a run in flight, the board changes nothing, opens no window and applies the change after the run ended (the record is in `myrmidonBotRolloutDeferred`; the activity shows "bot container update deferred"). This covers the periodic pass (card edits, including the card image edit of `bot-image-rollout.sh`), "Apply now", key rotation and the chat command. The check is repeated under the window to close the race with a run admitted in between. A deferred change that has waited past `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (6 hours by default) is applied with a drain, which interrupts the run, so a bot that never frees up converges. An unhealthy gateway is recovered at once. The image roll-out wave, the canary and the rollback apply at once with a drain, as before. The deferred-rollout watcher now reads the run table instead of the window view, and a record's clock survives a change of its target image. Of `runtimeConfig.heartbeat`, only `maxConcurrentRuns` reaches the gateway config; it is still a restart-class change, now deferred under a running run, and the other fields change no hash. What the operator notices: a card edit on a busy bot takes effect after its run, not at once; a bot that stays busy for the whole wait limit is restarted at its end.
- **Resuming after a pause (RESUME-AFTER-CANCEL).** When the operator cancelled an agent's runs and the board restarted, the recovery actions were closed with a "do not replay" outcome, and lifting the pause woke the tasks as system wakes that were parked as `execution_reconciliation_required`: each task needed a manual wake. Now lifting the pause is recognised as the operator's action: the wake stays a system wake (no bypass of the rewake freeze, the wake-storm guard or the worktree cutoff) but passes the hold, and retires it, when the run holding it is `cancelled` (operator cancel, queue removal). A hold of a `failed`, `timed_out` or `interrupted` run (unknown outcome), a hold that names no run or a purged one, a run still running, automatic and system wakes and `retry_failed_run` stay held. A queued run of a paused agent is no longer expired by the queue-age sweep (`queued_run_stale_timeout`): it waits for the resume and then starts with its own wake reason. Before, the sweep cancelled it and the replacement wake failed with 409 "Agent is not invokable", so nothing continued the task after the resume. The sweep's page of 200 rows also leaves out the runs of paused agents, so a mass pause does not crowd out the expired runs of other agents.
- **The age of a queued run after a pause (RESUME-QUEUE-AGE).** On candidate rc.3 on the live board, a run queued while its agent was paused was cancelled as stale (`queued_run_stale_timeout`) right after the pause was lifted, if the pause had lasted longer than `general.processes.queuedRunStaleAfterSec` (30 minutes): there were two such cancellations 11–19 seconds after the resume. The pause counted as waiting time in the queue, and the protection against the cancellation did not yet see any running run of the agent. Now, when a pause is lifted, the agent's queued runs get a timestamp `queueWaitResumedAtMs` (in the run's `context_snapshot`), and the age of the wait is counted from it: the time of the pause is not part of it. Writes of the wait reason (`waitReason`, queue position) now add to the run context instead of overwriting it, so the timestamp is not lost. The operator has nothing to do.
- **A content-filtered reply (CONTENT-FILTER-RETRY).** When the model provider cut a reply off with `finish_reason: content_filter` (an HTTP 200 reply, even for harmless work text), the bot ended the run at once with `content_policy_blocked` and the board restarted the task from the start: 58 engineer runs (675 minutes) in 7 days. The bot now re-issues the same model call up to twice per run, keeping the session and the work done so far. This applies only where the run used to fail at once: a bot with a configured fallback model still switches to it as before, and the re-issues leave room for those switches. A refusal that outlasts the re-issues ends the run as before, and the failure text says it repeated. The HTTP 4xx path (`content_policy_blocked` as an error) is unchanged. It is hermes patch 36 and takes effect when the bot image is rolled out; whether a re-issued call passes the provider's filter is not known in advance, each re-issue costs a model call. (CONTENT-FILTER-RETRY-PER-CALL, OPE-13076) The re-issue now has its own counter for each model call (at most 2 per call) and no longer consumes the turn's shared `restart_count` (limit `api_max_retries`); before, the retries competed with other restart reasons, so a turn with several filtered calls could end early. A bot with a fallback model chain still switches to the fallback first.

## The review stage in the task context

- **The stage is visible to the participant (REVIEW-STAGE-IN-CONTEXT).** Reviewers woken by CI, an idle pickup or an operator answered "executionStage=null, there is no active participant" and refused to record a decision although the stage was pending and they were its participant (OPE-12886, OPE-12906, OPE-12941): `executionStage` was built only for the wakes of the stage itself, and `GET /api/issues/:id/heartbeat-context` carried none. The response now has a top-level `executionStage` built by the same function: stage id and type, state, current participant, return assignee, last decision, allowed actions, `isCurrentParticipant` and a one-line `youAre`. The current participant gets `wakeRole: "reviewer"` (`"approver"`) and the actions `approve` and `request_changes`; the executor of a returned stage gets `"executor"`; anyone else gets `"observer"`, no actions and the text "You are not a participant of the review stage". The field is `null` only when no stage is in flight.
- **The approval is recorded (REVIEW-APPROVAL-RECORDED).** On rc.2 the approval of a reviewer was refused with HTTP 409 (`issue_done_pull_request_gate`), the stage stayed `pending` or fell to `idle`, and recovery blocked the task (OPE-13059, OPE-13061). When the move to `in_review` routed a reviewer and then deferred the reviewer's wake (CI wait or the per-tick wake quota), the admission monitor policy was built from the policy as it was before the routing and overwrote the stored policy with `stages: []`; the participant's `done` then met a stage that no longer existed in the policy. The wake that started the run did not matter. The monitor policy is now built on the policy as stored after the update and the routing. The approval of the current participant of a pending review stage is also recorded when the policy has lost the stage or is gone altogether: the stage completes with an approved decision, and with an open pull request the task waits for the merge as usual. Tasks already in that state need no manual repair; the approval needs a comment, as before.

## Plan gate, run cap and starter pack

- **Plan gate (PF-PLAN-GATE, OPE-13081).** Engineering issues labeled `size:M` / `size:L` without a `plan` document now start in planning mode and need an approval bound to the plan revision before implementation. An update moves an issue to planning only while it is in `backlog` or `todo` and its labels or assignee actually changed; work already started (`in_progress`, `in_review`) is never returned to planning, and an explicit `workMode` on create is kept. The approver is the first invokable `lead` / `architect` agent in the executor's manager chain, then any such agent of the company, then the agent `adm`; the board always sets the approver and rejects a plan request that its author would approve. While the plan approval is pending, no run of the assignee starts for any wake type (comment, interaction, automatic continuation); only the resolution of the plan approval card itself passes the gate. The entry names no switch.
- **Runs without a commit (PF-RUN-CAP-NO-COMMIT, OPE-13080).** When consecutive completed runs on an issue do not advance the PR head commit, the cap `general.processes.taskRunsWithoutCommitLimit` (default 4, `0` = disabled) stops them: automatic continuations and re-wakes are skipped, the task goes to `blocked` with the recent run summaries and the PR head SHA, and the project lead (or the assignee's manager, or `adm`) is woken with the details. The counter resets on a new commit in the PR branch or when a person moves the task from `blocked` to `todo` / `in_progress`; comments and other edits do not reset it.
- **Run-guard stop (OPE-13098).** When the run guard permanently halts an engineer's task ("needs new inputs"), the signal `run_guard_stop_needs_input` goes up the `reports_to` chain (up to 5 steps, cycle-guarded) to the nearest invokable `lead` or `architect`; reviewers are skipped because they do not author or slice tasks. With none found it goes to `adm`, and execution dispatch lets only that agent run on the stopped task.
- **Starter-pack scout (OPE-13095).** New instance setting `general.starterPackAgentId`, empty by default. When set, a newly created task of an engineer wakes that scout first (wake reason `starter_pack_scout`) instead of the assignee. The scout only reads the code and may write exactly one document, `starter-pack` (any other key is still refused with 403). Right after the document is saved, and as a fallback when the scout's run ends without it (any run status), the board wakes the assignee with the usual `issue_assigned` wake, once per task; there is no timeout, the end of the scout's run is the signal. The scout is not used when the setting is empty, the task already has a `starter-pack` document or the heading `### Стартовый пакет` in its description, or the assignee is not an engineer. The wake diagnostic shows `starter_pack_scout` instead of `other`.
- **Starter pack in the wake (STARTER-PACK-V1).** A task document with the key `starter-pack` is delivered to the assignee as a separate block, `Starter pack (start here; do not re-explore the project):`, at the start of the wake prompt, ahead of the continuation summary. The body is capped at 8000 characters (a longer one ends with `[starter pack truncated]`) and passes the same source-trust redaction as the continuation summary. An isolated reviewer run does not get it.
- **Developer sessions and memory (OPE-13087, DEV-SESSION-RESTORE, OPE-13096).** Developers (engineers and code reviewers) get no Hindsight memory, but their task session continues between runs. The forced reset on every developer run is removed: a run resumes the saved task session under the strategy on the card (`issue`, `run` or `none`); an agent-wide (`agent`) or empty strategy becomes `issue`. A wake that asks for a fresh session, a changed configuration and a long-task plan still start a new session. For developer roles (`developerRoles`, for example `engineer`, `reviewer`, `release`) the Hermes profile compiler now leaves `memory.provider: hindsight` out of `config.yaml`; other roles keep a byte-identical profile.

## Reviews, hand-offs and closed tasks

- **Hand-off without a review stage (OPE-13099).** An engineer's `PATCH {status: "in_review"}` on a task with no review path (no review stage, card, approval, human assignee or monitor) used to get 422 `missing: review_path`, which is why instructions carried a hand-made "reviewer by PR number modulo 6" rule. Now, with review routing enabled and a task that is not `human_only`, the board adds a review stage to the existing policy when the executor is an engineer. The participants are the invokable reviewers of the executor's own group (the author and assignee excluded), and the usual transition picks the least loaded one as the current participant in the same write. With no reviewer in the group, or for a non-engineer executor, nothing is added and the 422 stays. A task that already has a stage, a re-submission after `changes_requested`, and requests from the board or a user behave as before.
- **`myr-handoff` (PF-HANDOFF-REVIEW).** The bot-runtime image has a new command, `myr-handoff` (`docker/bot-runtime/myr-ws/myr-handoff`): it pushes the current branch, creates or reuses a GitHub PR with the issue key in the title, sets the issue to `in_review` with a summary comment through the Myrmidon API (the board picks the reviewer) and verifies the PR binding of the work product.
- **Verdict as a comment (OPE-13115).** A comment starting with `APPROVE` or `REQUEST CHANGES` from the current review-stage participant on an `in_review` issue is rejected with HTTP 422 and a hint to use `PATCH /api/issues/<id>`; before, such a verdict stalled the stage silently. Ordinary comments of reviewers, other comments and comments of operators or other agents are unaffected.
- **Request for changes with a lost stage (REVIEW-CHANGES-LOST-STAGE).** When the stage definition was lost from the policy (for example the policy monitor overwrote it with an empty array), a reviewer's `changes_requested` was rejected or cleared the execution state with no decision recorded. It is now recorded against the active pending stage: the review round count grows, the issue returns to `in_progress` and the assignment goes back to the `returnAssignee`.
- **A reviewer who ends without a verdict (OPE-13070).** When a reviewer run started by a CI completion ends with no verdict (the stage stays `pending`), the liveness pass of the review routing sweep wakes the idle reviewer again once `REVIEW_WAKE_STALE_AFTER_MS` has passed since the task's last update; later passes keep `REVIEW_WAKE_RETRY_BACKOFF_MS`.
- **Reassignment (OPE-13097).** When an issue is reassigned and its execution lock is held by a not-started `queued` or `scheduled_retry` run of the previous assignee, that run is cancelled (`lock_released_on_reassignment`) before the new assignee is woken, and the new wake is queued at once instead of waiting in `deferred_issue_execution`. Runs of the current review participant and running runs are not touched.
- **Red CI wake (OPE-13078).** When an engineer is woken by a failed or timed-out CI (`ci_completed`), the wake payload and prompt carry the names and ids of the failing jobs and a ready command (`gh run view <run> --job <job> --log-failed | tail -80`). When the board's installation token has `actions:read`, they also carry the log tail of the failing jobs (last 60 lines, the window ending at the last `##[error]` line, ANSI stripped, secrets masked; up to 3 jobs fetched at once, at most 12,000 characters in all); otherwise the reason is stated. The masking now also covers `ghs_` / `github_pat_` / `gh[ousr]_` tokens, `sk-` keys, `Authorization:` values, passwords in URLs and AWS keys. The line "Do not poll CI: the failing output is below" appears only when at least one job has a log tail.
- **Retry after maintenance (OPE-13077).** The retry of a run interrupted for maintenance used to get a short Russian instruction with no times and no branch (55 of 88 such retries on 13–14 Nov started over). It now comes in English, names the interrupted run and the window, gives the start time, the interrupt time and the run time, names the task branch and the head SHA when the board knows them from the issue's PR work product, and tells the agent to run `git status` and `git log --oneline -5`, read the latest comments and continue. Regular wakes (`issue_assigned`, `ci_completed`) do not get the block.
- **Closed tasks (CLOSED-TASK-COMMENT-RUN, CLOSED-TASK-COMMENT-RUN-2, OPE-13068).** A comment wake on a task already `done` or `cancelled` no longer lets the assignee's queued run start and fail in `buildExecutionContinuation` with an error-level log: it is cancelled at claim with `issue_terminal_status` (info log, no `failed`). A run taken from the queue before the task was closed, or one that bypassed the queue check with `resumeIntent`, is cancelled in the same way during preparation (`issue_terminal_status`, or `issue_assignee_changed`). Comment wakes of non-assignees, explicit resume intents and pending card answers behave as before. A queued run cancelled because its task reached a terminal status no longer produces a replacement wake with `queued_run_stale_timeout` (that loop created and cancelled runs for closed tasks endlessly); the replacement is made only when the cancellation really was `queued_run_stale_timeout`.
- **Issue API validation (ISSUES-LIST-BAD-ID).** `GET /api/companies/:companyId/issues` checks `participantAgentId`, `projectId`, `workspaceId`, `executionWorkspaceId` and `labelId` as UUIDs and answers 400 instead of a PostgreSQL 22P02 error; the task references `parentId`, `parentIssueId`, `descendantOf` and `createdFromIssueId` resolve issue identifiers first and give 400 for malformed values; a repeated (array) value gives 400 naming the parameter instead of a 500. `POST /api/companies/:companyId/issues` checks that `projectId`, `parentId`, `assigneeAgentId`, `labelIds` and `goalId` exist and answers 422 instead of a foreign-key error.
- **Worker log (OPE-13117).** In a split deployment (`general.processes.mode = split`) the worker logged "run start dispatch requested a remote start but no process bus is wired" 10–40 times a second for agents with one running and one queued run: the dispatchers built for routes and services did not know they run in an executor process. They now do, so the executor starts the run itself. The line is written once per process, later ones go to `debug`. An event-triggered dispatch is skipped for an agent already running as many runs as its limit allows (the end of its run dispatches again); the sweep and run-finish paths are unchanged. The dispatcher reads its settings at most once per 5 seconds.

## Bot containers, bot disk and host cleanup

- **Unhealthy container with a live run (BOT-HEALTH-LIVE-RUN).** On 14.11 the health probe (`curl /health`, 5 s) timed out under host load and Docker marked live bots `unhealthy`; the board restarted them and cut two runs (`myrmidon_maintenance_interrupted`). Now, when the container is `unhealthy` but the agent has a running run whose newest progress (run event, output flush or useful action) is younger than 120 s, recovery waits for the next pass and the activity log says "health recovery deferred: live run". A silent run, or no run, is recovered as before. The window is `MYRMIDON_BOT_HEALTH_LIVE_RUN_GRACE_SEC` (default 120, `0` = off).
- **Disk fill seen by botd (OPE-13107).** On 14.11 a reviewer bot's `disk-state.json` said `partitionPercent: 0`, `pressure: none` while the bot XFS volume was at 86% (threshold 85%), so the fast cleanup under pressure never ran: the board answers `0 / none` when it has no partition measurement (dockergate down or its sample stale). The board now marks that answer `partitionMeasured: false`; then botd measures the bot data volume itself (`statfs` of `/workspace`) and derives the level with the default thresholds (85% soft, 90% hard). If the local measurement also fails or shows 0% with used bytes, `disk-state.json` carries a `warning` and botd logs it. A measured board answer is never overridden. The copy of a review participant is released when its review is over: a task row of a bot that is not the assignee is closed only when the bot took part in a review stage of the task and is neither the current participant, nor the return assignee, nor the assignee; the executor's copy is kept until the task returns to it; a dirty or unpushed copy is still archived by botd.
- **Git mirror in the bot disk settings (OPE-13116, OPE-13110).** The panel has a switch for the git mirror, shows the effective list of repositories (with a "default" badge) and the roles that receive the shared mirror; turning the switch off explicitly clears the mirrored repositories. `GET /api/myrmidon/bot-disk` now also returns `effective`: `gitMirrorEnabled`, `gitMirrorRepos`, `gitMirrorReposIsDefault` and `sharedCacheRoles`. `PATCH /api/instance/settings/general` merges `botDisk` by key: a request naming only `scratchTtlHours` no longer erases the stored `gitMirrorRepos`; an absent key changes nothing, `null` clears the block. The default of `gitMirrorRepos` is the two built-in repositories (not "no mirrors"); an explicit `[]` is now stored and turns the mirror off, while an absent key (or `null`) means the default list. Only the `sharedCacheRoles` roles receive the mirror, and `<cache>/git` must belong to the board's process user (uid 1000 in production), otherwise new mirrors fail with EACCES (SETTINGS.md).
- **Old git bases (OPE-13118).** Bot bases under `/data/hermes/.myrmidon/git-base/<owner>/<repo>.git` (72 of 126 had no `objects/info/alternates`, 14.3 GiB of duplicated objects) now attach to the fleet mirror `/cache/git`: `findMirror` falls back to a case-insensitive scan when the exact path misses (17 wellboard bases had none), and the botd git migration writes the alternates (`syncMirrorAlternates`) before the repack and re-migrates a base when the alternates appear or change; `repack -l` then drops the duplicates. The "repack only on an idle bot" fleet lock is unchanged.
- **pnpm store (OPE-13112).** `general.botDisk.pnpmStoreDir` (`/cache/pnpm-store`) was written to the bot's `.env`, but processes still saw the image default `npm_config_store_dir=/workspace/.pnpm-store`, so installs used a per-bot store. The `pnpm` wrapper now reads `npm_config_store_dir` from `${HERMES_HOME}/.env` and uses it when it is an absolute path the bot can write to (the directory, or for a missing one its nearest existing parent). If nothing is set or it is not writable, the store stays `/workspace/.pnpm-store`.
- **Review copy (OPE-13111).** Reviewers held 14–17 full copies of 0.5–1.2 GB each. `myr-ws open <KEY> <owner/repo> --review` now makes a worktree without a working directory (`git worktree add --no-checkout`, empty sparse-checkout, so `git status` stays clean): kilobytes instead of ~0.5 GB, no dependencies installed, git hooks off. The PR branch is fetched first and a stale local branch is fast-forwarded to `origin/<branch>`; if the branch is not on the remote and `--branch` is not given, `open` fails with "no PR branch, pass --branch" instead of opening a copy of main; a local branch with commits not on the remote is not moved (error). The reviewer reads the change by refs (`gh pr diff <N>`, `git diff origin/main...HEAD`, `git show HEAD:<path>`). An already open copy is returned as it is, with a warning; `--review` cannot be combined with `--scratch`; plain `open` is unchanged.
- **Card save with a bad mount (OPE-13074).** Saving or updating an agent card (`POST /api/agents`, `PATCH /api/agents/:id`) with `adapterConfig.container.extraMounts` checks the sources against `MYRMIDON_BOT_MOUNT_SOURCES` (and the UI-saved `bot_mount_sources`). A disallowed source is rejected at once with HTTP 422 naming the source, instead of saving the card and crashing the bot container reconciliation in a loop. A partial update without `extraMounts` does not reject mounts already saved; the reconciler and container build checks stay as a second line against direct database edits.
- **Host cleanup (OPE-13104).** On 14.11 about 73 task clones (36 GB) appeared in 4 hours; with a 24-hour retention and a pass every 2 hours free space on the bot disk jumped by 10–15 GB and HOST_DISK / BOTS_DISK alerts fired several times a day. The default clone TTL (`CLONE_TTL_HOURS`, `--clone-ttl`) is now 3 hours and the systemd timer runs the cleanup every 30 minutes (`OnCalendar=*-*-* *:10/30:00`); the rules that keep active clones and archive dirty ones first are unchanged. A failed archive of a clone or a runner task folder no longer leaves an unfinished `.tar.zst` / `.tar.gz` (before, 1–2 GB per pass); the error text carries the exit code and signal, and a timeout reads "timed out after N s". Archives skip `node_modules`, `.pnpm-store`, `.turbo`, `dist`, `.next` and `coverage` (only build and dependency directories that git ignores); `.git` with unpushed commits and any file git does not ignore stay in. The cause: a 13 GB runner task folder with three repo copies did not fit the 600 s limit on any pass.
- **Terminal-workspace sweep (no entry label).** The sweep now archives `shared_workspace` rows of closed (`done` / `cancelled`) issues without looking at git or the GitHub API: they point at the project's shared directory, which has no per-task copy and nothing to delete. Before, every such row was blocked and an `issue_terminal_archive_blocked` event was written for each (over 180,000 events), loading the board every 30 seconds. The sweep still needs a closed issue tree, the cooldown and no active run, and a copy with an open linked issue is not archived. It works through the backlog in passes of up to 200 rows, each archived by its own single-row update, taken under `FOR NO KEY UPDATE SKIP LOCKED` with a pause between passes (`MYRMIDON_WORKSPACE_SHARED_SWEEP_PAUSE_MS`, 1 s by default), so sweepers in several processes never take the same row twice.
- **Ports without `lsof` (OPE-13075).** Preparing an isolated workspace runtime checked listener ownership with `lsof`; where it is missing, every candidate spawned it again (~32 attempts, ~19 s). The absence of `lsof` is now cached on the first miss (ENOENT / 127) and on Linux the check falls back to `/proc/net/tcp` and `/proc/<pid>/fd`, without accepting unrelated listeners.

## omp_local

- **Model call limit (OMP-RUN-GUARD-1).** An `omp_local` run had no limit of model calls, only `timeoutSec` (3 hours); on 13.11 sessions averaged 101 calls and the longest made 494. The adapter now feeds the board's
  run guard: the limit is the same as for hermes, 150 calls by default, overridden by the agent card `runGuard.modelCallLimit`, team liveness `runGuard` or `MYRMIDON_RUN_GUARD_MODEL_CALL_LIMIT`. Fifteen calls before the limit
  the agent gets the wrap-up message (commit, push, comment on the task); past the limit the adapter stops the process and the run-guard continuation (`run-guard-stop`) decides about the next run. The other guard stops
  (read-only exploration, repeated call, idle) now apply to `omp_local` runs as well. A run stopped over SSH restores its workspace. Expect some long omp sessions to end in a stop and a continuation.
- **Cancelling over SSH (OMP-RUN-GUARD-2).** On 13.11 two sessions kept running on the runner after their run was cancelled (46 and 22 minutes, 337 model calls). The adapter now listens to the run's cancellation
  signal itself and stops the local ssh client; an abort that came before the client was registered is applied when it starts.
- **Workspace upload (OPE-13041).** An upload to a remote runner failed with `ssh exited before tar finished (code 0)` when ssh closed a moment before tar although all data had been delivered. The outcome is now decided by the exit
  codes of both processes (tar gets up to 10 s after ssh exits with 0). The protocol and the layout are unchanged.

- **Prompt line (OMP-PROMPT-AGY-429).** At image build, the line `RFC 2119 keywords: MUST, REQUIRED, SHOULD, RECOMMENDED, MAY, OPTIONAL.` in the system prompt of the bundled `@oh-my-pi/pi-coding-agent` CLI is replaced with `Keywords MUST, REQUIRED, SHOULD, RECOMMENDED, MAY, OPTIONAL follow their usual meaning.`, which avoids the Antigravity / Google 429 rejections triggered by agent fingerprinting. The build fails fast when the target text is missing or altered in a newer package release; CI has regression tests.
- **Orphan processes (OPE-13105).** The omp SSH runner image has `/usr/local/bin/run-reap`. When an agent run ends (success, error, timeout or cancellation), the omp adapter calls `run-reap <task_dir>` on the runner: it ends lingering background processes (such as `@embedded-postgres` or child tools) whose working directory is inside the task workspace, checking `/proc/<pid>/cwd`, sparing system and session processes (`PID 1`, `$$`, `$PPID`, `sshd`), sending `SIGTERM`, waiting up to 5 seconds and then `SIGKILL`. The cleanup runs in a `finally` block, so its failures are logged without changing the run outcome.
- **Clones with a mirror (OPE-13113).** The git wrapper of omp SSH runners (`docker/agent-runtime/omp-ssh/git-reference/git`) used to keep the caller's shallow options when a bare mirror existed in `/cache/git/<owner>/<repo>.git`. Now, with a mirror, it strips `--depth` and `--shallow-*` and adds `--reference-if-able <mirror>`: the clone borrows objects from the mirror, keeps full history through alternates and its `.git` stays under 50 MB. Without a mirror the shallow options stay.

## Stale blocks

- **Stale-block sweep (STALE-BLOCK-LIVE-EDGES).** The board logged "stale block sweep failed for one task" about 50 times an hour for the same 14 blocked tasks. Each had a dead cited reason and at the same time a link to a
  task that is still open. The sweep now counts such an open blocker as a live reason: the task stays blocked and wakes through the ordinary `issue_blockers_resolved` path when the blocker closes. A dead reason whose blockers
  are all closed is unblocked as before. The failure warning now carries the exception class and its HTTP status.
- **An unassigned task (STALE-BLOCK-UNASSIGNED).** A task created straight in `blocked` with a closed blocker and no assignee made the sweep log "stale block sweep failed for one task" (HTTP 422) on every pass and stay blocked for good: the sweep chose `in_progress`, which the issue service refuses for a task with neither an agent nor a user assignee. Such a task now goes to `todo` (the dead edge is removed, the comment says "without assignee"); a task with an assignee returns to `in_progress` as before. The failure warning also carries `errorMessage`: the fixed refusal sentence of the issue service for a 4xx error (at most 120 characters), so the cause of a repeated 422 reads from the log.
- **A task closed before its run started (RUN-SETUP-STALE-TASK).** A run queued by `issue_assigned` waited for the agent's slot while the task was closed and its pull request merged; at start it failed with `setup_failed` / `continuation_task_ownership_changed` and an error-level log line (17 times in 7 days), because the staleness check let any wake with a comment through. Now such a run on a `done` or `cancelled` task is cancelled at claim with `issue_terminal_status` (an info line, no `failed`). Comment wakes, resume intents and pending-card addressees behave as before, and genuine setup failures stay `failed`.

## How to check after the update

These checks come from the pull request descriptions and were not run for this page.

- **GitHub wakes.** Within a day after a CI result arrives for a task in review there is a row in `agent_wakeup_requests` with `requested_by_actor_id = 'system:github-ci'` (it was 0 for three days before) and an executor run. The webhook request does not hang.
- **Deadlocks.** No `deadlock detected` on `issue_work_products` and no 500 from `POST /api/myrmidon/github-app/webhook` in the log.
- **Red main.** With `main` red, no `issue.ci_failed` rows appear for the shards that are red on main; the holds are rows `issue.ci_infra_retry_needed`, and every `issue.ci_failed` row carries `failedChecks`.
- **Empty runs.** The share of `swarm_matched` / `idle_pickup` runs that change nothing falls, and the repeated "stale block sweep failed" line for the same tasks disappears.
- **Card edit under a run (BOT-PROFILE-NO-RUN-INTERRUPT).** Change a restart-class field (for example `maxConcurrentRuns`) of an agent with a run in flight: the run finishes, the activity shows "bot container update deferred", the record is in `myrmidonBotRolloutDeferred`, and after the run the next pass restarts the bot. From the pull request description; not run for this page.
- **CI summary (CI-SNAPSHOT-CANCELLED).** `ciResult` of a task whose pull request had a replaced CI run shows `success`, not FAILURE; a head with only cancelled checks shows `cancelled` with "cancelled, not a test failure"; a real failure still shows FAILURE. Not run for this page.
- **Review stage (REVIEW-STAGE-IN-CONTEXT, REVIEW-APPROVAL-RECORDED).** `GET /api/issues/:id/heartbeat-context` of a task in review has `executionStage`; a reviewer's approval after a deferred wake is recorded and does not answer 409. Not run for this page.
- **Queue slot release (EMPTY-RUNS-6B, EMPTY-RUNS-6C).** The count of `queued_run_stale_timeout` cancellations of runs with `waitReason = agent_concurrency` is zero, and a run that waited for a slot starts with its original wake reason (for example `ci_completed`). From the pull request description; not run for this page.
- **Age of a queued run (RESUME-QUEUE-AGE).** After you lift the pause of an agent that was paused for more than 30 minutes with runs in the queue, there are no `queued_run_stale_timeout` cancellations in the first minutes; the queued runs of this agent have a numeric key `queueWaitResumedAtMs` in `context_snapshot`. Not run for this page.

- **Plan gate and run cap (PF-PLAN-GATE, PF-RUN-CAP-NO-COMMIT).** A new `size:M` / `size:L` engineering task without a `plan` document starts in planning mode with an approver set; a task whose consecutive runs add no commit goes to `blocked` after the 4th and the lead is woken. Not run for this page.
- **Host cleanup (OPE-13104).** The cleanup timer fires every 30 minutes, and clones of closed tasks older than 3 hours are archived or removed; no unfinished `.tar.zst` / `.tar.gz` files remain after a failed archive. Not run for this page.
- **Bot disk settings (OPE-13116, OPE-13110).** The settings screen shows the git mirror switch and the default badge; `GET /api/myrmidon/bot-disk` has `effective`; a `PATCH general` naming only `scratchTtlHours` leaves `gitMirrorRepos` in place. Not run for this page.
- **Review hand-off (OPE-13099, OPE-13115).** An engineer's `in_review` on a task without a review stage is accepted and gets a reviewer; a comment starting with `APPROVE` from the participant answers 422 with the hint. Not run for this page.

Known limits. A real failure on a red base branch is held until `main-green` is green on the head, so it is returned later, not lost. The holds and marks (`ciReturnHold`, `ciFinalCheckSeen`)
live in the work product metadata; if another writer overwrites it whole, the hold is written again and the return after the `main-green` re-run does not happen: the task goes the ordinary review way.
Reading GitHub happens inside the delivery and is limited to 10 seconds.

Known limits of the fixes of rc.4 and rc.5.
- A card edit on a busy bot waits for the end of the run, at most `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (6 hours); after that the run is drained and interrupted. The canary and the rollback do not wait. Which exact edit made the container of the bot recreated on 14.11 was not established (the board log had rotated).
- After a pause, tasks whose run ended as `failed`, `timed_out` or `interrupted` stay held. Not changed: a recovery action closed with the outcome `blocked` while the task stays `in_progress`, and `recovery-actions/resolve` with `restored` answering 200 without effect.
- A blocked reply of the content filter is re-issued at most twice per model call, and only for an agent without a fallback in the way described above; the HTTP 4xx path is unchanged. Since rc.5 the re-issues no longer share the turn's restart counter (CONTENT-FILTER-RETRY-PER-CALL). Whether the provider lets a re-issued call through is not known in advance, and each re-issue costs a model call.
- The approval is recovered for a stage that has left the policy, but a request for changes by the participant in that state is not covered by this fix. A run woken by another agent's comment on a closed task still starts, as before: the closed-task cancellation applies to `issue_assigned` wakes only.
- The comment-wake cancellation on closed tasks applies to the task assignee's runs; comment wakes of other agents, explicit resume intents and pending card answers still start (CLOSED-TASK-COMMENT-RUN).
- The terminal-workspace sweep for shared copies never uses git or the GitHub API, so it takes only the terminal state of the issue tree into account.
- The queued-run protection does not cover a wait that a start pass changed to `agent_fair_share` or `higher_priority_ready`.
- The timestamp `queueWaitResumedAtMs` is set only when an agent's pause is lifted. A maintenance window and a company pause are not covered by it.
