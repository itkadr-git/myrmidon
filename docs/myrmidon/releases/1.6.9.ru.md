# Выпуск 1.6.9 — заметки для оператора

> English version: [1.6.9.md](1.6.9.md)

Страница для оператора, который обновляет доску до 1.6.9 — выпуска исправлений после 1.6.8. Она описывает выпуск, собранный из кода кандидата 1.6.9-rc.5 (тег `myr-v1.6.9-rc.5`, ветка выпуска `rel/1.6.6-fixes`): что изменилось, что включено по умолчанию и что требует переключателя или проверки. В разделе «1.6.9» журнала изменений
([../CHANGELOG.ru.md](../CHANGELOG.ru.md)) 60 записей; здесь — то, что меняет увиденное или сделанное оператором, с отсылкой к записи
(в скобках номер задачи или метка). Полная процедура выката — [../deploy.md](../deploy.md); переменные окружения доски, названные ниже, перечислены с умолчаниями в
[../SETTINGS.md](../SETTINGS.md). Почти весь выпуск — об одном: в первый день после 1.6.8 заметная доля прогонов доски уходила на побудки, которые ничего не меняли (подбор задачи, которую агент
раз за разом возвращал в очередь; ревьюеры, разбуженные на ещё идущий или красный CI; задачи, возвращённые с ревью по первому закончившемуся джобу). В 1.6.9 эти пути закрыты. Кандидат rc.4 добавил одиннадцать исправлений дефектов, найденных на rc.2 и rc.3 (правка карточки агента при идущем прогоне, пауза и снятие паузы агентов, возраст прогона в очереди после паузы, сводка CI после заменённого прогона, стадия ревью в контексте задачи, блокировка ответа фильтром содержимого). Кандидат rc.5 добавляет ещё 36 записей: план-гейт и потолок прогонов для инженерных задач, необязательного разведчика стартового пакета, исправления передачи на ревью, обработку закрытых задач, настройки диска ботов и git-зеркала, более короткую чистку клонов на хосте и исправления раннера omp. Всё это описано в разделах ниже.

## Что сделать оператору при обновлении

Это делается сверх обычного выката.

1. **Выкатывать как обычно, все компоненты одним тегом**
   ([../deploy.md](../deploy.md), «Deploy the board and the release components together»). В записях этого выпуска нет нового обязательного параметра и — для изменения доставки CI (EMPTY-RUNS-3) — миграции базы данных. Единственное изменение на стороне хоста — чистка клонов закрытых задач (пункт 5).
2. **Пересмотреть то, что вы подкручивали на 1.6.8.** Если вы меняли `general.swarm.cooldownCeilingHours`, чтобы унять повторные подборы, проверьте значение: остывание задачи
   теперь ловит и задачу, которую агент возвращает в очередь (EMPTY-RUNS-1), а потолок по умолчанию — 24 часа.
3. **Ждать, что боты переключатся после конца прогонов.** Правка карточки агента, требующая перезапуска шлюза или пересоздания контейнера бота, и перекат образов скриптом `bot-image-rollout.sh` теперь ждут конца идущего прогона бота (BOT-PROFILE-NO-RUN-INTERRUPT); повтор при блокировке фильтром содержимого (CONTENT-FILTER-RETRY и его счёт по каждому вызову CONTENT-FILTER-RETRY-PER-CALL) входит в образ бота (патч hermes 36) и действует у бота только после переката его образа. Команда `myr-handoff` (PF-HANDOFF-REVIEW) добавлена в образ среды ботов, а нейтрализованная строка RFC 2119 (OMP-PROMPT-AGY-429), чистка осиротевших процессов (OPE-13105) и обёртка клонирования с `--reference` (OPE-13113) находятся в образах раннера omp, поэтому до раннера они доходят только с перекатом образа.
4. **Знать новые умолчания, меняющие работу агентов.** План-гейт (PF-PLAN-GATE, OPE-13081) держит инженерные задачи `size:M` / `size:L` без документа `plan` в режиме планирования, пока план не одобрен. Задача блокируется после 4 подряд идущих прогонов без нового коммита (`general.processes.taskRunsWithoutCommitLimit`, `0` = выключено; PF-RUN-CAP-NO-COMMIT). Сессии задач разработчиков теперь продолжаются между прогонами (OPE-13087). Разведчик стартового пакета выключен, пока не задан `general.starterPackAgentId` (OPE-13095).
5. **Проверить расписание чистки на хосте.** Умолчание срока клона в чистке хоста (`CLONE_TTL_HOURS`, `--clone-ttl`) теперь 3 часа, а её systemd-таймер срабатывает каждые 30 минут, `OnCalendar=*-*-* *:10/30:00` (OPE-13104). В записи журнала изменений не сказано, как заменяется уже установленный файл таймера; после выката проверьте таймер на хосте.
6. **После выката пройти проверки из раздела «Как проверить после обновления».** Первая важнее остальных: побудка по завершению CI от приложения GitHub в api-процессах
   отбрасывалась и теперь заработает впервые.

## Результаты CI и возвраты с ревью

- **Только итоговый результат (EMPTY-RUNS-3).** События приложения GitHub считали завершённым CI любой закончившийся джоб: с задачи снимался монитор, исполнителю ставилась побудка
  (`ci_completed`), а задача на ревью уходила исполнителю по первому закончившемуся джобу. 13.11 это дало 48 возвратов с ревью, 45 из них по одному
  `check_run`; один такой прогон сделал 139 вызовов модели, чтобы ответить «main красный, править нечего». Теперь считается только доставка с итоговым результатом текущей головы: завершённая
  проверка `CI result` (отменённая, пропущенная или устаревшая не в счёт) или, если у PR такой проверки нет, момент, когда GitHub показывает завершёнными все проверки.
  Закончившийся джоб ничего не меняет. Результат записывается в `lastCompletedCi`, при зелёном сообщает о возможном слиянии, снимает монитор и будит исполнителя
  один раз на результат; повторная доставка того же результата никого не будит, результат старой головы ничего не решает.
- **Красный main (EMPTY-RUNS-3).** Задача на стадии ревью при красном итоговом результате уходит исполнителю, упавшие проверки названы в комментарии. Красный
  результат при красной `main-green` на голове — это падение на красной базовой ветке: задача остаётся на ревью, исполнитель не будится, системная заметка объясняет причину, а
  запись `ci_infra_retry_needed` пишется один раз на голову. Когда main снова зелёный, workflow «Main green gate» перезапускает `main-green` на открытых PR; голова,
  которая и после этого красная, возвращается исполнителю с указанием сначала перезапустить упавшие джобы. Голову, на которой упал только `CI result`, держат так же. Если GitHub
  прочитать не удалось, красный итог возвращает задачу без списка проверок.
- **Побудки теперь доходят до очереди (EMPTY-RUNS-3).** Вебхук приложения принимают api-процессы, а сервису событий там вместо функции побудки была передана заглушка: ни одной побудки
  `ci_completed` не записалось на 54 возврата с ревью. Теперь api-процесс ставит побудку через сервис пульса своей роли, и каждая побудка по доставке отправляется после того, как транзакция
  доставки зафиксирована.
- **Взаимные блокировки (EMPTY-RUNS-3).** Десяток джобов одного PR, закончившихся в пределах секунды, убивали доставки друг друга (`deadlock detected`, 15 раз за час, 14 ответов
  500 на `POST /api/myrmidon/github-app/webhook`, событие терялось). Теперь доставки одного PR идут по очереди; транзакция, откатанная из-за
  взаимной блокировки (`40P01`) или сбоя сериализации (`40001`), выполняется заново, всего до четырёх попыток. Причина сбоя запроса (код и текст Postgres) теперь есть в журнале
  запросов и в `lastError` доставки.
- **Одна побудка на результат (EMPTY-RUNS-3B).** Голова, у которой есть проверка `CI result`, считается, только если она завершена и не пропущена, не отменена и не устарела; частичный прогон (событие метки, вспомогательный workflow) с пропущенной `CI result` больше никого не будит. Запасной вариант «все проверки завершены» применяется только к голове совсем без `CI result`. Один результат одной головы будит один раз, каким бы событием он ни пришёл (`check_run`, `check_suite`, `workflow_run`): обработанный результат хранится как `ciVerdictHandled` и, в отличие от `lastCompletedCi`, не сбрасывается стартом джоба; красный результат его сбрасывает, поэтому зелёный после перезапуска снова считается новостью. Побудка `ci_completed` для задачи на ревью идёт участнику её ожидающей стадии, а не исполнителю; задача на ревью без ожидающей стадии никого не будит.
- **Отменённые проверки заменённого прогона (CI-SNAPSHOT-CANCELLED).** Метка `full-ci` или перезапуск заменяли идущий CI, и отменённые проверки прежнего прогона давали в сводке CI, которую доска показывает агентам (`ciResult`, `pullRequestsCi`), ложный FAILURE. Теперь по каждому имени проверки берётся её последняя запись на голове, а представляет проверку последняя завершённая запись с вердиктом. Проверка, чья последняя запись `cancelled` и замены нет, показывается как «cancelled, not a test failure»: итог `cancelled` (ни `failure`, ни `success`), проверка попадает в новое поле `cancelledJobs`; в `failedJobs` остаются только настоящие `failure`, `timed_out` и `action_required`. Более поздняя запись `skipped`, `neutral` или `cancelled` не скрывает более раннего вердикта той же проверки: настоящее падение остаётся FAILURE. Успешная `CI result` без настоящих падений даёт `success` и поглощает только отменённые проверки своего же прогона workflow; отменённая обязательная проверка другого прогона оставляет сводку `cancelled`. В тексте задачи агенты видят отменённые проверки отдельным списком.
- **Переключатели.** `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED=off` возвращает прежнюю обработку (и, в api-процессе, прежнюю отброшенную побудку); `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED=off` убирает
  удержания, и любой красный итог возвращает задачу; `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` без `main-green` убирает удержание по красной базовой ветке.

## Меньше пустых побудок

- **Отложенная задача (EMPTY-RUNS-1).** 13.11 треть всех прогонов (258 из 780 за восемь часов) были подборами `swarm_matched` / `idle_pickup`, и 217 из них ничего не меняли:
  агент брал свою задачу из `todo`, писал «новых данных нет» и возвращал её обратно. Тормоз повторных побудок больше не считает такой возврат (перевод `in_progress` → `todo` и
  комментарий рядом) прогрессом, а остывание задачи больше не принимает «advanced» как доказательство для задачи в `todo`. После двух таких прогонов пауза растёт; после шести
  задача замораживается и спрашивают лида. Шаги остывания — 30 минут, затем 60, 120 и далее до `general.swarm.cooldownCeilingHours`; в списке остывающих такая задача идёт с причиной
  `no_progress`. Если задачу сдвинул человек или другой агент, остывание снимается; задачи в `in_progress`, `in_review` и `blocked` оцениваются как раньше.
- **Монитор, ждущий pull request (EMPTY-RUNS-4).** Когда CI текущей головы уже закончился и агент его видел, монитор всё равно будил агента с пометкой `no_signal` каждые
  30 минут. Это состояние теперь называется `settled`: монитор тихо взводится заново (`issue.monitor_deferred`, причина `pr_wait_unchanged`) с растущим интервалом, не больше 60 минут.
  О новостях агент по-прежнему узнаёт сразу (слит или закрыт, оставлено ревью, конфликт слияния, CI завершился снова) и, как последняя страховка, через 6 тихих часов. PR, по которому у доски нет
  данных о проверках, будится через 30 минут, как раньше.
- **Прогон в очереди (EMPTY-RUNS-6).** Прогон старше `general.processes.queuedRunStaleAfterSec` (30 минут) снимался, а после двух таких снятий подряд задача замораживалась с пометкой «2 прогона без
  прогресса», хотя ни один не стартовал. Прогон, который ждёт только из-за собственного предела параллельности агента (причина ожидания
  `agent_concurrency`, у агента идёт другой прогон), теперь остаётся в очереди и стартует, когда освободится слот. Переназначенная или закрытая задача по-прежнему снимает прогон; другие ожидания истекают как раньше. (EMPTY-RUNS-6B) Раньше защита кончалась в ту же секунду, когда заканчивался последний прогон агента: обход по возрасту снимал ждущий прогон с `queued_run_stale_timeout`, и стартовал заменяющий с этой причиной вместо исходной побудки (13.11 так заменили побудку `ci_completed` после 48 минут ожидания). Теперь ожидание отсчитывается от конца последнего стартовавшего прогона агента, если он позже начала ожидания: прогон, у которого слот освободился только что, остаётся и стартует со своей причиной побудки и данными. Слот, свободный весь порог без старта прогона, — потерянный старт, и прогон снимается как раньше. Ограничение 6B: защита действовала, только пока причина ожидания оставалась `agent_concurrency`. (EMPTY-RUNS-6C) В проходе, освобождающем слот, обход старта берёт самый тяжёлый ждущий прогон и переименовывает ожидание остальных готовых прогонов агента в `priority`; обход по возрасту в ту же секунду снимал их с `queued_run_stale_timeout`, а заменяющие прогоны теряли исходную причину (`pause_resume`, `execution_changes_requested`) и контекст. Теперь `priority` считается тем же ожиданием собственного слота агента: такой прогон остаётся, пока у агента есть прогон в `running` и в течение порога после конца любого стартовавшего прогона агента (успешного, упавшего или отменённого), и стартует со своей причиной побудки и данными. Прогон, который не стартовал при свободном слоте весь порог, и все другие причины снятия (переназначение, закрытая задача) не изменились. Ожидание, которое проход старта сменил на `agent_fair_share` или `higher_priority_ready`, по-прежнему не защищено. Порядок старта идёт по весу приоритета, а не по очереди прихода; это не менялось.
- **Побудки ревьюера (EMPTY-RUNS-2, EMPTY-RUNS-2B).** Сдача на ревью не будит ревьюера, пока голова не зелёная. Два пути этого не учитывали. Итоговый комментарий исполнителя,
  написанный через секунды после сдачи, будил ревьюера в обход ворот; теперь он удерживается (пишется запись `issue.review_comment_wake_deferred`, комментарий остаётся в треде), когда задача
  на стадии ревью, автор — агент, сдавший задачу, монитор «Review CI wait» взведён, а голова ещё не допущена. Комментарий человека, @-упоминание, критичная задача, зелёная голова и любой
  комментарий после допуска ревьюера будят как раньше. А монитор «Review CI wait» через десять минут будил ревьюера на той же красной голове; теперь он взводится заново,
  пока завершённая голова красная (`issue.monitor_deferred`, причина `review_head_red`, следующая проверка через десять минут), в пределах бюджета ожидания CI стадии ревью
  (18 срабатываний), после которого ревьюера будят как раньше. `MYRMIDON_REVIEW_COMMENT_WAKE_GATE_ENABLED=off` выключает ворота комментария. (EMPTY-RUNS-2C) Подбор простаивающего участника ревью проверял только сохранённое состояние CI «ожидает» или «неизвестно»; теперь он читает CI головы как есть и применяет то же правило допуска: пока CI головы не закончился, не читается или красный, ревьюера не подбирают (критичную задачу подбирают). Если чтение не удалось, будит как раньше; тот же переключатель его выключает.
- **Сверка слотов шлюза (OPE-12984).** Когда шлюз недоступен, проход `gateway-slot-reconcile` заканчивался только после опроса до 64 завершённых прогонов по одному (по таймауту на каждый), и старт
  прогона ждал их все. Теперь первый ответ `unreachable` завершает проход.

## Карточки агентов, паузы и фильтр содержимого

- **Правка карточки при идущем прогоне (BOT-PROFILE-NO-RUN-INTERRUPT).** Правка, которой нужно остановить шлюз бота (смена профиля с перезапуском, расхождение образа или ресурсов), открывала окно обслуживания, ждала слива прогона агента и в срок прерывала его («Interrupted by maintenance mode»). Теперь, если прогон идёт, доска ничего не меняет, окно не открывает и применяет изменение после конца прогона (запись лежит в `myrmidonBotRolloutDeferred`; в активности видно «bot container update deferred»). Это относится к периодическому проходу (правки карточки, включая правку образа в карточке скриптом `bot-image-rollout.sh`), «Применить сейчас», ротации ключей и команде из чата. Проверка повторяется под окном, чтобы закрыть гонку с прогоном, допущенным между ними. Отложенное изменение, которое ждёт дольше `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (по умолчанию 6 часов), применяется со сливом и прерывает прогон, чтобы бот, который никогда не освобождается, всё же дошёл до нужного состояния. Нездоровый шлюз восстанавливается сразу. Волна переката образов, канарейка и откат применяют сразу со сливом, как раньше. Сторож отложенных выкатов теперь читает таблицу прогонов, а не вид окна, и часы записи переживают смену целевого образа. Из `runtimeConfig.heartbeat` до конфигурации шлюза доходит только `maxConcurrentRuns`; это по-прежнему изменение с перезапуском, теперь отложенное при идущем прогоне, а остальные поля хеш не меняют. Что заметит оператор: правка карточки занятого бота вступает в силу после его прогона, а не сразу; бот, занятый весь предел ожидания, перезапускается по его истечении.
- **Продолжение после паузы (RESUME-AFTER-CANCEL).** Когда оператор отменил прогоны агента и доска перезапустилась, действия восстановления закрывались исходом «не повторять», а снятие паузы будило задачи системными побудками, которые парковались как `execution_reconciliation_required`: каждую задачу приходилось будить вручную. Теперь снятие паузы распознаётся как действие оператора: побудка остаётся системной (обходов тормоза повторных побудок, защиты от шторма побудок и отсечки рабочей папки нет), но проходит удержание и снимает его, если удерживающий прогон `cancelled` (отмена оператором, снятие из очереди). Удержание прогона `failed`, `timed_out` или `interrupted` (исход неизвестен), удержание без названного прогона или с вычищенным, ещё идущий прогон, автоматические и системные побудки и `retry_failed_run` по-прежнему удерживаются. Прогон в очереди агента на паузе больше не снимается обходом по возрасту очереди (`queued_run_stale_timeout`): он ждёт снятия паузы и стартует со своей причиной побудки. Раньше обход снимал его, а заменяющая побудка падала с 409 «Agent is not invokable», и после снятия паузы задачу никто не продолжал. Страница обхода в 200 строк теперь тоже не включает прогоны агентов на паузе, поэтому массовая пауза не вытесняет просроченные прогоны других агентов.
- **Возраст прогона в очереди после паузы (RESUME-QUEUE-AGE).** На кандидате rc.3 на бою прогон, поставленный в очередь, пока агент был на паузе, снимался как устаревший (`queued_run_stale_timeout`) сразу после снятия паузы, если пауза длилась дольше `general.processes.queuedRunStaleAfterSec` (30 минут): были две такие отмены через 11–19 секунд после снятия паузы. Пауза считалась временем ожидания в очереди, а защита от снятия ещё не видела ни одного идущего прогона агента. Теперь при снятии паузы прогонам агента в очереди ставится отметка времени `queueWaitResumedAtMs` (в `context_snapshot` прогона), и возраст ожидания считается от неё: время паузы в него не входит. Записи причины ожидания (`waitReason`, позиция в очереди) теперь дополняют контекст прогона, а не перезаписывают его, поэтому отметка не пропадает. Оператору делать ничего не нужно.
- **Ответ, заблокированный фильтром содержимого (CONTENT-FILTER-RETRY).** Когда поставщик модели обрезал ответ с `finish_reason: content_filter` (ответ HTTP 200, даже на безобидный рабочий текст), бот сразу завершал прогон с `content_policy_blocked`, а доска запускала задачу с начала: 58 прогонов инженеров (675 минут) за 7 дней. Теперь бот повторяет тот же вызов модели до двух раз на прогон, сохраняя сессию и сделанную работу. Это работает только там, где прогон раньше падал сразу: бот с настроенной резервной моделью по-прежнему переключается на неё, и повторы оставляют место для этих переключений. Отказ, переживший повторы, завершает прогон как раньше, а текст сбоя говорит, что отказ повторился. Путь HTTP 4xx (`content_policy_blocked` как ошибка) не менялся. Это патч hermes 36, он действует после переката образа бота; пропустит ли фильтр поставщика повторный вызов, заранее неизвестно, каждый повтор стоит вызова модели. (CONTENT-FILTER-RETRY-PER-CALL, OPE-13076) Повтор теперь имеет свой счётчик на каждый вызов модели (не больше 2 на вызов) и не тратит общий `restart_count` хода (предел `api_max_retries`); раньше повторы конкурировали с другими причинами перезапуска, и ход с несколькими отфильтрованными вызовами мог закончиться раньше. Бот с цепочкой резервных моделей по-прежнему сначала переключается на резерв.

## Стадия ревью в контексте задачи

- **Участник видит стадию (REVIEW-STAGE-IN-CONTEXT).** Ревьюеры, разбуженные CI, подбором простоя или оператором, отвечали «executionStage=null, активного участника нет» и отказывались записывать решение, хотя стадия ждала и они были её участниками (OPE-12886, OPE-12906, OPE-12941): `executionStage` строился только для побудок самой стадии, а `GET /api/issues/:id/heartbeat-context` его не содержал. Теперь в ответе есть поле верхнего уровня `executionStage`, построенное той же функцией: идентификатор и тип стадии, состояние, текущий участник, кому вернуть, последнее решение, допустимые действия, `isCurrentParticipant` и строка `youAre`. Текущий участник получает `wakeRole: "reviewer"` (`"approver"`) и действия `approve` и `request_changes`; исполнитель возвращённой стадии — `"executor"`; любой другой — `"observer"`, без действий и с текстом «You are not a participant of the review stage». Поле равно `null`, только когда стадии в работе нет.
- **Одобрение записывается (REVIEW-APPROVAL-RECORDED).** На rc.2 одобрение ревьюера отклонялось с HTTP 409 (`issue_done_pull_request_gate`), стадия оставалась `pending` или падала в `idle`, а восстановление блокировало задачу (OPE-13059, OPE-13061). Когда перевод в `in_review` назначал ревьюера, а затем побудка ревьюера откладывалась (ожидание CI или квота побудок на тик), политика монитора допуска строилась из политики до назначения и затирала сохранённую политику значением `stages: []`; `done` участника попадал на стадию, которой в политике уже не было. Побудка, начавшая прогон, значения не имела. Теперь политика монитора строится на политике, сохранённой после правки и назначения. Одобрение текущего участника ожидающей стадии ревью записывается и тогда, когда политика потеряла стадию или пропала целиком: стадия завершается с решением «одобрено», а при открытом PR задача, как обычно, ждёт слияния. Задачи, уже попавшие в такое состояние, ручной починки не требуют; одобрение, как и раньше, требует комментария.

## План-гейт, потолок прогонов и стартовый пакет

- **План-гейт (PF-PLAN-GATE, OPE-13081).** Инженерные задачи с меткой `size:M` / `size:L` и без документа `plan` теперь стартуют в режиме планирования, и до реализации нужно одобрение, привязанное к ревизии плана. Правка переводит задачу в планирование, только пока она в `backlog` или `todo` и метки или исполнитель действительно изменились; начатая работа (`in_progress`, `in_review`) в планирование не возвращается, а явный `workMode` при создании сохраняется. Одобряющий — первый доступный для вызова агент `lead` / `architect` в цепочке руководителей исполнителя, затем любой такой агент компании, затем агент `adm`; доска всегда назначает одобряющего и отклоняет запрос плана, который одобрил бы его автор. Пока одобрение плана не получено, прогоны исполнителя не стартуют ни по какой побудке (комментарий, интеракция, автоматическое продолжение); проходит только решение по самой карточке одобрения плана. Переключатель в записи не назван.
- **Прогоны без коммита (PF-RUN-CAP-NO-COMMIT, OPE-13080).** Если подряд завершённые прогоны по задаче не двигают коммит головы PR, их останавливает потолок `general.processes.taskRunsWithoutCommitLimit` (по умолчанию 4, `0` = выключено): автоматические продолжения и повторные побудки пропускаются, задача переходит в `blocked` с краткими итогами последних прогонов и SHA головы PR, а лид проекта (или руководитель исполнителя, или `adm`) получает побудку с подробностями. Счётчик сбрасывается новым коммитом в ветке PR или ручной разблокировкой (человек переводит задачу из `blocked` в `todo` / `in_progress`); комментарии и другие правки его не сбрасывают.
- **Остановка охранником прогона (OPE-13098).** Когда охранник прогона окончательно останавливает задачу инженера («нужны новые вводные»), сигнал `run_guard_stop_needs_input` поднимается по цепочке `reports_to` (до 5 шагов, с защитой от циклов) к ближайшему доступному для вызова `lead` или `architect`; ревьюеры пропускаются, потому что не ставят и не нарезают задачи. Если никого нет, сигнал уходит `adm`, и диспетчер выполнения допускает к остановленной задаче только этого агента.
- **Разведчик стартового пакета (OPE-13095).** Новый параметр инстанса `general.starterPackAgentId`, по умолчанию пустой. Если он задан, новая задача инженера сначала будит этого разведчика (причина побудки `starter_pack_scout`), а не исполнителя. Разведчик только читает код и может записать ровно один документ — `starter-pack` (документ с любым другим ключом по-прежнему отклоняется с 403). Сразу после сохранения документа, а также запасным путём, когда прогон разведчика закончился без него (при любом статусе), доска будит исполнителя обычной побудкой `issue_assigned`, один раз на задачу; таймаута нет, сигнал — конец прогона разведчика. Разведчик не ставится, если параметр пуст, у задачи уже есть документ `starter-pack` или заголовок `### Стартовый пакет` в описании, либо исполнитель — не инженер. В диагностике побудки видна причина `starter_pack_scout`, а не `other`.
- **Стартовый пакет в побудке (STARTER-PACK-V1).** Документ задачи с ключом `starter-pack` доставляется исполнителю отдельным блоком `Starter pack (start here; do not re-explore the project):` в начале текста побудки, перед сводкой продолжения. Тело ограничено 8000 символами (более длинное обрезается и заканчивается `[starter pack truncated]`) и проходит ту же очистку по доверию к источнику, что и сводка продолжения. Изолированный прогон ревьюера этот блок не получает.
- **Сессии и память разработчиков (OPE-13087, DEV-SESSION-RESTORE, OPE-13096).** У разработчиков (инженеров и ревьюеров кода) нет памяти Hindsight, но сессия задачи должна продолжаться между прогонами. Принудительный сброс на каждом прогоне разработчика убран: прогон возобновляет сохранённую сессию задачи по стратегии из карточки (`issue`, `run` или `none`); общеагентная стратегия (`agent`) или пустая заменяется на `issue`. Побудка, требующая свежую сессию, смена конфигурации и план долгой задачи по-прежнему начинают новую сессию. Для ролей разработчиков (`developerRoles`, например `engineer`, `reviewer`, `release`) компилятор профиля Hermes теперь не пишет `memory.provider: hindsight` в `config.yaml`; у остальных ролей профиль не меняется ни на байт.

## Ревью, передачи и закрытые задачи

- **Передача без стадии ревью (OPE-13099).** `PATCH {status: "in_review"}` инженера по задаче без пути ревью (нет стадии ревью, карточки, одобрения, человека-исполнителя или монитора) раньше получал 422 `missing: review_path`; из-за этого в инструкциях жило самодельное правило «ревьюер по номеру PR по модулю 6». Теперь при включённой маршрутизации ревью и задаче не `human_only` доска добавляет стадию ревью в существующую политику, если исполнитель — инженер. Участники — доступные для вызова ревьюеры группы самого исполнителя (автор и исполнитель исключены), а обычный переход выбирает наименее загруженного текущим участником в той же записи. Если в группе нет ревьюера или исполнитель — не инженер, ничего не добавляется и остаётся прежний 422. Задача, у которой стадия уже есть, повторная отправка после `changes_requested` и запросы от доски или пользователя ведут себя как раньше.
- **`myr-handoff` (PF-HANDOFF-REVIEW).** В образе ботов появилась команда `myr-handoff` (`docker/bot-runtime/myr-ws/myr-handoff`): она отправляет текущую ветку, создаёт или переиспользует PR на GitHub с ключом задачи в названии, переводит задачу в `in_review` с итоговым комментарием через API Myrmidon (ревьюера выбирает доска) и проверяет привязку PR к work product.
- **Вердикт комментарием (OPE-13115).** Комментарий, начинающийся с `APPROVE` или `REQUEST CHANGES`, от текущего участника стадии ревью по задаче в `in_review` отклоняется с HTTP 422 и подсказкой использовать `PATCH /api/issues/<id>`; раньше такой вердикт молча подвешивал стадию. Обычные комментарии ревьюеров, прочие комментарии и комментарии операторов или других агентов не затрагиваются.
- **Запрос правок при потерянной стадии (REVIEW-CHANGES-LOST-STAGE).** Если описание стадии пропало из политики (например, монитор политики перезаписал её пустым массивом), решение ревьюера `changes_requested` отклонялось или сбрасывало состояние выполнения без записи решения. Теперь оно записывается на активную ожидающую стадию: счётчик раундов ревью растёт, задача возвращается в `in_progress`, а назначение — к `returnAssignee`.
- **Ревьюер закончил без вердикта (OPE-13070).** Когда прогон ревьюера, начатый по завершению CI, кончился без вердикта (стадия осталась `pending`), проход живости обхода маршрутизации ревью снова будит простаивающего ревьюера, как только с последнего обновления задачи прошло `REVIEW_WAKE_STALE_AFTER_MS`; последующие проходы выдерживают `REVIEW_WAKE_RETRY_BACKOFF_MS`.
- **Переназначение (OPE-13097).** Когда задачу переназначили, а замок выполнения держит не начатый прогон прежнего исполнителя в состоянии `queued` или `scheduled_retry`, этот прогон отменяется (`lock_released_on_reassignment`) до побудки нового исполнителя, и его побудка ставится в очередь сразу, а не ждёт в `deferred_issue_execution`. Прогоны текущего участника стадии ревью и идущие прогоны не затрагиваются.
- **Побудка по красному CI (OPE-13078).** Когда инженера будит упавший или завершившийся по таймауту CI (`ci_completed`), в данных побудки и в тексте значатся имена и id упавших джобов и готовая команда (`gh run view <run> --job <job> --log-failed | tail -80`). Если у установочного токена доски есть `actions:read`, добавляется и хвост лога упавших джобов (последние 60 строк, окно кончается на последней строке `##[error]`, без ANSI, секреты замаскированы; до 3 джобов одновременно, не более 12 000 символов в сумме); иначе указывается причина. Маскировка теперь покрывает и токены `ghs_` / `github_pat_` / `gh[ousr]_`, ключи `sk-`, значения `Authorization:`, пароли в URL и ключи AWS. Строка «Do not poll CI: the failing output is below» печатается, только если хотя бы у одного джоба есть хвост лога.
- **Повтор после обслуживания (OPE-13077).** Повтор прогона, прерванного на обслуживание, получал короткую инструкцию только на русском, без времён и без ветки (55 из 88 таких повторов 13–14.11 начинали работу заново). Теперь она на английском, называет прерванный прогон и окно обслуживания, сообщает время старта, время прерывания и длительность, указывает ветку задачи и SHA головы, если доска знает их из work product с PR, и велит агенту выполнить `git status` и `git log --oneline -5`, прочитать последние комментарии и продолжить с места остановки. Обычные побудки (`issue_assigned`, `ci_completed`) этот блок не получают.
- **Закрытые задачи (CLOSED-TASK-COMMENT-RUN, CLOSED-TASK-COMMENT-RUN-2, OPE-13068).** Побудка по комментарию на уже закрытую (`done` или `cancelled`) задачу больше не даёт стартовать и упасть в `buildExecutionContinuation` поставленному в очередь прогону исполнителя с записью уровня error: он отменяется при взятии с `issue_terminal_status` (запись info, без `failed`). Прогон, взятый из очереди до закрытия задачи или обошедший проверку очереди через `resumeIntent`, так же чисто отменяется при подготовке (`issue_terminal_status` или `issue_assignee_changed`). Побудки по комментарию от не-исполнителей, явные намерения возобновления и ответы на карточки ведут себя как раньше. Прогон в очереди, отменённый из-за терминального статуса задачи, больше не порождает повторную побудку с `queued_run_stale_timeout` (этот цикл бесконечно создавал и отменял прогоны для закрытых задач); замена создаётся, только если отмена действительно была `queued_run_stale_timeout`.
- **Проверка параметров API задач (ISSUES-LIST-BAD-ID).** `GET /api/companies/:companyId/issues` проверяет `participantAgentId`, `projectId`, `workspaceId`, `executionWorkspaceId` и `labelId` как UUID и отвечает 400 вместо ошибки PostgreSQL 22P02; ссылки на задачи `parentId`, `parentIssueId`, `descendantOf` и `createdFromIssueId` сначала разрешают идентификатор задачи и дают 400 на некорректное значение; повторное (массивом) значение даёт 400 с названием параметра вместо 500. `POST /api/companies/:companyId/issues` проверяет, что `projectId`, `parentId`, `assigneeAgentId`, `labelIds` и `goalId` существуют, и отвечает 422 вместо нарушения внешнего ключа.
- **Журнал рабочего процесса (OPE-13117).** При раздельном развёртывании (`general.processes.mode = split`) рабочий процесс писал «run start dispatch requested a remote start but no process bus is wired» по 10–40 раз в секунду для агентов с одним идущим и одним ожидающим прогоном: диспетчеры, созданные для маршрутов и сервисов, не знали, что работают в процессе-исполнителе. Теперь знают, и исполнитель запускает прогон сам. Строка пишется один раз на процесс, остальные уходят на уровень `debug`. Диспетчеризация по событию пропускается для агента, который уже ведёт столько прогонов, сколько позволяет его лимит (конец его прогона диспетчеризует снова); обход и пути завершения прогона не менялись. Диспетчер читает свои настройки не чаще раза в 5 секунд.

## Контейнеры ботов, диск ботов и чистка хоста

- **Unhealthy-контейнер с живым прогоном (BOT-HEALTH-LIVE-RUN).** 14.11 проба здоровья (`curl /health`, 5 с) не уложилась по таймауту при нагрузке на хост, и Docker пометил живых ботов `unhealthy`; доска перезапустила их и оборвала два прогона (`myrmidon_maintenance_interrupted`). Теперь, когда контейнер `unhealthy`, но у агента идёт прогон с последним прогрессом (событие прогона, сброс вывода или полезное действие) моложе 120 с, восстановление ждёт следующего прохода, а в журнале активности пишется «health recovery deferred: live run». Молчащий прогон или его отсутствие восстанавливаются как раньше. Окно задаёт `MYRMIDON_BOT_HEALTH_LIVE_RUN_GRACE_SEC` (по умолчанию 120, `0` = выключено).
- **Заполнение диска глазами botd (OPE-13107).** 14.11 в `disk-state.json` бота-ревьюера было `partitionPercent: 0`, `pressure: none`, хотя том XFS ботов был занят на 86 % (порог 85 %), поэтому быстрая чистка под давлением не запускалась: доска отвечает `0 / none`, когда у неё нет замера раздела (dockergate недоступен или его замер устарел). Теперь доска помечает такой ответ `partitionMeasured: false`; тогда botd сам измеряет том данных ботов (`statfs` от `/workspace`) и определяет уровень по порогам по умолчанию (85 % мягкий, 90 % жёсткий). Если и локальный замер не удался или показал 0 % при занятых байтах, в `disk-state.json` появляется `warning`, и botd пишет его в журнал. Измеренный ответ доски не перекрывается. Копия участника ревью освобождается, когда ревью закончено: строка задачи бота, который не исполнитель, закрывается, только если бот участвовал в стадии ревью этой задачи и не является ни текущим участником, ни возвращаемым исполнителем, ни исполнителем; копия исполнителя хранится, пока задача к нему не вернётся; грязная или непушнутая копия по-прежнему архивируется botd.
- **Git-зеркало в настройках диска ботов (OPE-13116, OPE-13110).** В панели есть переключатель git-зеркала, она показывает действующий список репозиториев (с отметкой «по умолчанию») и роли, получающие общее зеркало; выключение переключателя явно очищает зеркалируемые репозитории. `GET /api/myrmidon/bot-disk` теперь возвращает и `effective`: `gitMirrorEnabled`, `gitMirrorRepos`, `gitMirrorReposIsDefault` и `sharedCacheRoles`. `PATCH /api/instance/settings/general` сливает `botDisk` по ключам: запрос только с `scratchTtlHours` больше не стирает сохранённый `gitMirrorRepos`; отсутствующий ключ ничего не меняет, `null` очищает весь блок. Умолчание `gitMirrorRepos` — два встроенных репозитория (а не «без зеркал»); явный `[]` теперь сохраняется и выключает зеркало, а отсутствующий ключ (или `null`) означает список по умолчанию. Зеркало получают только роли из `sharedCacheRoles`, а `<cache>/git` должен принадлежать пользователю процесса доски (uid 1000 в боевой среде), иначе новые зеркала падают с EACCES (SETTINGS.md).
- **Старые git-базы (OPE-13118).** Базы ботов в `/data/hermes/.myrmidon/git-base/<owner>/<repo>.git` (у 72 из 126 не было `objects/info/alternates`, 14,3 ГиБ дублирующихся объектов) теперь подключаются к зеркалу флота `/cache/git`: `findMirror` при промахе точного пути делает обход без учёта регистра (у 17 баз wellboard зеркала не находилось), а git-миграция botd пишет alternates (`syncMirrorAlternates`) перед перепаковкой и повторно мигрирует базу, когда alternates появились или изменились; `repack -l` убирает дубли. Блокировка флота «перепаковывать только простаивающего бота» не менялась.
- **Склад pnpm (OPE-13112).** `general.botDisk.pnpmStoreDir` (`/cache/pnpm-store`) записывался в `.env` бота, но процессы по-прежнему видели умолчание образа `npm_config_store_dir=/workspace/.pnpm-store`, и установки шли в склад каждого бота отдельно. Обёртка `pnpm` теперь читает `npm_config_store_dir` из `${HERMES_HOME}/.env` и применяет его, если это абсолютный путь, доступный боту на запись (сама папка, а для отсутствующей — ближайший существующий родитель). Если ничего не задано или запись невозможна, склад остаётся `/workspace/.pnpm-store`.
- **Копия для ревью (OPE-13111).** У ревьюеров лежало по 14–17 полных копий по 0,5–1,2 ГБ. `myr-ws open <KEY> <owner/repo> --review` теперь создаёт worktree без рабочей папки (`git worktree add --no-checkout`, пустой sparse-checkout, поэтому `git status` чистый): килобайты вместо ~0,5 ГБ, зависимости не ставятся, git-хуки выключены. Ветка PR сначала забирается с удалённого репозитория, а устаревшая локальная ветка перематывается на `origin/<branch>`; если ветки нет на удалённом репозитории и не задан `--branch`, `open` завершается ошибкой «no PR branch, pass --branch», а не открывает копию main; локальная ветка с коммитами, которых нет на удалённом репозитории, не двигается (ошибка). Ревьюер читает изменение по ссылкам (`gh pr diff <N>`, `git diff origin/main...HEAD`, `git show HEAD:<path>`). Уже открытая копия возвращается как есть, с предупреждением; `--review` нельзя сочетать с `--scratch`; обычный `open` не менялся.
- **Сохранение карточки с недопустимым монтированием (OPE-13074).** Сохранение или правка карточки агента (`POST /api/agents`, `PATCH /api/agents/:id`) с `adapterConfig.container.extraMounts` сверяет источники с `MYRMIDON_BOT_MOUNT_SOURCES` (и сохранёнными через интерфейс `bot_mount_sources`). Недопустимый источник сразу отклоняется с HTTP 422 с названием источника, а не сохраняется с последующим зацикленным падением сверки контейнера бота. Частичная правка без `extraMounts` не отклоняет уже сохранённые монтирования; проверки сверщика и сборки контейнера остаются второй линией защиты от прямых правок базы.
- **Чистка хоста (OPE-13104).** 14.11 за 4 часа появилось около 73 клонов задач (36 ГБ); при хранении 24 часа и проходе раз в 2 часа свободное место на диске ботов прыгало на 10–15 ГБ, и тревоги HOST_DISK / BOTS_DISK срабатывали по нескольку раз в день. Теперь умолчание срока клона (`CLONE_TTL_HOURS`, `--clone-ttl`) — 3 часа, а systemd-таймер запускает чистку каждые 30 минут (`OnCalendar=*-*-* *:10/30:00`); правила, по которым активные клоны сохраняются, а грязные сначала архивируются, не менялись. Неудавшийся архив клона или папки задачи на раннере больше не оставляет недописанный `.tar.zst` / `.tar.gz` (раньше — по 1–2 ГБ за проход); в тексте ошибки есть код выхода и сигнал, а таймаут выглядит как «timed out after N s». Архивы пропускают `node_modules`, `.pnpm-store`, `.turbo`, `dist`, `.next` и `coverage` (только каталоги сборки и зависимостей, которые git игнорирует); `.git` с непушнутыми коммитами и любые файлы, которые git не игнорирует, остаются. Причина: папка задачи на раннере в 13 ГБ с тремя копиями репозитория не укладывалась в лимит 600 с ни в одном проходе.
- **Обход рабочих папок закрытых задач (у записи нет метки).** Теперь обход архивирует строки `shared_workspace` закрытых (`done` / `cancelled`) задач, не заглядывая в git и API GitHub: они указывают на общий каталог проекта, у которого нет копии под задачу и нечего удалять. Раньше каждая такая строка блокировалась, и на каждую писалось событие `issue_terminal_archive_blocked` (больше 180 000 событий), нагружая доску каждые 30 секунд. Обход по-прежнему требует закрытого дерева задач, паузы остывания и отсутствия активного прогона, а копия с открытой связанной задачей не архивируется. Очередь разбирается проходами до 200 строк, каждая архивируется отдельным обновлением одной строки под `FOR NO KEY UPDATE SKIP LOCKED` с паузой между проходами (`MYRMIDON_WORKSPACE_SHARED_SWEEP_PAUSE_MS`, по умолчанию 1 с), поэтому обходчики в нескольких процессах не берут одну строку дважды.
- **Порты без `lsof` (OPE-13075).** При подготовке изолированной среды рабочей папки владелец слушающего порта проверялся через `lsof`; там, где его нет, каждая проверка кандидата запускала его заново (~32 попытки, ~19 с). Теперь отсутствие `lsof` запоминается после первой неудачи (ENOENT / 127), а в Linux проверка переходит на `/proc/net/tcp` и `/proc/<pid>/fd`, не принимая посторонних слушателей.

## omp_local

- **Предел вызовов модели (OMP-RUN-GUARD-1).** У прогона `omp_local` не было предела вызовов модели, только `timeoutSec` (3 часа); 13.11 сессия в среднем делала 101 вызов, самая длинная — 494. Теперь адаптер питает
  сторожа прогона доски: предел тот же, что у hermes, 150 вызовов по умолчанию, переопределяется карточкой агента `runGuard.modelCallLimit`, `runGuard` в живости команды или `MYRMIDON_RUN_GUARD_MODEL_CALL_LIMIT`. За пятнадцать вызовов до предела
  агент получает сообщение «завершайся» (коммит, push, комментарий к задаче); после предела адаптер останавливает процесс, а о следующем прогоне решает продолжение сторожа (`run-guard-stop`). Остальные остановки сторожа
  (чтение без правок, повтор вызова, простой) теперь действуют и на прогоны `omp_local`. Прогон, остановленный по SSH, восстанавливает рабочую папку. Часть длинных сессий omp теперь будет заканчиваться остановкой и продолжением.
- **Отмена по SSH (OMP-RUN-GUARD-2).** 13.11 две сессии продолжали работать на раннере после отмены прогона (46 и 22 минуты, 337 вызовов модели). Теперь адаптер сам слушает сигнал отмены прогона
  и останавливает локальный ssh-клиент; отмена, пришедшая до регистрации клиента, применяется при его запуске.
- **Выгрузка рабочей папки (OPE-13041).** Выгрузка на удалённый раннер падала с `ssh exited before tar finished (code 0)`, когда ssh закрывался чуть раньше tar, хотя все данные были доставлены. Теперь итог определяют коды
  выхода обоих процессов (tar получает до 10 с после выхода ssh с кодом 0). Протокол и раскладка не менялись.

- **Строка в промпте (OMP-PROMPT-AGY-429).** При сборке образа строка `RFC 2119 keywords: MUST, REQUIRED, SHOULD, RECOMMENDED, MAY, OPTIONAL.` в системном промпте встроенного CLI `@oh-my-pi/pi-coding-agent` заменяется на `Keywords MUST, REQUIRED, SHOULD, RECOMMENDED, MAY, OPTIONAL follow their usual meaning.`; это избавляет от отказов 429 со стороны Antigravity / Google, которые вызывает определение агента по «отпечатку». Сборка сразу падает, если искомый текст отсутствует или изменён в новом выпуске пакета; в CI есть регрессионные тесты.
- **Осиротевшие процессы (OPE-13105).** В образе раннера omp по SSH есть `/usr/local/bin/run-reap`. Когда прогон агента заканчивается (успех, ошибка, таймаут или отмена), адаптер omp вызывает на раннере `run-reap <task_dir>`: он завершает оставшиеся фоновые процессы (например, `@embedded-postgres` или дочерние инструменты), рабочая папка которых лежит внутри рабочей папки задачи, проверяя `/proc/<pid>/cwd`, не трогая системные и сеансовые процессы (`PID 1`, `$$`, `$PPID`, `sshd`), посылая `SIGTERM`, ожидая до 5 секунд и затем `SIGKILL`. Чистка выполняется в блоке `finally`, поэтому её сбои пишутся в журнал и не меняют исход прогона.
- **Клоны с зеркалом (OPE-13113).** Обёртка git раннеров omp по SSH (`docker/agent-runtime/omp-ssh/git-reference/git`) раньше сохраняла параметры неполного (shallow) клона, переданные вызывающим, когда в `/cache/git/<owner>/<repo>.git` было bare-зеркало (голый репозиторий). Теперь при наличии зеркала она убирает `--depth` и `--shallow-*` и добавляет `--reference-if-able <mirror>`: клон берёт объекты из зеркала, сохраняет полную историю через alternates, а его `.git` остаётся меньше 50 МБ. Без зеркала параметры shallow остаются.

## Устаревшие блокировки

- **Обход устаревших блокировок (STALE-BLOCK-LIVE-EDGES).** Доска писала «stale block sweep failed for one task» около 50 раз в час по одним и тем же 14 заблокированным задачам. У каждой названная причина была мертва, а связь
  с ещё открытой задачей — жива. Теперь обход считает такой открытый блокер живой причиной: задача остаётся заблокированной и просыпается обычным путём `issue_blockers_resolved`, когда блокер закроется. Мёртвая причина, у которой все блокеры
  закрыты, снимается как раньше. Предупреждение о сбое теперь содержит класс исключения и его HTTP-статус.
- **Задача без исполнителя (STALE-BLOCK-UNASSIGNED).** Задача, созданная сразу в `blocked` с закрытым блокером и без исполнителя, заставляла обход писать «stale block sweep failed for one task» (HTTP 422) на каждом проходе и оставалась заблокированной навсегда: обход выбирал `in_progress`, а сервис задач отказывает в нём, когда нет ни агента, ни пользователя в исполнителях. Теперь такая задача уходит в `todo` (мёртвая связь удаляется, в комментарии «без исполнителя»); задача с исполнителем возвращается в `in_progress`, как раньше. Предупреждение о сбое теперь несёт и `errorMessage`: фиксированную фразу отказа сервиса задач для 4xx-ошибки (не длиннее 120 символов), так что причину повторного 422 видно в журнале.
- **Задача закрыта до старта прогона (RUN-SETUP-STALE-TASK).** Прогон по `issue_assigned` ждал слот агента, пока задачу закрыли, а её PR влили; на старте он падал с `setup_failed` / `continuation_task_ownership_changed` и записью уровня error (17 раз за 7 дней), потому что проверка устаревания пропускала любую побудку с комментарием. Теперь такой прогон по задаче в `done` или `cancelled` отменяется при взятии с `issue_terminal_status` (запись info, без `failed`). Побудки по комментарию, намерения возобновления и адресаты карточек ведут себя как раньше, а настоящие сбои подготовки остаются `failed`.

## Как проверить после обновления

Проверки взяты из описаний pull request; для этой страницы они не запускались.

- **Побудки от GitHub.** В течение суток после прихода итога CI по задаче на ревью в `agent_wakeup_requests` есть строка с `requested_by_actor_id = 'system:github-ci'` (за трое суток до этого было 0) и прогон исполнителя. Запрос вебхука не зависает.
- **Взаимные блокировки.** В журнале нет `deadlock detected` по `issue_work_products` и ответов 500 от `POST /api/myrmidon/github-app/webhook`.
- **Красный main.** Пока `main` красный, записей `issue.ci_failed` по красным на main шардам не появляется; удержания — это записи `issue.ci_infra_retry_needed`, и каждая запись `issue.ci_failed` несёт `failedChecks`.
- **Пустые прогоны.** Доля прогонов `swarm_matched` / `idle_pickup`, ничего не менявших, падает, а повторяющаяся строка «stale block sweep failed» по тем же задачам исчезает.
- **Правка карточки при прогоне (BOT-PROFILE-NO-RUN-INTERRUPT).** Изменить поле с перезапуском (например, `maxConcurrentRuns`) у агента с идущим прогоном: прогон дойдёт до конца, в активности будет «bot container update deferred», запись появится в `myrmidonBotRolloutDeferred`, а после прогона следующий проход перезапустит бота. Из описания pull request; для этой страницы не запускалось.
- **Сводка CI (CI-SNAPSHOT-CANCELLED).** `ciResult` задачи, у PR которой CI был заменён, показывает `success`, а не FAILURE; голова только с отменёнными проверками показывает `cancelled` и «cancelled, not a test failure»; настоящее падение по-прежнему FAILURE. Для этой страницы не запускалось.
- **Стадия ревью (REVIEW-STAGE-IN-CONTEXT, REVIEW-APPROVAL-RECORDED).** В `GET /api/issues/:id/heartbeat-context` задачи на ревью есть `executionStage`; одобрение ревьюера после отложенной побудки записывается и не получает 409. Для этой страницы не запускалось.
- **Освобождение слота в очереди (EMPTY-RUNS-6B, EMPTY-RUNS-6C).** Число отмен `queued_run_stale_timeout` у прогонов с `waitReason = agent_concurrency` равно нулю, а прогон, ждавший слот, стартует с исходной причиной побудки (например, `ci_completed`). Из описания pull request; для этой страницы не запускалось.
- **Возраст прогона в очереди (RESUME-QUEUE-AGE).** После снятия паузы с агента, простоявшего на паузе дольше 30 минут с прогонами в очереди, в первые минуты нет отмен `queued_run_stale_timeout`; у стоящих в очереди прогонов этого агента в `context_snapshot` есть числовой ключ `queueWaitResumedAtMs`. Для этой страницы не запускалось.

- **План-гейт и потолок прогонов (PF-PLAN-GATE, PF-RUN-CAP-NO-COMMIT).** Новая инженерная задача `size:M` / `size:L` без документа `plan` стартует в режиме планирования с назначенным одобряющим; задача, у которой подряд идущие прогоны не добавляют коммит, после 4-го уходит в `blocked`, а лид получает побудку. Для этой страницы не запускалось.
- **Чистка хоста (OPE-13104).** Таймер чистки срабатывает каждые 30 минут, клоны закрытых задач старше 3 часов архивируются или удаляются; после неудачного архива недописанных `.tar.zst` / `.tar.gz` не остаётся. Для этой страницы не запускалось.
- **Настройки диска ботов (OPE-13116, OPE-13110).** На экране настроек есть переключатель git-зеркала и отметка «по умолчанию»; в `GET /api/myrmidon/bot-disk` есть `effective`; `PATCH general` только с `scratchTtlHours` оставляет `gitMirrorRepos` на месте. Для этой страницы не запускалось.
- **Передача на ревью (OPE-13099, OPE-13115).** `in_review` инженера по задаче без стадии ревью принимается и получает ревьюера; комментарий участника, начинающийся с `APPROVE`, получает 422 с подсказкой. Для этой страницы не запускалось.

Известные ограничения. Настоящее падение на красной базовой ветке удерживается до зелёной `main-green` на голове, то есть возвращается позже, а не теряется. Удержания и отметки (`ciReturnHold`, `ciFinalCheckSeen`)
хранятся в метаданных work product; если их целиком перезапишет другой писатель, удержание запишется повторно, а возврат после перезапуска `main-green` не произойдёт: задача пойдёт обычным путём ревью.
Чтение GitHub идёт внутри обработки доставки и ограничено 10 секундами.

Известные ограничения исправлений rc.4 и rc.5.
- Правка карточки занятого бота ждёт конца прогона, не дольше `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (6 часов); после этого прогон сливается и прерывается. Канарейка и откат не ждут. Какая именно правка пересоздала контейнер бота 14.11, установить не удалось (журнал доски успел ротироваться).
- После паузы задачи, чей прогон закончился как `failed`, `timed_out` или `interrupted`, остаются удержанными. Не менялось: действие восстановления, закрытое исходом `blocked`, пока задача остаётся в `in_progress`, и `recovery-actions/resolve` с `restored`, отвечающий 200 без эффекта.
- Ответ, заблокированный фильтром, повторяется не больше двух раз на вызов модели и только у агента без резерва, как описано выше; путь HTTP 4xx не менялся. Начиная с rc.5 повторы не делят счётчик перезапусков хода (CONTENT-FILTER-RETRY-PER-CALL). Пропустит ли поставщик повторный вызов, заранее неизвестно, а каждый повтор стоит вызова модели.
- Одобрение восстанавливается для стадии, вышедшей из политики, а запрос правок участником в таком состоянии этим исправлением не охвачен. Прогон, разбуженный комментарием другого агента по закрытой задаче, по-прежнему стартует, как раньше: отмена по закрытой задаче действует только на побудки `issue_assigned`.
- Отмена по закрытой задаче при побудке по комментарию действует на прогоны исполнителя задачи; побудки по комментарию от других агентов, явные намерения возобновления и ответы на карточки по-прежнему стартуют (CLOSED-TASK-COMMENT-RUN).
- Обход рабочих папок для общих копий не использует ни git, ни API GitHub и учитывает только терминальное состояние дерева задач.
- Защита прогона в очереди не покрывает ожидание, которое проход старта сменил на `agent_fair_share` или `higher_priority_ready`.
- Отметка `queueWaitResumedAtMs` ставится только при снятии паузы агента. Окно обслуживания и пауза компании ею не покрываются.
