# Выпуск 1.6.9 — заметки для оператора

> English version: [1.6.9.md](1.6.9.md)

Страница для оператора, который обновляет доску до 1.6.9 — выпуска исправлений после 1.6.8. Она описывает состав кандидата 1.6.9-rc.3 (тег `myr-v1.6.9-rc.3`, коммит `284bba6fd5…`): что изменилось, что включено по умолчанию и что требует переключателя или проверки. В разделе «1.6.9» журнала изменений
([../CHANGELOG.ru.md](../CHANGELOG.ru.md)) 23 записи; здесь — то, что меняет увиденное или сделанное оператором, с отсылкой к записи
(в скобках номер задачи или метка). Полная процедура выката — [../deploy.md](../deploy.md); переменные окружения доски, названные ниже, перечислены с умолчаниями в
[../SETTINGS.md](../SETTINGS.md). Почти весь выпуск — об одном: в первый день после 1.6.8 заметная доля прогонов доски уходила на побудки, которые ничего не меняли (подбор задачи, которую агент
раз за разом возвращал в очередь; ревьюеры, разбуженные на ещё идущий или красный CI; задачи, возвращённые с ревью по первому закончившемуся джобу). В 1.6.9 эти пути закрыты. Кандидат rc.3 добавляет десять исправлений дефектов, найденных на rc.2 (правка карточки агента при идущем прогоне, пауза и снятие паузы агентов, сводка CI после заменённого прогона, стадия ревью в контексте задачи, блокировка ответа фильтром содержимого); они описаны в разделах ниже.

## Что сделать оператору при обновлении

Это делается сверх обычного выката.

1. **Выкатывать как обычно, все компоненты одним тегом**
   ([../deploy.md](../deploy.md), «Deploy the board and the release components together»). В записях этого выпуска нет нового шага на хосте,
   нового обязательного параметра и — для изменения доставки CI (EMPTY-RUNS-3) — миграции базы данных.
2. **Пересмотреть то, что вы подкручивали на 1.6.8.** Если вы меняли `general.swarm.cooldownCeilingHours`, чтобы унять повторные подборы, проверьте значение: остывание задачи
   теперь ловит и задачу, которую агент возвращает в очередь (EMPTY-RUNS-1), а потолок по умолчанию — 24 часа.
3. **Ждать, что боты переключатся после конца прогонов.** Правка карточки агента, требующая перезапуска шлюза или пересоздания контейнера бота, и перекат образов скриптом `bot-image-rollout.sh` теперь ждут конца идущего прогона бота (BOT-PROFILE-NO-RUN-INTERRUPT); повтор при блокировке фильтром содержимого (CONTENT-FILTER-RETRY) входит в образ бота (патч hermes 36) и действует у бота только после переката его образа.
4. **После выката пройти проверки из раздела «Как проверить после обновления».** Первая важнее остальных: побудка по завершению CI от приложения GitHub в api-процессах
   отбрасывалась и теперь заработает впервые.

## Результаты CI и возвраты с ревью

- **Только итоговый результат (EMPTY-RUNS-3).** События приложения GitHub считали завершённым CI любой закончившийся джоб: с задачи снимался монитор, исполнителю ставилась побудка
  (`ci_completed`), а задача на ревью уходила исполнителю по первому закончившемуся джобу. 13.11 это дало 48 возвратов с ревью, 45 из них по одному
  `check_run`; один такой прогон сделал 139 вызовов модели, чтобы ответить «main красный, править нечего». Теперь считается только доставка с итоговым результатом текущей головы: завершённая
  проверка `CI result` (отменённая, пропущенная или устаревшая не в счёт) или, если у PR такой проверки нет, момент, когда GitHub показывает завершёнными все проверки.
  Закончившийся джоб ничего не меняет. Результат записывается в `lastCompletedCi`, при зелёном сообщает о возможном слиянии, снимает монитор и будит исполнителя
  один раз на результат; повторная доставка того же результата никого не будит, результат старой головы ничего не решает.
- **Красный main (EMPTY-RUNS-3).** Задача на стадии ревью при красном итоговом результате уходит исполнителю, упавшие проверки названы в комментарии. Красный
  результат при красной `main-green` на голове — это падение на красной базовой ветке: задача остаётся на ревью, исполнитель не будится, системная заметка объясняет причину, а
  запись `ci_infra_retry_needed` пишется один раз на голову. Когда main снова зелёный, workflow «Main green gate» перезапускает `main-green` на открытых PR; голова,
  которая и после этого красная, возвращается исполнителю с указанием сначала перезапустить упавшие джобы. Голову, на которой упал только `CI result`, держат так же. Если GitHub
  прочитать не удалось, красный итог возвращает задачу без списка проверок.
- **Побудки теперь доходят до очереди (EMPTY-RUNS-3).** Вебхук приложения принимают api-процессы, а сервису событий там вместо функции побудки была передана заглушка: ни одной побудки
  `ci_completed` не записалось на 54 возврата с ревью. Теперь api-процесс ставит побудку через сервис пульса своей роли, и каждая побудка по доставке отправляется после того, как транзакция
  доставки зафиксирована.
- **Взаимные блокировки (EMPTY-RUNS-3).** Десяток джобов одного PR, закончившихся в пределах секунды, убивали доставки друг друга (`deadlock detected`, 15 раз за час, 14 ответов
  500 на `POST /api/myrmidon/github-app/webhook`, событие терялось). Теперь доставки одного PR идут по очереди; транзакция, откатанная из-за
  взаимной блокировки (`40P01`) или сбоя сериализации (`40001`), выполняется заново, всего до четырёх попыток. Причина сбоя запроса (код и текст Postgres) теперь есть в журнале
  запросов и в `lastError` доставки.
- **Одна побудка на результат (EMPTY-RUNS-3B).** Голова, у которой есть проверка `CI result`, считается, только если она завершена и не пропущена, не отменена и не устарела; частичный прогон (событие метки, вспомогательный workflow) с пропущенной `CI result` больше никого не будит. Запасной вариант «все проверки завершены» применяется только к голове совсем без `CI result`. Один результат одной головы будит один раз, каким бы событием он ни пришёл (`check_run`, `check_suite`, `workflow_run`): обработанный результат хранится как `ciVerdictHandled` и, в отличие от `lastCompletedCi`, не сбрасывается стартом джоба; красный результат его сбрасывает, поэтому зелёный после перезапуска снова считается новостью. Побудка `ci_completed` для задачи на ревью идёт участнику её ожидающей стадии, а не исполнителю; задача на ревью без ожидающей стадии никого не будит.
- **Отменённые проверки заменённого прогона (CI-SNAPSHOT-CANCELLED).** Метка `full-ci` или перезапуск заменяли идущий CI, и отменённые проверки прежнего прогона давали в сводке CI, которую доска показывает агентам (`ciResult`, `pullRequestsCi`), ложный FAILURE. Теперь по каждому имени проверки берётся её последняя запись на голове, а представляет проверку последняя завершённая запись с вердиктом. Проверка, чья последняя запись `cancelled` и замены нет, показывается как «cancelled, not a test failure»: итог `cancelled` (ни `failure`, ни `success`), проверка попадает в новое поле `cancelledJobs`; в `failedJobs` остаются только настоящие `failure`, `timed_out` и `action_required`. Более поздняя запись `skipped`, `neutral` или `cancelled` не скрывает более раннего вердикта той же проверки: настоящее падение остаётся FAILURE. Успешная `CI result` без настоящих падений даёт `success` и поглощает только отменённые проверки своего же прогона workflow; отменённая обязательная проверка другого прогона оставляет сводку `cancelled`. В тексте задачи агенты видят отменённые проверки отдельным списком.
- **Переключатели.** `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED=off` возвращает прежнюю обработку (и, в api-процессе, прежнюю отброшенную побудку); `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED=off` убирает
  удержания, и любой красный итог возвращает задачу; `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` без `main-green` убирает удержание по красной базовой ветке.

## Меньше пустых побудок

- **Отложенная задача (EMPTY-RUNS-1).** 13.11 треть всех прогонов (258 из 780 за восемь часов) были подборами `swarm_matched` / `idle_pickup`, и 217 из них ничего не меняли:
  агент брал свою задачу из `todo`, писал «новых данных нет» и возвращал её обратно. Тормоз повторных побудок больше не считает такой возврат (перевод `in_progress` → `todo` и
  комментарий рядом) прогрессом, а остывание задачи больше не принимает «advanced» как доказательство для задачи в `todo`. После двух таких прогонов пауза растёт; после шести
  задача замораживается и спрашивают лида. Шаги остывания — 30 минут, затем 60, 120 и далее до `general.swarm.cooldownCeilingHours`; в списке остывающих такая задача идёт с причиной
  `no_progress`. Если задачу сдвинул человек или другой агент, остывание снимается; задачи в `in_progress`, `in_review` и `blocked` оцениваются как раньше.
- **Монитор, ждущий pull request (EMPTY-RUNS-4).** Когда CI текущей головы уже закончился и агент его видел, монитор всё равно будил агента с пометкой `no_signal` каждые
  30 минут. Это состояние теперь называется `settled`: монитор тихо взводится заново (`issue.monitor_deferred`, причина `pr_wait_unchanged`) с растущим интервалом, не больше 60 минут.
  О новостях агент по-прежнему узнаёт сразу (слит или закрыт, оставлено ревью, конфликт слияния, CI завершился снова) и, как последняя страховка, через 6 тихих часов. PR, по которому у доски нет
  данных о проверках, будится через 30 минут, как раньше.
- **Прогон в очереди (EMPTY-RUNS-6).** Прогон старше `general.processes.queuedRunStaleAfterSec` (30 минут) снимался, а после двух таких снятий подряд задача замораживалась с пометкой «2 прогона без
  прогресса», хотя ни один не стартовал. Прогон, который ждёт только из-за собственного предела параллельности агента (причина ожидания
  `agent_concurrency`, у агента идёт другой прогон), теперь остаётся в очереди и стартует, когда освободится слот. Переназначенная или закрытая задача по-прежнему снимает прогон; другие ожидания истекают как раньше. (EMPTY-RUNS-6B) Раньше защита кончалась в ту же секунду, когда заканчивался последний прогон агента: обход по возрасту снимал ждущий прогон с `queued_run_stale_timeout`, и стартовал заменяющий с этой причиной вместо исходной побудки (13.11 так заменили побудку `ci_completed` после 48 минут ожидания). Теперь ожидание отсчитывается от конца последнего стартовавшего прогона агента, если он позже начала ожидания: прогон, у которого слот освободился только что, остаётся и стартует со своей причиной побудки и данными. Слот, свободный весь порог без старта прогона, — потерянный старт, и прогон снимается как раньше. Ограничение 6B: защита действовала, только пока причина ожидания оставалась `agent_concurrency`. (EMPTY-RUNS-6C) В проходе, освобождающем слот, обход старта берёт самый тяжёлый ждущий прогон и переименовывает ожидание остальных готовых прогонов агента в `priority`; обход по возрасту в ту же секунду снимал их с `queued_run_stale_timeout`, а заменяющие прогоны теряли исходную причину (`pause_resume`, `execution_changes_requested`) и контекст. Теперь `priority` считается тем же ожиданием собственного слота агента: такой прогон остаётся, пока у агента есть прогон в `running` и в течение порога после конца любого стартовавшего прогона агента (успешного, упавшего или отменённого), и стартует со своей причиной побудки и данными. Прогон, который не стартовал при свободном слоте весь порог, и все другие причины снятия (переназначение, закрытая задача) не изменились. Ожидание, которое проход старта сменил на `agent_fair_share` или `higher_priority_ready`, по-прежнему не защищено. Порядок старта идёт по весу приоритета, а не по очереди прихода; это не менялось.
- **Побудки ревьюера (EMPTY-RUNS-2, EMPTY-RUNS-2B).** Сдача на ревью не будит ревьюера, пока голова не зелёная. Два пути этого не учитывали. Итоговый комментарий исполнителя,
  написанный через секунды после сдачи, будил ревьюера в обход ворот; теперь он удерживается (пишется запись `issue.review_comment_wake_deferred`, комментарий остаётся в треде), когда задача
  на стадии ревью, автор — агент, сдавший задачу, монитор «Review CI wait» взведён, а голова ещё не допущена. Комментарий человека, @-упоминание, критичная задача, зелёная голова и любой
  комментарий после допуска ревьюера будят как раньше. А монитор «Review CI wait» через десять минут будил ревьюера на той же красной голове; теперь он взводится заново,
  пока завершённая голова красная (`issue.monitor_deferred`, причина `review_head_red`, следующая проверка через десять минут), в пределах бюджета ожидания CI стадии ревью
  (18 срабатываний), после которого ревьюера будят как раньше. `MYRMIDON_REVIEW_COMMENT_WAKE_GATE_ENABLED=off` выключает ворота комментария. (EMPTY-RUNS-2C) Подбор простаивающего участника ревью проверял только сохранённое состояние CI «ожидает» или «неизвестно»; теперь он читает CI головы как есть и применяет то же правило допуска: пока CI головы не закончился, не читается или красный, ревьюера не подбирают (критичную задачу подбирают). Если чтение не удалось, будит как раньше; тот же переключатель его выключает.
- **Сверка слотов шлюза (OPE-12984).** Когда шлюз недоступен, проход `gateway-slot-reconcile` заканчивался только после опроса до 64 завершённых прогонов по одному (по таймауту на каждый), и старт
  прогона ждал их все. Теперь первый ответ `unreachable` завершает проход.

## Карточки агентов, паузы и фильтр содержимого

- **Правка карточки при идущем прогоне (BOT-PROFILE-NO-RUN-INTERRUPT).** Правка, которой нужно остановить шлюз бота (смена профиля с перезапуском, расхождение образа или ресурсов), открывала окно обслуживания, ждала слива прогона агента и в срок прерывала его («Interrupted by maintenance mode»). Теперь, если прогон идёт, доска ничего не меняет, окно не открывает и применяет изменение после конца прогона (запись лежит в `myrmidonBotRolloutDeferred`; в активности видно «bot container update deferred»). Это относится к периодическому проходу (правки карточки, включая правку образа в карточке скриптом `bot-image-rollout.sh`), «Применить сейчас», ротации ключей и команде из чата. Проверка повторяется под окном, чтобы закрыть гонку с прогоном, допущенным между ними. Отложенное изменение, которое ждёт дольше `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (по умолчанию 6 часов), применяется со сливом и прерывает прогон, чтобы бот, который никогда не освобождается, всё же дошёл до нужного состояния. Нездоровый шлюз восстанавливается сразу. Волна переката образов, канарейка и откат применяют сразу со сливом, как раньше. Сторож отложенных выкатов теперь читает таблицу прогонов, а не вид окна, и часы записи переживают смену целевого образа. Из `runtimeConfig.heartbeat` до конфигурации шлюза доходит только `maxConcurrentRuns`; это по-прежнему изменение с перезапуском, теперь отложенное при идущем прогоне, а остальные поля хеш не меняют. Что заметит оператор: правка карточки занятого бота вступает в силу после его прогона, а не сразу; бот, занятый весь предел ожидания, перезапускается по его истечении.
- **Продолжение после паузы (RESUME-AFTER-CANCEL).** Когда оператор отменил прогоны агента и доска перезапустилась, действия восстановления закрывались исходом «не повторять», а снятие паузы будило задачи системными побудками, которые парковались как `execution_reconciliation_required`: каждую задачу приходилось будить вручную. Теперь снятие паузы распознаётся как действие оператора: побудка остаётся системной (обходов тормоза повторных побудок, защиты от шторма побудок и отсечки рабочей папки нет), но проходит удержание и снимает его, если удерживающий прогон `cancelled` (отмена оператором, снятие из очереди). Удержание прогона `failed`, `timed_out` или `interrupted` (исход неизвестен), удержание без названного прогона или с вычищенным, ещё идущий прогон, автоматические и системные побудки и `retry_failed_run` по-прежнему удерживаются. Прогон в очереди агента на паузе больше не снимается обходом по возрасту очереди (`queued_run_stale_timeout`): он ждёт снятия паузы и стартует со своей причиной побудки. Раньше обход снимал его, а заменяющая побудка падала с 409 «Agent is not invokable», и после снятия паузы задачу никто не продолжал. Страница обхода в 200 строк теперь тоже не включает прогоны агентов на паузе, поэтому массовая пауза не вытесняет просроченные прогоны других агентов.
- **Ответ, заблокированный фильтром содержимого (CONTENT-FILTER-RETRY).** Когда поставщик модели обрезал ответ с `finish_reason: content_filter` (ответ HTTP 200, даже на безобидный рабочий текст), бот сразу завершал прогон с `content_policy_blocked`, а доска запускала задачу с начала: 58 прогонов инженеров (675 минут) за 7 дней. Теперь бот повторяет тот же вызов модели до двух раз на прогон, сохраняя сессию и сделанную работу. Это работает только там, где прогон раньше падал сразу: бот с настроенной резервной моделью по-прежнему переключается на неё, и повторы оставляют место для этих переключений. Отказ, переживший повторы, завершает прогон как раньше, а текст сбоя говорит, что отказ повторился. Путь HTTP 4xx (`content_policy_blocked` как ошибка) не менялся. Это патч hermes 36, он действует после переката образа бота; пропустит ли фильтр поставщика повторный вызов, заранее неизвестно, каждый повтор стоит вызова модели.

## Стадия ревью в контексте задачи

- **Участник видит стадию (REVIEW-STAGE-IN-CONTEXT).** Ревьюеры, разбуженные CI, подбором простоя или оператором, отвечали «executionStage=null, активного участника нет» и отказывались записывать решение, хотя стадия ждала и они были её участниками (OPE-12886, OPE-12906, OPE-12941): `executionStage` строился только для побудок самой стадии, а `GET /api/issues/:id/heartbeat-context` его не содержал. Теперь в ответе есть поле верхнего уровня `executionStage`, построенное той же функцией: идентификатор и тип стадии, состояние, текущий участник, кому вернуть, последнее решение, допустимые действия, `isCurrentParticipant` и строка `youAre`. Текущий участник получает `wakeRole: "reviewer"` (`"approver"`) и действия `approve` и `request_changes`; исполнитель возвращённой стадии — `"executor"`; любой другой — `"observer"`, без действий и с текстом «You are not a participant of the review stage». Поле равно `null`, только когда стадии в работе нет.
- **Одобрение записывается (REVIEW-APPROVAL-RECORDED).** На rc.2 одобрение ревьюера отклонялось с HTTP 409 (`issue_done_pull_request_gate`), стадия оставалась `pending` или падала в `idle`, а восстановление блокировало задачу (OPE-13059, OPE-13061). Когда перевод в `in_review` назначал ревьюера, а затем побудка ревьюера откладывалась (ожидание CI или квота побудок на тик), политика монитора допуска строилась из политики до назначения и затирала сохранённую политику значением `stages: []`; `done` участника попадал на стадию, которой в политике уже не было. Побудка, начавшая прогон, значения не имела. Теперь политика монитора строится на политике, сохранённой после правки и назначения. Одобрение текущего участника ожидающей стадии ревью записывается и тогда, когда политика потеряла стадию или пропала целиком: стадия завершается с решением «одобрено», а при открытом PR задача, как обычно, ждёт слияния. Задачи, уже попавшие в такое состояние, ручной починки не требуют; одобрение, как и раньше, требует комментария.

## omp_local

- **Предел вызовов модели (OMP-RUN-GUARD-1).** У прогона `omp_local` не было предела вызовов модели, только `timeoutSec` (3 часа); 13.11 сессия в среднем делала 101 вызов, самая длинная — 494. Теперь адаптер питает
  сторожа прогона доски: предел тот же, что у hermes, 150 вызовов по умолчанию, переопределяется карточкой агента `runGuard.modelCallLimit`, `runGuard` в живости команды или `MYRMIDON_RUN_GUARD_MODEL_CALL_LIMIT`. За пятнадцать вызовов до предела
  агент получает сообщение «завершайся» (коммит, push, комментарий к задаче); после предела адаптер останавливает процесс, а о следующем прогоне решает продолжение сторожа (`run-guard-stop`). Остальные остановки сторожа
  (чтение без правок, повтор вызова, простой) теперь действуют и на прогоны `omp_local`. Прогон, остановленный по SSH, восстанавливает рабочую папку. Часть длинных сессий omp теперь будет заканчиваться остановкой и продолжением.
- **Отмена по SSH (OMP-RUN-GUARD-2).** 13.11 две сессии продолжали работать на раннере после отмены прогона (46 и 22 минуты, 337 вызовов модели). Теперь адаптер сам слушает сигнал отмены прогона
  и останавливает локальный ssh-клиент; отмена, пришедшая до регистрации клиента, применяется при его запуске.
- **Выгрузка рабочей папки (OPE-13041).** Выгрузка на удалённый раннер падала с `ssh exited before tar finished (code 0)`, когда ssh закрывался чуть раньше tar, хотя все данные были доставлены. Теперь итог определяют коды
  выхода обоих процессов (tar получает до 10 с после выхода ssh с кодом 0). Протокол и раскладка не менялись.

## Устаревшие блокировки

- **Обход устаревших блокировок (STALE-BLOCK-LIVE-EDGES).** Доска писала «stale block sweep failed for one task» около 50 раз в час по одним и тем же 14 заблокированным задачам. У каждой названная причина была мертва, а связь
  с ещё открытой задачей — жива. Теперь обход считает такой открытый блокер живой причиной: задача остаётся заблокированной и просыпается обычным путём `issue_blockers_resolved`, когда блокер закроется. Мёртвая причина, у которой все блокеры
  закрыты, снимается как раньше. Предупреждение о сбое теперь содержит класс исключения и его HTTP-статус.
- **Задача без исполнителя (STALE-BLOCK-UNASSIGNED).** Задача, созданная сразу в `blocked` с закрытым блокером и без исполнителя, заставляла обход писать «stale block sweep failed for one task» (HTTP 422) на каждом проходе и оставалась заблокированной навсегда: обход выбирал `in_progress`, а сервис задач отказывает в нём, когда нет ни агента, ни пользователя в исполнителях. Теперь такая задача уходит в `todo` (мёртвая связь удаляется, в комментарии «без исполнителя»); задача с исполнителем возвращается в `in_progress`, как раньше. Предупреждение о сбое теперь несёт и `errorMessage`: фиксированную фразу отказа сервиса задач для 4xx-ошибки (не длиннее 120 символов), так что причину повторного 422 видно в журнале.
- **Задача закрыта до старта прогона (RUN-SETUP-STALE-TASK).** Прогон по `issue_assigned` ждал слот агента, пока задачу закрыли, а её PR влили; на старте он падал с `setup_failed` / `continuation_task_ownership_changed` и записью уровня error (17 раз за 7 дней), потому что проверка устаревания пропускала любую побудку с комментарием. Теперь такой прогон по задаче в `done` или `cancelled` отменяется при взятии с `issue_terminal_status` (запись info, без `failed`). Побудки по комментарию, намерения возобновления и адресаты карточек ведут себя как раньше, а настоящие сбои подготовки остаются `failed`.

## Как проверить после обновления

Проверки взяты из описаний pull request; для этой страницы они не запускались.

- **Побудки от GitHub.** В течение суток после прихода итога CI по задаче на ревью в `agent_wakeup_requests` есть строка с `requested_by_actor_id = 'system:github-ci'` (за трое суток до этого было 0) и прогон исполнителя. Запрос вебхука не зависает.
- **Взаимные блокировки.** В журнале нет `deadlock detected` по `issue_work_products` и ответов 500 от `POST /api/myrmidon/github-app/webhook`.
- **Красный main.** Пока `main` красный, записей `issue.ci_failed` по красным на main шардам не появляется; удержания — это записи `issue.ci_infra_retry_needed`, и каждая запись `issue.ci_failed` несёт `failedChecks`.
- **Пустые прогоны.** Доля прогонов `swarm_matched` / `idle_pickup`, ничего не менявших, падает, а повторяющаяся строка «stale block sweep failed» по тем же задачам исчезает.
- **Правка карточки при прогоне (BOT-PROFILE-NO-RUN-INTERRUPT).** Изменить поле с перезапуском (например, `maxConcurrentRuns`) у агента с идущим прогоном: прогон дойдёт до конца, в активности будет «bot container update deferred», запись появится в `myrmidonBotRolloutDeferred`, а после прогона следующий проход перезапустит бота. Из описания pull request; для этой страницы не запускалось.
- **Сводка CI (CI-SNAPSHOT-CANCELLED).** `ciResult` задачи, у PR которой CI был заменён, показывает `success`, а не FAILURE; голова только с отменёнными проверками показывает `cancelled` и «cancelled, not a test failure»; настоящее падение по-прежнему FAILURE. Для этой страницы не запускалось.
- **Стадия ревью (REVIEW-STAGE-IN-CONTEXT, REVIEW-APPROVAL-RECORDED).** В `GET /api/issues/:id/heartbeat-context` задачи на ревью есть `executionStage`; одобрение ревьюера после отложенной побудки записывается и не получает 409. Для этой страницы не запускалось.
- **Освобождение слота в очереди (EMPTY-RUNS-6B, EMPTY-RUNS-6C).** Число отмен `queued_run_stale_timeout` у прогонов с `waitReason = agent_concurrency` равно нулю, а прогон, ждавший слот, стартует с исходной причиной побудки (например, `ci_completed`). Из описания pull request; для этой страницы не запускалось.

Известные ограничения. Настоящее падение на красной базовой ветке удерживается до зелёной `main-green` на голове, то есть возвращается позже, а не теряется. Удержания и отметки (`ciReturnHold`, `ciFinalCheckSeen`)
хранятся в метаданных work product; если их целиком перезапишет другой писатель, удержание запишется повторно, а возврат после перезапуска `main-green` не произойдёт: задача пойдёт обычным путём ревью.
Чтение GitHub идёт внутри обработки доставки и ограничено 10 секундами.

Известные ограничения исправлений rc.3.
- Правка карточки занятого бота ждёт конца прогона, не дольше `MYRMIDON_BOT_ROLLOUT_DEFERRED_MAX_WAIT_SEC` (6 часов); после этого прогон сливается и прерывается. Канарейка и откат не ждут. Какая именно правка пересоздала контейнер бота 14.11, установить не удалось (журнал доски успел ротироваться).
- После паузы задачи, чей прогон закончился как `failed`, `timed_out` или `interrupted`, остаются удержанными. Не менялось: действие восстановления, закрытое исходом `blocked`, пока задача остаётся в `in_progress`, и `recovery-actions/resolve` с `restored`, отвечающий 200 без эффекта.
- Ответ, заблокированный фильтром, повторяется не больше двух раз на прогон и только у агента без резерва, как описано выше; путь HTTP 4xx не менялся. Повторы делят счётчик перезапусков хода, поэтому ход, в котором были и другие перезапуски, невидимые обработчику, всё же может закончиться раньше; повторы по каждому вызову со сбросом после успеха — отдельная задача на потом. Пропустит ли поставщик повторный вызов, заранее неизвестно.
- Одобрение восстанавливается для стадии, вышедшей из политики, а запрос правок участником в таком состоянии этим исправлением не охвачен. Прогон, разбуженный комментарием другого агента по закрытой задаче, по-прежнему стартует, как раньше: отмена по закрытой задаче действует только на побудки `issue_assigned`.
- Защита прогона в очереди не покрывает ожидание, которое проход старта сменил на `agent_fair_share` или `higher_priority_ready`.
