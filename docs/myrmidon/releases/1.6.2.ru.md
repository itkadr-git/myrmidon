# Выпуск 1.6.2 — заметки для оператора

> English version: [1.6.2.md](1.6.2.md)

включено по умолчанию и что требует переключателя или шага на хосте. Каждый
пункт прослежен до журнала изменений ([../CHANGELOG.ru.md](../CHANGELOG.ru.md))
и связанных руководств; полная процедура выката — в [../deploy.ru.md](../deploy.ru.md).

## Стабильность и исправления (без изменения настроек)

Это приходит с самим обновлением; включать ничего не нужно.

- **Задача, застрявшая из-за старого решения разбора, снова просыпается.**
  Задача, чья закрытая запись разбора держала `"replay": "blocked"`, стояла
  навсегда: каждая автоматическая побудка парковалась, а idle pickup считал
  припаркованную побудку покрывающей задачу. Теперь человек на доске,
  переведший задачу из `blocked` (или переназначивший рабочую задачу), в той же
  транзакции снимает её закрытые удержания, а припаркованная побудка больше не
  считается покрывающей задачу.
- **Чаты не удерживаются.** Чат (связанная ветка личных сообщений Telegram или
  чат агента на доске) — разговор, а не рабочая задача: разбор больше не
  переводит его в `blocked` и не записывает удержание повтора; новое сообщение
  человека всегда будит его. Если сообщение не может стартовать сразу
  (предыдущий ход завершается, открытый вопрос, агент на паузе, исчерпанный
  бюджет, порог памяти хоста), чат отвечает причиной простыми словами, с
  оценкой времени, где она известна. Руководство:
  [../guides/telegram-dm-status.ru.md](../guides/telegram-dm-status.ru.md).
- **Расход шлюза снова атрибутируется по ботам.** Сбор расходов не записывал
  ни одной строки: карточки ботов несут ключ шлюза привязкой `secret_ref`, а
  поиск ключей понимал только инлайн-значение или один общий секрет. Теперь
  ссылка карточки на секрет резолвится, и строки расхода атрибутируются агенту
  и его прогону. Сигнал подмены модели, использующий тот же поиск, чинится этим
  же изменением.
- **Плагины на старом SDK снова работают через bridge.** Плагинный bridge
  относил вызов воркера без эха идентификатора только к идущему вызову
  маршрута API плагина, поэтому вложенные вызовы из обработчиков
  `onEvent`/`performAction`/`getData`/`executeTool` отклонялись с «missing,
  expired, or unknown invocation scope» (пустой список страниц,
  неоткрывающиеся страницы, нерабочие инструменты записи в вики). Теперь
  атрибуция покрывает любой идущий вызов, выданный хостом. Условие-охранник не
  изменилось: атрибуция действует, только пока все идущие вызовы принадлежат
  одной компании.
- **Публикация релиза ждёт теговые прогоны образов.** Ворота публикации
  сопоставляли прогоны workflow только по `head_sha` коммита тега, поэтому
  видели уже зелёный прогон `main` того же коммита вместо тегового прогона
  образов, и проба дайджестов падала. Теперь ворота также фильтруют по
  `head_branch` и принимают зелёный прогон `main` того же коммита для полосы
  CI (`myrmidon-ci.yml` не имеет триггера на тег). Ручной перезапуск из `main`
  больше не переопределяет введённый тег.

## Допуск прогонов: порог свободной памяти хоста и плавный старт (включено по умолчанию)

До 1.6.2 проверка свободной памяти мерила cgroup сервера и не видела контейнеры
ботов: однажды 23 одновременных прогона исчерпали хост, пока сервер выглядел
здоровым. Два изменения чинят это:

- **Порог хоста.** Новый прогон (чем бы он ни был разбужен) стартует, только
  пока `MemAvailable` хоста минус бюджет прогонов, стартовавших за последние
  30 с, остаётся не ниже `minFreeHostMemoryMb` — по умолчанию **15360 МБ**
  (15 ГБ). Иначе прогон остаётся `queued` и повторяется каждые 15 с. Память
  хоста читается из `/proc/meminfo`; контейнерный meminfo (lxcfs) распознаётся
  и отвергается — смонтируйте файл хоста read-only и укажите его в
  `MYRMIDON_HOST_MEMINFO_PATH`.
- **Плавный старт.** `maxStartsPerMinute` теперь по умолчанию **5** (было
  выключено). Инстанс, уже сохранивший свои лимиты прогонов, сохраняет своё
  значение.

Где менять: Instance → General, раздел «Run limits» (а также Settings →
«Runs & queue») или `PATCH /api/myrmidon/runtime-limits`. Переопределения
окружения: `MYRMIDON_MIN_FREE_HOST_MEMORY_MB` (15360),
`MYRMIDON_MAX_RUN_STARTS_PER_MINUTE` (5); `0`/`off` выключает лимит. Изменения
применяются без перезапуска.

Как проверить, что работает:

- Опустите порог ниже свободной памяти хоста и верните обратно: стоящие в
  очереди прогоны стартуют в течение минуты, без перезапуска.
- Когда порог держит прогоны дольше 10 минут, стол внимания показывает «Runs
  held: host memory» с текущей свободной памятью и порогом; карточка исчезает с
  первым допущенным прогоном.

Руководство: [../guides/run-limits.ru.md](../guides/run-limits.ru.md); строки
настроек — в [../SETTINGS.ru.md](../SETTINGS.ru.md).

## Языковые серверы ботов по ролям (включено по умолчанию)

Каждый языковой сервер для рабочей копии TypeScript стоит около 1 ГБ кучи, а
большинство ботов никогда не пишет код. С 1.6.2 режим определяется для каждого
бота:

- Роли, пишущие код (по умолчанию `engineer`, `qa`, `devops`, `reviewer`,
  `release`), работают в режиме **limited**: один TypeScript-сервер на рабочую
  копию, без автоматической загрузки типов, потолок кучи 1024 МБ, таймаут
  простоя 120 с.
- Каждый другой бот работает в режиме **none** (`lsp.enabled: false`).

Согласие не требуется: политика применяется при обновлении (один перезапуск на
контейнерного бота, под его паузой). Тайпчек монорепо не затронут — он идёт
через сборочный сервер.

Где менять: политика инстанса на Instance → General → «Bot language servers»
(`GET`/`PATCH /api/myrmidon/bot-lsp`): какие роли пишут код, режим для
кодовых и прочих ролей (`off` / `limited` / `full`), таймаут простоя, потолок
памяти, исключённые корни рабочих копий. Один агент может закрепить свой режим
в разделе «Language servers» своей карточки. Изменения применяются без
перезапуска сервера, на следующем такте сверки.

Как проверить, что работает: панель политики показывает, сколько ботов
работает в каждом режиме; после изменения блок `lsp` в `config.yaml` бота
обновляется на следующем проходе сверки.

Руководство: [../guides/bot-lsp.ru.md](../guides/bot-lsp.ru.md); справочник
полей — в [../SETTINGS.ru.md](../SETTINGS.ru.md).

## Общий кэш пакетов для ботов разработки (по умолчанию выключен)

Боты разработки скачивают одни и те же пакеты pnpm, модули Go и зависимости
Gradle снова и снова, каждый в свой том. С общим кэшем пакетов каждый бот хоста
доски монтирует один набор каталогов кэша на запись, и скачанное хранится один
раз:

| Каталог хоста | Точка монтирования в боте | Переменная в профиле бота |
|---|---|---|
| `<cache>/pnpm` | `/cache/pnpm` | `npm_config_store_dir` |
| `<cache>/go-mod` | `/cache/go-mod` | `GOMODCACHE` |
| `<cache>/go-build` | `/cache/go-build` | `GOCACHE` |
| `<cache>/gradle` | `/cache/gradle` | `GRADLE_USER_HOME` |

pip не покрыт (`PIP_NO_CACHE_DIR` образа нельзя снять). Боты на хосте fleetd
кэш не получают.

Шаги включения (нужны все три):

1. Создайте четыре подкаталога и отдайте их пользователю бота (uid и gid 10001
   в образе бота) — иначе Docker создаст отсутствующий от root, и бот не
   сможет в него писать:

   ```sh
   install -d -o 10001 -g 10001 /srv/package-cache/{pnpm,go-mod,go-build,gradle}
   ```

2. Задайте тот же каталог как `packageCacheRoot` в конфигурации dockergate и
   пошлите dockergate `SIGHUP` (применяется без перезапуска). Без этого
   dockergate отказывает каждой привязке кэша с `mount_source_not_allowed`, и
   ошибка сверки называет бота. См. [../dockergate.ru.md](../dockergate.ru.md).
3. Сохраните путь в настройке инстанса: Instance → General, панель «Shared
   package cache for bots», или `PATCH /api/myrmidon/bot-disk` с
   `{"sharedPackageCachePath": "/srv/package-cache"}` (только администратор
   инстанса). `null` или пустая строка выключает кэш.

Перезапуск сервера не нужен: локальный драйвер и компилятор профилей перечитывают
настройку на каждом проходе сверки, так что на следующем проходе каждый бот
пересоздаётся с новыми привязками и перезапускается с новыми переменными.
Каталог должен быть простым абсолютным путём и не должен лежать внутри корня
томов ботов.

Как проверить, что работает:

- После прохода сверки у контейнера бота есть четыре привязки `/cache/*`, а его
  `hermes/.env` направляет четыре переменные на них.
- Привязка кэша при незаданном `packageCacheRoot` отклоняется с
  `mount_source_not_allowed` в журнале dockergate — этот отказ называет бота,
  чья сверка пыталась её сделать.

Компромисс: все боты хоста делят кэш на запись, поэтому включайте его только
для ботов, которые уже доверяют друг другу (боты разработки одной команды).
Полное руководство: [../bot-disk-cache.ru.md](../bot-disk-cache.ru.md).

## Ключи активации плагинов (шлюз включён; ключи добавляете вы)

Плагин, чей манифест задаёт `requiresEntitlement: true`, остаётся неактивным —
ни процесса воркера, ни слотов интерфейса, скрыт из меню и настроек, — пока
администратор инстанса не примет действующий ключ активации для его точного id
плагина. Где: блок «Plugin keys» на странице настроек инстанса или
`GET`/`POST`/`DELETE /api/myrmidon/plugin-entitlement/keys`. Шлюз перечитывает
настройки на каждом проходе активации, так что принятие или удаление ключа
действует без перезапуска. Без зарегистрированных ключей для плагинов, не
требующих ключа, ничего не меняется. Руководство:
[../guides/plugin-entitlement-keys.ru.md](../guides/plugin-entitlement-keys.ru.md).

## Тяжёлые сборки заблокированы в dev-образе бота (включено по умолчанию, только dev-образ)

Вариант образа бота для разработки больше не полагается на договорённость
держать тяжёлые сборки вне контейнера бота: заглушки `pnpm`, `tsc`, `vitest`,
`gradle` и `go` (первые в `PATH`) отказывают каждому нетривиальному вызову с
кодом 1 и сообщением, называющим точную замену `devbuild …`. Лёгкие проверки
работают локально (`pnpm --version`, `pnpm config …`, голые
`--version`/`--help`), а `git`, `node`, `cargo`, `gh`, `docker` не обёрнуты.
Для сборки: `devbuild pnpm install`, `devbuild pnpm exec tsc --noEmit`,
`devbuild pnpm vitest run`, `devbuild go build ./...` — рабочая копия
монтируется в сборочный контейнер на сборочном хосте, и та же команда
выполняется там. См. `docker/bot-runtime/README.md`, раздел «Heavy builds are
blocked at the image level».

## Режим обслуживания: асинхронный выход и пост-деплойная проверка парка

Выход из режима обслуживания асинхронен: вызов `exit` возвращается, как только
окно помечено `leaving`, а хвост (возобновление очереди побудок, хук выхода,
снятие окна) выполняется на такте обслуживания
(`MYRMIDON_MAINTENANCE_TICK_SEC`, по умолчанию 5 с). Выкат опрашивает состояние
обслуживания, пока окно не станет `off`, с границей `MAINTENANCE_EXIT_WAIT_SEC`
(по умолчанию 120 с).

Выкат завершается пост-деплойной проверкой парка только на чтение (шаг 9): при
заданных `BOARD_API_URL` и `BOARD_COMPANY_ID` она спрашивает у доски задачи в
`blocked`, обновлённые с начала выката, и перечитывает состояние обслуживания;
попадание завершает прогон с `DEPLOY DEGRADED` — это вердикт, а не провал уже
переключённого и здорового выката. Без этих двух настроек проверка
пропускается. Задайте их в окружении выката, чтобы включить её.

## Режимы исполнения бюджетных лимитов (умолчание соответствует прежнему поведению)

Что делает пересечённый бюджет расхода — теперь режим, а не фиксированная
остановка: `signal_only` (по умолчанию — инцидент и сигнал владельцу
появляются, прогоны стартуют), `soft` (пауза и карточка «поднять бюджет или
оставить на паузе»), `hard` (новые прогоны пересёкшего лимит скоупа
отказываются). Один режим на весь инстанс, меняется на лету с экрана
Instance → General или `PATCH /api/myrmidon/budget-enforcement`; переопределение
окружения — `MYRMIDON_BUDGET_ENFORCEMENT_MODE`. С умолчанием поведение
соответствует прежнему выпуску. Руководство:
[../guides/budget-enforcement.ru.md](../guides/budget-enforcement.ru.md).

## Лимит WIP (подсчёт включён; лимиты по желанию)

Лимит незавершённой работы на агента: умолчание для всей компании и
переопределения по агентам редактируются на экране «WIP limit» в настройках
компании. Текущая нагрузка `in progress + in review` каждого агента видна в
таблице экрана, значком `wip/limit` на странице агентов и в ленте внимания. Без
сохранённого лимита нагрузка всё равно считается и показывается, но ничего не
сигналит. Руководство: [../guides/wip-limit.ru.md](../guides/wip-limit.ru.md).

## Автооткат по здоровью: руководство оператора (только документация)

Существующее поведение (провал проверки здоровья после выката откатывает доску
на запомненный прежний образ) получает руководство оператора: когда срабатывает
откат, шаги работы и фазы отчёта, куда записывается причина сбоя, что видит
владелец при неудачном откате и настройки обеих половин выключателя. Код не
меняется. Руководство:
[../guides/deploy-auto-rollback.ru.md](../guides/deploy-auto-rollback.ru.md).

## Распознавание голоса, серверное ядро (по умолчанию выключено)

Серверное ядро распознавания речи поставляется с бэкендами `dashscope` (через
общий шлюз LiteLLM) и `deepgram` и контрактом `transcribeAudio` со стабильными
кодами ошибок. По умолчанию выключено: без `MYRMIDON_STT_ENABLED` путь не
делает исходящих запросов. Ключи бэкендов — секреты компании, на которые
ссылаются только по имени. См. [../SETTINGS.ru.md](../SETTINGS.ru.md), раздел
VOICE-STT.
