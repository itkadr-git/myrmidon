# Режимы принуждения ограждений (1.7)

Каждое правило ограждений базового слоя 1.6.1 теперь работает в одном из трёх
режимов принуждения. Режим задаётся в интерфейсе доски на уровне компании,
касты или агента и применяется **без перезапуска**: смена режима действует на
следующий ответ затронутого агента.

## Правила

| Правило | Точка | Что проверяет |
|---|---|---|
| `secret` | `run_output` | Финальный текст прогона (формы ключей/токенов). |
| `pii` | `run_output` | Финальный текст прогона (e-mail, телефоны, карты, СНИЛС/ИНН). |
| `injection` | `wake_queue` | Комментарий внешнего автора в очереди до того, как его прочитает прогон. |

Реквизиты юрлиц сознательно **не** входят в правила — владелец отложил эту
работу.

## Режимы

| Режим | Поведение в точке |
|---|---|
| `flag` (умолчание) | Записать событие в журнал; ничего не менять. Поведение 1.6.1. |
| `mask` | Записать событие (severity `warn`) и заменить каждый совпавший фрагмент в видимом тексте нейтральным заполнителем `[masked]`. Хранимые данные прогона/журнала не меняются, сниппет маскируется как раньше. |
| `block` | Записать событие (severity `error`) и отказаться отдавать вывод: ответ заменяется отказом на языке оператора — правило, число срабатываний, где задан режим; сами совпавшие значения не раскрываются. |

Для правила `injection` исполнение происходит в очереди побудок: `block`
сохраняет комментарий как есть, но подменяет то, что несёт payload прогона,
обёрткой-отказом; `mask` заменяет текст внутри маркеров
`<untrusted-data>` в payload. Вид комментария в интерфейсе доски не меняется
ни в одном режиме.

## Приоритет

Эффективный режим правила для одного агента резолвится при каждом срабатывании:

```
env force  >  агент  >  каста (роль)  >  компания  >  flag (умолчание)
```

- Каста = роль агента (`agents.role`).
- `MYRMIDON_GUARDRAILS_MODE_FORCE` — **аварийный рычаг только для оператора**:
  валидное значение (`flag`, `mask`, `block`) принудительно включает этот режим
  для всех правил и всех агентов, перекрывая настройки интерфейса. Всё
  остальное — не задано, пусто, опечатка — означает «без принуждения»;
  ошибочное значение не может молча переписать политику блокировки. Это
  единственная переменная окружения фичи.

Настройки перечитываются из базы при каждом срабатывании (два чтения по
первичному ключу на финализацию прогона); кэша и перезапуска нет.

## Где хранятся настройки

Документ настроек лежит в `instance_settings.general.guardrailModes`
(тот же механизм, что лимит WIP, отдельной таблицы нет):

```json
{
  "company": { "secret": "mask" },
  "castes": { "engineer": { "pii": "flag" } },
  "agents": { "<agent-uuid>": { "injection": "block" } }
}
```

Переопределяют только заданные ключи; каждый незаданный ключ наследует. Схема
строгая: неизвестное правило, режим или вложенность дают 400 вместо
частичного применения.

## Интерфейс

`Настройки компании → Guardrails` (текущий интерфейс, не 2.0):

- по строке на правило для уровня компании, по селекту на правило;
- выбор касты с правилами по касте и таблица агентов с правилами по агенту;
- колонка **эффективного режима** на агента — резолвнутый режим с источником
  (`env` / `агент` / `каста` / `компания` / `по умолчанию`), берётся с сервера,
  а не вычисляется на клиенте — экран показывает настоящую цепочку приоритетов;
- под ним журнал срабатываний: свежие события с фильтрами по правилу (kind),
  важности и id прогона.

API:

- `GET /api/myrmidon/companies/:companyId/guardrails/settings`
- `PUT /api/myrmidon/companies/:companyId/guardrails/settings` (инстанс-админ)
- `GET /api/myrmidon/companies/:companyId/guardrails/resolve?agentId=…`
- `GET /api/myrmidon/companies/:companyId/guardrails/events?limit&kind&severity&surface&runId`

## Поведение при сбое

Резолв режима fail-open: если настройки или строка агента не читаются, правило
резолвится в `flag` (умолчание) и прогон продолжается. Ограждение не может
уронить прогон из-за сбоя чтения собственной политики.
