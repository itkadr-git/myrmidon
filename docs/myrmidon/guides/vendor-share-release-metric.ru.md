# Доля vendor-производных файлов в заметках релиза (VENDOR-SHARE-METRIC, 1.6.5)

Каждый релиз, опубликованный по тегу `myr-v*`, показывает, какая часть дерева
всё ещё унаследована от кода вендора и как это изменилось к прошлому релизу.

## Строка

```
Vendor-derived files: 6123 of 6812 (89.89%), Δ to myr-v1.6.4: +0.10 pp (+7 files)
```

В теле релиза она стоит под своим заголовком:

```
## Vendor-derived files
```

Саму долю считает `scripts/myrmidon/vendor-share.mjs` (слит в #563 / OPE-4151)
по базе вендора из `scripts/myrmidon/vendor-base.txt`. Δ считается к **строке
прошлого релиза**: тело предыдущего тега читается через
`gh release view <прошлый тег> --json body`, и старые числа разбираются из него.
Проценты пересобираются из двух количеств, а не из округлённого `89.78 %` в
тексте, чтобы дельта сравнивала сопоставимое с сопоставимым.

У релиза, вышедшего до появления метрики (или с телом, написанным руками),
строки нет — раздел говорит:

```
нет данных (no vendor-share line in that release)
```

## Где это работает

`scripts/myrmidon/release/publish-github-release.sh`, шаг **3b** — сразу после
сборки тела релиза (шаг 3, `release-body.mjs`) и до публикации (шаг 4,
`gh release create --notes-file release-body.md`). Строка дописывается в файл
тела, поэтому опубликованные заметки — ровно тот файл, что ушёл в релиз.

Работу делает `scripts/myrmidon/release/vendor-share-notes.mjs`: печатает одну
строку, возвращает `0` при успехе и `3` с причиной в stderr, когда долю
посчитать нельзя (пустой или нечитаемый файл состояния, рабочая копия без базы
вендора).

## Сбой метрики не роняет публикацию

Метрика совещательная. Ненулевой код возврата `vendor-share-notes.mjs` заставляет
публикатор записать

```
## Vendor-derived files

не посчитано (vendor-share metric failed; the release continues)
```

и предупреждение в лог, а релиз всё равно выходит. Ничто другое в гейте
публикации (дайджесты компонентов, CI самого тега, файл манифеста) от метрики
не зависит.

## Офлайн-швы

Релизный job ходит в GitHub, тесты — нет. Вместо внешнего мира подставляются две
переменные, рядом с существующей `MYRMIDON_RELEASE_REGISTRY_STATE`:

- `MYRMIDON_RELEASE_VENDOR_SHARE_STATE` — JSON-файл с текущей сводкой доли
  (`{"summary":{"inherited":6123,"totalFiles":6812,"share":0.899...}}`) вместо
  запуска `vendor-share.mjs`.
- `MYRMIDON_RELEASE_PREVIOUS_BODY` — файл с заметками прошлого релиза вместо
  `gh release view`.

Обе читает только `vendor-share-notes.mjs`; сервер их не видит. См.
`docs/myrmidon/SETTINGS.md`, раздел `Track 5 — operations`.

## Шаг CI

`vendor-share.mjs` также запускается на `main` в CI, публикует свой JSON
артефактом сборки и печатает ту же строку в лог — число видно на каждом
слиянии, а не только на релизе. Файлы workflow (`.github/workflows/*`)
применяет оператор доски: изменение едет вложением `format-patch` на задаче, а
не коммитом в PR с этим документом.

Релизному job нужна достаточная история, чтобы база вендора была в клоне; если
её нет, метрика вырождается в «не посчитано», а релиз не страдает.

## Тесты

```
node --test scripts/myrmidon/release/vendor-share-notes.myrmidon.test.mjs
node --test scripts/myrmidon/release/release-publish.test.mjs
```

Первый — юнит-контракт строки (формат, знак дельты, «нет данных», «не
посчитано», код 3, round-trip); второй прогоняет настоящий публикатор
end-to-end с поддельным `gh` и проверяет раздел в опубликованных заметках — в
том числе что релиз всё равно создаётся, когда метрика упала.
