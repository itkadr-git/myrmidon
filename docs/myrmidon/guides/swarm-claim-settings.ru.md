# Настройки очередей ролей (SWARM-CLAIM)

> English version: [swarm-claim-settings.md](swarm-claim-settings.md)

Очереди задач по ролям управляются из интерфейса, без перезапуска
доски: кто берёт задачи из очереди, сколько живёт аренда, сколько задач может
держать один агент, как часто ходит сторож и обгоняет ли задача P0 очередь. С
1.6.1 каждое значение — настройка инстанса.

## Где живут настройки

Instance → General → **Role queues (SWARM-CLAIM)**. Экран пишет
`instance_settings.general.swarmClaim` через `GET`/`PATCH /api/myrmidon/swarm-claim`
(чтение — любой член board; запись — instance-admin). Сервер перечитывает
строку при каждом клейме, checkout, тике сторожа и чтении супервизора — ничего
не кешируется при старте, рестарт не нужен.

## Поля

| Поле | Что ограничивает | По умолчанию |
|---|---|---|
| Enable role queues | Главный выключатель очередей | выкл |
| Roles in scope | Область очередей по ролям: какие роли клеймят. Через запятую (например `engineer`); **пусто = все роли** (это ограничение области, не «пилот»). Очереди на команде разработки — это ровно это поле с одной ролью | пусто |
| Companies in scope | Область очередей по компаниям: id через запятую; **пусто = все компании** | пусто |
| Idle wake batch | Сколько задач один idle-проход отдаёт агентам за раз (с 1.6.5 — сначала назначение и аренда, потом побудка) | `5` |
| Lease TTL, seconds | Сколько живёт одна аренда без heartbeat; прогон продлевает её на каждом проходе checkout | `900` |
| Max active tasks per agent | Потолок живых клеймов на агента; пусто = без потолка | `3` |
| Sweep interval, seconds | Как часто ходит сторож истёкших аренд; читается на лету, стартовое значение — нижняя граница | `30` |
| P0 preempts the queue | Вкл — задача `critical` стоит первой в очереди. Выкл — строго от старых к новым | вкл |

## Откуда берётся каждое значение

Рядом с каждым полем показан его источник — «Saved here» (сохранено здесь),
«Environment override» (переопределение из окружения) или «Default» — и тот же
источник показывает экран надзора SWARM (маршрут /swarm-claim) для своих значений. Переменные
`MYRMIDON_SWARM_*` — **принудительные переопределения**: заданная в окружении
переменная перекрывает сохранённое значение только своего ключа (см.
[SETTINGS.ru.md](../SETTINGS.ru.md)). Снимите переменную, чтобы вернуть
управление интерфейсу.

## Проход очереди: захват на сервере, потом побудка

У сторожа есть третий проход — **idle wake**; он идёт после освобождения
просроченных аренд и снятия зависших заявок. До 1.6.5 проход будил агента с
id неназначенной задачи и ждал, что захват случится на checkout прогона: но
диспетчер запуска видит у такой задачи исполнителя `NULL`, а у прогона —
другого агента, и отменяет побудку (`skipped`, «issue assignee changed before
the queued run could start»). Прогон до checkout не доходил, и за 7 дней ни
одна неназначенная задача так и не была взята (разбор
`ops/audit/swarmdiag-20261009.md`, OPE-6608).

С 1.6.5 порядок обратный: на пару «роль с готовой очередью + свободные агенты
этой роли» проход **сам назначает** верхнюю задачу свободному агенту и сразу
пишет аренду того же вида, что и checkout, — и только затем будит его этой
назначенной задачей. Побудок «иди поищи работу» без конкретной задачи нет: у
каждой побудки уже есть исполнитель. Если свободного агента роли нет — не
будится никто. Если запись аренды не удалась, назначение откатывается и задача
возвращается в очередь.

Агент считается свободным, если у него нет живой заявки и живого прогона, он
не на паузе, не в ошибке и не достиг потолка активных задач. Кто вообще может
брать задачи очереди — отдельный переключатель у агента (метаданные
`swarmQueueEligible`): по умолчанию он включён только роли исполнителя, а у
лида, ревьюера, архитектора и прочих агентов с `role=engineer` — выключен, они
получают причину `agent_excluded`. Сторож также не будит роли вне области
(`enabledRoles`/`enabledCompanyIds`) и касты с `swarmEligible: false`
(`caste_excluded`); потолок задач касты переопределяет глобальный для её
агентов.

Свободные агенты роли упорядочены по загруженности (живые аренды), при равной
загруженности — по времени последней активности: дольше всех простаивающий идёт
первым, поэтому верхушка списка не «прилипает» между проходами. У прохода два
ограничения:

- не больше `Idle wake batch` задач на роль за проход (по умолчанию `5`,
  значение вне диапазона 1–25 подрезается) — массовый импорт задач не может
  разбудить весь парк одним залпом;
- каждая побудка идёт через обычный допуск (`enqueueWakeup`), поэтому пауза,
  режим обслуживания и пороги памяти и CPU хоста продолжают действовать — пока
  порог закрыт, проход никого не будит и пишет причину в журнал (не чаще одной
  строки за пять минут).

Побудки идут с причиной `swarm_claim_queue`, и к этому моменту задача уже
назначена агенту — прогон проходит допуск и доходит до checkout. Запасной путь
самозахвата остаётся: агент может взять верхнюю задачу очереди своей роли через
`POST /api/myrmidon/companies/{companyId}/swarm-claim/claim` (описан в
агентском навыке).

## Как проверить, что самоорганизация работает

1. Включите *Enable role queues*, выставьте *Roles in scope* = `engineer`
   (пусто = все роли) и, если компаний несколько, *Companies in scope*.
2. Внизу панели смотрите строку **«Queues right now»**: «в очереди» — сколько
   готовых задач ждёт исполнителя, «захвачено за час» и «отменено за час» — по
   живым арендам и по отменённым побудкам за последний час. Через минуту после
   включения при непустой очереди «захвачено за час» должно стать ≥ 1, а
   «отменено за час» — не расти.
3. Второй способ — по задаче: у неназначенной задачи появляется исполнитель без
   участия человека, в `issue_claims` лежит живая аренда, у агента стартует
   прогон с причиной `swarm_claim_queue`, а не `skipped`.
4. Сводка экрана надзора за роем (маршрут /swarm-claim) показывает счётчик
   **freeAgentsWithQueue** — свободные агенты роли с непустой очередью. Здоровые
   очереди держат его на нуле: если оно не падает, проход не может отдавать
   задачи (агенты на паузе, потолки исчерпаны, закрыт порог допуска, role/agent
   вне области) — и очередь ждёт оператора.

## Включение очередей на одну роль

Поток приёмки: включите *Enable role queues*, впишите `engineer` в *Roles in
scope* (и id компании в *Companies in scope*, когда компаний на инстансе
несколько), сохраните. В течение минуты свободный инженер получит верхнюю
задачу очереди инженеров: проход назначит её и запишет аренду, затем разбудит
инженера, checkout подтвердит аренду, а завершающийся прогон освободит её и
передаст следующему инженеру роли.

## Выключение

Выключение *Enable role queues* (или принудительное
`MYRMIDON_SWARM_CLAIM_ENABLED=0`) действует сразу: живые аренды освобождаются
синхронно — ответ сохранения сообщает, сколько (`releasedClaims`) — а сторож
повторит проход на своём тике с причиной освобождения `pilot_disabled`,
покрывая то, до чего синхронный проход не добрался. Прогоны, державшие
освобождённые аренды, завершаются сами; задачи возвращаются к вендорскому
поведению назначений.

## Журнал изменений

Каждое сохранение дописывает запись журнала — кто, что и когда, новее сверху —
она показана внизу секции и хранится в `general.swarmClaimJournal` (не больше
50 записей). То же изменение пишет строку `instance.swarm_claim.updated` в
журнал активности, который остаётся аудиторским следом.
