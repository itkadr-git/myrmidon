# Асимметричные дебаты: генератор, критик и судья вне спора (1.7 DEBATE-ASYM A)

> Английская версия: [debate-asym.md](debate-asym.md)

Одна модель, оценивающая собственный ответ, — не рецензия, а эхо. Движок
дебатов запускает структурированный спор об одном вопросе задачи между
моделями **разных семейств**, так что слепое пятно одного вендора атакует
другой:

| Роль | Полярность | Правило |
|---|---|---|
| **Генератор** | конструктивная | предлагает и затем защищает лучший конкретный ответ |
| **Критик** | адверсариальная | ищет каждую ошибку, пропуск и рискованное допущение; в его промпте сказано, что за пропущенную ошибку он штрафуется, поэтому он не смягчается. Когда ничего не осталось неразрешённым, пишет `[AGREE]` — обмен останавливается |
| **Судья** | вне спора | третье семейство: читает весь протокол и выносит вердикт вместе с ответом — стороны не принимает |

Два первых ответа **независимы**: критик излагает свою позицию, не видя
ответа генератора, поэтому критика не привязана к нему. Обмен идёт не больше
**трёх кругов**; останавливается досрочно по согласию или по **потолку
токенов** (потолок общий на все вызовы дебатов). Результат — все позиции,
вердикт судьи и **стоимость** — кладётся на задачу документом `debate-result`,
а расход пишется cost-событиями на уровне задачи, поэтому бюджетный контроль
BUDGET-CONFIG считает дебаты как любую другую работу.

## Правило разных семейств

`getModelFamily()` относит id модели к семейству по одной расширяемой таблице
(те же правила, что ввёл EVALS-JUDGE-FAMILY для эвалов). Конфигурация
отклоняется — до единого вызова, до любого сохранения — когда:

- генератор и критик из одного семейства (`qwen-plus-free` и
  `qwen-turbo-free` — один вендор; дебаты обязаны быть асимметричными), или
- судья делит семейство с кем-то из спорщиков (судья обязан быть вне спора).

Id, которого таблица не знает, — семейство `unknown`; два неизвестных
считаются разными вендорами: проверка строга к известным коллизиям и
консервативна к отказам.

## Где настраивается

Экран — **Instance → General → Asymmetric debates** (рядом с панелью
бюджетного контроля), API — `GET`/`PATCH /api/myrmidon/debate/settings`
(GET читает доска, PATCH пишет админ экземпляра). Сохранение пишет
`instance_settings.general.debate` и применяется к **следующему запуску
дебатов — без перезапуска**: конфигурация читается во время запуска, никогда
не кэшируется при старте. Источник действующего значения показан рядом с
формой: *Saved here* / *Forced by the server environment* / *Built-in
default*.

| Уровень | Значение |
|---|---|
| Сохранённые настройки | что сохранил экран — источник истины после сохранения |
| `MYRMIDON_DEBATE_CONFIG` | принудительное JSON-переопределение для экземпляра, который ничего не сохранял |
| Встроенное умолчание | бесплатные модели, по семейству на роль: `qwen-plus-free` генератор, `glm-4-flash-free` критик, `deepseek-chat-free` судья; 3 круга; потолок 50 000 токенов |

Невалидное или симметричное значение на любом уровне сообщается как причина и
отклоняется — никогда молча не заменяется следующим уровнем.

Контур шлюза (адрес chat-completions и *имя* корпоративного секрета с
ключом) сначала читает `MYRMIDON_DEBATE_BASE_URL` /
`MYRMIDON_DEBATE_KEY_SECRET` и падает на evals-контур (`MYRMIDON_EVALS_*`).
Пока не резолвится ни один, endpoint запуска отвечает 503 с причиной, и экран
настроек показывает её — доска видит, почему кнопка отказала.

## Запуск дебатов по задаче

```
POST /api/myrmidon/companies/{companyId}/debates/issues/{issueId}/run
```

Тело необязательное: `{ "question": "..." }`; без него вопросом служит
заголовок задачи. Вызывать могут и доска, и агент — по матрице автономии
(правило владельца): доска матрицей не ограничена; агент проходит проверку по
классу `spend_above_threshold` — дебаты расходуют шлюз. `forbidden` даёт 403
(`autonomy_forbidden`), `approval_required` — 403 с
`autonomy_approval_required` (та же промежуточная форма, что у других
маршрутов принуждения, до появления held-action для маршрутов без вызова).

При успехе ответ несёт весь итог (круги, причина остановки, токены против
потолка, разбивка стоимости по ролям и моделям), и на задаче лежит документ
`debate-result` — с позициями, вердиктом и стоимостью. Ошибки
сопоставлены по роду: 422 с точной причиной семейной коллизии при
симметричной конфигурации, 503 при неразрешённом контуре шлюза или секрете
ключа, 502 при сбое самого шлюза.

## Стоимость и бюджетный контур

Каждый вызов считается по конфигу роли (`inputCentsPer1k` /
`outputCentsPer1k`, отсутствие = бесплатно = 0) против usage, который
сообщил шлюз, — при отсутствии usage используется оценка «символов / 4».
Разбивка стоимости попадает в документ результата по ролям и итогом, и расход
каждой роли пишется строкой `cost_events` (код `myrmidon-debate`, id задачи,
агент-инициатор если запуск агента) — из той же таблицы читает контроль
BUDGET-CONFIG, поэтому расход дебатов считается на уровне задачи как любой
другой.

Одна тонкость: вызов, пересёкший потолок токенов, **не тарифицируется** — его
стоимость записывается отдельно как `ceilingCrossedCents` и видна в документе,
но не входит в итог и в cost-события, поэтому потолок действительно значит
«не больше этого». Запуск от доски (без идентичности агента) не пишет
cost-строк (таблица привязана к агенту); его расход несут журнал активности и
документ.

## Тесты

Движок чистый — каждый вызов модели идёт через один порт `call`, — поэтому
критерии приёмки прогоняются на фейках дословно:
`packages/shared/src/myrmidon-debate.test.ts` (отказ симметричной
конфигурации, остановка на третьем круге и на потолке, стоимость в документе)
и `server/src/myrmidon/debates/{service,gateway,settings}.myrmidon.test.ts`
(поток сервиса, контур шлюза, живая прецедентность настроек).
