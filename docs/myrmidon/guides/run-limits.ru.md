# Лимиты допуска прогонов

> English version: [run-limits.md](run-limits.md)

Сервер может ограничивать, сколько прогонов побудок он запускает одновременно,
как быстро он их стартует и сколько свободной памяти он держит в запасе. С выпуска
1.3 эти лимиты меняются на лету: из интерфейса или через API, без перезапуска
сервера и без обрыва уже идущих прогонов.

## Лимиты

| Настройка | Что ограничивает | По умолчанию |
|---|---|---|
| `maxConcurrentRuns` | Сколько прогонов этот процесс сервера держит в работе одновременно. Прогоны сверх потолка остаются `queued`; очередь идёт от старых к новым | выключено |
| `maxStartsPerMinute` | Плавный старт: сколько прогонов может стартовать за скользящую минуту, кто бы их ни разбудил | `5` (с 1.6.2; было выключено) |
| `minFreeMemoryMb` | Прогон стартует, только если после его бюджетирования в cgroup сервера (v2) останется столько свободной памяти. С 1.6.5 OWNER-CHAT-ADMISSION это пол, по которому допускается ответ на сообщение владельца в чате, — к контейнеру и к `MemAvailable` хоста: более высокий порог хоста ниже его не держит | выключено |
| `runMemoryEstimateMb` | Сколько мегабайт бюджетируется на один прогон при подсчёте свободной памяти | `300` |
| `minFreeHostMemoryMb` | Прогон стартует, только пока у ХОСТА остаётся не меньше столько `MemAvailable` (за вычетом бюджета прогонов, стартовавших за последние 30 с). Боты работают в своих контейнерах вне cgroup сервера, `minFreeMemoryMb` их не видит, а этот порог видит. С 1.6.5 OWNER-CHAT-ADMISSION он разводит только автоматические прогоны: ход владельца в чате допускается по `minFreeMemoryMb` (в том числе к `MemAvailable` хоста) и стартует при закрытом пороге хоста | `15360` (15 ГБ, с 1.6.2) |

Значение «выключено» (пустое поле, `null` в сохранённых настройках) снимает этот
лимит. `runMemoryEstimateMb` выключить нельзя: это бюджет, по которому считается
проверка свободной памяти.

### Порог свободной памяти хоста (1.6.2)

`minFreeHostMemoryMb` читает `MemAvailable` из `/proc/meminfo`. В Docker-контейнере
без lxcfs это файл хоста, поэтому доске не нужны ни монтирование, ни доступ к
Docker API. Если lxcfs подставляет в файл лимит контейнера, порог отвергает такое
чтение, один раз пишет в журнал `run admission cannot read host memory…` и не
действует; смонтируйте `/proc/meminfo` хоста только на чтение и укажите путь в
`MYRMIDON_HOST_MEMINFO_PATH`.

Прогон, задержанный порогом, остаётся `queued`; проход очереди повторяет попытку
каждые 15 с, и прогон стартует, как только память хоста освободится или порог
понизят. Проход swarm idle wake, пока порог закрыт, никого не будит. Если порог
держит прогоны дольше 10 минут, оператор получает карточку внимания «Runs held:
host memory» с текущей свободной памятью и порогом; она исчезает с первым
допущенным прогоном. Понижение (или выключение) порога в настройках отпускает
очередь в пределах минуты, без перезапуска.

### Кто ждёт при каком пороге (1.6.5 OWNER-CHAT-ADMISSION)

Пороги меряют разные вещи, поэтому с 1.6.5 они держат разные прогоны:

- `minFreeHostMemoryMb` и `maxHostLoadPercentPerCore` разводят АВТОМАТИЧЕСКИЕ
  прогоны — расписания, мониторы, idle pickup, фоновые доработки. Задержанный ими
  прогон остаётся `queued`, проход очереди повторяет попытку каждые 15 с (см.
  выше).
- `minFreeMemoryMb` — жёсткий пол контейнера сервера и с 1.6.5 единственный
  пол памяти для ответа на сообщение, которое владелец написал в чате. Он
  применяется дважды: к свободной памяти контейнера и к `MemAvailable` хоста (за
  вычетом бюджета стартующих прогонов) — боты живут вне контейнера, и видит их
  только чтение хоста. Когда хост между `minFreeMemoryMb` и `minFreeHostMemoryMb`,
  ответ стартует сразу, а автоматические прогоны продолжают ждать; на хосте ниже
  `minFreeMemoryMb` ждёт и он.

Ход опознаётся по durable-квитанции входящего сообщения (запрос побудки, у
которого `idempotencyKey` начинается с `chat-inbound:`, а инициатор — участник
доски) — на неё ссылается прогон в очереди; кнопка чата «повторить упавший
прогон» и чат-побудка от системного актора ходом владельца не считаются. Проход
очереди ставит такие ходы раньше автоматических, поэтому ход, который всё-таки
ждёт (его держит только `minFreeMemoryMb`), стартует первым, раньше любого
автоматического прогона, в каком бы состоянии ни была его задача. Ход, чья задача
ещё ждёт зависимостей, остаётся за готовыми прогонами.

Весь конвейер по-прежнему называет, кто ждёт: у прогонов в очереди причина
ожидания читается как `host_memory` / `host_cpu` / `memory`, карточка внимания
оператора и экран «Прогоны и очередь» их перечисляют, а чат говорит об ожидании,
только пока ход действительно ждёт (то есть пока его держит `minFreeMemoryMb` —
по контейнеру или по хосту), и говорит, что очередь перепроверяется каждые 15 секунд.

Префикс ключа идемпотентности `chat-inbound:` зарезервирован за durable-квитанцией
чата: публичные маршруты побудки агента отклоняют ключ с этим префиксом (`422`).

## Откуда берётся действующее значение

У каждого лимита есть один из трёх источников; он показан рядом с полем в
интерфейсе и в ответе API:

- `settings` — значение, сохранённое в настройках инстанса;
- `env` — переменная окружения, значение по умолчанию при первом старте;
- `default` — встроенное значение (только у `runMemoryEstimateMb`: 300 МБ).

Переменные окружения — `MYRMIDON_MAX_CONCURRENT_RUNS`,
`MYRMIDON_MAX_RUN_STARTS_PER_MINUTE`, `MYRMIDON_MIN_FREE_MEMORY_MB` и
`MYRMIDON_RUN_MEMORY_ESTIMATE_MB` (см. [SETTINGS.md](../SETTINGS.md)). Это значения
по умолчанию при первом старте: после того, как лимиты сохранены из интерфейса или
через API, действуют сохранённые настройки, и переменные больше не применяются.

## Изменение лимитов из интерфейса

Откройте Instance → General и найдите секцию «Run limits». Четыре поля показывают
действующие значения и их источники:

- **Concurrent runs**, **Starts per minute**, **Free memory to keep, MB** —
  введите целое число больше нуля или оставьте поле пустым, чтобы выключить лимит
  («No limit»).
- **Memory per run, MB** — бюджет на один прогон; поле обязательно, очистить его
  нельзя.

Нажмите «Save run limits». Нецелое или неположительное значение блокирует
сохранение.

## Изменение лимитов через API

Прочитать действующие лимиты и их источники (любой член организации доски):

```sh
curl -H "Authorization: Bearer <token>" http://localhost:3100/api/myrmidon/runtime-limits
```

Записать новые лимиты (только администратор инстанса). Передавайте только меняемые
ключи; ключ со значением `null` выключает этот лимит:

```sh
curl -X PATCH \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"maxConcurrentRuns": 8, "minFreeMemoryMb": 2048}' \
  http://localhost:3100/api/myrmidon/runtime-limits
```

`0`, отрицательное, дробное или нечисловое значение, `null` у бюджета памяти или
лишний ключ отклоняются с `400`, и ничего не записывается.

## Что происходит после изменения

Изменение сохраняется в `instance_settings.general.runLimits`, в журнал активности
каждой компании пишется запись `instance.runtime_limits.updated` со старыми и новыми
значениями, и только после этого новые лимиты применяются к живому допуску. Подъём
лимита также назначает проход очереди, так что задержанные старым потолком прогоны
стартует в пределах минуты — без перезапуска сервера и без обрыва идущих прогонов.
Понижение лимита тоже не останавливает идущие прогоны; оно лишь задерживает новые
старты, пока счёт не опустится ниже нового потолка.

При старте сервера сохранённые лимиты читаются и применяются до запуска
планировщика.

## Когда проверка памяти не действует

Если процесс не видит предел памяти своего cgroup (`memory.max` равен `max`, на
хосте cgroup v1 или сервер не в контейнере), проверка свободной памяти неактивна, и
один раз в журнал пишется предупреждение `run admission cannot read the cgroup
memory limit…`. Потолки одновременных прогонов и стартов в минуту при этом
действуют. Если предупреждение есть, а предел контейнера задан, — проверьте, как
запущен сервер.

## Как увидеть отказы допуска (1.6.5)

Секция Run limits рисует ещё одну строку:

```
Admission refusals: 12 since the server started. By reason: concurrency ceiling
x7, start ramp x3, host memory floor x1, memory floor x1. The last refusal: the
start ramp.
```

Итог считает проходы очереди, которые оставили queued-прогон в ожидании из-за
глобального или хостового потолка, — прогон, который просто стоит за другими в
очереди, в счёт не входит. Рядом с итогом строка показывает разбивку по причинам
(от большей к меньшей) и причину последнего отказа; причина, которой экран не
знает, показывается под своим именем.

Строку питает поле `admissionDenials` в ответе
`GET /api/myrmidon/runtime-limits`. Сервер, который это поле не отдаёт (старше
изменения, которое его добавляет), строки не рисует вовсе — экран не показывает
выдуманный ноль, остальная секция работает как прежде.

## Почему прогон ждёт в очереди (1.6.5 F-09)

Прогон, остающийся в `queued`, всегда несёт причину ожидания — она записана в
его снимке контекста как `waitReason`. Каждый выход обхода очереди, который
оставляет прогоны ждать, оставляет и причину; захват, стартующий прогон, снова
стирает пометку, поэтому у работающего прогона устаревшей причины нет.

| `waitReason` | Почему прогон ждёт |
|---|---|
| `global_cap` | Потолок одновременных прогонов (`maxConcurrentRuns`) занят |
| `start_ramp` | Предел стартов в минуту (`maxStartsPerMinute`) исчерпан на текущую минуту |
| `memory` | Порог свободной памяти контейнера (`minFreeMemoryMb`) закрыт |
| `host_memory` | Порог свободной памяти хоста (`minFreeHostMemoryMb`) закрыт |
| `host_cpu` | Потолок загрузки CPU хоста (`maxHostLoadPercentPerCore`) закрыт |
| `agent_fair_share` | Агент исчерпал свою долю стартов (`maxPerAgentStartSharePercent`) |
| `agent_concurrency` | Собственный потолок одновременных прогонов агента занят |
| `priority` | Проход очереди стартовал прогоны, но слот занял более тяжёлый |
| `higher_priority_ready` | Готовая задача того же агента с более высоким приоритетом держит этот прогон |
| `maintenance` | Открыто окно обслуживания агента |
| `agent_not_invokable` | Агента нельзя разбудить (пауза, вывод из строя и т. п.), и он не отменяется |
| `scheduling_suppressed` | Весь проход планировщика подавлен (например, паузой) |

Прогон, который ждёт дольше порога объяснения, гарантированно несёт причину;
порог — `MYRMIDON_QUEUED_RUN_EXPLAIN_AFTER_SEC` (умолчание `60` секунд,
зажимается в 10…86400 с), живое перекрытие —
`instance_settings.general.queuedRunExplainAfterSec`.

Есть одно намеренное исключение: прогон, чьё ожидание не объяснил ни один
выход, остаётся с `waitReason = null`. Это и есть дефект, от которого защищает
исправление F-09, и именно о нём сообщает карточка внимания `queue_stall` — см.
[queued-run-stall.ru.md](queued-run-stall.ru.md).

## Отмена queued-прогонов до потолков (1.6.5 F-09)

До того, как сработают выходы по потолку агента и честной доле, обход отменяет
каждый queued-прогон, чья задача нестартуема: задача в `backlog`. Отмена
записывается на прогоне с кодом ошибки `queued_run_issue_not_startable`,
поэтому история прогона говорит, куда делась работа, а не выглядит тихой
потерей. Прогон со скрытой задачей остаётся в очереди — скрытые задачи todo —
поддерживаемый шаблон Суммаризатора, их судьбу решает путь захвата.
