# Оверлей потокового учёта стоимости LiteLLM v1.104.1

> English version: [litellm-streaming-cost-overlay.md](litellm-streaming-cost-overlay.md)

Этот runbook описывает рабочий оверлей для шлюза LiteLLM v1.104.1. Он исправляет конкретный
сбой учёта: потоковый ответ Experiential или `hosted_vllm` может сообщить `usage.cost = 0.0`,
даже если для deployment заданы собственные цены модели.

## Область и фиксация образа

Оверлей предназначен для образа LiteLLM на шлюзе `vm-core`:

- образ: `ghcr.io/berriai/litellm:v1.104.1@sha256:501909ec...`;
- upstream-тег: `v1.104.1`;
- upstream-коммит: `48963be81b8a1844e09a7769c940bc25d5c66d54`.

Сокращённый digest выше перенесён из README оверлея deployment. При монтировании используйте
полный production digest из конфигурации deployment; не подменяйте версию LiteLLM без сборки и
проверки соответствующего оверлея.

## Что монтируется

Оверлей заменяет эти полные модули в виртуальном окружении LiteLLM внутри контейнера:

- `litellm/main.py` → `/app/.venv/lib/python3.13/site-packages/litellm/main.py`;
- `litellm/litellm_core_utils/litellm_logging.py` →
  `/app/.venv/lib/python3.13/site-packages/litellm/litellm_core_utils/litellm_logging.py`.

Монтируйте оба файла из `litellm/patches/1.104.1/`. Если заменить только один модуль, расчёт
потока и путь записи журнала трат могут разойтись.

## Сбой и ожидаемое поведение

В chunk провайдера может быть числовой `usage.cost`, равный `0.0`. Немодифицированный LiteLLM
v1.104.1 считает это значение окончательным, поэтому builder потока и путь логирования не
используют заданную собственную цену. Непотоковые вызовы при этом могут записываться правильно,
из-за чего дефект легко пропустить.

С оверлеем, если включено собственное ценообразование и провайдер сообщил ноль, LiteLLM считает
стоимость по ценам токенов:

`prompt_tokens × input_price + completion_tokens × output_price`

Результат записывается в `usage.cost`, передаётся как `response_cost`, а затем попадает в
`LiteLLM_SpendLogs.spend`. Ненулевое значение от провайдера и deployment без собственных цен
сохраняют обычное поведение. Если собственной цены нет, оверлей не выдумывает её.

## Выкатка

1. Убедитесь, что шлюз работает на закреплённом образе LiteLLM v1.104.1.
2. Во время согласованного рестарта шлюза скопируйте или смонтируйте оба модуля по указанным
   путям.
3. Не монтируйте удалённый исторический backfill-скрипт и каталог оверлея `1.108.0`.
4. Перезапустите шлюз в утверждённом окне обслуживания.
5. Убедитесь, что контейнер здоров, и отправьте представительный потоковый запрос к deployment
   с известными ненулевыми ценами входа и выхода.
6. Сохраните идентификатор запроса и число токенов для записи о проверке, но не помещайте API-ключи
   и их значения в логи или комментарий задачи.

Оверлей меняет только расчёт при работе. Исторические строки не пересчитываются: по решению от
26 октября и подтверждению ADM от 30 октября backfill не выполняется.

## Проверка потоковой стоимости

Первичная проверка после изменения оверлея — тест из репозитория:

```bash
python3 litellm/patches/1.104.1/tests/test_stream_spend_cost.py
# или
python3 -m unittest discover -s litellm/patches/1.104.1/tests -v
```

Тест должен загрузить файлы оверлея по пути и пройти все семь тестов. Он проверяет:

1. прямой импорт обоих модулей;
2. обнаружение нулевой стоимости потока при включённых собственных ценах;
3. замену `usage.cost` расчётом по токенам и цене;
4. обход нулевого `hidden_params["response_cost"]` для моделей с собственными ценами;
5. сквозное сохранение положительного значения `tokens × price` в `SpendLogs.spend`.

Для живой smoke-проверки используйте модель с известной ненулевой ценой и небольшой потоковый
запрос. В одном окне запроса проверьте всё перечисленное:

- поток завершился нормально;
- присутствует usage prompt- и completion-токенов;
- `usage.cost` от провайдера может быть `0.0`, но рассчитанная стоимость ответа положительна;
- соответствующая строка `LiteLLM_SpendLogs` имеет `spend > 0` и равна расчёту по заданным ценам,
  с обычной для шлюза точностью;
- повторный запрос не создаёт дублирующую строку для того же request id.

Если строка равна нулю, сначала проверьте, что запрос использовал смонтированные файлы v1.104.1
и что у deployment действительно есть собственные цены. Если одна из проверок не пройдена,
результат не подтверждает оверлей. Если обе пройдены, прекратите дальнейший трафик, сохраните
request id и очищенные логи и эскалируйте проблему выкатки шлюза.

## Откат

Если шлюз стал нездоров или smoke-проверка не прошла, снимите монтирования оверлея и восстановите
ранее утверждённые образ и конфигурацию LiteLLM штатной процедурой отката шлюза. Не изменяйте
исторические строки трат при откате. Зафиксируйте digest образа, ревизию оверлея, request id и
наблюдавшееся значение spend для инцидента.
