# Лимиты расхода по уровням иерархии (1.7 BUDGET-CONFIG)

Myrmidon хранит лимиты расхода по уровням иерархии и отдаёт их через API с
полным журналом изменений. Лимит отвечает на один вопрос: «сколько этот скоуп
может тратить за период и что происходит на лимите». Модуль —
`server/src/myrmidon/budget-limits/` (трек 1.7 BUDGET-CONFIG, часть A).

## Уровни

Одна строка на `(company, level, ref)`:

| Уровень | `ref` | Что ограничивает |
|---|---|---|
| `nest` | `company` или uuid проекта | вся компания или один проект |
| `caste` | ключ роли (`engineer`, `designer`, …) | все агенты касты |
| `foraging` | `foraging` | бюджет прохода фуражировки (поглощает OPE-3964) |
| `issue` | uuid задачи | одна задача |

Поля строки: `amountCents`, `period` (`calendar_month_utc` или `lifetime`),
`mode`:

- `hard` — жёсткий: отказ, работа сверх лимита отклоняется;
- `soft` — мягкий: пауза и карточка владельцу «расширить на $N или остановить».

## Глобальный режим «только сигнал»

Режим `signalOnly` включён по умолчанию и остаётся включённым, пока владелец
явно его не выключит. Пока он включён, лимиты не останавливают работу — любое
превышение это сигнал, а не блокировка. Режим меняется на лету (без
перезапуска):

```
GET   /api/myrmidon/companies/:companyId/budget-limits/signal-only
PATCH /api/myrmidon/companies/:companyId/budget-limits/signal-only   (board)
      тело: { "signalOnly": false }
```

GET отвечает действующим значением **и его источником** — `stored` (то, что
задал владелец), `default` (ничего не задано; включён) или `env` (задано
принудительное переопределение `MYRMIDON_BUDGET_LIMITS_SIGNAL_ONLY`, оно
важнее сохранённого значения). Опечатка в значении env никогда не меняет выбор
владельца: принимаются только `1/true/yes/on` и `0/false/no/off`, всё
остальное игнорируется.

## API

База: `/api/myrmidon/companies/:companyId/budget-limits`. Чтение — участники
компании; каждая мутация — только board, с записью в журнал активности.

```
GET    .../budget-limits                  список (можно ?level=)
GET    .../budget-limits/limits/:level/:ref       один лимит
PUT    .../budget-limits/limits/:level/:ref       создать или заменить (board)
       тело: { amountCents, period, mode, isActive }
DELETE .../budget-limits/limits/:level/:ref       удалить (board)
GET    .../budget-limits/journal          журнал изменений, новые сверху
GET    .../budget-limits/usage            расход по каждому лимиту + overLimit
GET    .../budget-limits/signal-only      действующий флаг + источник
PATCH  .../budget-limits/signal-only      включить/выключить блокировку (board)
```

`PUT` идемпотентен на `(company, level, ref)`: сохранение той же тройки
заменяет строку.

## Журнал изменений

Каждое создание, изменение и удаление пишет строку `budget_limit_changes`:
кто (`actorType`/`actorId`), когда (`at`) и что (снапшоты `before`/`after`
изменённых полей). Журнал только appending: удаление лимита сохраняет его
историю. `GET …/journal` отдаёт список, новые сверху, можно по уровню.

## «Израсходовано за период»

`GET …/usage` считает расход каждого лимита из существующего учёта — журнала
`litellm_cost_events`, который собирает свип M2-A (атрибуция по агенту, по
задаче, с `occurredAt`):

- nest `company` → все события компании в окне;
- nest проект → события задач проекта;
- каста → события агентов с ролью ref;
- задача → события с `issueId` = ref;
- фуражировка → бюджетное состояние свипа FORAGING.

Окно — это `period` лимита: `calendar_month_utc` — [первый день текущего
месяца UTC, первый день следующего), `lifetime` — без границы. Это та же
математика окон, что у вендорских бюджетных политик.

## Таблицы

Миграция `0301` добавляет две таблицы, обе аддитивные (вендорские таблицы не
тронуты):

- `budget_limits` — строки лимитов, одна на `(company_id, level, ref)`;
- `budget_limit_changes` — журнал.

Флагу «только сигнал» таблица не нужна: он живёт в
`instance_settings.general.budgetLimits` (тот же паттерн JSON-колонки, что у
WIP-лимита и runtime-настроек STT).
