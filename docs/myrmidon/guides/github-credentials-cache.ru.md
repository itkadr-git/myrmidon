# Политика кэширования и предохранителя учетных данных GitHub (1.6.6 OPE-9997, 1.6.7 OPE-12446)

Сервер Myrmidon предоставляет учетные данные операций GitHub агентам и интеграционным инструментам через сервис брокера (`server/src/services/github-operation-credentials.ts`).

До версии 1.6.6 (OPE-9997) каждый запрос учетных данных или операция git выпускали новый installation access token от GitHub. Это приводило к задержкам (несколько секунд на каждую операцию) и повышенной нагрузке на лимиты GitHub App. В версии 1.6.7 (OPE-12446) добавлены дисковый кэш на стороне бота, single-flight дедупликация запросов на брокере и предохранитель частоты запросов прогона для защиты почасовых квот установки GitHub App от циклов ботов.

## Архитектура и уровни кэширования

### 1. Кэш брокера в оперативной памяти (на стороне сервера)

- **Время жизни (TTL)**: 50 минут (`50 * 60 * 1000` мс). Стандартное время жизни installation token от GitHub составляет 60 минут; TTL в 50 минут гарантирует валидность токена в течение всего периода кэширования и предотвращает использование протухших токенов.
- **Ключ кэша**:
  ```text
  companyId:agentId:runId:identityContextId:revision:responsibleUserId:repository
  ```
  Ключ изолирует учетные данные по компании, агенту, прогону (run), контексту identity, ревизии, ответственному пользователю и репозиторию. Токены никогда не переиспользуются между разными контекстами или задачами.
- **Single-Flight дедупликация**: Одновременные запросы с одинаковым ключом кэша присоединяются к единому активному промису резолва токена. Брокер выпускает ровно один токен из GitHub, и все параллельные вызовы получают один и тот же результат без повторного расхода лимитов GitHub App.

### 2. Дисковый кэш среды выполнения бота (на стороне клиента)

Для исключения сетевых обращений к брокеру при каждом локальном вызове `git` или `gh` среда выполнения бота предоставляет дисковый кэш:

- **Каталог кэша**: Активируется переменной окружения `PAPERCLIP_GITHUB_CREDENTIALS_CACHE_DIR`. При запуске раннер указывает в ней рабочий каталог прогона (`$PAPERCLIP_RUN_SCRATCH_DIR` / run scratch). Если переменная не задана, клиентский кэш выключен (что позволяет юнит-тестам проверять точное число обращений к брокеру).
- **Хранение и безопасность**: Файлы кэша сохраняются в `<cacheDir>/.paperclip-broker-cache/<hash>.json` с правами `0600` (доступны только пользователю процесса). Имя файла: `sha256(brokerToken|repository)[0..32].json`.
- **TTL клиентского кэша**: 45 минут (`45 * 60 * 1000` мс), но не более заявленного срока действия токена с запасом безопасности в 1 минуту (`CACHE_EXPIRY_MARGIN_MS = 60 * 1000`).
- **Валидация**: При каждом чтении клиентский помощник проверяет наличие токена, конечность таймстемпов и границы срока действия. Устаревшие, некорректные или поврежденные записи немедленно удаляются (`fs.rmSync(file, { force: true })`), после чего запрашивается новый токен.

## Предохранитель частоты запросов прогона (Rate Limiting)

Чтобы предотвратить исчерпание лимита установки GitHub App (5000 запросов в час) из-за зациклившихся ботов или некорректных скриптов, брокер применяет предохранитель запросов перед проверкой кэша или выпуском токена:

- **Настройка**:
  - `MYRMIDON_GITHUB_CREDENTIALS_FUSE_PER_MINUTE` (устаревший псевдоним: `PAPERCLIP_GITHUB_CREDENTIALS_FUSE_PER_MINUTE`).
  - По умолчанию: `60` запросов в минуту.
  - Нечисловое или неположительное значение (`<= 0`) сбрасывается в умолчание (60).
- **Семантика скользящего минутного окна**:
  - Брокер хранит отметки времени запросов по ключу `companyId:runId` в скользящем 60-секундном окне (`GITHUB_CREDENTIALS_FUSE_WINDOW_MS = 60 * 1000`).
  - Устаревшие отметки времени старше 60 секунд очищаются при каждом обращении. При превышении 2000 записей в таблице отслеживания полностью устаревшие окна удаляются.
- **HTTP 429 Too Many Requests**:
  Если один прогон совершает более допустимого лимита запросов за 60 секунд, брокер возвращает HTTP 429:
  ```text
  Too many GitHub credential requests from this run: over <limit> per minute. Cache the issued token until it expires instead of requesting one per git/gh call.
  ```

## Проверка безопасности и политик

1. **Проверка политики экспорта**: Перед чтением из кэша или генерацией токена функция `allowsGitHubCredentialExport` (`server/src/services/github-credential-policy.ts`) проверяет, разрешен ли экспорт учетных данных политикой инстанса и компании.
2. **Проверка активности гранта**: При попадании в кэш функция `isCachedCredentialStillActive` проверяет:
   - Подключение остается активным (`connection.status === "connected"`).
   - Грант не был отозван (`grant.revokedAt === null`).
   Если грант отозван или подключение отключено, запись в кэше немедленно удаляется.
3. **Сброс и очистка**:
   - Явный сброс: вызов `clearGitHubOperationCredentialCache()` очищает кэш токенов, незавершенные промисы in-flight и окна предохранителя при обновлении настроек подключения или ключей GitHub App.
   - Устаревшие записи удаляются автоматически при обращении к кэшу.

## Рекомендации операторам при ошибках HTTP 429

Если оператор видит ошибку `429 Too Many Requests` или сообщения о срабатывании предохранителя credentials:

1. **Диагностика источника**:
   Проверьте журнал упавшего прогона или задачи. Код 429 означает, что конкретный прогон совершил более 60 запросов credentials за 60 секунд. Типичные причины:
   - Команды git (`git status`, `git fetch`, `git diff`) вызываются в цикле в bash-скриптах или кастомных инструментах без переиспользования учетных данных.
   - Переменная `PAPERCLIP_GITHUB_CREDENTIALS_CACHE_DIR` не передана или каталог недоступен для записи в кастомном адаптере.
   - Параллельный запуск множества процессов `git`/`gh` без передачи общего окружения.
2. **Исправление на клиенте**:
   - Убедитесь, что среда выполнения передает `PAPERCLIP_GITHUB_CREDENTIALS_CACHE_DIR`, указывающий на валидный временный каталог прогона, чтобы работал встроенный кэш токенов.
   - Переиспользуйте полученный `GH_TOKEN` или `GITHUB_TOKEN` между вызовами в скриптах, не запрашивая авторизацию заново на каждую строчку.
3. **Действия оператора**:
   Если пакетной операции или массовому прогону объективно требуется более высокий лимит запросов, увеличьте порог в переменных окружения сервера:
   ```bash
   MYRMIDON_GITHUB_CREDENTIALS_FUSE_PER_MINUTE=120
   ```
   Переменная применяется сразу или при перезапуске процесса без изменения политик компании.

## Эксплуатация и мониторинг

Операторы могут отслеживать работу брокера учетных данных через:
- **Метрики нагрузки API**: `GET /api/myrmidon/board-load/api-load` замеряет количество вызовов `/runtime-tools/github/credentials`, p50, p95 и максимальную длительность.
- **Журнал лимитов GitHub**: Расход лимитов брокером логируется с префиксом `[github-rate-limit]` и тегом `broker`, что позволяет контролировать почасовой выпуск токенов (`broker` ≤ 300 в час при обычной нагрузке).
