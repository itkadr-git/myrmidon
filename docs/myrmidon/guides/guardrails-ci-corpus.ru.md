# GUARDRAILS: проверка ложных срабатываний на эталонном корпусе в CI

myrmidon(1.7-GRD-CI): блокирующие режимы не включаются вслепую. Прежде чем
детектор режима «только флаг» станет блокирующим, CI должен доказать, что он
не срабатывает на чистом тексте. Этот трек подключает эталонный корпус 1.6.1
(часть C GUARDRAILS, нейтральные фикстуры) к отчёту precision/recall по правилам и к
блокирующей проверке в CI: любой ложный блок на чистой фикстуре — красный.

## Как это работает

1. Корпус (`server/src/myrmidon/guardrails/corpus/`) — размеченные кейсы:
   каждый говорит, какой детектор обязан сработать (`expect.detector`:
   `secret`, `pii`, `injection`) или `null` — чистая фикстура, на которой не
   должно сработать ничего.
2. Харнесс (`server/src/myrmidon/guardrails/eval/evaluate.ts`) прогоняет
   каждое зарегистрированное правило по каждому кейсу и считает по правилу:
   support, TP/FP/FN, ложные блоки (правило сработало на кейсе с
   `expect.detector: null`), precision и recall. Скоринг чистый — один код,
   один корпус, одни числа; артефакт воспроизводим.
3. Реестр правил (`server/src/myrmidon/guardrails/eval/rules.ts`) связывает
   детекторы корпуса с поставленными детекторами:
   - `injection` — эвристика очереди пробуждений на shipped-пороге 0.6.
     Eval всегда измеряет порог по умолчанию; env-переопределение меняет
     только рантайм, никогда — артефакт.
   - `secret` / `pii` — выходные детекторы части A. Их модуль
     приходит своим мержем; пока `detect.ts` нет в ветке, правила
     регистрируются как `pending-base-layer`: покрытие показывается, правила
     не срабатывают и не могут закрасить гейт. Как только модуль появляется,
     правила активируются сами, без правки этого кода.
4. Отчёт по правилам закоммичен как генерируемый артефакт рядом с харнессом:
   `report.json` (машиночитаемый) и `report.md` (та же таблица для людей).
   CI-тест (`eval.myrmidon.test.ts`) пересчитывает отчёт и падает на любом
   расхождении — правку детектора, сдвинувшую ложные срабатывания или
   пропуски, невозможно слить так, чтобы дифф артефакта это не показал.

## Гейт

Блокирующее число — `totalFalseBlocks`, срабатывания правил на чистых
фикстурах. Цель: 0. Тест проверяет:

- ноль ложных блоков у активных правил (критерий приёмки задачи);
- закоммиченные `report.json` / `report.md` равны пересчитанному отчёту;
- заведомо ложносрабатывающее правило красит гейт (сигнализация регрессии:
  то же утверждение сработает, когда реальный детектор начнёт блокировать
  чистую фикстуру);
- переразметка кейса корпуса без обновления артефакта тоже ловится
  проверкой расхождения.

## Обновление артефакта

После любой правки детектора или корпуса — пересоздать осознанно:

```sh
pnpm --filter @paperclipai/server exec tsx \
  ../scripts/myrmidon/guardrails-eval/refresh.ts
```

Генератор отказывается писать (код 1), если eval красный. Два файла отчёта
коммитятся в том же PR, что сдвинул числа, — эта видимость на ревью и есть
смысл артефакта.

Порядок слияния с частью A (`secret`/`pii` — выходные детекторы): до появления
её модуля в main правила находятся в `pending-base-layer` и активируются её
мержем. Ветка, которая мержится второй, обновляет артефакт на ребейзе (команда
выше): на бейзе со слитой частью A проверка расхождения красная, пока в
закоммиченном отчёте не появятся активные строки secret/pii. Обновление — за
PR, который мержится вторым.

## Что отчёт пока не гейтит

Recall. Injection-эвристика пока не ловит часть корпуса (таблица по подтипам
в `report.md` называет каждый пропущенный кейс); recall измеряется,
отслеживается в артефакте и проверяется только как «tp + fn = support».
Поднимать его — задача трека режимов ограждений, который решает
блокировку по правилу; числа этого артефакта — его доказательная база.
Ложные пропуски слияние не блокируют; ложные блоки — всегда.

## Настройка

В рантайме — ничего. Eval — фиксированное измерение shipped-умолчаний: без
env, без UI-переключателя, без semantics перезапуска — он живёт только в CI.
У самих детекторов свои настройки (см. SETTINGS: `MYRMIDON_GUARDRAILS_*`).
