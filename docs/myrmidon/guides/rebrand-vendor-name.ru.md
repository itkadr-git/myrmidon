# Имя вендора в сборке (REBRAND F)

> English version: [rebrand-vendor-name.md](rebrand-vendor-name.md)

Правило ребренда 1.7: название вендора остаётся только в `LICENSE`, в файле
сторонних уведомлений и в строке «based on … (MIT)» на экране About. Всё, что
человек читает в интерфейсе, и всё, что отвечает сервер, — **Myrmidon**.

Это руководство описывает сторож, который так и держит. Он читает **собранный**
интерфейс и **записанные ответы сервера**, поэтому ловит имя вендора, которое
появилось только после сборки — в склеенной строке бандла, в сжатой константе, в
теле ответа эндпоинта, — а не только упоминание в исходниках.

## Где имя остаётся

| Где | Почему |
|---|---|
| `LICENSE`, `NOTICE`, файл сторонних уведомлений | Лицензия MIT требует сохранить исходный copyright и текст разрешения |
| Строка «based on … (MIT)» на About | Атрибуция, которой требует лицензия, показанная там, где человек её найдёт |
| Заголовки `X-Paperclip-*`, переменные `PAPERCLIP_*`, пакеты `@paperclipai/*`, пути API, ключи хранилища | Идентификаторы протокола и хранения, а не видимый текст. Они живут один релиз как алиасы, чтобы установленные системы и навыки агентов не сломались (см. [CONVENTIONS.md](../CONVENTIONS.md), §8) |
| `Paperclip Cloud`, `Paperclip Labs`, `Paperclip EE`, `Paperclip Enterprise` | Реальные внешние сервисы вендора: переименовать их — назвать то, чего не существует |
| Старые фразы уведомлений восстановления «Paperclip …» | Комментарии, сохранённые до переименования, всё ещё несут их, и интерфейс распознаёт такие уведомления по точному тексту |
| Название части нашего продукта | Исключения нет: «Myrmidon Runner», «Myrmidon Computer», «Myrmidon-managed» |

Список исключений сторожа повторяет аллоулист сторожевого теста исходников
`ui/src/lib/myrmidon-branding-guard.myrmidon.test.ts` (B1a). Новое упоминание
вендора, которого нет ни в одном из списков, — утечка.

## Что читает сторож

Две цели:

- **bundle** — собранный интерфейс (`ui/dist`): ровно тот текст, который получает
  браузер.
- **snapshots** — записанные тела ответов основных эндпоинтов
  (`scripts/myrmidon/vendor-name/snapshots`):
  - `GET /` — index.html с брендингом;
  - `GET /site.webmanifest` — имя, которое получает иконка на домашнем экране;
  - `GET /api/openapi.json` — документ API: его заголовок и описание, а также
    summary, описание и текст полей каждой операции. Снимок хранит именно текст
    (уникальный, отсортированный), а не мегабайты сгенерированной структуры
    вокруг него.

Обе цели считаются в двух классах, потому что ребренд намеренно оставляет имя
вендора как идентификатор:

- **visible** — имя вендора с заглавной буквы (`\bPaperclip\b`): то, что читает
  человек. Именно по этому классу сторож и срабатывает.
- **identifier** — любое другое написание (`paperclip`): `@paperclipai/*`,
  `PAPERCLIP_*`, `/api/paperclip/…`, ключи хранилища. Печатается в отчёте, но не
  гейтится: это алиасы, которые обязаны работать один релиз.

## Режимы

| Режим | Сторож падает, когда | Когда применяется |
|---|---|---|
| `ratchet` (по умолчанию) | число видимых вхождений цели **выросло выше базы** из файла политики | сейчас: видимые строки REBRAND A (интерфейс) и REBRAND B (тексты сервера) ещё на подходе |
| `strict` | осталось любое видимое вхождение вне исключений | после слияния REBRAND A и REBRAND B: в собранном интерфейсе и в ответах сервера остаются только исключения выше |

Порядок выбора режима:

1. `--mode ratchet|strict` в командной строке;
2. `MYRMIDON_VENDOR_NAME_CHECK_MODE` — принудительное переопределение на один
   прогон или одну установку;
3. поле `mode` в файле политики — умолчание репозитория, его же использует CI.

Переход в `strict` — правка в две строки в одном PR: `"mode": "strict"` в файле
политики и обе базы опущены до числа вхождений-исключений, которые остаются.
Никогда не поднимайте базу, чтобы CI стал зелёным: уберите вхождение или
добавьте исключение с причиной.

## Как запускать

```sh
# обе цели, локально (интерфейс должен быть собран)
pnpm --filter @paperclipai/ui build
node scripts/myrmidon/vendor-name/check-vendor-name.mjs

# одна цель, с машиночитаемым отчётом
node scripts/myrmidon/vendor-name/check-vendor-name.mjs --target bundle --json /tmp/vendor-name.json

# так это делает сборочная полоса CI, со свежими снимками:
pnpm --filter @paperclipai/server exec tsx \
  ../scripts/myrmidon/vendor-name/capture-snapshots.ts --out "$RUNNER_TEMP/vendor-name-snapshots"
node scripts/myrmidon/vendor-name/check-vendor-name.mjs --target snapshots \
  --snapshots "$RUNNER_TEMP/vendor-name-snapshots"
node scripts/myrmidon/vendor-name/check-vendor-name.mjs --target bundle
```

Коды возврата: `0` — прошло, `1` — имя вендора сверх допуска, `2` — ошибка
использования или чтения (нечитаемая политика или отсутствующий каталог цели
никогда не считаются «чисто»).

## Как обновлять снимки

Записанные тела ответов формируют собственные функции сервера — те же, что отдают
эндпоинты, — поэтому снимок это настоящее тело, а не его копия:

```sh
pnpm --filter @paperclipai/server exec tsx \
  ../scripts/myrmidon/vendor-name/capture-snapshots.ts
```

Запись детерминирована (отсортированные ключи, без отметок времени, без версии
релиза). Тело, совпавшее с секретом или внутренним адресом, не записывается —
снимок в репозитории остаётся публикуемым. Обновляйте его в том же PR, в котором
изменился источник; CI в сборочной полосе снимает свою свежую копию, поэтому
сторож не зависит от свежести закоммиченного набора.

## База

Поле `targets.<имя>.baseline` — число видимых вхождений, записанное при последнем
обновлении файла. В режиме `ratchet` условие `count <= baseline`; ключ
`--baseline <n>` переопределяет базу обеих целей на один прогон (удобно, когда
храповик опускают раньше, чем обновили файл).

## Файл политики

`scripts/myrmidon/vendor-name/vendor-name-policy.json` владеет всем правилом: два
шаблона токенов, режим, базы, исключения по файлам (`LICENSE`, уведомления,
source maps) и исключения по участкам текста (атрибуция, внешние сервисы, имена
заголовков, старые фразы уведомлений). Политика — единственный источник правды:
один и тот же файл читают CI, запуск разработчика и панель настроек экземпляра.

Изменение внутри `scripts/myrmidon/vendor-name/` включает полный уровень CI
(`scripts/myrmidon/ci/select.mjs`), поэтому на изменение собственного правила
сторож всегда выполняется.

## Настройки

| Переменная | Умолчание | Что делает |
|---|---|---|
| `MYRMIDON_VENDOR_NAME_CHECK_MODE` | не задана — режим берётся из файла политики | Принудительное переопределение режима. Обычный способ менять режим — настройка экземпляра ниже |
| `MYRMIDON_VENDOR_NAME_CHECK_BASELINE` | не задана — база берётся из файла политики | Принудительное переопределение базы. Ключ `--baseline` скрипта старше переменной, переменная старше файла политики |

Значение, которое не разбирается, не является переопределением:
`MYRMIDON_VENDOR_NAME_CHECK_MODE=maybe` игнорируется, панель продолжает
показывать «Сохранено здесь» или «Умолчание», и только значение
`ratchet`/`strict` когда-либо показывается как принудительное.

Настройка экземпляра лежит в `instance_settings.general.vendorNameCheck`
(`{ mode, baseline }`), читается через `GET /api/myrmidon/vendor-name-check` и
пишется через `PATCH` по тому же пути (только администратор экземпляра), правится
на **Instance → General → «Имя вендора в сборке»**. Панель показывает по каждому
полю, откуда взято действующее значение (сохранено здесь / переопределение
окружением / умолчание), и приводит собственный ответ сторожа про эту сборку —
число видимых вхождений и написаний-идентификаторов по каждой цели вместе с базой
и файлы, где вхождение найдено. Чтение запускает тот же скрипт репозитория, что и
CI; в опубликованном образе репозитория рядом нет, и панель говорит об этом, а не
выдумывает число. Кнопка «Проверить сборку снова» перечитывает без перезапуска, а
сохранение никогда не запекает действующее переопределение окружения в базу:
патч накладывается на сохранённое значение, поэтому переменную можно потом снять
без оставшегося выбора.

Как и остальные настройки экземпляра, применяется без перезапуска.

## Тесты

```sh
node --test scripts/myrmidon/vendor-name/check-vendor-name.test.mjs
node --test scripts/myrmidon/ci/select.test.mjs
pnpm --filter @paperclipai/shared exec vitest run src/myrmidon-vendor-name.test.ts
pnpm --filter @paperclipai/server exec vitest run src/myrmidon/vendor-name
pnpm --filter @paperclipai/ui exec vitest run src/components/myrmidon/VendorNameCheckSettingsPanel.myrmidon.test.tsx
```

Первый набор несёт критерий приёмки сторожа: одна добавленная строка с именем
вендора в собранном интерфейсе — или в записанном ответе — роняет проверку.
