# Авторизоваться в GitHub один раз на весь сервер (GITHUB-SHARED-IDENTITY)

> English version: [github-shared-identity.md](github-shared-identity.md)

Агенты разработки пушат код через брокер GitHub, привязанный к прогону
(`POST /runtime-tools/github/credentials`, см. CONTAINER-GITHUB-WRITE в
[SETTINGS.ru.md](../SETTINGS.ru.md)). До сих пор брокер знал только
OAuth-идентичности, подключённые **на человека** или **на агента**: каждому
агенту нужна была своя авторизация GitHub, либо прогон работал, только если
ответственный за него человек подключил свой аккаунт. Общая авторизация GitHub
это снимает: один проход OAuth на весь сервер, ей пользуется каждый агент,
которого разрешил оператор.

Общих авторизаций может быть несколько — например, репозитории одного продукта
под одним аккаунтом GitHub, а репозитории другого продукта под отдельным
бот-аккаунтом. Брокер выбирает идентичность по **целевому репозиторию каждой
операции**, поэтому они никогда не смешиваются.

## Что это

- **Подключение.** Обычное управляемое подключение GitHub (Apps → GitHub) с
  идентичностью **«Shared company GitHub account»**: политика учётных данных
  `shared`, ровно один грант `organization`, создаётся одним проходом OAuth, в
  котором приложение GitHub ставится на выбранные репозитории. Установить его
  на компанию («Any agent») или на выбранных агентов.
- **Правила доступа.** Настройки компании → **Shared GitHub authorization**
  (`GET`/`PUT /api/myrmidon/companies/:companyId/github-shared-identity`):
  общий выключатель и для каждого общего подключения — кто им пользуется
  (роли и/или отдельные агенты) и для каких репозиториев (`owner/repo` или
  `owner/<шаблон с *>`; владелец всегда буквальный). Хранится в
  `instance_settings.general.myrmidonGithubSharedIdentity`; брокер читает при
  каждом запросе, поэтому изменение действует со следующей операции git/gh —
  без перезапуска.
- **Старшинство.** Выделенный (на агента) грант главнее общего; личный грант
  ответственного за прогон — тоже. Общий грант — последний вариант.
- **Выбор по репозиторию.** Для каждой операции брокер берёт подключения, чьё
  правило включает агента **и** чьи шаблоны совпали с целевым репозиторием:
  - ни одного — общих идентичностей для этой операции нет (как раньше:
    `absent`, серверный git рабочих областей сохраняет старый откат);
  - одно — выдаётся оно;
  - два и больше с разными аккаунтами GitHub — ошибка
    (`More than one shared GitHub identity matches repository …`), никогда не
    молчаливый выбор. Сузьте шаблоны, чтобы каждый репозиторий принадлежал
    одному подключению.
- **Выдача.** Прямо перед чтением токена брокер перепроверяет правило и
  требует, чтобы репозиторий входил в установку приложения GitHub этого гранта
  (если грант хранит список). Отказ пишется в журнал
  (`myrmidon.github_shared.denied`), ответ — `unavailable`.
- **Авторство.** Общая только аутентификация. Автор и коммиттер — агент: его
  имя и `<slug-агента>@<домен>`, домен — «Commit email domain» в правилах
  (пусто — зарезервированный `agents.myrmidon.invalid`).
- **Аудит.** Каждая выдача пишет событие доступа хранилища секретов
  (потребитель `workspace-git-credential`, агент, прогон, задача, путь
  `github_shared:<owner/repo>`) и запись активности
  `myrmidon.github_shared.issued` (агент, прогон, репозиторий, подключение,
  грант). Токен не логируется, не сохраняется в идентичности прогона и не
  возвращается нигде, кроме самого ответа с учётными данными.

## Шаги оператора

1. **Решить, какие аккаунты.** По аккаунту GitHub на продукт (или один на
   всё). Лучше машинный аккаунт с правом записи только в репозитории своего
   продукта.
2. **Авторизоваться один раз на аккаунт.** Apps → GitHub → идентичность
   **«Shared company GitHub account (advanced)»** (нужно право
   connection-manager) → «Any agent» → войти в GitHub этим аккаунтом и
   поставить приложение GitHub только на репозитории этого продукта.
   Повторить для следующего аккаунта.
3. **Задать правила.** Настройки компании → Shared GitHub authorization →
   включить, и для каждого подключения: отметить «Allow agents to use this
   connection», перечислить репозитории (`owner-a/*`), роли (`engineer`) и/или
   отметить отдельных агентов. По желанию — домен почты коммитов. Сохранить.
4. **Проверить.** В прогоне агента: `git ls-remote https://github.com/<owner>/<repo>`
   и push в черновую ветку. Запись идентичности прогона
   (`run_identity_contexts.github`) показывает `available / shared / <login> /
   <owner/repo>`, журнал активности — `myrmidon.github_shared.issued`.
   Репозиторий другого продукта получает другой login; репозиторий, не
   указанный ни в одном правиле, остаётся `absent`.

## Куда попадает токен в контейнере бота

Патч рантайма 09 по-прежнему вырезает сырые токены (`GH_TOKEN`,
`GITHUB_TOKEN`, …) из окружения терминала, когда у прогона есть capability
брокера. Единственный путь к учётке — хелпер `git-credential-paperclip` и
обёртка `gh` образа:

- `/etc/gitconfig` включает `useHttpPath = true` для github.com: git передаёт
  хелперу путь репозитория, хелпер шлёт брокеру `{"repository": "owner/repo"}`
  и отвечает git выданной учёткой на одну операцию;
- обёртка `gh` берёт репозиторий из `-R/--repo`, `GH_REPO` или remote `origin`
  текущего каталога и запускает настоящий `gh` с токеном только в окружении
  этого дочернего процесса.

Общий грант никогда не выдаётся без репозитория и не попадает в список
MCP-инструментов доски (фильтр MCP-подключений GitHub и серверный git вне
прогона общие гранты не рассматривают).

## Ограничения

- Выдаётся OAuth-токен (user-to-server) общего гранта; он истекает, доска его
  обновляет. GitHub не умеет сузить такой токен до одного репозитория:
  решение по репозиторию принимает брокер, а жёсткая техническая граница —
  набор репозиториев, выбранный при установке приложения GitHub в шаге 2.
  Ставьте приложение каждого аккаунта только на репозитории его продукта.
- Токены установки, суженные до репозитория, требуют приватного ключа
  приложения GitHub на этом сервере; приложение управляемого коннектора
  обслуживается вне сервера, поэтому в это изменение не входит.
- Локальный/SSH-лаунчер не-контейнерных адаптеров пока не называет
  репозиторий и общий грант не получает.
