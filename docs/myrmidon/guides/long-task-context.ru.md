# Гард контекста долгой задачи (1.6.6 LONG-TASK-CONTEXT)

> English version: [long-task-context.md](long-task-context.md).

Задача без срока конца — портирование, долгое ревью, задача, у которой просто
растёт переписка, — раньше убивала собственные прогоны. 09.10.2026 две задачи
сделали это за один вечер:

- OPE-3931 (165 комментариев, ~120 тыс. символов): прогоны 19:51 и 21:25 упали с
  `Context compression timed out: approximately 214 298 / 378 739 tokens`;
- OPE-6298 в 19:04: `Context compression timed out without reducing this
  conversation`.

В обоих случаях статус агента становился `error`, и задача не двигалась, пока
человек не сбросит сессию задачи вручную. Сброс помогал на один-два прогона, и
задача распухала снова.

У гарда три части, и они закрывают разные моменты этой истории.

## 1. Таймаут сжатия — восстановимый сбой

Рантайм печатает эти два сообщения, когда его собственное уплотнение контекста
сдаётся. Они не попадали в подписи контекстного окна, поэтому прогон уходил общим
путём отказа и оставлял агента в `error`. Теперь обе формы входят в
`CONTEXT_WINDOW_ERROR_SIGNATURES` (`server/src/services/heartbeat.ts`): такой
прогон сбрасывает сессию задачи и оставляет агента в покое, то есть идёт путём,
который для ошибки контекстного окна уже был, — следующая побудка задачи
начинается со свежей сессии вместо застрявшего агента.

## 2. Сжатие до порога, а не после него

Ждать таймаута — значит за него платить: прогон потерян, а рантайм уже потратил
время на уплотнение сессии, которую уплотнить не смог.

Перед тем как прогон продолжит сессию задачи, гард измеряет, какую долю окна
модели занял последний промпт этой же задачи (берётся новейший прогон этого
агента по этой задаче с разбором промпта, и окно модели, настроенной у агента;
запасное окно применяется, когда у модели нет известного `maxInputTokens`). На
`resetPct` окна и выше сессия сбрасывается до того, как её продолжат, а причина
пишется в контекст самого прогона:

```
long-task context guard: the last run's prompt took 71.3% of the 378739-token
window (threshold 70%), so the task session is reset and the run starts from the
continuation summary
```

```
Long-task context guard: this run starts a FRESH task session. The previous
session's last prompt was 270000 tokens (71.3% of the 378739-token window,
threshold 70%), so it was dropped before the window was reached — resuming it
would have ended in "Context compression timed out". The continuation summary
below carries the work done so far; older entries of the thread stay readable
through GET /api/issues/<issueId>/comments (oldest first).
```

Контекст задачи при этом не теряется: сводка продолжения, которую доска и так
строит для задачи, едет вместе с payload побудки, а вся переписка задачи
остаётся читаемой по API.

## 3. Payload перестаёт расти вместе с перепиской

`MYRMIDON_CONTINUATION_HISTORY_LIMIT` (30 новейших записей на список) ограничивал
*число* записей истории, но не её объём: тридцать комментариев по 4 тыс. символов
— это 120 тыс. символов в каждом прогоне, а один огромный комментарий ехал
целиком. Теперь предел двумерный
(`server/src/myrmidon/continuation-history-limit.ts`):

- `MYRMIDON_CONTINUATION_HISTORY_CHARS` (умолчание `24000`) — общий бюджет текста
  сообщений в payload. Едут новейшие записи, помещающиеся в бюджет;
- `MYRMIDON_CONTINUATION_MESSAGE_MAX_CHARS` (умолчание `8000`) — предел одной
  записи: хвост заменяется пометкой, где остаётся полный текст.

Исходный запрос, последний запрос и комментарии, которые вызвали прогон, всегда
остаются в payload (это и значит «закреплены»), а `truncationNotice` называет
отброшенное и указывает на `GET /api/issues/:issueId/comments`. `0` в любой из
переменных выключает соответствующий предел.

## Настройки

Настройки гарда живут вместе с остальными живыми настройками экземпляра, в
`instance_settings.general.longTaskContext`:

| Поле | По умолчанию | Что делает |
|---|---|---|
| `enabled` | `true` | `false` — давление всё равно измеряется и попадает в контекст, но сессия заранее не сбрасывается |
| `resetPct` | `70` | Доля окна модели, на которой сессия сбрасывается до того, как следующий прогон её продолжит |
| `fallbackWindowTokens` | `200000` | Окно, от которого считается доля, когда у модели агента нет известного `maxInputTokens` |
| `historyChars` | `24000` | Значение `historyChars`, выставленное оператором (сам предел во время прогона читается из `MYRMIDON_CONTINUATION_HISTORY_CHARS`) |

Отсутствующая или испорченная строка настроек откатывается к полному набору
умолчаний — правленная руками строка не применяется наполовину. Каждое поле
переопределяется окружением (`MYRMIDON_LONG_TASK_CONTEXT_*`, см.
[SETTINGS.md](../SETTINGS.md), Трек 2), и у каждого действующего значения известен
источник: окружение, сохранённая строка или умолчания. Отдельная панель для
этой области настроек в эту часть не входит; ключ принимает общий валидатор
настроек инстанса (`packages/shared/src/validators/instance.ts`), поэтому
строка записывается существующим маршрутом настроек.

## Как убедиться, что сработало

- Критерий приёмки — журнал прогонов: **0 прогонов в сутки с `Context compression
  timed out`**. Прогон, который вместо этого упирается в гард, несёт строку
  сброса в своём контексте (`Skipping saved session resume for task … because
  long-task context guard: …`), то есть починка видна там же, где раньше был
  сбой.
- Задача, которая упирается в порог прогон за прогоном, значит, что её отдельные
  промпты велики сами по себе: смотри разбор промпта прогона и уменьшай
  `MYRMIDON_CONTINUATION_HISTORY_CHARS`, или уноси длинную историю в документ
  задачи вместо переписки.
- Полностью выключить гард: `MYRMIDON_LONG_TASK_CONTEXT_ENABLED=0` (сбросы
  сессий прекращаются, распознавание подписей из части 1 остаётся — оно
  возвращает поведение вендора и выключателем не предусмотрено).
