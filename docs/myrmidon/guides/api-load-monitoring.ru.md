# Мониторинг нагрузки API и алерты задержки (1.6.6 OPE-9997)

Myrmidon включает встроенный журнал задержек HTTP-запросов в оперативной памяти (`server/src/myrmidon/monitoring/board-load/request-load.ts`), позволяющий отслеживать производительность маршрутов без внешних систем мониторинга.

## Отслеживаемые маршруты и middleware

Middleware `boardLoadRequestMiddleware()` фиксирует длительность выполнения, HTTP-статус и путь запроса. Он подключен к критичным по производительности эндпоинтам:
- `POST /runtime-tools/github/credentials` (брокер учетных данных GitHub)
- `GET /api/companies/:companyId/issues` (список задач)

## Метрики и алерт по p95

Журнал нагрузки рассчитывает скользящие перцентили за заданное временное окно:
- `p50Ms`: медианная длительность (50-й перцентиль) в миллисекундах.
- `p95Ms`: 95-й перцентиль длительности в миллисекундах.
- `p99Ms`: 99-й перцентиль длительности в миллисекундах.
- `maxMs`: максимальная зафиксированная длительность в миллисекундах.
- `count`: общее число запросов за окно.
- `errorCount`: количество ошибочных ответов (HTTP >= 400).
- **`alert`**: флаг превышения порога задержки. Рассчитывается как `alert: p95Ms > 2000`. Выставляется в `true`, когда 95-й перцентиль превышает **2000 мс (2 секунды)**.

## API инспекции

Операторы и проверки доступности могут получить метрики через:
```http
GET /api/myrmidon/board-load/api-load?windowMs=60000&limit=50
```

### Параметры:
- `windowMs` (опционально, по умолчанию 60000): окно выборки в миллисекундах.
- `limit` (опционально, по умолчанию 50): максимальное количество маршрутов в ответе, отсортированных по убыванию `p95Ms`.

### Пример ответа:
```json
{
  "samples": [
    {
      "method": "GET",
      "route": "/api/companies/:companyId/issues",
      "count": 142,
      "errorCount": 0,
      "p50Ms": 45,
      "p95Ms": 180,
      "p99Ms": 350,
      "maxMs": 420,
      "alert": false
    }
  ]
}
```

## Регламент оператора при срабатывании алерта

При появлении маршрута с `alert: true` (`p95Ms > 2000`):

1. **Проверить нагрузку на список задач**:
   - Убедиться, что клиенты используют `view=compact` и ограниченные лимиты (≤ 200).
   - Проверить, включена ли настройка инстанса `issuesListAgentDefaults`.
2. **Проверить нагрузку на брокер токенов**:
   - Убедиться, что кэш учетных данных GitHub работает и процент попаданий высок.
   - Проверить доступность и время ответа upstream GitHub API.
3. **Проверить состояние базы данных**:
   - Оценить загрузку CPU PostgreSQL и наличие блокировок в таблице `issues`.
