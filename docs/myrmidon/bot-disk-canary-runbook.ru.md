# Диск ботов (BOT-DISK-H): канарейка, интеграционный прогон и выключение хост-скриптов

Регламент трёх последних шагов механизма BOT-DISK-H: интеграционная проверка
всех частей вместе, канарейка на трёх dev-ботах и выключение старой уборки на
хосте. CI это не запускает; автоматизированная часть интеграционной проверки —
`scripts/myrmidon/bot-runtime/bot-disk-integration.test.mjs`. Настройки —
[bot-disk-cache.md](bot-disk-cache.md), [bot-disk-quota.md](bot-disk-quota.md),
контракт — [bot-disk-contract/](bot-disk-contract/README.md).

English version: [bot-disk-canary-runbook.md](bot-disk-canary-runbook.md).

## 1. Что закрывает автотест, а что только стенд

| Сценарий дизайна | Автотест (настоящий git, локальный origin, фальшивая доска) | Только стенд / канарейка |
|---|---|---|
| Задача закрыта: копия уходит за grace + один проход | да: внутри grace ничего, после — удаление, активный сосед цел, отчёт проходит схему C4 | реальные 15 минут на живой доске |
| Незапушенная работа сначала в архив | да: bundle и untracked-tar есть до удаления копии; упавший архив оставляет копию и запись реестра | нет |
| `myr-ws restore` возвращает ветку и коммит | да (вершина ветки и содержимое файла) | diff на реальной задаче |
| Доска лежит: ничего не удаляется | да (`desired` не ok: ноль действий, строка `skip` в отчёте) | реальный 503/таймаут доски |
| Дрейф: копию снесли руками | да: запись worktree снята `prune`, база цела | карточка внимания на доске |
| Копия-сирота ждёт срок сироты | да | нет |
| В образе `myr-ws`, `botd`, обёртка git; 15 форм клона | нет (файлы покрывают гейт Dockerfile и тесты обёртки) | `git --version` через обёртку, формы клона, нет токена в `.git/config` |
| Прогон с `workspace` в `/v1/runs` | нет | реальный прогон на канарейке |
| Квота (`prjquota`): ENOSPC только у бота на лимите | нет | нужен раздел с квотами |
| pnpm: reflink-самопроверка, вес копии <= 350 МБ физически | нет | нужно общее хранилище на разделе |

Находка при написании теста: `myr-ws close` убирает запись из реестра, а
`myr-ws restore <KEY>` берёт репозиторий из этой записи. После того как botd
закрыл копию, для restore сначала нужна запись (повторный
`myr-ws open <KEY> owner/repo` её пишет). Тест идёт в этом порядке. Поведение
описано здесь, не изменено.

## 2. Канарейка на трёх dev-ботах

Порядок (из эпика): образ с `myr-ws`, `botd` и обёрткой сначала на трёх
канареечных ботах; шаг с квотами раздела и остальные волны — только после
прохождения замеров ниже.

1. Предполётная проверка на хосте доски, факты — в комментарий задачи:
   - свободное место на разделе ботов и на корневой ФС (корень выше 90 %
     блокирует запись в базу доски: сначала чинить это);
   - `GET /api/myrmidon/bot-disk` показывает `enabled: true` и нужные
     настройки; три канареечных бота на целевом поколении образа.
2. На каждом канареечном боте `botd --once --plan` (сухой прогон: ничего не
   исполняется и не отправляется) и чтение плана: допустимы только закрытые
   копии и сироты. План с копией активной задачи — стоп.
3. Пустить цикл. Замеры через 24 часа (первая контрольная точка) и в конце
   окна:
   - чужие каталоги, promisor-паки, `.git/config` с userinfo: ноль за окно
     (отчёт botd и `myr-ws list`);
   - копии терминальных задач убраны за grace + 15 минут: не менее 95 %;
   - физический вес новой копии после `pnpm install`: не более 350 МБ
     (`du` копии, без хранилища);
   - reflink-самопроверка в порядке.
4. После монтирования раздела с проектными квотами: тест ENOSPC только на
   одном канареечном боте (`PUT .../quota` через доску, набить бота до
   лимита): бот получает ENOSPC, `myr-ws open` отвечает
   `BOT_DISK_QUOTA_EXCEEDED:`, соседи пишут. Потом вернуть квоту.
5. В задачу — цифры (не «ок»), затем волны на остальной флот.

Выключатель всего механизма: `PATCH /api/myrmidon/bot-disk` с
`{"enabled": false}`. Маршрут желаемого состояния тогда отвечает 503, botd
считает это «желаемого состояния нет» и ничего не удаляет (это fail-safe
случай интеграционного теста). Включение обратно — тот же вызов с `true`.

## 3. Выключение хост-скриптов (фаза 5)

Старая уборка (systemd-таймер с `duperemove` и разовые скрипты `prune-*`)
выключается только когда замена доказана на живом флоте. Это боевой шаг для
владельца инфраструктуры, не для CI.

Условия, к каждому — вывод команды:

1. Раздел смонтирован с проектными квотами (в `findmnt` есть `prjquota`),
   отчёт по квотам не пуст.
2. botd жив на флоте: отчёты disk-report свежие, открытых карточек дрейфа и
   чужого нет.
3. Занято на разделе ботов не больше 60 %. Выше — не выключать, эскалировать с
   цифрами (рост без скриптов измерялся несколькими ГиБ в час).
4. На хосте нет идущих прогонов агентов (обычное окно рестартов).

Шаги:

1. Бэкап юнитов и crontab в датированный файл (`systemctl cat <сервис и таймер
   dedupe>`, `crontab -l` всех пользователей, `ls /etc/cron.d`).
2. `systemctl disable --now <таймер dedupe>`; проверить `is-enabled` =
   disabled, `is-active` = inactive и что `list-timers` его не показывает.
3. Скрипты не удалять: переименовать в `<имя>.disabled-F5-<дата>`. Проверка:
   число disabled-файлов равно числу скриптов, исполняемых `prune-*` и
   скриптов миграции под старыми именами не осталось.
4. Объявить в треде инфраструктуры, что ручные prune на разделе ботов
   прекращаются с этой даты (критерий 6 их считает).
5. Писать занятое место раздела каждые 10 минут 24 часа, приложить ряд.

Откат до удаления: `systemctl enable --now <таймер dedupe>` и переименовать
файлы обратно. Скрипты только освобождают место, откат данных не теряет.

Удаление через 14 суток — отдельная проверка с датой: только если все 14 суток
суточное изменение раздела было в пределах 5 ГиБ, занято не больше 60 % и не
было ручных `rm`/prune, удалить disabled-скрипты, файлы юнитов (затем
`daemon-reload`), файл хешей и лог — после проверки, что бэкап юнитов на месте.
Если метрики нестабильны — не удалять, отчёт владельцу с цифрами.
