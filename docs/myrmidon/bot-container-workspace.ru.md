# Рабочая копия задачи в контейнере бота (1.6.9)

> English version: bot-container-workspace.md

Агенты адаптеров `hermes_gateway` и `omp_local` работают в своём контейнере.
Их код лежит в каталоге задачи бота, `/workspace/<ISSUE>`, на диске ботов.
Доска код для них не исполняет и копию репозитория для них не держит.

## Что доска делает для такого прогона

- Не создаёт git worktree.
- Не выдаёт checkout общей рабочей копии проекта.
- Ничего не клонирует и не создаёт каталогов проекта на своём диске: ни
  управляемого checkout, ни временного каталога клонирования, ни копий
  связанных проектов. `repoUrl` и `repoRef` берутся из строки рабочей копии
  проекта.
- Пишет одну строку `execution_workspaces` на задачу: режим
  `isolated_workspace`, стратегия `bot_container`, провайдер
  `adapter_managed`, по умолчанию cwd `/workspace/<ISSUE>`. Контекст прогона
  (`paperclipWorkspace`) указывает на этот каталог.
- Две задачи одного агента дают две строки. Они не конфликтуют, сообщение
  «копию держит другой прогон» для них невозможно.
- Следующий прогон той же задачи берёт ту же строку. Строка от прежней копии
  на стороне доски (`git_worktree`, `project_primary`) для такой задачи не
  восстанавливается, создаётся новая строка `bot_container`.

Правило действует только для прогонов в режиме `isolated_workspace`. Прогон в
режиме `shared_workspace` по-прежнему получает общую рабочую копию доски.

## Аренда и уборка

Строка и есть аренда задачи: она привязана к задаче, а не к прогону. После
перехода задачи в `done` или `cancelled` терминальный обход архивирует строку
без git-инспекции. Удалять на доске нечего. Каталог задачи на диске ботов
подчиняется политике диска ботов (`general.botDisk`: пороги, срок scratch,
срок простоя).

## Автономная копия на постоянном томе

Оператор доски с правом `runtime:manage` в компании вызывает
`POST /api/companies/:companyId/issues/:issueId/offline-bot-workspace`.
Используйте UUID компании и задачи, не ключ вида `OPE-123`. Для первого
вызова нужна стандартная проектная задача без назначения и без привязки
workspace, а также запущенный управляемый `hermes_gateway` этой компании.

1. Отправьте `{"action":"reserve","botId":"<UUID бота>"}`. Ответ `{id: null, cwd}`
   означает, что каталог выделен, но рабочая копия ещё не зарегистрирована.
   Путь имеет вид `<канонический Hermes home>/offline-workspaces/<companyId>/<issueId>`
   на постоянном томе вне `/workspace`.
2. Подготовьте в `cwd` автономный checkout с собственным каталогом `.git`,
   без linked worktree, symlink и внешнего Git object store. Владелец UID/GID —
   пользователь runtime, режим каталога checkout — `0700`. Runtime проверяет,
   что `cwd` — корень рабочего дерева и `HEAD` указывает на локально доступный
   коммит. Пустой `git init` не подходит; Git-транспорты при проверке запрещены.
3. Отправьте `{"action":"register","botId":"<UUID бота>"}`. Успешный ответ
   `{id, cwd}` означает атомарную привязку workspace к задаче. Повтор с тем
   же ботом и неизменной идентичностью каталога возвращает тот же UUID.
4. Запустите задачу штатным swarm. При следующем swarm wake проверяется та
   же привязка: UUID и cwd сохраняются без вызова `myr-ws open` или сетевых
   операций Git при открытии workspace. Несовместимый runtime, смена владельца,
   пути или идентичности тома/каталога останавливают запуск без fallback.

Аренда привязана к UUID задачи, а не к отдельному прогону. После архивации
строки каталог на постоянном томе остаётся под управлением оператора, вне
обычной уборки `/workspace`. Выдача одного физического каталога двум задачам
отклоняется; `0700` не изолирует задачи с одним UID.

После выката ADM сверяет UUID и cwd двух swarm-прогонов, а в целевом runtime
сравнивает `realpath "$cwd"`, `findmnt -T "$cwd" -o TARGET,SOURCE,FSTYPE,OPTIONS`
и `stat -Lc '%n %u:%g %a %d:%i' "$cwd"` для обоих прогонов.

## Bare-базы с extensions.worktreeConfig

Рабочая копия задачи — это linked worktree общей bare-базы репозитория
(база класса D в домашнем каталоге бота). База может нести git-расширение
`extensions.worktreeConfig=true`. В такой конфигурации git не создаёт
`config.worktree` у нового worktree, и копия наследует от базы `core.bare=true`:
`git rev-parse` работает, но `git status`, `read-tree` и sparse checkout
отказывают с ошибкой "this operation must be run in a work tree".

`myr-ws` обрабатывает такие базы сам:

- После `git worktree add` команда `myr-ws open` пишет `core.bare=false` в
  собственный `config.worktree` копии (внутри административного git-каталога
  копии). Общий конфиг базы не трогается; база остаётся bare.
- Копия, оставшаяся полусозданной прежним `open` (в каталоге только `.git`,
  checkout нет), чинится, а не отклоняется: при повторном использовании `open`
  и сторожевой команде `myr-ws repair` (botd) исправляют конфиг и затем
  материализуют checkout так же, как при новом open. HEAD, ветка, индекс и
  неотслеживаемые файлы копии сохраняются; ничего не сбрасывается и не
  удаляется. База остаётся bare и не получает `config.worktree`.
- `repair` пропускает копию, внутри которой работает живой процесс.
- Review-копия, вылеченная таким путём, получает обычный checkout; `open
  --review` и так предупреждает, когда переиспользует существующую копию
  вместо пересоздания.

## Адаптеры, работающие на хосте доски

Локальный адаптер сохраняет git worktree в `.paperclip/worktrees` проекта.
Перед созданием worktree доска измеряет раздел (statfs каталога worktree).
При заполнении не ниже `general.botDisk.partitionRefuseOpenPercent` (по
умолчанию 90) доска отказывает с кодом `WORKTREE_PARTITION_FULL`. В тексте
указаны заполнение раздела и порог. Освободите место или измените порог и
повторите прогон. Повторное использование существующего worktree не
блокируется. Терминальный обход удаляет worktree после `done` или `cancelled`.

## Безопасный порядок включения изоляции

1. Выкатите сборку со стратегией `bot_container`.
2. Проверьте, что задача `hermes_gateway` получает строку со стратегией
   `bot_container`, а `.paperclip/worktrees` проекта остаётся пустым.
3. Только после этого включайте `experimental.enableIsolatedWorkspaces` и
   политику проекта `isolated_workspace`.
4. Два часа наблюдайте корневой диск хоста доски.
