## changelog-en

### A burst of events of one GitHub pull request no longer takes every database connection of the board (WEBHOOK-LOCK-POOL)

- On 16.11 the board stopped for 1 to 4 minutes (08:03–08:09 and 08:12–08:14). Hundreds of requests answered after more than 5 s, the longest after 268 s: `POST /api/myrmidon/github-app/webhook` (495 slow), `POST /runtime-tools/github/credentials` (156), `GET`/`PATCH /api/issues/:id`, comments and the MCP gateways. The Postgres log (auto_explain) had 263 waits on `select pg_advisory_xact_lock(hashtextextended($1, 0))` with `$1 = 'github-pr:<company>:itkadr-git/myrmidon#<N>'`: median 11 s, p90 90 s, longest 112 s. The bots lost their push and the write of their result.
- Cause: since EMPTY-RUNS-3 the deliveries of one pull request wait for each other on the advisory lock inside their transaction, so each waiting delivery held a connection of the pool. Tens of `check_run` events of one pull request in seconds used all of the pool, and every other route waited for a connection.
- The wait for the turn of a pull request is now in the process, before a connection is taken: deliveries of one pull request go through an in-process queue, one after another, in the order they arrived (the key is removed when the queue is empty). The advisory lock stays in the transaction and keeps the two api processes apart; in the database at most one delivery of a pull request per process waits for it.
- The number of open delivery transactions per process is limited to 3 (`GITHUB_DELIVERY_MAX_CONCURRENT_TRANSACTIONS`). The pool has 10 connections by default (`DATABASE_POOL_MAX`); a delivery transaction uses one, so at least 7 stay for the other routes. A delivery that waits for its pull request holds no slot.
- Kept as they were: the order of deliveries of one pull request, the repeat of a transaction after 40P01/40001, and the answers of the webhook route. The route still answers after the delivery is processed (the delivery is stored first; a redelivery of a processed delivery answers `duplicate`). Answering earlier with 202 and processing after the answer is possible, but it is not done here.

## changelog-ru

### Всплеск событий одного PR GitHub больше не занимает все соединения доски с базой (WEBHOOK-LOCK-POOL)

- 16.11 доска вставала на 1–4 минуты (08:03–08:09 и 08:12–08:14). Сотни запросов отвечали дольше 5 с, самые долгие — 268 с: `POST /api/myrmidon/github-app/webhook` (495 медленных), `POST /runtime-tools/github/credentials` (156), `GET`/`PATCH /api/issues/:id`, комментарии и шлюзы MCP. В журнале Postgres (auto_explain) 263 ожидания `select pg_advisory_xact_lock(hashtextextended($1, 0))` с `$1 = 'github-pr:<company>:itkadr-git/myrmidon#<N>'`: медиана 11 с, p90 90 с, максимум 112 с. У ботов отваливались push и запись итога.
- Причина: после EMPTY-RUNS-3 доставки одного PR ждут друг друга на advisory-блокировке внутри транзакции, и каждая ждущая доставка держала соединение пула. Десятки событий `check_run` одного PR за секунды занимали весь пул, и все остальные маршруты ждали соединения.
- Ожидание очереди PR теперь в процессе, до взятия соединения: доставки одного PR идут через внутрипроцессную очередь, по одной, в порядке прихода (ключ удаляется, когда очередь пуста). Advisory-блокировка осталась в транзакции и разделяет два процесса api; в базе ждёт её не больше одной доставки PR от процесса.
- Число одновременно открытых транзакций доставок в процессе ограничено 3 (`GITHUB_DELIVERY_MAX_CONCURRENT_TRANSACTIONS`). Пул по умолчанию — 10 соединений (`DATABASE_POOL_MAX`); транзакция доставки занимает одно, так что другим маршрутам остаётся не меньше 7. Доставка, ждущая очередь своего PR, слота не занимает.
- Без изменений: порядок доставок одного PR, повтор транзакции при 40P01/40001, ответы маршрута вебхука. Маршрут по-прежнему отвечает после обработки доставки (доставка сохраняется первой; повторная доставка уже обработанной отвечает `duplicate`). Отвечать раньше (202) и обрабатывать после ответа можно, но здесь это не делается.
