## changelog-en

### An Alertmanager `status=resolved` webhook closes the alert's open task by itself (AM-RESOLVED-AUTOCLOSE, OPE-12085)

- 1.6.6 opened one task per firing alert (Zabbix / Alertmanager) and closed it only through the alert-recovery sweep after the hold window. A plain Alertmanager webhook with `status: "resolved"` was answered with a dedup note, but the task stayed open until the sweep got to it. Roadmap-v1 §3.3 (OPE-3919) calls for the resolved webhook itself to close the task.
- A new handler in the monitoring domain (`alertmanager-webhook-handler.ts`) processes `status=resolved` deliveries: for every resolved alert it looks up the open task by the alert `fingerprint` and, when the fingerprint does not match (or is absent), falls back to the `alertname` label (the alert's own labels, then the payload's `commonLabels` / `groupLabels`). The found task receives an auto-close comment («Recovered: the alertmanager alert … reported resolved at … Closing automatically.») and is transitioned to `status=done`; the dedup registry entry is marked resolved. When no open task matches, the handler is a no-op and the endpoint still answers HTTP 200, so Alertmanager retries do not pile up errors. Firing alerts leave the handler untouched (no-op as well).
- The handler is wired through two small ports (`AlertmanagerIssuePorts` for comment + status transitions, `AlertmanagerTaskFinder` for lookup/mark-resolved) and ships with `adaptAlertDedupStore`, an adapter over the existing 1.6.6 dedup registry (`AlertDedupStore`), so the same storage backs both the firing path and the resolved path. The Express router (`createAlertmanagerWebhookRouter`) mounts the endpoint on `POST /` and always replies 200 with a per-alert processing summary.

## changelog-ru

### Вебхук Alertmanager со `status=resolved` закрывает открытую задачу тревоги сам (AM-RESOLVED-AUTOCLOSE, OPE-12085)

- В 1.6.6 каждая сработавшая тревога (Zabbix / Alertmanager) открывала одну задачу, а закрывалась она только сбросом alert-recovery после окна удержания. Обычный вебхук Alertmanager со `status: "resolved"` получал ответ о дедупликации, но задача оставалась открытой до сброса. Roadmap-v1 §3.3 (OPE-3919) требует, чтобы resolved-вебхук закрывал задачу сам.
- Новый обработчик в домене мониторинга (`alertmanager-webhook-handler.ts`) обрабатывает доставку со `status=resolved`: для каждого resolved-алерта он ищет открытую задачу по `fingerprint` алерта, а если fingerprint не совпал (или отсутствует) — по лейблу `alertname` (собственные лейблы алерта, затем `commonLabels` / `groupLabels` payload). Найденная задача получает комментарий об автозакрытии («Recovered: the alertmanager alert … reported resolved at … Closing automatically.») и переводится в `status=done`; запись реестра дедупликации помечается resolved. Если открытой задачи нет, обработчик — no-op, и эндпоинт всё равно отвечает HTTP 200, поэтому ретраи Alertmanager не копят ошибки. Firing-алерты обработчик не трогает (тоже no-op).
- Обработчик собран на двух маленьких портах (`AlertmanagerIssuePorts` — комментарий и смена статуса, `AlertmanagerTaskFinder` — поиск и пометка resolved) и поставляется с `adaptAlertDedupStore` — адаптером над существующим реестром дедупликации 1.6.6 (`AlertDedupStore`), так что одно хранилище обслуживает и firing-, и resolved-путь. Express-роутер (`createAlertmanagerWebhookRouter`) монтирует эндпоинт на `POST /` и всегда отвечает 200 со сводкой обработки по каждому алерту.
