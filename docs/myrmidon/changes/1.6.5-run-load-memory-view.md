## changelog-en

### Memory snapshot in the run load view (1.6.5 C0-ui)

- `GET /api/myrmidon/runtime-limits` now ships a `memory` block next to
  `hostLoad` and `queue`: the host's available and total memory (the numbers
  the memory floors `MYRMIDON_MIN_FREE_MEMORY_MB` /
  `MYRMIDON_MIN_FREE_HOST_MEMORY_MB` decide on) and the server container's
  cgroup v2 usage against its limit (`memory.max` − `memory.current`, with
  the reclaimable `inactive_file` page cache counted as free — the same rule
  the admission's memory guard applies). Either side is `null` when the
  server cannot read it (no cgroup limit, host memory unreadable), so a
  consumer shows nothing rather than a number the server made up.
- Both run settings panels (Instance → General «Run limits», Settings →
  «Runs & queue») show the snapshot next to the queue line: the load screen
  now covers the queue, the ceiling, and the memory of the host and the
  server container in one place. See [SETTINGS.md](../SETTINGS.md).

## changelog-ru

### Снимок памяти в виде нагрузки прогонов (1.6.5 C0-ui)

- `GET /api/myrmidon/runtime-limits` теперь отдаёт блок `memory` рядом с
  `hostLoad` и `queue`: свободную и полную память хоста (числа, на которые
  опираются пороги `MYRMIDON_MIN_FREE_MEMORY_MB` /
  `MYRMIDON_MIN_FREE_HOST_MEMORY_MB`) и использование cgroup v2 контейнера
  сервера против его лимита (`memory.max` − `memory.current`, с возвращаемым
  страничным кэшем `inactive_file` в свободной памяти — то же правило, что у
  стража памяти допуска). Любая из сторон `null`, когда сервер не может её
  прочитать (нет лимита cgroup, память хоста не читается), — потребитель
  ничего не показывает вместо выдуманного числа.
- Обе панели настроек прогонов (Instance → General «Run limits», Настройки →
  «Прогоны и очередь») показывают снимок рядом со строкой очереди: экран
  нагрузки теперь покрывает очередь, потолок и память хоста и контейнера
  сервера в одном месте. См. [SETTINGS.ru.md](../SETTINGS.ru.md).

## settings-en-replace

| `MYRMIDON_MAX_CONCURRENT_RUNS` | C0 | unset (disabled) | Ceiling of concurrent runs started by this server process: beyond it runs stay `queued`, the queue goes from oldest to newest. Counts runs of all agents of the process, not of one agent: the vendor only has a per-agent limit, and on 28.09 a mass wake started about 35 processes per container, the kernel killed the server together with all runs. A triggered limit schedules a repeat queue pass in 15 s instead of waiting for the next scheduler tick. The variable is the default at the FIRST start: afterwards the effective values are stored in settings (`instance_settings.general.runLimits`) and change on the fly on the Instance → General page ("Run limits") or via `GET`/`PATCH /api/myrmidon/runtime-limits` — the queue starts within a minute after the ceiling is raised, no server restart needed. The same `GET` view is the run-load screen of the instance: it carries the queue snapshot (runs in flight against the ceiling, how many wait, the head of the queue with its agent), the host CPU load the ceiling is measured against, and the memory snapshot — the host's available/total memory and the server container's cgroup v2 usage against its limit (`memory.max` − `memory.current`, the reclaimable `inactive_file` cache counted as free). Both settings panels show these lines next to the fields | Unset, empty, `0`, negative or non-numeric — the limit is off. Works together with the two variables below. An empty field in settings — the limit is off (same as `null` in `general.runLimits`); editing the DB row by hand takes effect after a restart |

## settings-ru-replace

| `MYRMIDON_MAX_CONCURRENT_RUNS` | C0 | не задана (выключено) | Потолок одновременных прогонов, запущенных этим процессом сервера: сверх него прогоны остаются `queued`, очередь идёт от старых к новым. Считает прогоны всех агентов процесса, а не одного агента: у вендора лимит есть только на агента, и 28.09 массовая побудка запустила около 35 процессов на контейнер, ядро убило сервер вместе со всеми прогонами. Сработавший лимит назначает повторный проход очереди через 15 с, а не ждёт следующего тика планировщика. Переменная — значение по умолчанию при ПЕРВОМ старте: дальше действующие значения хранятся в настройках (`instance_settings.general.runLimits`) и меняются на лету на странице Instance → General («Run limits») или через `GET`/`PATCH /api/myrmidon/runtime-limits` — очередь стартует после подъёма потолка в пределах минуты, перезапуск сервера не нужен. Тот же `GET`-вид — экран нагрузки экземпляра: он несёт снимок очереди (прогоны в работе против потолка, сколько ждут, голова очереди с её агентом), загрузку CPU хоста, против которой меряется потолок, и снимок памяти — свободную/полную память хоста и использование cgroup v2 контейнера сервера против его лимита (`memory.max` − `memory.current`, возвращаемый кэш `inactive_file` считается свободным). Обе панели настроек показывают эти строки рядом с полями | Не задана, пустая, `0`, отрицательное или не число — лимит выключен. Работает вместе с двумя переменными ниже. Пустое поле в настройках — лимит выключен (то же `null` в `general.runLimits`); правка строки БД вручную вступает в силу после перезапуска |
