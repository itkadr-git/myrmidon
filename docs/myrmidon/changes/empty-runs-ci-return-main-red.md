## changelog-en

### A CI delivery is handled by the final result of the head; a failed result does not return a task while main is red (EMPTY-RUNS-3)

- The GitHub connection events treated every finished job, and every finished run of an auxiliary workflow, as a finished CI of the pull request: the monitor of the task was disarmed, its assignee was to be woken (`ci_completed`), and a task in review went back to its executor — all on the first job that ended. On 13.11, the first day the App delivered check events, that was 48 returns from review (45 of them on a single `check_run`); after main went red, 13 more, 6 of them on the very shards that were red on main; one such run made 139 model calls on 5.88M input tokens to answer "main is red, nothing to change". A task whose monitor had been disarmed by the first job was picked up minutes later by the stranded-task recovery: one such run cost 888K input tokens to report "4 jobs still running".
- Now only the delivery that carries the final result of the current head counts: the finished `CI result` check (a cancelled, skipped or stale one is not a result), or — for a pull request that has no such check — the moment GitHub shows every check finished. A job that ends changes nothing: the monitor stays armed, nobody is woken, `lastCompletedCi` is not written. The final result is recorded as `lastCompletedCi` of the pull request rows, announces a possible merge when green, disarms the monitor and wakes the assignee once per result; the same result delivered again wakes nobody, and a result of an older head decides nothing. A job that starts after the result of the head (the re-run of a gate, an auxiliary workflow) does not reopen it; the final check does. The wake goes to a task that is being worked on or reviewed, or whose agent armed a monitor; a parked task without a monitor and a closed task are not woken.
- A task in a pending review stage goes back to its executor on a failed final result, with the failed checks named in the comment. A failed result with `main-green` red on the head is a failure on a red base branch: the task stays in review, the executor is not woken, a system note says why and the `ci_infra_retry_needed` row is written, once per head. When main is green again the "Main green gate" workflow re-runs `main-green` on open pull requests; that delivery brings the head back, and a head that is still red is returned to its executor with the instruction to re-run the failed jobs first. A head on which only `CI result` failed is held the same way as an infrastructure failure.
- The wakes of a delivery really reach the queue now. The App webhook is served by the api processes, where the event service had been given a stub instead of a wake function: not one `ci_completed` wake was recorded for 54 returns from review. An api process now enqueues the wake through a heartbeat service of its own role (it executes nothing itself and announces the queued run to the worker over the process bus), and every wake of a delivery — `ci_completed`, the merge-conflict return, the merged-PR confirmation — is sent after the transaction of the delivery has committed: the admission of a wake locks the task row the delivery has just written, so a wake sent from inside the transaction would wait for its own caller.
- The name of the check is kept in the stored record of a `check_run` delivery (`checkName`).
- `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED=off` brings back the old handling (and, in an api process, the dropped wake); `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED=off` removes the holds — every failed final result returns the task; `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` without `main-green` removes the base-branch hold. When GitHub cannot be read a failed final result returns the task without the list of checks.

## changelog-ru

### Доставка CI обрабатывается по итоговому результату головы; красный результат не возвращает задачу при красном main (EMPTY-RUNS-3)

- События GitHub считали завершённым CI любой закончившийся джоб и любой закончившийся прогон вспомогательного процесса: с задачи снимался монитор, исполнителю ставилась побудка (`ci_completed`), задача на ревью уходила исполнителю — всё по первому завершившемуся джобу. 13.11, в первый день, когда приложение стало доставлять события проверок, это дало 48 возвратов с ревью (45 из них по одному `check_run`); после того как main покраснел — ещё 13, из них 6 по тем же шардам, что красные на main; один такой прогон сделал 139 вызовов модели на 5,88 млн входных токенов, чтобы ответить «main красный, править нечего». Задачу, с которой монитор снят первым джобом, через минуты поднимал обход застрявших: один такой прогон потратил 888 тыс. входных токенов, чтобы сообщить «4 джоба ещё идут».
- Теперь считается только доставка с итоговым результатом текущей головы: завершённая проверка `CI result` (отменённая, пропущенная или устаревшая — не результат) либо, если у PR такой проверки нет, момент, когда GitHub показывает завершёнными все проверки. Закончившийся джоб ничего не меняет: монитор остаётся взведённым, никто не будится, `lastCompletedCi` не пишется. Итоговый результат записывается в `lastCompletedCi` строк PR, при зелёном уведомляет о возможном слиянии, снимает монитор и будит исполнителя один раз на результат; повторная доставка того же результата никого не будит, результат старой головы ничего не решает. Джоб, стартовавший после результата головы (перезапуск ворот, вспомогательный процесс), результат не сбрасывает; итоговая проверка — сбрасывает. Побудка идёт задаче, над которой работают или которую ревьюят, либо той, где агент взвёл монитор; отложенная задача без монитора и закрытая не будятся.
- Задача в ожидающей стадии ревью возвращается исполнителю по красному итоговому результату, упавшие проверки названы в комментарии. Красный результат при красной `main-green` на голове — падение на красной базовой ветке: задача остаётся на ревью, исполнитель не будится, системная заметка объясняет причину, пишется запись `ci_infra_retry_needed` — один раз на голову. Когда main позеленеет, процесс «Main green gate» перезапускает `main-green` на открытых PR; эта доставка возвращает голову на разбор, и всё ещё красная голова уходит исполнителю с указанием сначала перезапустить упавшие джобы. Голова, на которой упал только `CI result`, удерживается так же — как инфраструктурный сбой.
- Побудки доставки теперь действительно попадают в очередь. Вебхук приложения принимают api-процессы, а сервису событий там вместо функции побудки была передана заглушка: на 54 возврата с ревью не записано ни одной побудки `ci_completed`. Api-процесс теперь ставит побудку через сервис пульса своей роли (сам ничего не исполняет, о поставленном прогоне сообщает рабочему процессу по шине процессов), а все побудки доставки — `ci_completed`, возврат по конфликту слияния, подтверждение слитого PR — отправляются после фиксации транзакции доставки: приём побудки блокирует строку задачи, которую доставка только что записала, и побудка изнутри транзакции ждала бы собственного вызывающего.
- В сохраняемой записи доставки `check_run` хранится имя проверки (`checkName`).
- `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED=off` возвращает прежнюю обработку (и, в api-процессе, отброшенную побудку); `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED=off` убирает удержания — любой красный итоговый результат возвращает задачу; `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` без `main-green` убирает удержание по красной базовой ветке. Если GitHub прочитать не удалось, красный итоговый результат возвращает задачу без списка проверок.

## divergence

| EMPTY-RUNS-3 | Обработка доставок CI по итоговому результату головы PR: при подключённом читателе проверок (`resolveCiReturnFacts`, подключается в `server/src/index.ts`) `applyCiCompletionEvent` передаёт доставку в `applyCiDeliveryByVerdict`. Закончившийся джоб (`check_run` не `CI result`) ничего не меняет; итог — завершённая `CI result` либо, пока у PR её не видели (отметка `ciFinalCheckSeen` в метаданных work product), завершённый прогон, подтверждённый чтением GitHub без кэша (`readPullRequestHeadCheckRunsNow`). Итог пишет `lastCompletedCi` (а `activeCi` держится от старта джобов до итога), уведомляет слияние при зелёном, снимает монитор и будит исполнителя один раз на результат; задаче не в работе, не на ревью и без монитора побудка не ставится. Красный итог возвращает задачу из ожидающей стадии ревью, кроме красной `main-green` на голове и падения одних инфраструктурных проверок: удержание — отметка `ciReturnHold`, системная заметка, запись `issue.ci_infra_retry_needed`, один раз на голову; доставка по удержанной голове (перезапуск `main-green`) пересматривает решение (ключ побудки `…:hold-released`). Решения — чистые функции `classifyCiDelivery`, `ciVerdictOfHead`, `decideCiFailureReturn`. Все побудки доставки (`ci_completed`, возврат по конфликту, подтверждение слитого PR) отправляются после фиксации транзакции доставки (`DeliveryWakes`); в api-процессе сервис событий получает настоящую побудку (сервис пульса роли api, создаётся при первой побудке, шина процессов) вместо заглушки. В нормализованную запись `check_run` добавлено имя проверки (`checkName`). ## settings-en

| `MYRMIDON_GITHUB_CI_FINAL_ONLY_ENABLED` | EMPTY-RUNS-3 | unset (on) | A CI delivery of a pull request (`check_run`, `check_suite`, `workflow_run`) is handled by the final result of the current head: one finished job changes nothing; the finished `CI result` check (or, for a pull request without it, every check finished on GitHub) records `lastCompletedCi`, disarms the monitor of the task, wakes its assignee once and returns a task from review when red. In an api process the wakes of the GitHub events are really enqueued | `off`, `0`, `false` or `no` brings back the old handling: every completed delivery is a finished CI, and an api process drops the wake as before. Read on every CI delivery |

## settings-en-replace

| `MYRMIDON_REVIEW_RETURN_GUARD_ENABLED` | REVIEW-RETURN-GUARD | unset (on) | An agent reviewer's return of a task (`changes_requested`) on the same pull request head as the previous return, or only because infrastructure checks of the head failed, is recorded but does not wake the executor. The rest of the board (a new CI result, a comment, a new head) still does. EMPTY-RUNS-3: the same switch covers the holds of the board's own return on a failed final CI result — a task stays in review while `main-green` is red on the head or only infrastructure checks failed | `off`, `0`, `false` or `no` brings back a wake for every return, and every failed final CI result returns the task. Read on every review decision and every CI delivery |

## settings-en-replace

| `MYRMIDON_REVIEW_INFRA_CHECK_NAMES` | REVIEW-RETURN-GUARD | `CI result,main-green` | Comma or newline separated names of the checks whose failure does not say anything about the code (whole names, case-insensitive). A return is infrastructure-only when every check that failed on the head is on this list and the decision comment reports only CI. EMPTY-RUNS-3: the board's own return on a failed final CI result holds a task in review when only these checks failed, and — while `main-green` is on the list — when `main-green` failed on the head (red base branch) | An empty value leaves no infrastructure check: only the same-head rule works and every failed final CI result returns the task; a list without `main-green` removes the base-branch hold. Read on every review decision and every CI delivery |
