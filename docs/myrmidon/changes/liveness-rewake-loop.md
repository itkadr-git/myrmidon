## changelog-en

### The blockers-resolved backstop wakes a task once per resolution and no longer undoes the continuation stop (LIVENESS-REWAKE-LOOP)

- On 16.11, in 24 hours, the continuation guard stopped tasks 39 times (16 tasks) with the comment "Остановлено: 3 продолжения подряд без внешнего события". In 23 of the 39 cases the task was woken again within 15 minutes by `issue_blockers_resolved` with `backstop = issue_graph_liveness_reconciliation`, although its blocker had been done for a long time and nothing new had happened. Each wake started three more continuations, then the next stop. Result: 166 runs and 48 million input tokens for nothing.
- Cause, in two parts. (1) The backstop (`reconcileResolvedDependencyWakeBackstop`, `services/recovery/service.ts`) deduplicates by a key that contains `blockedTransitionAt`. The continuation stop moves the task to `blocked`, which changes `blockedTransitionAt`, so the key is new on every cycle and the same resolved blocker wakes the task again. (2) The wake the backstop emits is logged as `issue.blockers_resolved_wake_emitted`, which the continuation cap counts as an external event, so the cap count restarted each time.
- Now the backstop wakes once per resolution: it takes the close time of the newest blocker (`completedAt`/`cancelledAt`) and does not wake if a `issue_blockers_resolved` wake for the same task and agent was requested at or after it, whatever the cycle of its key. A blocker that is reopened and closed again has a newer close time, so the task is woken again.
- The backstop does not wake a task that the continuation stop parked, unless an external event came after the stop: a comment or movement by a person or another agent, a PR/CI sync event, a blocker closed after the stop, or a change of assignee. The emission of the backstop itself is not such an event. The stop is found by the `issue.continuation_cap_reached` activity (`isIssueInContinuationStop`, `myrmidon/continuation-cap.ts`).
- The result of the backstop has a new counter, `continuationStopSkipped`.
- Second fix, in the same guard: a push of the agent did not restart the count of continuations. `loadExternalMovements` first filtered the activity by the list of movement actions, which has no `issue.work_product_head_changed`, so the row of the webhook (`system:github-webhook`) was dropped before the branch that accepts it. On 16.11 an engineer who pushed in each run was stopped after 3 continuations (`consecutiveContinuations: 3`, expected 1); the guard fired 33 times in 3 hours. The filter now takes the union of the movement actions and the allowed system actions; the rule "system actions only from the list" stays. `isIssueInContinuationStop` uses the same function, so a PR head change after the stop also lifts the stop.

## changelog-ru

### Резервная побудка «блокер снят» будит задачу один раз на снятие и не отменяет остановку сторожа продолжений (LIVENESS-REWAKE-LOOP)

- 16.11 за сутки сторож продолжений остановил задачи 39 раз (16 задач) комментарием «Остановлено: 3 продолжения подряд без внешнего события». В 23 случаях из 39 задачу снова будили в течение 15 минут побудкой `issue_blockers_resolved` с `backstop = issue_graph_liveness_reconciliation`, хотя блокер давно закрыт и нового ничего не случилось. Каждая побудка начинала ещё три продолжения, затем следующую остановку. Итог: 166 прогонов и 48 млн входных токенов впустую.
- Причина из двух частей. (1) Резервная сверка (`reconcileResolvedDependencyWakeBackstop`, `services/recovery/service.ts`) дедуплицирует по ключу, в который входит `blockedTransitionAt`. Остановка продолжений переводит задачу в `blocked`, `blockedTransitionAt` меняется, ключ каждый раз новый, и тот же снятый блокер будит задачу снова. (2) Побудка сверки пишется в журнал как `issue.blockers_resolved_wake_emitted`, а счётчик продолжений считает её внешним событием, поэтому счёт начинался заново.
- Теперь сверка будит один раз на снятие: берёт время закрытия самого нового блокера (`completedAt`/`cancelledAt`) и не будит, если побудка `issue_blockers_resolved` для той же задачи и агента запрошена не раньше него, при любом цикле в ключе. Блокер, переоткрытый и закрытый снова, имеет новое время закрытия, и задачу будят снова.
- Сверка не будит задачу, которую остановил сторож продолжений, пока после остановки не было внешнего события: комментария или движения человека либо другого агента, события синхронизации PR/CI, блокера, закрытого после остановки, смены исполнителя. Собственная побудка сверки таким событием не считается. Остановка определяется по записи `issue.continuation_cap_reached` (`isIssueInContinuationStop`, `myrmidon/continuation-cap.ts`).
- В результате сверки новый счётчик `continuationStopSkipped`.
- Второе исправление в том же сторожe: пуш агента не начинал счёт продолжений заново. `loadExternalMovements` сначала отбирал записи по списку действий движения, в котором нет `issue.work_product_head_changed`, и строка вебхука (`system:github-webhook`) отсекалась до ветки, которая её допускает. 16.11 инженер, пушивший в каждом прогоне, останавливался после 3 продолжений (`consecutiveContinuations: 3`, ожидалось 1); за 3 часа сторож сработал 33 раза. Теперь фильтр берёт объединение действий движения и допустимых системных действий; правило «системные действия только из списка» осталось. `isIssueInContinuationStop` использует ту же функцию, поэтому смена головы PR после остановки тоже снимает остановку.
