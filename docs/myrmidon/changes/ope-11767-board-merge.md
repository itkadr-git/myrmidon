## changelog-en

### Review routing: the board merges an approved pull request once its head is green; conflicts go back for a rebase (OPE-11767)

- A task whose board review stage is approved and whose open pull request is green and mergeable on the approved head is now merged by the board itself through the shared GitHub App identity (squash, the repository's convention). It fires when a review is approved, when a CI run completes, and on the periodic review-routing pass as the safety net; the pass merges at most `boardMerge.maxMergesPerPass` pull requests. Before this, a PR approved while CI was still running was merged by nobody once CI turned green: the steward lane only creates a human "Merge PR" task (and its GitHub resolver finds no token on the release board), and the host script that covered the gap was removed.
- The merge is bound to the exact approved head: the approving verdict must name the current head (a full or abbreviated sha anywhere in the verdict — the reviewers' `APPROVE PR #N <sha>` is now read; before only the spelling `head <sha>` was, which left the GitHub approval marker unset on PR #2449 and #2467), the required check `CI result` must be `success` on that head (latest run per name; cancelled, skipped and stale runs are not a verdict), the base must be `main` (or a configured release base) and GitHub must report the PR mergeable. The merge call carries the approved sha, so a head that moved is refused by GitHub itself (409). A branch that is merely behind main is merged as it is: the board never calls `update-branch` after an approval, because it would move the head and void the approval.
- A conflict with the base after the approval — or a head behind a base that the repository requires to be up to date — returns the task to its implementer once (status `in_progress`, changes requested) with a system comment "конфликт с main после одобрения — нужен rebase", and wakes the implementer. Before, such a task stayed in `in_review` forever.
- A PR blocked only by the missing `review-approved` marker (the hot-files gate) gets the marker from the board and is merged on the next look.
- The behavior is the new `boardMerge` block of `instance_settings.general.reviewRouting`, ON by default; `boardMerge.enabled = false` restores the previous behavior exactly. A settings screen that does not know the block keeps the stored value on save.

## changelog-ru

### Маршрутизация ревью: доска сама вливает одобренный PR, когда голова позеленела; конфликт возвращает задачу на rebase (OPE-11767)

- Задача, у которой этап ревью доски одобрен, а открытый PR зелёный и вливаемый на одобренной голове, теперь вливается самой доской через общую идентичность GitHub App (squash — соглашение репозитория). Срабатывает при одобрении ревью, при завершении прогона CI и на периодическом проходе маршрутизации ревью как страховка; проход вливает не больше `boardMerge.maxMergesPerPass` PR. Раньше PR, одобренный при идущем CI, не вливал никто, когда CI позеленел: полоса стюарда только заводит человеку задачу «Merge PR» (а её GitHub-резолвер на боевой доске не находит токен), хост-скрипт, закрывавший разрыв, снят.
- Вливание привязано к точной одобренной голове: вердикт одобрения должен назвать текущую голову (полный или сокращённый sha где угодно в тексте — формат ревьюеров `APPROVE PR #N <sha>` теперь читается; раньше читалась только запись `head <sha>`, из-за чего на PR #2449 и #2467 не ставилась метка одобрения на GitHub), обязательная проверка `CI result` должна быть `success` на этой голове (последний прогон по имени; отменённые, пропущенные и устаревшие прогоны вердиктом не считаются), база — `main` (или настроенная релизная), и GitHub должен считать PR вливаемым. Вызов слияния несёт одобренный sha, поэтому сместившуюся голову GitHub отклоняет сам (409). Ветка, которая просто отстала от main, вливается как есть: доска после одобрения никогда не зовёт `update-branch` — он сдвинул бы голову и обнулил одобрение.
- Конфликт с базой после одобрения — или голова, отставшая от базы, которая по правилам репозитория должна быть актуальной, — один раз возвращает задачу исполнителю (статус `in_progress`, запрошены правки) системным комментарием «конфликт с main после одобрения — нужен rebase» и будит исполнителя. Раньше такая задача висела в `in_review` бесконечно.
- PR, заблокированный только отсутствием метки `review-approved` (гейт горячих файлов), получает метку от доски и вливается при следующем просмотре.
- Поведение задаётся новым блоком `boardMerge` в `instance_settings.general.reviewRouting`, по умолчанию ВКЛЮЧЕНО; `boardMerge.enabled = false` точно возвращает прежнее поведение. Экран настроек, не знающий блока, при сохранении не затирает сохранённое значение.

## settings-en-append

<!-- section: REVIEW-ROUTING: automatic reviewer for tasks in review -->

Board-side merge (OPE-11767). The fields live under `boardMerge` in the same `instance_settings.general.reviewRouting` document; a settings screen that does not send the block keeps the stored value. Absent or malformed `boardMerge` — or any field of it — falls back to the defaults above.

When it runs. Three triggers share one evaluation: a review approval (the approval hook of the issue routes), a completed CI run of a pull request (the GitHub connection events), and the review-routing pass every 60 s as the safety net. Nothing polls on its own. The pass is skipped during maintenance mode, and the merge pauses while the board's GitHub budget is exhausted.

What it merges. A task in `in_review` (or `in_progress` after the guard-return) whose last review decision is `approved` with a completed stage, and whose pull request work product is open. The PR is read once (`GET /pulls/{n}`, a conditional request: a 304 spends no rate limit); the board merges it only when ALL of these hold: the base branch is in `boardMerge.baseBranches`; the approving verdict names the current head (an abbreviated or full sha anywhere in the text); GitHub reports the PR mergeable (`clean`, `unstable` or `has_hooks`); every `boardMerge.requiredChecks` check is `success` on that head. The merge call (`PUT /pulls/{n}/merge`) carries the approved sha, so GitHub refuses a head that moved. A branch that is only behind main is merged as it is; the board never calls `update-branch` after an approval.

What it sends back. A conflict with the base (`mergeable=false` / `dirty`), or a head `behind` a base the repository requires to be up to date, returns the task to its implementer once: status `in_progress`, review state `changes_requested`, a system comment ("конфликт с main после одобрения — нужен rebase") and a wake of the implementer. The activity entries are `issue.review_routing.board_merged`, `issue.review_routing.board_merge_returned` and `issue.review_routing.board_merge_labeled`.

Identity. The token comes from the shared GitHub identity: the one App entry that serves the repository (`allowedRepos`) with `contents` and `pull_requests` write, narrowed to that repository (and `checks` read when the entry has it); otherwise from a company secret named `GITHUB_TOKEN` / `GH_TOKEN` / `PAPERCLIP_GITHUB_TOKEN`. A repository nobody serves is never touched.

## settings-ru-append

<!-- section: REVIEW-ROUTING: автоназначение ревьюера задачам на ревью -->

Слияние силами доски (OPE-11767). Поля живут в блоке `boardMerge` того же документа `instance_settings.general.reviewRouting`; экран настроек, не присылающий блок, не затирает сохранённое значение. Отсутствующий или битый `boardMerge` — или любое его поле — читается как умолчания выше.

Когда срабатывает. Три триггера делят одну проверку: одобрение ревью (хук одобрения в маршрутах задач), завершённый прогон CI пулл-реквеста (события подключения GitHub) и проход маршрутизации ревью раз в 60 с как страховка. Своего опроса нет. Проход пропускается в режиме обслуживания, а слияние замирает, пока исчерпан бюджет запросов доски к GitHub.

Что вливается. Задача в `in_review` (или в `in_progress` после guard-return), у которой последнее решение ревью — `approved` при завершённом этапе, а рабочий продукт «пулл-реквест» открыт. PR читается одним запросом (`GET /pulls/{n}`, условным: ответ 304 не тратит лимит); доска вливает его, только когда выполнено ВСЁ: база входит в `boardMerge.baseBranches`; вердикт одобрения назвал текущую голову (сокращённый или полный sha где угодно в тексте); GitHub считает PR вливаемым (`clean`, `unstable` или `has_hooks`); каждая проверка из `boardMerge.requiredChecks` — `success` на этой голове. Вызов слияния (`PUT /pulls/{n}/merge`) несёт одобренный sha, поэтому сместившуюся голову GitHub отклоняет. Ветка, которая лишь отстала от main, вливается как есть; `update-branch` после одобрения доска не зовёт никогда.

Что возвращается. Конфликт с базой (`mergeable=false` / `dirty`) или голова `behind` относительно базы, которая по правилам репозитория должна быть актуальной, один раз возвращает задачу исполнителю: статус `in_progress`, состояние ревью `changes_requested`, системный комментарий («конфликт с main после одобрения — нужен rebase») и побудка исполнителя. Записи активности — `issue.review_routing.board_merged`, `issue.review_routing.board_merge_returned` и `issue.review_routing.board_merge_labeled`.

Идентичность. Токен берётся из общей идентичности GitHub: единственная запись App, обслуживающая репозиторий (`allowedRepos`) с записью в `contents` и `pull_requests`, суженная до этого репозитория (и чтение `checks`, если оно есть в записи); иначе — из секрета компании `GITHUB_TOKEN` / `GH_TOKEN` / `PAPERCLIP_GITHUB_TOKEN`. Репозиторий, который никто не обслуживает, не затрагивается.
