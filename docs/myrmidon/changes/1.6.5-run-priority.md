## changelog-en

### The queue starts reviews, releases and current-release work first (1.6.5 RUN-PRIORITY, part A)

- While run admission is closed, a freed slot no longer goes to whoever queued
  first: every queued run now carries an effective weight banded by its agent's
  role — the role opens the band, and the issue priority, the current-release
  lift and the aging step only order the runs *inside* it. The role therefore
  decides who starts whatever the issue priority is: a review or release run
  goes before an engineer's critical-issue run, and a run carrying the current
  release goes before every other role, one whole band above the heaviest one.
  Default role weights put `review` and `release` on top, `lead` next, then
  `engineer` and `docs`, everything else at the floor; default issue weights
  follow the familiar critical > high > medium > low order inside the band.
- Both queue paths apply it: the global sweep visits agents by their
  best-weighted queued run (weight, then the age of that run, then id) before
  starting anything, and the per-agent comparator sorts each agent's own queue
  by the same weight inside each readiness rank, with a `createdAt`
  tie-break. The admission gates themselves (load, memory, starts per
  minute, per-agent slots, the fair share) are unchanged — priority only
  reorders the choice inside the slots admission admits.
- The waiting run also says where it stands: with priority on, every pass writes
  `queuePosition` of `queueLength` into each queued run's `contextSnapshot` (the
  rank that pass's order gave it), and a run left behind by a pass that did start
  runs of its agent gets `waitReason: "priority"` — its slot went to a heavier
  run. The claim that starts a run clears both fields, so they describe the
  current wait only; the run card renders the position beside the reason (UI,
  part B).
- Against starvation: the effective weight grows by a configurable step per
  configurable waiting minutes (capped by a maximum bonus) *inside* the band,
  and a run that waits past the starvation limit takes the escape lane outright
  — one that outranks every role and the current-release lift, so no queued run
  can stay behind the queue forever.
- The weights are live settings, the run-limits pattern: the sweeps read them
  fresh every pass, so a change through `PATCH /api/myrmidon/run-priority`
  (or the environment at boot) reorders the very next sweep without a server
  restart. Turning the feature off falls back to the pre-feature ordering
  (fair-share oldest-first globally, priority-rank + `createdAt` per agent).

## changelog-ru

### Очередь первым делом запускает ревью, релизы и задачи текущего релиза (1.6.5 RUN-PRIORITY, часть A)

- Пока допуск прогонов закрыт, освободившееся место больше не достаётся тому,
  кто встал в очередь первым: каждый queued-прогон получает эффективный вес,
  разбитый на полосы по роли агента — роль открывает полосу, а приоритет
  задачи, надбавка за текущий релиз и aging-шаг упорядочивают прогоны только
  *внутри* неё. Поэтому старт решает роль, каким бы ни был приоритет задачи:
  ревью или релизный прогон идёт раньше инженерного с critical-задачей, а
  прогон текущего релиза — раньше любой другой роли, на целую полосу выше
  самой тяжёлой из них. Дефолтные веса ролей ставят наверх `review` и
  `release`, затем `lead`, потом `engineer` и `docs`, остальных — на пол; веса
  приоритетов задач идут привычным порядком critical > high > medium > low
  внутри полосы.
- Применяется в обоих проходах: глобальный sweep обходит агентов по их
  лучшему по весу queued-прогону (вес, затем возраст этого прогона, затем id)
  перед стартом, а компаратор внутри агента сортирует его очередь по тому же
  весу внутри ранга готовности зависимостей, с tie-break по `createdAt`.
  Гейты допуска сами (нагрузка, память, старты в минуту, слоты агента,
  справедливая доля) не меняются — приоритет лишь упорядочивает выбор внутри
  допущенных слотов.
- Ожидающий прогон сообщает и своё место: при включённом приоритете каждый
  проход пишет `queuePosition` из `queueLength` в `contextSnapshot` каждого
  queued-прогона (место, которое дал порядок этого прохода), а прогон,
  оставшийся в очереди после прохода, который стартовал прогоны его агента,
  получает `waitReason: "priority"` — место ушло более тяжёлому прогону.
  Старт прогона стирает оба поля, поэтому они описывают только текущее
  ожидание; карточка прогона показывает место рядом с причиной (UI, часть B).
- Против голодания: эффективный вес растёт на настраиваемый шаг за каждые
  настраиваемые минуты ожидания (с потолком) *внутри полосы*, а прогон,
  простоявший дольше предела голодания, получает отдельную полосу-побег —
  выше любой роли и надбавки за текущий релиз, поэтому ни одна очередь не
  может ждать вечно.
- Веса — живые настройки, паттерн run-limits: проходы читают их каждый раз
  заново, поэтому изменение через `PATCH /api/myrmidon/run-priority` (или из
  окружения при старте) переставляет следующий же sweep без перезапуска
  сервера. Выключение возвращает дословно довоенный порядок (глобально —
  oldest-first по справедливой доле, внутри агента — ранг готовности, вес
  приоритета задачи, createdAt).

## divergence

| 1.6.5-RUN-PRIORITY | Эффективный вес queued-прогона = полоса роли агента (`agents.role`, регистронезависимо) × ширину полосы + вес приоритета задачи из `contextSnapshot.issueId` + надбавка за совпадение метки задачи/имени ветки воркспейса с текущим релизом + aging-бонус (шаг за каждые `agingStepMinutes` ожидания, не выше `agingMaxBonus`). ## settings-en

| `MYRMIDON_RUN_PRIORITY_ENABLED` | 1.6.5 RUN-PRIORITY | `on` | Master switch of the queue priority core. With it off, both sweeps keep the pre-feature ordering (global oldest-first fairness, per-agent readiness rank + issue-priority rank + createdAt). `0`, `off`, `false` turn it off; anything else (or unset) keeps it on. Stored as `instance_settings.general.runPriority.enabled` and flipped live on `PATCH /api/myrmidon/run-priority` | unset — on. The sweeps re-read the in-force settings every pass, so the next sweep after a settings change uses the new value without a restart |
| `MYRMIDON_RUN_PRIORITY_ROLE_WEIGHTS` | 1.6.5 RUN-PRIORITY | `review=90,release=90,lead=80,engineer=50,docs=50` | Weight per agent role (`agents.role`, compared case-insensitively). The run of a review agent at a closed admission starts ahead of an engineer's older run. Pairs `role=weight` separated by commas; a role with no entry falls back to the default role weight. Stored in `general.runPriority.roleWeights`; a settings write merges over the environment, then over the defaults | malformed pair — skipped with a log; negative/NaN — the whole map falls back to defaults. Weights are integers 0..1000 |
| `MYRMIDON_RUN_PRIORITY_DEFAULT_ROLE_WEIGHT` | 1.6.5 RUN-PRIORITY | `30` | The weight of any role not named in the role weights (including the built-in `general`). Stored in `general.runPriority.defaultRoleWeight` | non-integer/out of 0..1000 — default |
