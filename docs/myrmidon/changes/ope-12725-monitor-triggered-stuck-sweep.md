## changelog-en

### OPE-12725: scheduler sweeps issue monitors stuck in `triggered` state forever

- After an issue monitor fires, `buildIssueMonitorTriggeredPatch` strips the policy monitor and nulls `monitorNextCheckAt`. If the woken run dies without settling the external wait, the issue kept `execution_state.monitor.status = "triggered"` forever: no timer existed, so nothing ever re-checked it, and comment-driven wakes kept deferring behind the dead monitor.
- `tickDueIssueMonitors` now runs `sweepStuckTriggeredIssueMonitors` next to the existing inactive-monitor drop. The sweep selects active-company agent-assigned issues (`in_progress`/`in_review`/`blocked`) whose `monitorNextCheckAt` is null and whose execution-state monitor still says `triggered`, after a 10-minute grace since `monitorLastTriggeredAt`.
- A monitor whose state `timeoutAt` (persisted at trigger time) is still ahead gets a bounded re-arm: `monitorNextCheckAt` = min(now + 30 s × 2^min(attempts, 4), timeoutAt), capped at 10 minutes, activity `issue.monitor_rearmed_after_trigger`.
- An expired monitor is cleared with `clearReason: "timeout_exceeded"` through the same `buildIssueMonitorClearedPatch` path as normal monitor expiry (activity `issue.monitor_timeout_swept`) and wakes the assignee once per trigger with a new `issue_monitor_timeout` wake reason (idempotency key `issue-monitor-timeout:<issueId>:<lastTriggeredAt>`), so the agent learns the wait was abandoned instead of sitting silently. Orphaned monitors (post-trigger shape with no policy) are covered by the same predicate; once cleared, comment wakes no longer defer.
- Rows missing either `timeoutAt` or `lastTriggeredAt` are skipped — the sweep never invents a timeout. Both new wake and sweep paths reuse existing guardrails (`withRecoveryContext` status-only payload, per-row try/catch, limit 50 per tick). No wake-queue change: the comment-wake deferral gate keys on `monitorNextCheckAt`, not the monitor status, so clearing the monitor is sufficient.

## changelog-ru

### OPE-12725: планировщик подчищает мониторы задач, навсегда застрявшие в состоянии `triggered`

- После срабатывания монитора задачи `buildIssueMonitorTriggeredPatch` вырезает монитор из политики и обнуляет `monitorNextCheckAt`. Если разбуженный прогон умирал, не закрыв внешнее ожидание, задача навсегда оставалась с `execution_state.monitor.status = "triggered"`: таймера не существовало, перепроверки не происходило, а пробуждения от комментариев продолжали откладываться из-за мёртвого монитора.
- `tickDueIssueMonitors` теперь рядом с существующим сбросом неактивных мониторов запускает `sweepStuckTriggeredIssueMonitors`. Выборка: задачи активной компании с агентом-исполнителем (`in_progress`/`in_review`/`blocked`), где `monitorNextCheckAt` пуст, а монитор в состоянии исполнения всё ещё `triggered`, после 10 минут с `monitorLastTriggeredAt`.
- Монитор, чей `timeoutAt` из состояния (сохранённый в момент срабатывания) ещё не наступил, получает ограниченный перезапуск: `monitorNextCheckAt` = min(сейчас + 30 с × 2^min(попытки, 4), timeoutAt), с потолком в 10 минут, активность `issue.monitor_rearmed_after_trigger`.
- Просроченный монитор закрывается с `clearReason: "timeout_exceeded"` тем же путём `buildIssueMonitorClearedPatch`, что и обычное истечение монитора (активность `issue.monitor_timeout_swept`), а исполнитель получает одно пробуждение на срабатывание с новой причиной `issue_monitor_timeout` (ключ идемпотентности `issue-monitor-timeout:<issueId>:<lastTriggeredAt>`): агент узнаёт, что ожидание брошено, вместо молчания. Осиротевшие мониторы (после срабатывания без политики) покрываются тем же предикатом; после закрытия пробуждения от комментариев больше не откладываются.
- Строки без `timeoutAt` или `lastTriggeredAt` пропускаются — sweep никогда не выдумывает таймаут. Оба новых пути переиспользуют существующие предохранители (`withRecoveryContext` со status-only, try/catch на строку, лимит 50 за тик). Очередь пробуждений не менялась: врата откладывания комментариев завязаны на `monitorNextCheckAt`, а не на статус монитора, поэтому достаточно закрыть сам монитор.
