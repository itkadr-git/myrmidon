## changelog-en

### Runs wait instead of failing when the bot volume has less than 5% free space (OPE-13419)

- On 16.11 the bot volume filled up to 100% and 63 runs failed in 10 minutes: `myr-ws open` refused the workspace (`BOT_DISK_QUOTA_EXCEEDED`) after the run had already started. Now, while the physical bot volume (read from dockergate) has less than 5% free, a queued run is not started and not cancelled: the same run waits in `scheduled_retry` with the reason `disk_budget` (`contextSnapshot.diskBudgetDeferral`, a run event) and is looked at again after 1, 2, then every 5 minutes. At 5% free or more the threshold blocks nothing, and the run starts by itself once space is back. A wake made by a user is not held; a volume that cannot be measured never blocks. `myr-ws open` also refuses a new copy at less than 5% free with `BOT_DISK_QUOTA_EXCEEDED: disk_budget` (reuse of an existing copy is not blocked). The minimum is 5% free by default (about 11.5 GB of a 230 GB volume) and is set with the env variable `MYRMIDON_DISK_BUDGET_MIN_FREE_PERCENT` (a number above 0 up to 50; a wrong value means 5) on the board and in the bot image (`myr-ws`). The existing partition pressure rules (85/90/95%) are unchanged.
- The first deferral asks the host for an extraordinary cleanup: the board writes the file named by `MYRMIDON_HOST_GC_REQUEST_FILE`, a systemd path unit (`myrmidon-host-gc-request.path`) starts host GC, and host GC removes the file when its pass starts and runs in its disk-pressure mode (it never deletes more than a normal pass may). The request is sent once per 10 minutes, and many deferred runs ask once. If the request cannot be written, the runs still wait and the board asks again after 1 minute. Host GC keeps its own lock, so two cleanups never run together.

## changelog-ru

### Прогоны ждут, а не падают, когда на томе ботов свободно меньше 5% (OPE-13419)

- 16.11 том ботов заполнился до 100%, за 10 минут упало 63 прогона: `myr-ws open` отказывал в рабочей копии (`BOT_DISK_QUOTA_EXCEEDED`) уже после старта прогона. Теперь, пока на физическом томе ботов (данные dockergate) свободно меньше 5%, прогон из очереди не стартует и не отменяется: тот же прогон ждёт в `scheduled_retry` с причиной `disk_budget` (`contextSnapshot.diskBudgetDeferral`, событие прогона) и перепроверяется через 1, 2 и далее каждые 5 минут. При 5% и больше порог ничего не запрещает, а прогон стартует сам, когда место вернулось. Запуск пользователем не откладывается; том, который не удалось измерить, не блокирует. `myr-ws open` тоже отказывает в новой копии при свободных менее 5% текстом `BOT_DISK_QUOTA_EXCEEDED: disk_budget` (повторное открытие существующей копии не блокируется). Минимум по умолчанию 5% свободного (около 11,5 ГБ тома 230 ГБ), задаётся переменной окружения `MYRMIDON_DISK_BUDGET_MIN_FREE_PERCENT` (число больше 0 до 50; неверное значение даёт 5) на доске и в образе бота (`myr-ws`). Прежние правила давления на раздел (85/90/95%) не изменены.
- Первое откладывание просит хост о внеочередной уборке: доска пишет файл из `MYRMIDON_HOST_GC_REQUEST_FILE`, path-юнит systemd (`myrmidon-host-gc-request.path`) запускает host GC, а он удаляет файл в начале прохода и работает в своём режиме давления диска (удаляет не больше, чем обычный проход). Запрос уходит не чаще раза в 10 минут, много отложенных прогонов просят один раз. Если файл записать не удалось, прогоны всё равно ждут, а доска повторит просьбу через 1 минуту. У host GC свой замок, поэтому две уборки одновременно не идут.
