# MODEL-SWITCH-SESSION

## Обзор

Переключение агента на модель с меньшим контекстным окном раньше выводило
агента из строя. Сохранённая сессия переставала помещаться в новое окно, каждый
прогон падал с `Context compression could not bring this session under the
model's context window` (а на очень большой очереди — с HTTP 400 `Exceeded limit
on max bytes to request body`), агент уходил в «залипающее» состояние ошибки, и
сессию приходилось сбрасывать вручную через `runtime-state/reset-session`.
Переполнение контекста — восстановимая ситуация, а не отказ агента. Это
изменение делает её самовосстанавливаемой.

## Что изменено

### Сервер — `server/src/services/heartbeat.ts`

- `isContextWindowError(message)` сопоставляет сообщение об ошибке прогона с
  известными сигнатурами переполнения контекста. Сравнение без учёта регистра;
  null, undefined и пустая строка никогда не дают совпадения.
- Ошибка контекстного окна больше не переводит агента в `error`. Обе точки
  финализации передают для неё `keepIdleOnFailure` (`finalizeAgentStatus` на
  пути прогона и путь упавшего прогона в catch), рядом с существующими
  причинами `provider_quota`, конфликт синхронизации воркспейса и транзиентный
  сбой вышестоящего сервиса. Агент остаётся idle: его очередь не упирается в
  состояние здоровья, которого у него нет.
- Если прогон упал с ошибкой контекстного окна и у прогона есть task key,
  сохранённая сессия этого task key удаляется (`clearTaskSessions`). Следующий
  прогон поэтому начинает новую сессию вместо повтора той, что не помещается.
  Удаление ограничено этим task key; сессии других task key не затрагиваются.
- Удаление пишет одно информационное событие прогонного журнала `lifecycle`.
  В сообщении — task key, в payload — `reason: "context_window_error"` и task
  key. Ошибка удаления только логируется и не роняет прогон.

### Интерфейс — `ui/src/components/AgentConfigForm.tsx`

Выбор модели не может сравнивать контекстные окна. Список включённых моделей,
который читает карточка агента (`AdapterModel`), несёт только `id`, `label` и
`pricing`: по-модельного контекстного окна в интерфейсе нет, а размер окна,
который он показывает (живой readout использования в чате задачи), приходит из
текущей сессии, а не из каталога моделей.

Поэтому карточка предупреждает о самом действии, а не о числе токенов, которого
у неё нет: смена модели у существующего агента поднимает toast тона `warn`
через собственный канал уведомлений доски (`useOptionalToastActions`). В toast
названы прежняя и новая модель и сказано, что сохранённая сессия остаётся и
будет очищена автоматически, если не поместится. Хук опциональный, поэтому форма
рендерится и вне `ToastProvider`.

## Распознаваемые сигнатуры ошибок

- `Context compression could not bring this session under the model's context window`
- `Exceeded limit on max bytes to request body`
- `context window exceeded`
- `session too large`
- `context limit exceeded`
- `max tokens exceeded`
- `input too long`
- `prompt too long`

## Тесты

`server/src/__tests__/context-window-error.test.ts` покрывает каждую сигнатуру,
сравнение без учёта регистра и негативные случаи (null, undefined, пустая строка
и сообщение без единой сигнатуры).

## Поведение после изменения

1. Прогон падает с ошибкой контекстного окна.
2. Агент остаётся idle, а не в ошибке.
3. Сохранённая сессия этого task key удаляется, в прогонном журнале появляется
   запись.
4. Следующий прогон начинает новую сессию, агент продолжает работу.

Ручной сброс (`POST /agents/:id/runtime-state/reset-session` с `taskKey`)
остаётся доступен и остаётся запасным путём, если автоматическая очистка сама не
удалась — прогонный журнал сообщает об этом предупреждением.

## Настройка

Не нужна. Ни обнаружение, ни очистка настройки не требуют.

## Ограничения

- Обнаружение основано на сигнатурах. Провайдер, который переформулирует ошибку
  переполнения без единой сигнатуры из списка, распознан не будет. Негативные
  тесты фиксируют текущее поведение.
- Очистка теряет контекст текущей сессии этого task key. Это и есть задуманное
  восстановление: оно эквивалентно ручному сбросу оператора.
- Предупреждение показывается на любой смене модели существующего агента, потому
  что интерфейс не знает, меньше ли новое окно. Это предостережение о действии, а
  не вычисленный прогноз.
