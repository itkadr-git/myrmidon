# Прогоны: одна копия executionContinuation (PERF-DIET)

Аудит 04.10 по базе доски: таблица `heartbeat_runs` выросла до 1,1 ГБ
(1,07 ГБ — TOAST-данные, тяжёлый JSON). В `context_snapshot` конверт
`executionContinuation` лежал дважды — на верхнем уровне и внутри
`paperclipWake`, по 90-100 КБ на копию, около 354 МБ дублей по таблице. Все
запросы, которые измеряют вес, лежат в
`docs/performance/heartbeat_runs_optimization.sql`.

## Что изменено

1. **Конверт continuation хранится один раз.** Снапшот прогона больше не
   получает `executionContinuation` на верхнем уровне; конверт живёт внутри
   `paperclipWake` — именно оттуда его уже читают адаптеры
   (`packages/adapter-utils/src/server-utils.ts`). `buildPaperclipWakePayload`
   теперь принимает конверт явным аргументом, а не достаёт его из снапшота.
   Сам wake-payload не меняется: он собирается из памяти, поэтому прогон
   по-прежнему получает свой конверт.
2. **Читатели ходят через один аксессор.** `readExecutionContinuation`
   (server/src/services/execution-continuation.ts) возвращает копию из
   wake-payload и откатывается на старую копию верхнего уровня для строк, до
   которых миграция ещё не дошла. Его используют путь возобновления
   (`buildExecutionContinuation`), учёт исходных комментариев и обратная связь
   нативного завершения.
3. **Существующие строки разбираются миграцией**
   (`0303_remove_execution_continuation_duplication.sql`). Она переносит копию
   верхнего уровня внутрь `paperclipWake`, если там её ещё нет — ни один конверт
   не теряется — и затем удаляет дублирующий ключ. Перезапись идёт по первичному
   ключу батчами по 200 строк, поэтому таблица на гигабайт не переписывается
   одним запросом. Заявление идемпотентно: повторный запуск после частичного
   применения трогает только оставшиеся строки.

## Как проверить

Запустите файл замеров на копии базы доски (или в окне обслуживания):
`docs/performance/heartbeat_runs_optimization.sql`. Он показывает

- общий размер отношения, размер TOAST и средний
  `pg_column_size(context_snapshot)` до и после миграции,
- сколько байт занимал дублирующийся конверт верхнего уровня и каков payload
  wake-копии одного прогона после миграции,
- `EXPLAIN (ANALYZE, BUFFERS)` для проекции списка прогонов, которую читает
  горячий роут.

Модульный сторож — `server/src/services/execution-continuation-wake-dedupe.test.ts`
(`pnpm --filter @paperclipai/server exec vitest run src/services/execution-continuation-wake-dedupe.test.ts`):
он закрепляет каноническую копию из wake-payload, откат на старую копию,
приоритет wake-payload, когда в строке обе копии, пустой конверт и исходные
комментарии.

В контейнере агента, готовившего изменение, нет ни клиента базы, ни `docker`,
поэтому цифры ниже — это данные аудита и арифметика из них; все запросы, которые
их дают, лежат в SQL-файле.

| Метрика | До | После (ожидаемо) |
|---|---|---|
| Общий размер `heartbeat_runs` | 1,1 ГБ (1,07 ГБ TOAST) | около 0,75 ГБ — один конверт на прогон вместо двух |
| Дублирующиеся конверты | ~354 МБ | 0 |
| `executionContinuation` верхнего уровня | есть у каждого прогона до миграции | удалён; payload без копии сначала получил её |

## DIVERGENCE

Форма хранения снапшота прогона меняется (одна копия вместо двух) — строка
записана во фрагменте изменений
`docs/myrmidon/changes/myr-1-6-5-continuation-dedupe.md`.

## Риски и откат

- Строки, у которых `paperclipWake` отсутствует или не объект, сохраняют конверт
  на верхнем уровне и пропускаются дедупликацией, поэтому миграция никогда не
  удаляет единственную копию.
- Откат — это откат кода: аксессор по-прежнему читает старую копию верхнего
  уровня, поэтому возвращённый писатель продолжает работать; сама миграция
  отмены не требует (она лишь удаляет дублирующийся ключ).
