# Семантика исполнения

> English version: [execution-semantics.md](execution-semantics.md)

Статус: актуальное руководство по реализации
Дата: 2026-08-18
Аудитория: продукт и инженерия

Этот документ объясняет, как Paperclip трактует назначение исполнителя на задачу,
статусы задач, исполнительные прогоны, побудки, структуру «родитель/подзадача»
и связи блокеров.

`doc/SPEC-implementation.md` остаётся контрактом V1. Этот документ описывает
детальную модель исполнения, стоящую за этим контрактом.

## 1. Базовая модель

Paperclip разделяет четыре понятия, которые легко смешать в одно:

1. структура: связи «родитель/подзадача»
2. зависимости: связи блокеров
3. владение: кто сейчас отвечает за задачу
4. исполнение: есть ли у плоскости управления сейчас живой путь, чтобы
   продвинуть задачу

Система работает лучше всего, когда эти понятия держат раздельно.

## 2. Семантика исполнителя

У задачи не может быть больше одного исполнителя.

- `assigneeAgentId` означает, что задачей владеет агент
- `assigneeUserId` означает, что задачей владеет человек — пользователь доски
- оба поля не могут быть установлены одновременно

Это жёсткий инвариант. Paperclip по построению допускает только одного
исполнителя.

## 3. Семантика статусов

Статусы задач в Paperclip — не просто ярлыки интерфейса. Они подразумевают
разные ожидания относительно владения и исполнения.

### `backlog`

Задача не готова к активной работе.

- нет ожидания исполнения
- нет ожидания подбора
- безопасное состояние покоя для будущей работы

### `todo`

Задача готова к работе, но ещё не захвачена активно.

- может быть назначена или не назначена
- блокировка checkout/исполнения пока не требуется
- для задач, назначенных агентам, Paperclip может всё ещё нуждаться в пути
  побудки, чтобы исполнитель действительно их увидел

### `in_progress`

Задача — активно ведущаяся работа.

- требует исполнителя
- для задач, которыми владеют агенты, это строгое состояние, подкреплённое
  исполнением
- для задач, которыми владеют люди, это состояние человеческого владения, и оно
  не подкреплено heartbeat-исполнением

Для задач, которыми владеют агенты, `in_progress` не должно иметь возможности
стать молча мёртвым состоянием.

### `blocked`

Задача не может продолжаться, пока что-то внешнее не изменится.

Это правильное состояние для:

- ожидания другой задачи
- ожидания человеческого решения
- ожидания внешней зависимости или системы, когда Paperclip не владеет
  запланированной перепроверкой
- работы, которую автоматическое восстановление не смогло безопасно продолжить

Вход в `blocked` требует маршрутизируемого пути ожидания. Задача может
перейти в `blocked` только с хотя бы одним из:

- первоклассных блокеров (`blockedByIssueIds`)
- ожидающей интеракции в треде задачи или связанного одобрения, в которых
  назван отвечающий
- структурированного дескриптора разблокирования `{owner, action}`, где
  `owner` — это id агента, id пользователя или доска, а `action` — конкретный
  шаг, который разблокирует задачу

Когда структурированный дескриптор разблокирования является путём ожидания,
Paperclip немедленно уведомляет названного владельца: владелец-агент получает
побудку, владелец-пользователь или доска — уведомление во входящих. Блок
только прозой — свободный текст, называющий владельца или действие в
комментарии без какого-либо из путей выше, — никого не маршрутизирует. Такой
блок отклоняется на уровне API или автоматически классифицируется как
`needs_attention` с уведомлением доски, но никогда молча не принимается как
здоровое состояние ожидания.

Отказ в разрешении сам по себе не является блокером. Если предписанный шаг
отклонён на границе авторизации, но собственный результат задачи завершён,
правильная диспозиция — `done`, а не `blocked` (см. правила делегирования
ревью в §6).

Это требование действует только перспективно, с момента выката: оно относится
к переходам в `blocked`, сделанным после выпуска фичи, и гейтится меткой
времени blocked-перехода против маркера выката, а не `createdAt` задачи.
Задачи, уже заблокированные на момент апгрейда, не затрагиваются — никаких
обратных уведомлений, никакой ретроактивной валидации, никакого шторма
`needs_attention` при деплое. Триаж существующих заблокированных прозой задач —
это однократный opt-in дайджест, а не значение по умолчанию.

### `in_review`

Исполнительская работа приостановлена, потому что следующий ход принадлежит
ревьюеру или утверждающему, а не текущему исполнителю.

Внешний сервис ревью тоже может быть валидным путём ревью, когда задача
сохраняет исполнителя-агента и имеет активный одноразовый монитор, который
разбудит этого исполнителя, чтобы позже проверить сервис.

### `done`

Работа завершена и терминальна.

### `cancelled`

Работа не будет продолжена, и это состояние терминально.

## 4. Исполнение за агентом против исполнения за человеком

Модель исполнения различается в зависимости от типа исполнителя.

### Задачи, которыми владеют агенты

Задачи, которыми владеют агенты, — часть исполнительного цикла плоскости
управления.

- Paperclip может разбудить исполнителя
- Paperclip может отслеживать прогоны, связанные с задачей
- Paperclip может восстановить часть потерянного состояния исполнения после
  крашей/перезапусков

### Задачи, которыми владеют люди

Задачи, которыми владеют люди, не исполняются heartbeat-планировщиком.

- Paperclip может отслеживать владение и статус
- Paperclip не может полагаться на семантику heartbeat/прогонов, чтобы они
  двигались
- реконсайл повисшей назначенной работы к ним не применяется

Поэтому `in_progress` может быть строгим для агентов, не навязывая те же
рантайм-правила работе в руках человека.

## 5. Checkout и активное исполнение

Checkout — это мост от владения задачей к активному исполнению агентом.

- checkout требуется, чтобы перевести задачу в `in_progress`, принадлежащую
  агенту
- `checkoutRunId` представляет блокировку владения задачей для текущего прогона
  агента
- `executionRunId` представляет текущий активный путь исполнения задачи

Они связаны, но не идентичны:

- `checkoutRunId` отвечает, кто сейчас владеет правами исполнения задачи
- `executionRunId` отвечает, какой прогон реально жив прямо сейчас

Paperclip уже очищает устаревшие блокировки исполнения и может усыновить
некоторые устаревшие блокировки checkout, когда исходный прогон исчез.

Жизненный цикл активной блокировки — часть контракта checkout:

- прогон владеет `checkoutRunId`, только пока этот прогон нетерминален
- когда прогон достигает `succeeded`, `failed`, `cancelled` или `timed_out`,
  финализация должна сравнить-и-очистить колонки блокировки, которые всё ещё
  указывают на этот прогон
- финализация не должна очищать блокировку, уже переаквированную
  прогоном-преемником
- передача при потере процесса не должна оставлять `checkoutRunId`
  приколоченным к упавшему прогону, когда `executionRunId` переходит к прогону
  повторной попытки
- проверки checkout и владельца checkout могут самолечить колонки блокировки,
  указывающие на терминальные или отсутствующие прогоны, прежде чем оценивать
  конфликты
- поток восстановления может очищать строки, у которых и checkout-, и
  execution-блокировки указывают на терминальные или отсутствующие прогоны

Восстановление после устаревшей блокировки — это восстановление после краша,
а не цикл повторных попыток. Paperclip не должен очищать или усыновлять
блокировки, удерживаемые нетерминальными прогонами. После очистки устаревшего
состояния checkout-`409` должен означать реального живого владельца,
несоответствие статуса/исполнителя, неразрешённый блокер или активный гейт,
которые всё ещё мешают checkout. Агенты должны трактовать такой `409` как
конфликт владения и остановиться, а не повторять тот же checkout.

### Известные ожидания исполнения при допуске

Известный холд исполнения — это состояние ожидания, а не новая попытка
исполнения. Каждая побудка задачи обязана прочитать текущий эффективный холд
реконсайла под блокировкой допуска задачи перед созданием прогона. Решённое
восстановительное бухгалтерское учёведение может всё ещё нести холд
без-повтора; только очистка эффективного холда снова делает допуск
доступным. Финальный гейт диспетчеризации остаётся обязательным для изменений
после допуска.

Повторяющиеся автоматические сигналы для неизменившегося гейта делят одну
долговечную диагностику пропущенной побудки с привязкой к компании,
агенту, задаче, коду гейта и идентичности условия. Диагностика сохраняет
первый запрос и считает последующие наблюдения. Это применяется к
реконсайлу исполнения, зависимостям, холдам паузы, доступности компании и
агента, блокировкам бюджета и выключенным heartbeat. Эти диагностики не
расходуют попыток провайдера и никогда не являются доказательством, что
будущая побудка была доставлена. Все текущие гейты проверяются снова на
следующей побудке, включая периодический проход реконсайла зависимостей.
Очистка одного гейта не обходит другой.

Новые комментарии, полученные во время холда исполнения, сохраняют свои
индивидуальные отложенные квитанции и упорядоченные id комментариев. Выпуск
не может слить эти квитанции, пока повтор остаётся заблокированным; следующая
допустимая побудка может их усыновить. Авторизованные запросы внешнего чата
также остаются отложенными со своей точной долговечной квитанцией. Они должны
использовать обычную промоцию и текущую авторизацию; родовая побудка не может
усыновить только их id комментариев и отбросить их актёра или контракта
сессии. Ожидание не авторизует повтор, не сбрасывает бюджет повторов инцидента
и не обходит правила доставки интеракции.

Диалог группирует повторяющиеся пустые отмены пре-стартового реконсайла в
нейтральное уведомление об ожидании. Запущенные прогоны, реальные сбои старта
и история прогонов остаются доступными для просмотра. Исторические записи
прогонов не удаляются.

Конкуренция за workspace (`workspace_busy`) показывает **Waiting for
workspace** и продолжается автоматически, когда workspace освобождается.
Внутренние попытки планирования остаются в журнале прогона без маркеров
отмены диалога, тостов отмены или ручных кнопок Retry. Пользователи могут
продолжать отправлять инструкции.

Legacy-релей удалённых ACP process-сессий работает на хосте плоскости
управления. Его команда запуска использует абсолютный Node-исполняемый файл
хоста, даже когда окружение запуска адаптера санитизировано для удалённой
песочницы; PATH песочницы остаётся принадлежащим образу песочницы.

### Проверка конфигурации перед диспетчеризацией

Проверка конфигурации перед диспетчеризацией — отдельный гейт, который
выполняется после того, как владение и checkout разрешены, но до того, как
плоскость управления реально диспетчеризует прогон.

> Перед диспетчеризацией прогона обязательные привязки секретов/env
> валидируются; отсутствующие привязки дают показанный блокер
> configuration-incomplete, а не диспетчеризованный прогон.

Результат configuration-incomplete — это исход гейта, а не рантайм-сбой. Это
один из активных гейтов, которые проверка на этапе checkout или
диспетчеризации может показать вместо старта прогона, и он оставляет задачу в
явном состоянии ожидания, называющем отсутствующую привязку. Показ блокера
держит задачу здоровой по контракту liveness и одновременно предотвращает
прогон, обречённый на падение, как только он не сможет разрешить свои
обязательные привязки секретов/env. Прогон «диспетчеризован и упал» —
неверная форма для отсутствующей конфигурации: отсутствующая привязка —
известное пред-диспетчерское условие, поэтому плоскость управления обязана
показать его как блокер configuration-incomplete, а не позволять прогону
стартовать и затем падать.

Неразрешённый базовый ref workspace — другое условие
configuration-incomplete. Workspace `git_worktree` базирует свежий worktree
на настроенном базовом ref. Paperclip сначала делает fetch удалённого ref
перед диспетчеризацией: он отображает неквалифицированное имя (например
`fix/foo`) или remote-tracking имя (например `origin/fix/foo`) в
`origin/<branch>`, выполняет авторизованный fetch и перепроверяет коммит.
Ref, который разрешился, позволяет работе продолжиться на разрешённом
коммите. Ref, который всё ещё не разрешается после fetch, даёт блокер
configuration-incomplete, называющий запрошенный ref, а не прогон
«диспетчеризован и упал». Поскольку адаптер так и не стартовал, Paperclip не
ставит в очередь повтор из-за отсутствующего комментария. Действие
восстановления дедуплицируется по каноническому удалённому ref
(`origin/<branch>`), а не по написанию оператора. Два эквивалентных
написания одной удалённой ветки, например `fix/foo` и `origin/fix/foo`, делят
одну идентичность восстановления, поэтому повторный сбой переиспользует
активное действие и не сбрасывает счётчик попыток и не публикует второе
уведомление. Другая удалённая ветка — отдельный блокер. Paperclip разрешает
предыдущее действие восстановления, создаёт новое действие для нового ref и
уведомляет оператора с новым ref вместо перезаписи активного действия
предыдущего ref.

## 6. Родитель/подзадача против блокеров

Paperclip использует две разные связи для разных задач.

### Родитель/подзадача (`parentId`)

Это структура.

Используйте её для:

- разбивки работы
- контекста сводки
- объяснения, почему подзадача существует
- побудки исполнителя родителя, когда все прямые дети становятся терминальными

Не трактовайте `parentId` сам по себе как зависимость исполнения.

### Блокеры (`blockedByIssueIds`)

Это семантика зависимостей.

Используйте их для:

- «эта задача не может продолжаться, пока та задача не сменит статус»
- явных связей ожидания
- автоматических побудок, когда все блокеры разрешаются

Заблокированные задачи должны оставаться в покое, пока блокеры не разрешены.
Paperclip не должен создавать отложенный heartbeat-прогон для такой задачи,
пока финальный блокер не завершён и побудка `issue_blockers_resolved` не
сможет начать реальную работу.

`cancelled` терминален для самой задачи-блокера, но не удовлетворяет
зависимость. Отменённое ребро блокера остаётся неразрешённым, пока ребро не
удалено или заменено, и Paperclip обязан показывать внимание к блокеру у
зависимой задачи независимо от того, отображается ли та сейчас как `blocked`,
`todo`, `backlog` или другой нетерминальный статус с исполнителем-агентом.

Если родитель действительно ждёт ребёнка, смоделируйте это блокерами. Не
полагайтесь только на связь родитель/ребёнок.

### Отчёт ребёнка родителю (child→parent)

Право записи в рантайме ограничено поддеревом: прогон может мутировать
свою задачу, взятую в checkout, и потомков этой задачи. Делегированная работа
ребёнка всё равно должна отчитываться наверх, поэтому платформа даёт ровно
три канонических канала отчёта. Ничто другое не пересекает границу.

1. **Сигнал завершения (всегда включён).** Когда ребёнок, блокирующий
   родителя, достигает `done`, побудка `issue_blockers_resolved` включает
   исполнителя родителя, который может прочитать тред ребёнка. Завершение не
   требует комментария-отчёта: собственный тред ребёнка — запись результата,
   а пересылка `done` прозой дублировала бы первоклассную побудку.
2. **Комментарий-отчёт прямому родителю (гейтится доверием).** Граница записи
   расширяется ровно на один шаг вверх: прогон, взявший в checkout подзадачу,
   может POST-ить комментарии на **прямого родителя** ребёнка — только
   комментарии (без записи статусов, полей, назначения или документов),
   только прямой родитель (никогда дедов, братьев, никогда латерально). Это
   гейтится пресетом доверия: **включено** для `standard`, **выключено по
   умолчанию** для `low_trust_review` и других review-содержащих пресетов, чей
   ввод — недоверенный контент (диффы, внешние тикеты) и чей комментарий-отчёт
   был бы носителем prompt-injection в более доверенный контекст.
3. **Релей только об остановке (фолбэк, где комментарий-отчёт выключен).** Для
   пресетов с выключенным комментированием прямого родителя платформа
   доставляет приписанный системе релей-комментарий прямому родителю, когда
   ребёнок переходит в `blocked` или `cancelled` — никогда на `done` или
   `in_review`. Остановка — то событие, о котором родитель обязан услышать;
   завершение уже имеет первоклассный сигнал выше. Релей — это комментарий, а
   не переход диспозиции, поэтому он не может триггерить другой релей (глубина
   1 по построению), и релеи дедуплицируются по (ребёнок, целевой статус),
   чтобы флаппинг статуса не спамил родителя.

### Делегирование ревью

Задачи ревью — секьюрити-ревью, код-ревью, вердикты QA — обязаны инструктировать
делегата публиковать выводы на **его собственной задаче ревью** и помечать её
`done`. Вердикт — это и есть результат: завершённое ревью с негативными
выводами — это `done`, а не `blocked`. Владелец родителя подключается побудкой
`issue_blockers_resolved` (плюс комментарий-отчёт прямому родителю, где пресет
ревьюера это позволяет) и владеет любыми последующими правками.

Никогда не инструктируйте делегата низкого доверия комментировать задачу
родителя. Такая инструкция гарантированно отклоняется на границе авторизации,
а ревьюер, превращающий отказ в диспозицию `blocked` с владельцем, названным
только прозой, подвешивает всё дерево на неопределённый срок.

### Паттерн «курьер» (латеральная координация)

Комментарий-отчёт прямому родителю намеренно не открывает латеральный доступ к
комментированию: никаких записей в поддеревья братьев или границы других
агентов. Разрешённый латеральный канал — это **паттерн «курьер»**: создаётся
новая задача, назначенная целевому агенту, несущая полные инструкции и
контекст в описании (создание задач в границах компании разрешено из любого
прогона). Задача-курьер будит целевого агента через обычное назначение,
держит координацию аудируемой и избегает расширения доступа к комментированию
в границу другого агента. Поскольку прогон целевого агента может быть не в
состоянии читать ваши задачи, описание курьера обязано быть самодостаточным —
не полагайтесь на ссылки назад в ваше собственное поддерево для существенных
инструкций.

## 7. Исполнение принятого плана и опциональная декомпозиция

Подтверждение принятого плана авторизует исполнение одной конкретной принятой
ревизии плана. Принятие не выбирает топологию задач. Источник `planning`
атомарно переходит в `standard`; источник, который уже `standard`, остаётся
`standard`. Продолжение стартует свежую сессию дефолтного исполнения на той же
задаче и несёт id принятого документа, id/номер ревизии и одобренный Markdown.

По умолчанию реализация идёт на исходной задаче. Руководство с областью действия прогона
`paperclip-converting-plans-to-tasks` решает, оправдан ли минимальный граф
детей границей владения, параллелизма, зависимости, ревью или жизненного
цикла. Ребёнок не должен создаваться лишь потому, что план был принят, и
источник не должен блокироваться лишь потому, что дети существуют.

`create_task` и `set_dependencies` — обычные авторизованные возможности
прогона `standard`. `create_task` создаёт стандартного ребёнка под активной
задачей с долговечной идемпотентностью, привязанной к исходной задаче и
ключу вызывающего; дети без блокеров стартуют в `todo`, дети с
неразрешёнными блокерами стартуют в `blocked`, и будятся только назначенные
дети, готовые по зависимостям. `set_dependencies` меняет первоклассные
блокеры активной исходной задачи и используется, только когда источник
действительно ждёт делегированных результатов.

API декомпозиции принятого плана и его записи остаются опциональной
поверхностью совместимости. Когда этот API используется явно, Paperclip
трактует его как exact-once примитив плоскости управления, а не как обычный
биндинг раннера для создания детей.

### Exact-once фингерпринт

Канонический фингерпринт декомпозиции:

- `(sourceIssueId, acceptedPlanRevisionId)`

Где:

- `sourceIssueId` — задача, ревизия документа `plan` которой была принята
- `acceptedPlanRevisionId` — принятая ревизия документа `plan`

Для API совместимости декомпозиции это остаётся продуктовым контрактом,
потому что принятая ревизия — это и есть то, что декомпозируют. Повторное
принятие, повторная побудка или перечитывание той же принятой ревизии не
должны авторизовать второе дерево детей через этот API. Более поздняя принятая
ревизия на той же исходной задаче — новый фингерпринт и может дать другой
результат декомпозиции.

Реализация может также хранить id принятой интеракции, id прогона принятия
или другие доказательства, но эти значения обязаны схлопываться в ту же
гарантию уникальности. Они не должны позволять вторую заявку на декомпозицию
для той же пары `(sourceIssueId, acceptedPlanRevisionId)`.

### Долговечная заявка совместимости и результат

Перед созданием подзадач первая попытка декомпозиции обязана создать или
переиспользовать долговечную запись для фингерпринта.

Эта долговечная запись обязана уметь отвечать, не реконструируя тред из
комментариев или транскриптов:

- находится ли декомпозиция для фингерпринта в `in_flight` или `completed`
- какой прогон или владелец сейчас держит заявку in-flight
- какие подзадачи, если таковые есть, уже созданы под этим фингерпринтом
- какие финальные id подзадач принадлежат завершённому результату

Paperclip не обязан предписывать конкретную форму хранения в этом документе.
Запись может жить в отдельной таблице, в состоянии исполнения исходной задачи,
в метаданных интеракции или другой долговечной продуктовой поверхности. Важно
содержание контракта:

- заявка долговечна до начала fan-out
- частичный прогресс долговечен, пока fan-out идёт
- завершённый набор детей долговечен после окончания fan-out

Если прогон создаёт часть детей и умирает, повторные попытки обязаны
продолжаться с того же фингерпринта и переиспользовать уже записанный
частичный результат. Они не должны рестартовать декомпозицию, как будто ничего
не происходило.

### Живой путь источника, пока опциональная декомпозиция in-flight

Пока декомпозиция для принятого фингерпринта не завершена, исходная задача
обязана показывать явный живой путь для того же фингерпринта.

Сама принятая интеракция — лишь доказательство, что план одобрен. Это
недостаточный живой путь, когда декомпозиция началась. Исходная задача обязана
делать ясным, что двигает фингерпринт дальше, например:

- активный прогон декомпозиции
- отложенная побудка-продолжение для того же исполнителя
- монитор или явное действие восстановления, привязанные к той же заявке
  декомпозиции
- состояние `blocked`, называющее реальный блокер для завершения той заявленной
  декомпозиции

Если живой прогон исчезает, Paperclip обязан починить, возобновить или видимо
заблокировать существующую заявку. Он не должен оставлять исходную задачу в
состоянии, где второй прогон может интерпретировать то же принятие как свежее
разрешение снова создать задачи-братья.

Когда источник сохраняет ответственность за реализацию, интеграцию или
верификацию и действительно должен ждать детей, он обязан держать
первоклассный путь блокера вместо полагания на rollup `parentId`. Если он
может продолжаться независимо, он остаётся открытым без блокеров-детей. Если
его единственный результат был планированием и вся оставшаяся работа полностью
делегирована, он может завершиться после проверки графа.

### Параллельные и повторные попытки

Каждый позднейший вызывающий API совместимости декомпозиции для того же
фингерпринта принятого плана обязан консультировать долговечную
заявку/результат перед созданием детей.

- Если заявки нет, прогон может атомарно создать заявку и стать владельцем
  декомпозиции.
- Если заявка существует и `in_flight`, позднейший прогон обязан её
  переиспользовать. Он может возобновить ту же декомпозицию, если является
  валидным владельцем продолжения, или выйти, увидев, что другой прогон уже
  владеет работой.
- Если заявка существует и `completed`, позднейший прогон обязан
  переиспользовать записанный результат детей и не должен создавать новых
  задач-братьев.
- Если предыдущая попытка закончилась после частичного создания детей, повтор
  обязан продолжаться под тем же фингерпринтом и сохранить уже созданные id
  детей.

Параллельные попытки совместимой декомпозиции поэтому идемпотентны
относительно фингерпринта. Создание нескольких деревьев детей через этот API
для той же пары `(sourceIssueId, acceptedPlanRevisionId)` — продуктовый баг.

## 8. Контракт liveness нетерминальных задач

Для задач, которыми владеют агенты и которые нетерминальны, Paperclip никогда
не должен оставлять работу в состоянии, где никто не отвечает за следующий ход
и ничто не разбудит или не покажет её.

Это контракт видимости, а не контракт автозавершения. Если Paperclip не может
безопасно вывести следующее действие, он должен показать неоднозначность
заблокированным состоянием, видимым уведомлением или явным действием
восстановления. Он не должен молча помечать работу выполненной по комментариям
прозой или угадывать, что зависимость завершена.

Задача здорова, когда продукт может ответить «что двигает это дальше?» без
требования к человеку реконструировать намерение из всего треда. Задача
застаилась, когда она нетерминальна, но не имеет живого пути исполнения,
явного пути ожидания и пути восстановления.

Валидные примитивы пути действия:

- активный прогон, связанный с задачей
- отложенная побудка или продолжение, которое может быть доставлено
  ответственному агенту
- типизированный участник execution-policy, например
  `executionState.currentParticipant`
- ожидающая интеракция в треде задачи или связанное одобрение, которое ждёт
  конкретного отвечающего
- одноразовый монитор задачи (`executionPolicy.monitor.nextCheckAt`), который
  разбудит исполнителя для будущей проверки
- человек-владелец через `assigneeUserId`
- первоклассная цепочка блокеров, чьи неразрешённые листья сами здоровы
- открытое явное действие восстановления, называющее владельца и действие,
  необходимые для восстановления liveness

### Долговечные внешние ожидания и финализация heartbeat

Внешнее ожидание считается живым или ожидающим путём, только когда следующий
ход переживает текущий heartbeat и представлен в долговечном состоянии
плоскости управления Paperclip. Валидные формы внешнего ожидания:

- одноразовый монитор задачи или другая сохранённая (persisted) запланированная побудка,
  называющая ответственного исполнителя, время следующей проверки и
  ограниченную политику таймаута/попыток
- первоклассный блокер или диспозиция `blocked`, называющие внешнего владельца
  и конкретное действие, необходимое для разблокирования задачи
- делегированная подзадача с ответственным владельцем и её собственным
  здоровым путём действия плюс ребро блокера, когда исходная задача обязана
  ждать этого ребёнка; `parentId` сам по себе не зависимость

Одноразовый монитор задачи расходует свой сохранённый `nextCheckAt`, когда он
диспетчеризует побудку исполнителю. Если этот потребляющий монитор прогон
потерян до того, как записать новую диспозицию или будущий монитор, Paperclip
восстанавливает ровно одно ограниченное продолжение, используя существующий
лимит повторов при потере процесса; если это продолжение тоже потеряно,
следующий шаг забирает обычная эскалация действия восстановления вместо
создания ещё одного цикла монитора.

Неуправляемый локальный процесс — не долговечный путь действия. Shell-задачи,
запущенные через `&`, `nohup`, локальные циклы опроса, отцепленные PTY-сессии,
дочерние процессы адаптера и подобные фоновые наблюдатели не держат задачу
живой, если Paperclip не сохраняет их как прогон или не сочетает
управляемый рантайм-сервис с монитором, запланированной побудкой, блокером или
делегированной задачей, которая владеет следующей проверкой. PID, id сессии,
файл журнала, комментарий или обещание проверить позже — только
доказательства. Процесс может быть убит, когда вызов адаптера или heartbeat
завершается, и нельзя предполагать, что другой воркер сможет его наблюдать
или восстановить.

Прежде чем heartbeat финализируется, диспозиция его задачи обязана поэтому
оцениваться из долговечного состояния Paperclip, а не из процессов, видимых
только этому heartbeat. Задача с исполнителем-агентом может оставаться
`in_progress` после heartbeat, только когда уже существует другой валидный
примитив пути действия. Если единственное заявленное продолжение —
локальный/фоновый наблюдатель, финализация трактует задачу как не имеющую
живого пути, даже если процесс ещё не наблюдался завершающимся.

Если полезная работа над результатом может продолжаться без внешнего
результата, агент должен продолжать эту работу или делегировать её, а не
парковать задачу. Используйте `blocked` только для реальной зависимости,
которая мешает продуктивному прогрессу. Используйте монитор, когда
исполнитель владеет ограниченной будущей проверкой, и делегированную
подзадачу, когда другой владелец может продвигаться независимо.

Восстановление из невалидного внешнего ожидания ограничено и идемпотентно:

1. Записать ограниченное доказательство, что завершённый heartbeat не оставил
   долговечного пути действия, включая терминальный прогон и любые
   сообщённые метаданные локального наблюдателя, не трактуя эти метаданные как
   liveness.
2. Поставить в очередь максимум одно продолжение на нормальной модели для
   того же состояния источника и фингерпринта восстановления, чтобы
   исполнитель мог осмотреть внешний результат, заменить наблюдателя
   долговечным ожиданием, продолжить продуктивную работу или выбрать валидную
   диспозицию.
3. Если это продолжение тоже выходит без создания долговечного пути, не
   ставить в очередь другое эквивалентное продолжение. Перевести задачу в
   `blocked`, только когда можно назвать реальную внешнюю зависимость; иначе
   открыть или обновить явное действие восстановления с названным владельцем и
   конкретным действием починки/эскалации.
4. Новая долговечная активность источника может дать новый фингерпринт
   восстановления, но неизменные доказательства убитых локальных наблюдателей
   не должны создавать бесконечный цикл побудка/восстановления.

Это правило намеренно консервативно: доказательства локального наблюдателя
могут помочь владельцу восстановления решить, что произошло, но только
сохранённое состояние плоскости управления может доказать, что работа снова
двинется.

### Источники побудки: комментарии и активность документов

Комментарии в треде задачи и комментарии, привязанные к документам, имеют
разную семантику побудки.

Комментарий верхнего уровня в треде задачи, созданный пользователем доски или
другим пользователем на нетерминальной задаче с исполнителем-агентом, может
разбудить исполнителя этой задачи. Это обычный путь «владелец должен увидеть
новую обратную связь в треде задачи», и payload побудки должен по возможности
идентифицировать комментарий задачи, вызвавший побудку.

Комментарии к документам задачи, аннотационные комментарии к документам и
комментарии ревью документов по умолчанию не будят исполнителя задачи. Они
остаются видимыми как активность документов и должны быть находимы из
документных/ревью-поверхностей задачи, но активность документов сама по себе
не путь исполнения задачи. Комментарий к документу может дать доказательство
или контекст для следующего прогона, но он не должен трактоваться как
отложенная побудка, монитор, одобрение, ответ на интеракцию, блокер или
терминальная диспозиция.

Активность, привязанная к документам, всё же может маршрутизировать работу,
когда она конвертирована в явный примитив пути действия. Валидные исключения
маршрутизации включают:

- упоминание задачи или структурированное упоминание агента, которое
  намеренно будит или назначает названного участника
- назначение ревью документа, называющее ревьюера или исполнителя для
  состояния ревью
- ответ на интеракцию в треде задачи, например `request_confirmation`,
  `ask_user_questions` или `suggest_tasks`
- намеренная маршрутизация доски, которая назначает или переназначает задачу,
  открывает первоклассный блокер, создаёт делегированную последующую работу
  или ставит в очередь типизированную побудку

Свободный текст одобрения документа — не автопринятие. Одобрение плана,
одобрение реализации или принятие ревью обязаны проходить через явные
примитивы интеракции, одобрения, execution-policy, назначения или блокера,
которые определяют, кто владеет следующим ходом.

### Комментарии-прерывания и передача владения

Комментарий доски может быть прерыванием, сменой владения, обоими или ни тем
ни другим. Paperclip обязан держать эти понятия раздельными в продуктовом
контракте.

Прерывание останавливает текущий живой путь исполнения задачи. Оно само по
себе не выбирает следующего владельца. Если активный прогон прерван доской,
прогон всё ещё может завершиться со своим базовым статусом `cancelled`, но
активность задачи и контекст побудки должны делать намерение оператора видимым
как прерывание, а не необъяснённый рантайм-сбой.

Для legacy-раннеров **Interrupt** на отложенном сообщении останавливает
активный прогон и явно продолжает отложенную очередь после очистки исполнения.
Оно валидирует ревизию очереди и целевой прогон, затем диспетчеризует текущие
тела сообщений запрошенной очереди в их сохранённом порядке. Очереди других
актёров не могут потребить это прерывание. Сохранённое намерение прерывания
ретраится планировщиком после ошибки промоции или рестарта сервера, пока та
очередь не диспетчеризована или отброшена. Правки и сбросы остаются
авторитетными до диспетчеризации; удаление финального сообщения не должно
создавать пустое продолжение. Отложенные сообщения остаются видимыми после
остановки прогона. Отмена только прогона сохраняет очередь для более поздней
явной побудки; пауза задачи сохраняет своё отдельное поведение отмены очереди.
Нативный same-turn steering держит свой отдельный протокол подтверждения.
Legacy Codex использует Ctrl-C для остановки своих tool-сессий и не может
ретраить фолбэк отсутствующей сессии после того, как провайдер подтвердил,
что сессия стартовала.

Смена владения выбирает, кто владеет задачей после коммита комментария:

- установка `assigneeAgentId` делает названного агента владельцем
- установка `assigneeUserId` или очистка `assigneeAgentId` делает задачей
  владеющей человек или без исполнителя
- неизменность полей исполнителя сохраняет текущего владельца

Побудка — путь доставки для выбранного владельца-агента. Если прерывающее
обновление также назначает нетерминальную, небэклогную задачу агенту,
Paperclip должен поставить в очередь одну побудку для нового исполнителя и
включить прерывающий комментарий и id прерванного прогона в payload/контекст
побудки, где они доступны. Устаревшие запланированные ретраи для предыдущего
владельца не должны выполняться после ухода владения от того владельца.

Если закоммиченное обновление назначает задачу пользователю, очищает
исполнителя-агента или оставляет задачу без владельца-агента, Paperclip не
должен подразумевать, что произошла передача агенту. Задача тогда ждёт
владельца-человека или будущего явного назначения, блокера, одобрения,
интеракции, монитора или действия восстановления.

Простой текст — не назначение. Написание имени агента, роли или ярлыка
команды в комментарии не меняет владение и не создаёт агентскую побудку.
Маршрутизация агента из текста комментария требует структурированного
упоминания агента, которое разрешается внутри компании, явной мутации
`assigneeAgentId` или существующего текущего исполнителя-агента, получающего
обычную обратную связь в треде задачи.

Комментарий-делегация из прогона текущего исполнителя на этом родителе не
должен стартовать конкурирующую работу родителя, когда названный воркер уже
владеет указанным ребёнком. Это применяется к обновлениям задачи с комментарием
и к одиночным комментариям. Проверьте контекст компании, агента и
родительской задачи исходного прогона. Затем проверьте, что комментарий
ссылается на идентификатор ребёнка, `parentId` ребёнка называет этого
родителя, и ребёнок принадлежит той же компании и назначен упомянутому
воркеру. Применяйте child-aware маршрутизацию только в одном из этих
состояний:

- Родитель `blocked` и ребёнок `in_progress`. У ребёнка обязано быть ребро
  блокера к родителю. Execution- или checkout-прогон ребёнка обязан всё ещё
  быть `running`, принадлежать тому воркеру и компании и называть этого
  ребёнка в своём контексте прогона. Проверьте доступ комментария и мутации к
  ребёнку, затем сохраните комментарий родителя и добавьте связанную копию на
  ребёнке. Сохраните полный комментарий, автора, исходный прогон,
  атрибуцию ответственного пользователя и source trust. Нацельте обычную
  побудку упоминания на ребёнка и новый id его комментария с явным намерением
  resume и follow-up. Это держит новую обратную связь доступной воркеру и
  позволяет существующей очереди сериализовать продолжение ребёнка за его
  текущим исполнением.
- Родитель и ребёнок оба `done`. Закрывающий комментарий исполнителя не должен
  стартовать ещё один прогон воркера для завершённой делегации. Ребро блокера
  после завершения не требуется: быстрый ребёнок может завершиться до того,
  как лиду понадобится записать ожидание. Новая работа агента обязана
  использовать явный `resume: true`, смену статуса или новую назначенную
  задачу. Явный resume выводит родителя из `done` до того, как это правило
  работает; проза комментария сама не перезапускает завершённую работу.

Комментарий завершённой делегации остаётся на родителе без побудки воркера.
Ни один путь не меняет владение. Комментарии пользователей доски и
не связанные упоминания сохраняют своё нормальное поведение побудки. Если
несколько указанных детей квалифицируются для того же воркера, ребёнок или
прогон больше не соответствует этим условиям, доступ к комментарию или мутации
ребёнка отклонён или поиск/копирование падает — используйте обычный путь
упоминания родителя. Не парсите упоминания повторно во время копирования
комментария, что создало бы ещё один цикл маршрутизации. Завершение ребёнка
всё ещё использует существующую побудку разрешения блокеров для исполнителя
родителя.

Родитель может получить закрывающий комментарий до того, как его исполнитель
сменит статус на `done`. Перепроверьте правило завершённой делегации при
выпуске этого исполнения родителя, перед промоцией отложенного упоминания. В
той же транзакции проверьте финальное состояние родителя, завершающий прогон
и каждый исходный отложенный id комментария. Каждый комментарий обязан
принадлежать этому родителю и компании, исходить из завершающего прогона его
исполнителя и ссылаться ровно на одного завершённого прямого ребёнка,
назначенного упомянутому воркеру. Ссылка на самого родителя разрешена; любая
другая дополнительная ссылка на задачу сохраняет обычный путь упоминания,
включая неизвестную или чужую ссылку. Смешанный ввод — человеческий, из других
прогонов, несвязанный или неоднозначный — сохраняет свой нормальный путь
побудки. Явные запросы продолжения и интеракции также сохраняют свой обычный
путь.

Принятая обратная связь агента обязана переживать смену ребёнка на `done` до
выхода его активного прогона. Промоция отложенной побудки может переоткрыть
того завершённого ребёнка только для его текущего исполнителя, с явным
намерением agent resume и живыми отслеживаемыми комментариями другого автора.
Промоция заявки перед переоткрытием. Отменённые задачи, удалённые
комментарии, собственные комментарии, пустые продолжения и агентские
продолжения без явного намерения сохраняют свои существующие правила
подавления. Обычные гейты паузы, владения, авторизации и бюджета всё ещё
применяются.

Превью паузы и tree-управления должны показывать то же различие. Они должны
сообщать, содержит ли затронутое поддерево живую работающую работу,
отложенные побудки, работу с исполнителем-агентом или только
человеческие/статические задачи, чтобы пауза после передачи не выглядела
прервавшей агентское исполнение, когда агентского пути исполнения не было.

### Когерентность workspace для adapter-backed исполнения

Для adapter-backed исполнения активный прогон или отложенная побудка считается
живым путём, только когда Paperclip может также доказать, что выбранный
workspace когерентен для этого вызова адаптера. Побудка, которая не может
стартовать в предназначенном workspace, — это лишь неудачная попытка доставки,
а не здоровый путь liveness.

Когерентный adapter-путь означает:

- выбранные `executionWorkspaceId`, `projectWorkspaceId`, `projectId`, исходная
  задача и компания все ссылаются на один рабочий контекст в границах компании
- любой `projectWorkspaceId` сопровождается владеющим `projectId`, и эта связь
  проекта однозначна
- адаптер получит тот же эффективный workspace/cwd, который Paperclip разрешил
  для прогона, включая те же id workspace и значения окружения
  `PAPERCLIP_WORKSPACE_*`
- эффективный cwd существует или достижим для провайдера, согласно провайдеру
  workspace
- когда адаптер или стратегия workspace полагается на git-состояние, cwd
  git-валиден для выбранного workspace: он разрешается в ожидаемый корень
  репозитория, требуемые базовые ref или метаданные ветки разрешимы, а
  созданные в рантайме worktree всё ещё зарегистрированы или явно
  восстанавливаемы

Adapter-backed liveness также требует достижимости плоскости управления с
фактической поверхности мутаций агента, а не только с хостового процесса
адаптера. Если ожидается, что агент использует Bash, shell-инструменты,
рантайм-хелперы или исполнение команд в песочнице для обновления задач,
создания комментариев, загрузки артефактов или отправки ревью-решений,
`PAPERCLIP_API_URL` и `PAPERCLIP_API_KEY`, видимые этой поверхности, обязаны
успешно маршрутизировать в Paperclip.

Для локальных адаптеров с песочницей Paperclip может выполнить этот контракт
через привязанный к прогону мост внутри песочницы. Хост-адаптер держит
реальный run JWT на стороне хоста, инжектит только URL/токен моста в
окружение инструментов песочницы и форвардит разрешённые запросы Paperclip API
с прикреплённым id прогона. Креды моста — это исполнительная обвязка, а не
пользовательский контекст: они не должны записываться в промпты, видимые
комментарии, документы задач, восстановленные файлы workspace или долговечные
журналы. Агенты и скиллы обязаны использовать env-переменные, доступные в
Bash/curl, а не предполагать, что localhost API URL хоста достижим из
браузера или web-extraction инструментов внутри песочницы.

Состояние `projectWorkspaceId` плюс `executionWorkspaceId` без `projectId`
невалидно для исполнения в границах проекта. Paperclip может трактовать его как
восстановимое, только когда он может вывести ровно один владеющий проект из
execution workspace, project workspace или исходной задачи в той же компании и
затем починить сохранённое состояние перед доставкой. Если владеющий проект
отсутствует, неоднозначен или кросс-компанийный, отложенный adapter-прогон не
должен считаться живым путём.

Некогерентность workspace попадает в ту же модель нетерминального liveness и
повисшей назначенной работы, что и исчезнувший прогон. Путь восстановления
должен сначала уронить или отклонить некогерентную побудку, затем либо
починить и перекверстать одно ограниченное продолжение для того же
исполнителя, либо показать явное действие восстановления. Он не должен
оставлять задачу `in_progress` с владельцем-агентом здоровой только потому,
что существует запись побудки, которая вызвала бы адаптер в неправильном cwd,
не-git каталоге, где git требуется, неродственном project workspace или
невосстановимом отсутствующем worktree.

Для созданных в рантайме execution workspace `git_worktree` когерентность ветки
— часть когерентности workspace. Сохранённая ветка execution workspace — это
записанная ветка для будущей диспетчеризации. Переиспользование этого
workspace обязано проверять, что worktree всё ещё зарегистрирован и что `HEAD`
на записанной ветке. Успешная финализация прогона обязана выполнять ту же
проверку перед записью `workspace_finalize=succeeded`. Если прогон
переключился на publishing/PR ветку без обновления записи execution workspace,
финализация может авто-восстановить записанную ветку, только когда worktree
чист, всё ещё зарегистрирован и записанная ветка указывает на текущий `HEAD`;
починка записывается как операция workspace перед строкой успешной
финализации. Если эту безопасную починку нельзя доказать, финализация
записывает failed workspace finalize, и прогон падает с ограниченным
доказательством ожидаемой и фактической ветки. Смена ветки санкционирована,
когда путь плоскости управления обновляет запись execution workspace до
финализации, когда работа публикации происходит в отдельном worktree и
управляемый worktree задачи остаётся на своей записанной ветке или когда
финализатор выполняет эту чистую реставрацию того же коммита.

### Сбои сканирования workspace перед стартом провайдера

Обнаружение репозитория различает обычную папку и неудачное чтение Git.
Таймаут, полная очередь сканирования, отмена, лимит вывода или сбой Git
обязаны сохранять свою типизированную причину через подготовку workspace и
сохранение состояния прогона. Это не должно отчитываться как отсутствующий
репозиторий или падать в неотфильтрованное копирование каталога.

Когда подготовка workspace падает до начала работы провайдера, таймауты
сканирования и насыщение очереди используют существующий долговечный бюджет
сбоев: две автоматические повторные попытки с интервалом 30 секунд.
Запланированный преемник сохраняется до того, как исполнение освобождено.
Рестарт и обработка дублированных побудок переиспользуют того преемника.
Обычные гейты задач, владения, паузы, зависимостей, одобрений и бюджета всё
ещё применяются. Существующее содержимое workspace сохраняется, и неполные
временные клоны не публикуются.

Отменённые сканы, сбои лимита вывода и другие сбои Git не авторизуют
автоматический retry настройки. Исчерпание или небезопасный retry открывает
привязанный к источнику путь восстановления с конкретной причиной скана и
действием оператора. Родовое восстановление повисшей работы не должно давать
ещё один бюджет для этих ошибок. Это не перепроигрывает автоматически
исторические родовые прогоны `setup_failed`.

### Ограничение handshake старта ACP

Adapter-backed живой путь также требует, чтобы сам handshake старта ACP не мог
повиснуть навсегда. Движок ограничивает handshake фиксированным дедлайном
старта и опросом диспозиции дуплексного контрольного канала. Любое из условий
заканчивает handshake и отчитывает закрытый типизированный код, чтобы задача
могла достичь урегулированной диспозиции вместо того, чтобы оставаться
`in_progress` без наблюдаемого следующего действия.

Код сбоя handshake отличен от несовпадения идентичности сессии. Таймаут или
потеря дуплексного канала во время старта не должны отчитываться тем же
кодом, что и неудачный resume сессии, потому что они требуют разных реакций
оператора.

### Явные действия восстановления

Явное действие восстановления — это типизированный путь починки liveness для
исходной задачи. Это примитив восстановления; действие может рендериться
напрямую на исходной задаче или подкрепляться отдельной recovery-задачей,
когда починке нужен свой собственный рабочий элемент.

Новое сообщение пользователя может продолжить терминальный нативный прогон,
чьи поля процесса были очищены до появления локальных квитанций остановки.
Допуск обязан проверить точный прогон, раннер, workspace и сессию провайдера в
сохранённом приостановленном состоянии, без активного хода провайдера,
ожидающего tool-вызова или недоставленного вывода. Отсутствующее или
несовпадающее состояние сохраняет холд. Более поздний записанный запуск
процесса также сохраняет холд, пока его остановка не верифицирована. Обычные
гейты назначения, решений, контроллера, очистки окружения и активного прогона
всё ещё применяются. Сообщение начинает один свежий ход диалога; оно не
переигрывает упавший прогон, не сбрасывает его бюджет восстановления и не
сертифицирует неизвестные исходы действий.

Тред задачи показывает существующее охраняемое действие Retry для упавших или
истёкших legacy-диалоговых прогонов. Где сервер поддерживает явную новую
попытку после остановленного legacy-диалога, тред не должен прятать это
действие только потому, что у старого прогона всё ещё есть проекция
recovery-needed. Нативные и процессные холды восстановления, ожидающие
решения, активное исполнение и другие retry-гейты остаются в силе. Когда гейт
прячет Retry, тред говорит, что сообщение сохранено, вместо обещания
недоступного действия. Это изменение презентации не переписывает
исторические исходы и не сертифицирует предыдущие действия.

Валидное действие восстановления обязано называть:

- исходную задачу и компанию
- вид восстановления и идемпотентный фингерпринт
- владельца восстановления плюс предыдущего или возвращающегося владельца,
  когда владение может временно сместиться
- причину, ограниченное доказательство и следующее действие
- политику побудки, монитора, таймаута, retry или эскалации, которая двигает
  действие вперёд
- исход разрешения при закрытии, например restored, delegated, false positive,
  blocked, escalated или cancelled

Привязанное к источнику действие восстановления — форма по умолчанию.
Используйте его, когда следующий безопасный ход — напрямую починить liveness
исходной задачи: вернуть исходную задачу в `todo`, чтобы её можно было
ретраить, прояснить диспозицию, восстановить монитор, записать ложное
срабатывание или делегировать реальную последующую работу из исходной задачи.

Владение действием восстановления и владение исходной задачей — отдельные
контракты. Назначение менеджера или владельца доски на действие восстановления
авторизует этого владельца чинить или маршрутизировать действие восстановления;
это не записывает этого владельца в `assigneeAgentId` исходной задачи.
Автоматический retry и эскалация сохраняют исполнителя источника.
Переназначение требует явного решения по исходной задаче или
определённого политикой пути серьёзного сбоя с обычными проверками компании,
авторизации, бюджета, checkout, активной блокировки исполнения,
governed-action и журнала активности.

Используйте действие восстановления, подкреплённое задачей, только когда
восстановление — действительно независимая работа или когда обработка в границах
источника была бы небезопасной или неясной. Примеры включают:

- долгую или кросс-агентскую работу починки со своим исполнителем,
  подзадачами или блокерами
- реальную делегированную последующую работу, которая должна блокировать
  исходную задачу как первоклассную зависимость
- работу watchdog активного прогона, который должен наблюдать всё ещё
  работающий процесс источника, не вмешиваясь в него
- восстановление, которому нужны отдельные ревью, одобрение, секьюрити-
  обработка или владение эскалацией
- случаи, когда владение исходной задачей нельзя безопасно изменить или
  восстановить

Комментарий или системное уведомление может быть доказательством для действия
восстановления, но сам по себе он не действие восстановления. Восстановление
только комментарием — не здоровый путь liveness, потому что не определяет
типизированного владельца, политику побудки или монитора, границу retry,
таймаут, путь эскалации или исход разрешения.

#### Свежесть действия восстановления

Привязанные к источнику действия восстановления — снимки состояния liveness
исходной задачи на момент открытия. Они обязаны ревалидироваться после более
новой долговечной активности источника, включая смены статуса исходной задачи,
смены исполнителя, смены блокеров, смены execution-policy или монитора,
обновления документов или work products, определяющие валидный путь ожидания,
и структурированные обновления resume или диспозиции.

Когда более новая активность источника восстанавливает валидный живой или
ожидающий путь, действие восстановления устарело и должно быть свёрнуто через
явный жизненный цикл восстановления вместо того, чтобы быть спрятанным или
удалённым. Свёртывание означает разрешение или отмену действия восстановления
с исходом разрешения и заметкой, сохраняющими аудиторский след.

Одни простые комментарии не делают действие восстановления устаревшим.
Комментарий может дать доказательство, но действие восстановления должно
оставаться видимым, когда исходная задача всё ещё застойна и комментарий не
создаёт валидный примитив пути действия, такой как побудка, монитор,
интеракция, одобрение, блокер, человек-владелец, участник исполнения,
терминальная диспозиция или делегированная последующая работа.

### Назначенный агентом `todo`

Это состояние диспетчеризации: готово к старту, ещё не захвачено активно.

Здоровое состояние диспетчеризации означает, что хотя бы одно из этого верно:

- у задачи уже есть отложенный путь побудки
- задача намеренно отдыхает в `todo` после завершённого агентского heartbeat
  без доказательств прерванной диспетчеризации
- задача явно показана как повисшая через видимый blocked/recovery-путь

Назначенная `todo` задача застойна, когда диспетчеризация была прервана, не
осталось отложенной или работающей побудки и не открыт путь восстановления.

### Назначенный агентом `backlog`

Это состояние парковки, а не состояние диспетчеризации.

Назначение задачи обычно подразумевает намерение исполнять. Когда API
создания получают исполнителя и без явного статуса, Paperclip по умолчанию
делает задачу `todo`, чтобы у исполнителя был путь побудки вместо молчаливого
наследования неназначенного дефолта `backlog`.

Явная назначенная `backlog` задача остаётся валидной, когда создатель
намеренно паркует работу. Она не должна будить исполнителя только потому, что
у неё есть исполнитель. Paperclip должен делать этот выбор видимым в
активности и UI, чтобы операторы могли различить намеренную парковку и
упущенную передачу.

Назначенная `backlog` задача становится проблемой liveness, когда другая
задача заблокирована на ней и нет явного пути ожидания, такого как
человек-владелец, активный прогон, отложенная побудка, ожидающая интеракция
или одобрение, монитор или открытое действие восстановления. В этом случае
заблокированный родитель должен показать «blocked by parked work» вместо
трактовки цепочки зависимостей как здоровой.

### Назначенный агентом `in_progress`

Это состояние активной работы.

Здоровое состояние активной работы означает, что хотя бы одно из этого верно:

- есть активный прогон для задачи
- уже есть отложенная побудка-продолжение
- есть активный одноразовый монитор, который разбудит исполнителя для будущей
  проверки
- есть открытое явное действие восстановления для потерянного пути исполнения

Задача `in_progress` с владельцем-агентом застойна, когда у неё нет активного
прогона, отложенного продолжения, сохранённого монитора и явной поверхности
восстановления. Неуправляемый локальный/фоновый наблюдатель не удовлетворяет
ни одному из этих условий. Отслеживаемый Paperclip прогон, который всё ещё
работает, но молчит, не застойен автоматически; им управляет контракт
watchdog активного прогона.

### `in_review`

Это состояние ревью/одобрения: исполнение приостановлено, потому что
следующий ход принадлежит ревьюеру, утверждающему, пользователю доски или
владельцу восстановления.

Здоровая `in_review` задача имеет хотя бы один валидный путь действия:

- типизированный участник execution-policy, который может одобрить или
  запросить изменения
- ожидающая интеракция в треде задачи или связанное одобрение, ждущие
  названного отвечающего
- человек-владелец через `assigneeUserId`
- активный прогон или отложенная побудка, которая, как ожидается, обработает
  состояние ревью
- активный одноразовый монитор для внешнего сервиса или асинхронного
  ревью-цикла, которым владеет исполнитель
- открытое явное действие восстановления для неоднозначной передачи ревью

Назначенное агентом `in_review` без типизированного участника здорово, только
когда существует один из других путей. Назначение тому же агенту, который
сделал передачу, само по себе не путь ревью.

Задача `in_review` застойна, когда у неё нет типизированного участника,
ожидающей интеракции или одобрения, владельца-пользователя, активного
монитора, активного прогона, отложенной побудки и явного действия
восстановления. Paperclip должен показывать это состояние как работу
восстановления вместо молчаливого завершения задачи или оставления цепочек
блокеров припаркованными на неопределённый срок.

Когда у стадии ревью execution-policy есть ожидающий участник-агент, прогон
участника — часть пути ревью, только пока он жив или отложен. Если прогон
участника достигает терминального состояния, пока `executionState.status`
остаётся `pending`, решение не записано. После успешного прогона без
ревью-решения Paperclip должен поставить в очередь одну ограниченную
восстановительную побудку на нормальной модели для того же участника, когда
агент вызываем и другого пути ревью нет. Упавший участник вместо этого следует
правилам провайдер-непрерывности ниже: локальные диалоговые адаптеры могут
стартовать ограниченный ход продолжения, тогда как нативные сессии используют
валидированный resume/замену. Другие адаптеры сохраняют свои гейты
action-recovery. Исходный исполнитель остаётся неизменным. Если тот
восстановительный прогон тоже завершается, пока стадия остаётся pending, или
участник не может быть вызван, Paperclip обязан перевести исходную задачу в
явный blocked/recovery-путь вместо того, чтобы оставлять `in_review` молча
дрейфовать.

### Мониторы задач

Монитор задачи — это одноразовый отложенный путь действия для задач с
исполнителем-агентом в `in_progress` или `in_review`.

Используйте монитор, когда текущий исполнитель владеет будущей проверкой
против асинхронной системы или внешнего сервиса. Примеры включают циклы
ревью Greptile, GitHub checks, деплои Vercel или задания провайдера, где
агент должен вернуться позже и решить, что происходит дальше.

Политика монитора живёт под `executionPolicy.monitor` и включает:

- `nextCheckAt`: когда Paperclip должен разбудить исполнителя
- `notes`: несекретные инструкции, что исполнителю проверить
- `serviceName`: опциональный несекретный контекст внешнего сервиса
- `externalRef`: опциональный вход ссылки внешнего сервиса; Paperclip трактует
  его как secret-adjacent, редуцирует перед сохранением/видимостью и
  опускает из активности и payload побудок
- `timeoutAt`, `maxAttempts` и `recoveryPolicy`: опциональные подсказки
  восстановления для ограниченных ожиданий

Мониторы — не повторяющиеся интервалы. Когда монитор срабатывает, Paperclip
очищает запланированный монитор и ставит в очередь побудку `issue_monitor_due`
для исполнителя. Если внешний сервис всё ещё pending, исполнитель обязан явно
перезарядить монитор с новым `nextCheckAt`. Если задача переходит в `done`,
`cancelled`, невалидный статус или к человеку/без исполнителя, монитор
очищается.

Баннер ожидания задачи и обратный отсчёт композера также показывают
автоматические ретраи, пока их прогон `scheduled_retry`. Как только retry
`queued` или `running`, его сохранённый `scheduledRetryAt` историчен и не
должен производить предупреждение об ожидании или просрочке. Отдельно
запланированный монитор остаётся видимым. Завершённые и отменённые задачи
прячут обе поверхности ожидания, даже если устаревшее расписание остаётся в
ответе.

Поскольку `serviceName` и `notes` остаются видимыми в активности задачи и
контексте побудки, операторы должны держать их короткими и несекретными.
Достаточно контекста, чтобы исполнитель знал, что осматривать, но без
подписанных URL, bearer-токенов, секретов клиентов, приватных идентификаторов
тенантов или ссылок провайдера с вшитыми кредами.

Границы монитора соблюдаются. Paperclip отклоняет попытки перезарядить
монитор, чей `timeoutAt` или `maxAttempts` уже исчерпан. Когда запланированный
монитор достигает исчерпанной границы в момент срабатывания, Paperclip
очищает его и следует `recoveryPolicy`: `wake_owner` ставит в очередь
ограниченную восстановительную побудку для исполнителя, `create_recovery_issue`
открывает видимую задачу восстановления, а `escalate_to_board` записывает
видимый доске комментарий/активность эскалации.

Используйте `blocked` вместо монитора, когда ни один исполнитель Paperclip не
владеет ответственным путём опроса. В этом случае назовите внешнего
владельца/действие или создайте первоклассную работу восстановления/блокера.

### `blocked`

Это явное состояние ожидания.

Здоровая `blocked` задача имеет явный путь ожидания:

- первоклассные блокеры существуют, и каждый неразрешённый лист имеет валидный
  путь действия по этому контракту
- у задачи есть явное действие восстановления, у которого самого есть живой
  или ожидающий путь
- задача ждёт ожидающую интеракцию, связанное одобрение, человека-владельца
  или ясно названного внешнего владельца/действия

Цепочка блокеров покрыта, только когда её неразрешённый лист жив или явно
ожидает. Промежуточная `blocked` задача сама по себе не делает цепочку
здоровой.

Задача `blocked` застойна, когда у неразрешённого листа блокера нет активного
прогона, отложенной побудки, типизированного участника, ожидающей интеракции
или одобрения, владельца-пользователя, внешнего владельца/действия или
действия восстановления. В этом случае родитель должен показывать первый
застойный лист вместо представления зависимости спокойно покрытой.

## 9. Восстановление после крашей и рестартов

Paperclip теперь трактует восстановление после краша/рестарта как проблему
повисшей назначенной работы, а не только как проблему повисшего прогона.

Есть два разных режима отказа.

### 9.1 Повисший назначенный `todo`

Пример:

- задача назначена агенту
- статус `todo`
- исходная побудка/прогон умерла во время или после диспетчеризации
- после рестарта нет отложенной побудки, и никто не подбирает задачу обратно

Правило восстановления:

- если последний связанный с задачей прогон упал/истёк/отменён и не осталось
  живого пути исполнения, Paperclip ставит в очередь одну автоматическую
  восстановительную побудку назначения
- если та восстановительная побудка тоже завершается, а задача всё ещё
  повисшая, Paperclip переводит задачу в `blocked` и открывает или обновляет
  принадлежащее доске действие восстановления, не меняя исполнителя источника
  и не будя агента-замену; видимый комментарий — доказательство, а не сам
  путь восстановления

Это восстановление диспетчеризации, а не восстановление продолжения.

Возврат из восстановления покрыт той же гарантией liveness:

- побудка `issue_recovery_action_restored`, запрошенная, пока разрешающий
  recovery-прогон ещё активен, сохраняется как follow-up и диспетчеризуется
  только после выхода того прогона, поэтому она не может быть коалесцирована
  в прогон, который её запросил
- если тот follow-up всё же потерян, страховка повисшей работы трактует
  назначенную `todo` задачу с разрешённым `handed_back` действием
  восстановления из или после её последнего успешного прогона как повисшую и
  ставит в очередь ограниченную восстановительную побудку назначения;
  успешный разрешающий прогон сам по себе не доказательство, что
  возвращённая работа источника жива

### 9.2 Повисший назначенный `in_progress`

Пример:

- задача назначена агенту
- статус `in_progress`
- живой прогон исчез
- после рестарта нет активного прогона и отложенного продолжения

Правило восстановления:

- Paperclip ставит в очередь одну автоматическую побудку-продолжение
- если та побудка-продолжение тоже завершается, а задача всё ещё повисшая,
  Paperclip переводит задачу в `blocked` и открывает или обновляет
  принадлежащее доске действие восстановления, не меняя исполнителя источника
  и не будя агента-замену; видимый комментарий — доказательство, а не сам
  путь восстановления

Это восстановление непрерывности активной работы.

После продуктивного успешного прогона восстановление проверяет, что задача
всё ещё `in_progress` и назначена тому же агенту под блокировкой задачи
транзакции enqueue. Более ранний снимок прохода не может авторизовать
продолжение после завершения, отмены, переназначения или смены статуса.
Несоответствие записывает квитанцию пропущенной побудки без создания прогона.
Пустое отложенное продолжение, отменённое из-за терминальности задачи,
опускается из чата задачи; его отмена остаётся в журнале прогона. Прогоны,
которые реально стартовали, всё ещё показывают своё состояние остановки.

То же ограниченное правило применяется, когда предыдущий heartbeat отчитался
ожидающим локального/фонового наблюдателя, и тот наблюдатель был убит,
исчез или никогда не был представлен долговечным примитивом Paperclip.
Paperclip ставит в очередь максимум одно продолжение для того же
фингерпринта восстановления. Если продолжение тоже оставляет только
локальные доказательства наблюдателя, Paperclip обязан показать реальный
блокер или явное действие восстановления вместо повторения продолжения
восстановления. Новый монитор, запланированная побудка, здоровая делегированная
задача-блокер или другая долговечная мутация источника нормально разрешает тот
фингерпринт восстановления.

#### Намеренное ожидание — не потерянный прогон

Продолжение, отменённое гейтом устаревания с
`issue_continuation_waiting_on_review`, — это *преднамеренная парковка*, а не
исчезнувший путь исполнения. Последний прогон отчитался, что задача ждёт
ревью/одобрения (например, зонтичная задача, чья работа только что была
декомпозирована в подзадачи). Трактовка этой парковки как повисшего прогона
ретраила бы её, затем эскалировала в `blocked` с действием восстановления и
уведомлением об ошибке для оператора — хотя ничего не упало и человеку нечего
делать.

Правило восстановления для продолжения, припаркованного под ревью:

- если у задачи есть реальная цель ожидания — открытые (нетерминальные)
  подзадачи или существующие неразрешённые блокеры — Paperclip конвертирует
  намеренное ожидание в первоклассное ожидание зависимости: он ставит задачу
  `blocked` на эти задачи, сохраняет исходного исполнителя и публикует
  комментарий простым языком, объясняющий, что задача возобновится
  автоматически, когда её зависимости завершатся. Задача затем
  самовозобновляется через обычный путь `issue_blockers_resolved`; действие
  восстановления или владелец эскалации не участвуют
- если у задачи нет текущей типизированной цели ожидания и исходный владелец
  вызываем, Paperclip классифицирует это как `deliberate_wait_without_target`
  и даёт тому владельцу пять попыток на нормальной модели починить диспозицию:
  немедленно, затем через 60, 120, 240 и 480 секунд, с джиттером до 10
  процентов на отложенных попытках
- перед каждой попыткой Paperclip ревалидирует неразрешённые блокеры и детей,
  интеракции, связанные одобрения, мониторы, стадии исполнения, отложенные
  побудки, активные прогоны, work products, вызываемость владельца и гейты
  бюджета или governance. Любой реальный живой или ожидающий путь подавляет
  retry
- граница retry ключуется идемпотентным долговечным фингерпринтом
  состояния источника. Комментарии, повторяющиеся парковочные сводки и
  эквивалентная проза не сбрасывают её. Долговечные изменения, такие как смена
  статуса источника или исполнителя, смены зависимостей или интеракций, смены
  одобрений или execution-policy, смены мониторов или изменения work products,
  могут создать новый фингерпринт
- при апгрейде последовательные исторические отмены
  `issue_continuation_waiting_on_review` для той же принятой интеракции и всё
  ещё неизменного долговечного состояния источника засеивают этот же счётчик.
  Пять применимых предапгрейдных парковок поэтому исчерпывают потолок
  немедленно; отсутствие исторической строки действия восстановления
  `deliberate_wait_without_target` не даёт пять новых попыток
- действие сохраняет неизменённый фингерпринт, счётчик попыток источника,
  время наступления, владельца источника и возвращающегося владельца. Стартовый
  и периодический реконсайл переиспользуют это состояние, сворачивают
  действие, когда появляется текущее типизированное ожидание, и
  перепланируют или эскалируют истёкшую попытку без живого запланированного
  прогона. Ключи идемпотентности предотвращают создание рестартом
  дублированных побудок или запланированных прогонов
- после пяти попыток с тем же фингерпринтом Paperclip открывает одно
  принадлежащее доске действие восстановления в области действия источника.
  Исполнитель источника остаётся неизменным, никакой менеджер/создатель/
  исполнитель-замена не будится, и доска выбирает: чинить, ретраить исходного
  владельца, явно переназначать или разрешать
- действие восстановления — здоровое ожидание, только пока у его владельца
  есть живой прогон, отложенная побудка, запланированный retry, типизированное
  ожидание или явная эскалация доске. Liveness источника и каждая проекция
  цепочки блокеров используют тот же вложенный результат

Принятая интеракция вытесняет парковку продолжения, записанную до этого
принятия. Отложенное продолжение, несущее парсибельный `interactionResolvedAt`,
не должно отменяться только потому, что более старая сводка продолжения
говорит ждать ревью или одобрения. Восстановление интеракции-продолжения
ограничено: после трёх последовательных отменённых побудок-продолжений без
старта прогона восстановление конвертирует реальное ожидание зависимости,
когда оно существует, или видимо эскалирует отсутствующий путь исполнения
вместо бесконечного перекверстания.

Это держит зонтик после декомпозиции (§7) на реальном пути ожидания вместо
полагания на rollup `parentId`, который §6 не трактует как зависимость.

### 9.3 Классы восстановительной работы

Только статусное операционное восстановление может обновлять liveness задач,
сбрасывать плохой статус, записывать диспозицию или просить вмешательства
человека или менеджера. Эти побудки обязаны нести контекст-ограждение,
например `allowDeliverableWork: false`, `allowDocumentUpdates: false` и
`resumeRequiresNormalModel: true`. Класс восстановительной работы не выбирает
и не меняет модель агента.

Автоматические ретраи, которые могут продолжать работу источника, используют
настроенную модель агента. Это включает ретраи упавшей работы источника,
ретраи при потере процесса, транзиентные или запланированные ретраи,
продолжения max-turn, продолжения исполнителя источника, восстановление
диспетчеризации назначенного `todo` и любой прогон, который может обновлять
файлы репо, документы задач, планы, work products или вложения. Когда
только статусное восстановление определяет, что реальная работа осталась, оно
обязано вернуть работу прогону-воркеру до возобновления работы источника или
постоянных обновлений результата.

## 10. Стартовый и периодический реконсайл

Стартовое восстановление и периодическое восстановление отличаются от обычной
доставки побудок.

На старте и в цикле периодического восстановления Paperclip выполняет
следующие проходы:

1. пожать осиротевшие `running` прогоны
2. возобновить сохранённые `queued` прогоны
3. реконсилить повисшую назначенную работу
4. сканировать молчащие активные прогоны только для source-aware свёртывания
   терминальных состояний и legacy-очистки; чтения API классифицируют
   обычную тишину вывода для UI доски

Проход повисшей работы закрывает разрыв, где состояние задачи переживает
краш, а путь побудки/прогона — нет. Скан молчащих прогонов покрывает отдельный
случай, где живой процесс существует, но перестал производить наблюдаемый
вывод.

Автоматические ревью продуктивности уволены. Счётчики прогонов, отсутствующие
комментарии и прошедшее время задач не создают задач ревью и не навязывают
холды продолжения. Ограниченное продолжение, восстановление провайдера,
лимиты бюджета, явные блокеры и обычные стадии ревью/одобрения остаются в
силе. Существующие задачи productivity-ревью, комментарии, назначения и
зависимости остаются неизменными и читаемыми; их исторические происхождения
всё ещё идентифицируют их как восстановительную работу для подавления
рекурсии.

### Разрешение интеракций в треде задачи

Каждый вид интеракции в треде задачи наследует resolver-политику `anyone`,
когда создатель опускает политику. `anyone` включает агента-создателя и
создающий прогон. Вызывающие оп-инятся в независимое ревью через
`not_creator` или человеческое разрешение через `human_only`; названный
адресат и кап компании могут сузить эффективную аудиторию. Легаси-алиасы
`board_or_agents` и `board_only` нормализуются в `anyone` и `human_only` для
новых записей.

Resolver-политика снимается в снимок с явным/унаследованным происхождением и
эффективным источником (`requested`, `company_cap` или `governed_action`).
Существующие неоднозначные легаси-строки помечаются
`legacy_inherited_restriction` и сохраняют старое ограничение:
`board_or_agents` становится `not_creator`, а не `anyone`, тогда как
`board_only` становится `human_only`. Ожидающие карточки никогда молча не
расширяются.

Разрешение — exact-once и требует доступа к задаче в той же компании.
Агентское разрешение также требует валидной атрибуции прогона и остаётся под
low-trust и task-bridge сдерживанием. Свежесть цели и вытеснение проверяются
до коммита исхода. Разрешение записывает ответ; каждое продолжение, создание
задачи, вызов инструмента/провайдера, переход execution-policy, трата,
деплой или другой эффект независимо перезапускает свои собственные гейты
авторизации и одобрения.

## 11. Task Watchdog для деревьев задач

Task watchdog наблюдает настроенное поддерево задач после того, как это
поддерево перестало двигаться. Это продуктовый механизм верификации и
восстановления для выбранной работы, а не монитор процессов.

Держите раздельными три понятия watchdog/восстановления:

- task watchdog: наблюдает настроенную исходную задачу плюс потомков не
  watchdog и спрашивает, легитимно ли остановившееся поддерево
- silent active-run watchdog: наблюдает всё ещё работающий процесс, который
  перестал производить вывод
- liveness-восстановление: чинит повисшие пути плоскости управления, когда
  нетерминальная задача не имеет живого, ожидающего или восстановительного
  пути

### Конфигурация и область сканирования

У исходной задачи может быть максимум одна активная конфигурация task
watchdog. Конфигурация называет watchdog-агента той же компании, которого
можно вызвать, и опциональные пользовательские инструкции.

Скоуп сканирования:

- исходная задача
- потомки, достижимые через `parentId`
- исключая каждую задачу с `originKind` = `task_watchdog`
- исключая каждого потомка ниже исключённой task-watchdog задачи

Переиспользуемая watchdog-задача — ребёнок наблюдаемой исходной задачи для
аудита и навигации, но она исключена из наблюдаемого рабочего поддерева. Это
предотвращает рекурсивные watchdog-циклы.

### Оценка остановившегося поддерева

Оценка task watchdog консервативна. Если у любой включённой задачи есть живой
прогон, отложенная побудка или запланированный retry, которые должны
сработать без вмешательства, поддерево живо, и task watchdog не запускается.

Если ни у одной включённой задачи нет живого пути, Paperclip вычисляет
фингерпринт остановки из долговечного состояния поддерева, включая как
минимум:

- id включённых листьев, статусы, исполнителей и последние долговечные метки
  времени обновления
- первоклассные блокеры и сводки неразрешённых листьев блокеров
- ожидающие интеракции и одобрения, определяющие пути ожидания
- активные мониторы и запланированные ретраи
- доказательства терминальных или отменённых листьев
- ревизию конфигурации watchdog, включая смены watchdog-агента и инструкций

Если фингерпринт равен последнему просмотренному watchdog-ом фингерпринту,
Paperclip подавляет ещё одну watchdog-побудку. Если фингерпринт новый,
Paperclip создаёт или переоткрывает переиспользуемую watchdog-задачу и будит
настроенного watchdog-агента с исходной задачей, конфигурацией watchdog,
фингерпринтом остановки, сводкой листьев, мандатом по умолчанию,
пользовательскими инструкциями и выведенными сервером метаданными
возможностей, называющими разрешённые операции, запрещённые операции,
переиспользуемую watchdog-задачу и не-watchdog целевую область.

Смена watchdog-агента или пользовательских инструкций инвалидирует
просмотренный фингерпринт и форсирует свежую оценку, даже если состояние
поддерева иначе не изменилось.

### Живой путь, созданный работой watchdog

Активная watchdog-задача или отложенная watchdog-побудка может быть видимым
путём восстановления для остановившегося наблюдаемого поддерева, но это не
доказательство, что исходная работа результата завершена. Это значит, что
следующее действие — верификация watchdog.

Когда исходная задача нетерминальна и не имеет другого живого пути, продукт
должен показывать watchdog-задачу или действие восстановления в области источника как
причину, по которой поддерево покрыто. Когда корректность
требует, чтобы исходная задача ждала watchdog-ревью, исходная задача должна
быть заблокирована на переиспользуемой watchdog-задаче или эквивалентном
явном действии восстановления. Не полагайтесь только на структуру
родитель/ребёнок.

### Полномочия watchdog во время исполнения

Watchdog-агент действует в ограниченной роли, не как исходный воркер
результата и не как доска. Сервер обязан обеспечивать контракт полномочий из
`doc/SPEC-implementation.md` из сохранённого watchdog-контекста. Текст
промпта и пользовательские инструкции могут направлять суждение watchdog, но
не могут дать полномочия вне наблюдаемого поддерева или расширить обычную
эффективную аудиторию интеракции.

Watchdog не должен создавать видимые probe-задачи, комментарии или одноразовые
задачи, чтобы обнаруживать границы возможностей. Им следует полагаться на
метаданные возможностей побудки и явные отклонения API, а затем записывать
любую отклонённую операцию как доказательство в переиспользуемой
watchdog-задаче.

Watchdog должен проверять остановившиеся листья против комментариев,
документов, work products, тестов, скриншотов, блокеров, состояния ревью и
контекста прогонов. Он не должен принимать «я не смог» или «жду одобрения»
как достаточное само по себе.

Когда работа должна продолжаться, watchdog восстанавливает живой путь внутри
наблюдаемого поддерева: переоткрыть или переназначить застрявшую работу,
создать задачи продолжения, починить блокеры, поставить монитор или разрешить
интеракцию, которую позволяет его обычная агентская аудитория. Когда
остановившееся состояние легитимно, watchdog записывает почему и оставляет
поддерево с валидным терминальным, ожидающим, заблокированным, ревью или
явным восстановительным путём.

### Атомарный пакет восстановления

Восстановление — часто больше одной записи: переоткрыть лист-тупик **и**
объяснить это на родителе. Watchdog-прогон может подать маленький атомарный
пакет восстановления: максимум 3 мутации из списка разрешённых, провалидированные против фингерпринта остановки, который прогон наблюдал. Сервер применяет
пакет всё-или-ничего и прерывает остаток, если фингерпринт поддерева изменился
посреди пакета, потому что работа concurrently ожила.

Это сохраняет цель stale-guard — никогда не мутировать поддерево, которое
только что ожило под ногами watchdog — и убирает режим отказа, где трата
единственной разрешённой записи на информационный комментарий сжигает
восстанавливающую состояние мутацию, которая была реально нужна
восстановлению.

### Решения по интеракциям

Task watchdog — обычный агент для разрешения интеракций. Его watchdog-контекст
не даёт специальной аудитории, маркера plan-purpose или allowlist видов, и это
не категорический отказ. Обычный эвалюатор проверяет эффективную политику,
названного адресата, область компании и задачи, атрибуцию прогона, low-trust/
task-bridge сдерживание, свежесть цели и exact-once состояние.

Это не даёт watchdog downstream-полномочий. Связанные/формальные одобрения
остаются отдельными, решения execution-policy всё ещё требуют типизированного
участника, и принятая интеракция не может авторизовать траты, найм, секреты,
деплой, деструктивные изменения данных, кросс-компанийскую работу или любую
мутацию, которую область действия watchdog иначе запрещает.

### Завершение и обновления фингерпринта

Просмотренный watchdog-ом фингерпринт должен обновляться только после того,
как watchdog-задача достигла валидной диспозиции:

- `done` с доказательством, что остановившееся состояние приемлемо
- `in_review` с реальным ревьюером, одобрением, интеракцией, владельцем-
  пользователем, монитором или путём восстановления
- `blocked` с первоклассными блокерами или названным внешним владельцем/
  действием
- мутация watchdog, восстанавливающая живую работу, где последующая мутация
  поддерева источника естественно меняет фингерпринт остановки

Если watchdog продвинул работу, Paperclip не должен помечать старый
фингерпринт как постоянно приемлемый только потому, что watchdog-задача
завершилась. Следующий скан должен наблюдать изменённое состояние поддерева и
либо подавиться, потому что работа жива, либо позже вычислить новый
фингерпринт остановки.

### Верификация восстановления и эскалация

Просмотренный фингерпринт подавляет повторное срабатывание, только когда
записанной диспозицией watchdog было «это остановившееся состояние
легитимно». Диспозиция **«живой путь восстановлен»** не зарабатывает
постоянного подавления; она взводит ограниченную верификацию.

Фингерпринт остановки обязан вычисляться из долговечного состояния поддерева
так, чтобы восстановление, не меняющее ничего наблюдаемого, обнаруживалось
как неудавшееся восстановление. В частности, активность на промежуточных
(нелистовых) узлах — комментарии, побудки, доставленные исполнителю
промежуточной задачи, прогоны, заканчивающиеся без мутации любого
остановившегося листа, — обязаны попадать во фингерпринт или линию попыток;
фингерпринт, выведенный только из остановившихся листьев, делает неудавшееся
восстановление промежуточного узла побайтово идентичным
просмотренному-и-приемлемому состоянию остановки, что навсегда заглушает
watchdog.

Семантика верификации и эскалации:

- если после диспозиции «живой путь восстановлен» поддерево наблюдается
  снова остановившимся с фингерпринтом, равным тому, который watchdog заявил
  как починенный, восстановление не удалось, и watchdog срабатывает снова с
  увеличенным счётчиком попыток
- линия попыток — долговечное состояние watchdog: номер попытки, фингерпринт,
  который каждая попытка заявляла починить, и предпринятые действия
  восстановления
- после N попыток (N = 2–3) на той же линии фингерпринта платформа перестаёт
  срабатывать повторно и эскалирует человеку — владельцу watchdog или
  уведомлению доски — с историей попыток

Это ограничивает оба режима отказа: неудавшееся восстановление ретраится
вместо молчания (liveness), а граница попыток плюс человеческая эскалация
предотвращает бесконечный цикл срабатываний (нет runaway watchdog).
Легитимные остановки подавляются точно как раньше.

Task watchdog не должен молча помечать работу источника выполненной по
комментариям прозой, не должен дублировать деревья детей для той же принятой
ревизии плана и не должен создавать ещё одну task-watchdog задачу для той же
исходной задачи.

## 12. Silent Active-Run Watchdog

Активный прогон всё ещё может быть нездоров, когда его процесс `running`.
Paperclip трактует длительную тишину вывода как сигнал watchdog, а не как
доказательство, что прогон упал.

Владельцем этого контракта является служба восстановления:

- классифицировать тишину вывода активного прогона как `ok`, `suspicious`,
  `critical`, `snoozed` или `not_applicable`
- уважать активные snooze и continue-решения на прогоне
- навсегда подавлять сигнал для прогона после решения
  `dismissed_false_positive`
- строить сводку `outputSilence`, показываемую ответами live-run и
  active-run API
- сохранять ссылки на открытые легаси-задачи `stale_active_run_evaluation`,
  не обновляя и не меняя их

Подозрительная и критическая тишина — информационные сигналы UI доски. Они не
создают задачу или действие восстановления. Они не комментируют и не
блокируют исходную задачу. Они не меняют назначение, не будят агента, не
отменяют активный процесс и не меняют прогон. Доска использует существующие
элементы управления прогоном, когда решает, что вмешательство необходимо.

Решения watchdog — явные решения доски, сохранённые против прогона:

- `snooze` записывает выбранное оператором будущее время тихости-до и прячет
  сигнал в этом окне
- `continue` записывает, что текущие доказательства приемлемы, не отменяет и
  не мутирует активный прогон и ставит 30-минутное окно перезарядки по
  умолчанию, прежде чем watchdog оценит всё ещё молчащий прогон снова
- `dismissed_false_positive` записывает, почему сигнал не был actionable, и
  подавляет его навсегда для этого прогона

Операторам следует предпочитать `snooze` для известных ограниченных по времени
периодов тишины. `continue` — только короткое подтверждение текущих
доказательств. Если прогон остаётся молчащим после окна перезарядки, сигнал
UI появляется снова.

Сигнал появляется в UI снова после истечения окна snooze или continue. Работа
ревью не создаётся при его появлении. Доска может записывать решения без
evaluation-задачи. Для совместимости назначенный владелец открытой
легаси-evaluation задачи тоже может записать решение, привязанное к той
задаче и прогону. Другие агенты не могут.

### Source-aware свёртывание watchdog

Скан очистки активных прогонов source-aware. Он перечитывает связанную
исходную задачу и решает, представляет ли всё ещё работающий handle
продуктивную работу источника или устаревшее бухгалтерское учёждение
прогона/процесса. Он не создаёт работу ревьюера.

Свёртывайте работу watchdog, когда всё это верно:

- прогон связан с исходной задачей в той же компании
- исходная задача терминальна (`done` или `cancelled`)
- долговечная активность источника из того же прогона доказывает, что
  исходная задача достигла той терминальной диспозиции после точки
  доказательств stale-прогона или тишины вывода
- нет независимых доказательств, что всё ещё работающий или отцепленный
  процесс делает вредную работу, всё ещё владеет внешней очисткой, требующей
  решения оператора, или нуждается в отдельном секьюрити/ownership-ревью

Свёртывание означает финализацию устаревшего прогона и разрешение любого
легаси-действия восстановления watchdog или evaluation-задачи через явный
жизненный цикл восстановления. Оно обязано сохранять id прогона, исходную
задачу, обнаруженную тишину или доказательства отцепленного процесса,
терминальную активность источника, причину решения и best-effort результат
очистки процесса. Оно обязано быть идемпотентным для сигнала
`(companyId, runId, sourceIssueId)` и не должно рекурсивно восстанавливать
собственно watchdog evaluation-задачу.

Не свёртывайте прогон только потому, что он тих. Держите информационный
сигнал видимым, когда:

- исходная задача всё ещё `todo` или `in_progress`, потому что продуктивная
  работа может всё ещё происходить или застрять
- исходная задача остаётся `in_progress` после успешного прогона без валидной
  диспозиции, потому что путь успешной передачи прогона владеет тем
  ограниченным исправлением
- прогон завершился или исчез, пока исходная задача остаётся `in_progress`
  без живого пути, потому что восстановлением непрерывности владеет
  восстановление повисшей назначенной работы
- исходная задача терминальна, но нет долговечной same-run терминальной
  активности после точки устаревших доказательств
- есть независимые доказательства, что процесс может всё ещё мутировать
  внешнее состояние, утекать ресурсы, пересекать границы компании или
  владения или иным образом требует решения оператора

В обычном нетерминальном случае критическая тишина остаётся сигналом UI и не
блокирует исходную задачу. В source-resolved случае завершённая задача
источника не приобретает новое ревью или блокер только потому, что старый
handle прогона остался активным. Только реальная неразрешённая работа должна
блокировать работу.

Source-aware свёртывание watchdog касается устаревшего бухгалтерского
учёта активных прогонов после валидной терминальной диспозиции. Оно не
выводит продуктивность из счётчиков прогонов, частоты комментариев или
прошедшего времени задач.

Очистка отцепленных процессов — операционная гигиена, а не liveness исходной
задачи. Очистка должна быть best-effort и аудируемой. Если очистка падает, но
исходная задача уже терминальна с same-run долговечными доказательствами,
Paperclip должен сохранить сбой очистки в аудиторском следе прогона/watchdog и
маршрутизировать только заботу об очистке в ограниченное восстановление,
когда реальный владелец/действие остаётся.

## 13. Автовосстановление, явное восстановление и эскалация человеку

Paperclip использует три разных исхода восстановления — в зависимости от того,
сколько он может безопасно вывести.

### Автовосстановление

Автовосстановление разрешено, когда владение ясно и плоскость управления потеряла
только непрерывность исполнения.

Примеры:

- повторная постановка одной побудки диспетчеризации для назначенной задачи `todo`,
  чей последний прогон упал, истёк по таймауту или был отменён по ограниченным
  правилам разговора или непрерывности провайдера ниже
- повторная постановка одной побудки-продолжения для назначенной задачи `in_progress`,
  у которой исчез живой путь исполнения, по тем же ограниченным правилам ниже
- возврат осиротевшего блокера его создателю, когда этот блокер уже мешает другой работе

Автовосстановление сохраняет существующего владельца. Оно не выбирает
агента-замену.

### Инструменты завершения и финальные ответы

Инструмент завершения вроде `paperclip_finish` сообщает диспозицию задачи; он не
завершает ход провайдера. Paperclip продолжает сохранять и отображать события
провайдера, пока не придёт авторитетный терминал хода. Отчёт о завершении не
запускает ни одного таймера прерывания. Существующие таймауты исполнения,
отмена, управляемые ожидания и правила активной цели продолжают действовать.
Более поздний упавший или отменённый терминал остаётся упавшим или отменённым,
даже если агент уже отчитался о завершённой работе.

Финальное сообщение ассистента — это видимый ответ на задачу. Выбор ответа
выполняется после завершения сохранения предшествующих событий; краткая сводка
завершения не может заменить доступный финальный ответ. Существующие правила
фолбэка и приоритета явных комментариев продолжают действовать. Закрытие потока
без терминала хода не является доказательством успеха. Повтор событий
использует существующие квитанции источника и никогда не повторяет работу
провайдера только ради восстановления записанного вывода.

Если runnerd синтезирует результат при остановке провайдера, он публикует этот
результат до терминала хода провайдера, а терминал прогона публикует последним.
Адаптер поэтому может удерживать результат, пока соответствующий ход ещё обладает
полномочиями. Поздний результат не должен переоткрывать уже финализированный ход.

Обычное завершение задачи и запросы человеческого ввода должны работать под
консервативными правами раннера. Изолированный рантайм Claude даёт только узкий
набор задачных инструментов на принадлежащем раннеру мосту; он не меняет общие
права на инструменты. Вопросы должны создаваться как долговечные интеракции до
того, как агент заявит, что ждёт. Прямой комментарий на доске, переоткрывающий
завершённую работу, имеет ту же пассивную семантику ожидания ответа, что и
комментарий на открытой задаче, с теми же проверками источника, идентичности
и управления. Автоматическое продолжение не является ответом пользователя.

Идентичность хода провайдера отделяет ответы восстановления от более раннего
вывода ассистента. Ход восстановления не может перезаписать доставленный ответ.
Вложения файлов и рабочие продукты обновляются в видимом разговоре при доставке.
Неопределённость доставки из композера выверяется по точному долговечному ID
клиентского запроса; другой комментарий не может её закрыть, а более новый черновик
текста должен быть сохранён.

Действие **Stop** в композере отменяет текущий ответ и проверяет завершение; оно
не создаёт удержания паузы. Подтверждённая намеренная отмена остаётся нейтральной,
даже если teardown освобождает lease прогона или не возвращает смыслового
результата. **Pause work** отдельно управляет будущим исполнением. Крах, мешающий
движению, — это **Blocked**; **In Review** требует конкретного человеческого
решения.

Пауза и отмена поддерева записывают аутентифицированного актёра доски в каждом
прогоне, который они прерывают. Проверенная нативная остановка не должна
превращаться в необъяснимый сбой только потому, что она произошла от действия
по поддереву. Явное удержание паузы всё равно блокирует будущее исполнение до
Resume, а отсутствие доказательства остановки по-прежнему блокирует продолжение.

### Непрерывность провайдера и ограниченная финализация

Безвозвратно непригодная нативная сессия раннера может быть заменена только
с доказательством того, что предшественница остановлена и ограждена, завершённые
результаты и состояние воркспейса сохранены, необходимая история задачи доступна,
а отложенные эффекты выверены. Нативная shell-команда провайдера или внешняя
запись без надёжной квитанции результата неизвестны. Неизвестные эффекты, сбои
целостности и непроверенное владение процессами никогда не авторизуют
спекулятивный повтор. Когда автовосстановление исключено, Paperclip выбирает
консервативный дефолт: сохранить записанную работу, остановить затронутую задачу
и удерживать долговечный запрет повтора (no-replay hold). Неизвестные исходы
действий остаются неизвестными. Форма выверки или пользовательская диагностика
не требуются.

Локальная замена упавшего Codex может использовать полный инвентарь прерванного
хода, аутентифицированные доказательства остановки процесса и неизменные
отпечатки сохранённого состояния. На этот путь подходят только текст и точно
квитанцированный вызов завершения задачи; неизвестные операции или частичные
транскрипты — нет. Замена использует свежую сессию и снимает только устаревшее
удержание восстановления ровно этого предшественника, записывая доказательство
и линию наследования преемника. Сохранённые файлы провайдера не редактируются.

Повторы бутстрапа, возобновления по точному чекпоинту и свежие замещающие сессии
делят три суммарные попытки провайдера, включая исходную. Связанные ID прогонов,
рестарты контроллера и дублирующиеся побудки не сбрасывают этот бюджет.
Автоматические попытки сохраняют задержку в 30 секунд. Планирование замены и
линия наследования предшественника фиксируются вместе, с одним преемником на
предшественника и допуском через обычные блокировки задач, авторизацию, паузу,
согласования и бюджетные гейты.

Исполнение провайдера и финализация плоскости управления идут по разным часам.
Здоровый провайдер может думать или исполнять долгий инструмент без вывода.
Когда исполнение устаканивается, шаги восстановления и финализации имеют дедлайн
60 секунд, проверяемый на старте и каждые 15 секунд. При здоровой базе и
планировщике брошенный переход должен быть починен или показан за 90 секунд.
Терминальная запись состояния не должна ждать очистки или публикации провайдера;
поздний финализатор не может изменить переназначенную или закрытую задачу и не
может снять блокировки чужого прогона. Исторические неоднозначные прогоны никогда
не повторяются автоматически после апгрейда.

Каждое продолжение несёт запрос-триггер, упорядоченные указания пользователя,
исходы интеракций, завершённую работу и явное покрытие истории. Доставленное
сообщение остаётся частью запроса задачи после разрешения его соединения или
согласования. Исходный заголовок — фон; выполненное чтение Notion не закрывает
более поздний запрос Gmail. Границы авторства и доверия к источнику переживают
рендеринг в нативные и легаси-промпты. Отсутствующую обязательную историю нужно
дозапросить до диспетчеризации, а не описывать как полную.

### Продолжение прерванного разговора

Перед диспетчеризацией провайдера допуск чат-управления повторяет транзиентные
конфликты блокировок базы до 50 ожиданий по 100 мс. Каждая попытка начинает новую
транзакцию и перепроверяет текущий прогон и зафиксированные доказательства
закрытия разговора. Блокировка не удерживается между попытками, и вызовы
провайдера не повторяются. Захваты очереди остаются неблокирующими.
Затяжная конкуренция оставляет ограниченный сбой допуска с явной ошибкой
блокировки базы; отсутствующие или невалидные доказательства источника всё равно
останавливают прогон без повторной проверки допуска.

Прерванный разговор не блокирует свою задачу навсегда. Для локальных
разговорных адаптеров Paperclip начинает новый ограниченный ход с существующей
сессией, если она совместима, или полный разговор задачи, когда сессия
недоступна. Промпт говорит: «Ваш предыдущий прогон был прерван. Продолжите
с того места, где остановились». Агент сам решает, что осталось от истории и
последнего запроса пользователя. Paperclip никогда не повторяет записанные
вызовы инструментов автоматически. Неизвестные исходы прошлых действий не
являются задаче-широким гейтом исполнения, и анкета выверки действий не требуется.

Выключение, потеря процесса и сбой провайдера используют существующий долговечный
счётчик повторов сбоев и задержку. Обычное восстановление после сбоя допускает
не более двух автоматических повторов в цепочке сбоев. Восстановление
инфраструктуры принятых интеракций сохраняет свою ограниченную политику.
Повторные визиты планировщика переиспользуют того же преемника; рестарт сервера
не сбрасывает счётчик. После исчерпания автоматические попытки прекращаются.
Новое явное сообщение пользователя может начать свежий прогон и свежий бюджет
сбоев. Продолжение по max-turns продуктивного прогона и подтверждённые ожидания
воркспейса сохраняют свою отдельную семантику.

Реальные гейты продолжают действовать: владение компанией и задачей, активное
владение провайдером, лимиты бюджета, доступность агентов, зависимости,
ожидающие пути согласования/ревью и явные удержания паузы. Перецепление и
финализация нативного раннера сохраняют свой протокол владения. Процессные,
HTTP- и gateway-адаптеры сохраняют свои правила восстановления, потому что
вызов таких адаптеров сам по себе может повторить внешнее действие, а не начать
ход разговора.

Операторский Stop ждёт завершения провайдера. Удалённые сэндбокс-провайдеры
могут вернуть квитанцию остановки/удаления после завершения своей операции в
плоскости управления. Paperclip привязывает эту квитанцию к компании, прогону
и точному lease; успешная очистка файлов, терминальная строка прогона или
событие выключения в сэндбоксе недостаточны. Легаси-разговорные прогоны получают
подтверждение отмены после подтверждения остановки всех удалённых lease. Stop
сам по себе никогда не создаёт продолжения. Сообщение пользователя, вставшее
в очередь во время удалённой очистки, пересматривается, когда провайдер
подтверждает остановку; оно всё равно проходит обычный допуск и принимает
ожидающие ID комментариев по порядку. После остановки следующий явный wake
использует ту же очередь. Совместимая сохранённая ACP-сессия может возобновиться,
недоступная или несовместимая — начать заново с полным контекстом задачи.
Креды прогона и пути скретча остаются в области действия нового прогона. Пауза
поддерева требует Resume; сообщение её не обходит.

Для нативных разговоров аутентифицированное сообщение пользователя, отправленное
после завершения предыдущего прогона, может снять его удержания восстановления
исполнения и начать свежий ход. Снятие удержаний и новый прогон атомарны.
Предыдущий транскрипт, исходы инструментов и история восстановления остаются
нетронутыми. Это новый разговор; он не повторяет вызовы инструментов с
неизвестными исходами.

Локальное восстановление записывает авторскую от сервера квитанцию остановки
до того, как очистит проверенно отсутствующую идентичность процесса. Новый запрос
исполнения инвалидирует эту квитанцию до того, как любой процесс сможет
стартовать; запись новой идентичности процесса тоже её инвалидирует. Отсутствующие
PID без квитанции всё равно блокируют допуск. Удалённое исполнение продолжает
требовать квитанции остановки для каждого lease.

Если очистка или другой гейт исполнения ещё ожидают, сообщение остаётся в своей
существующей квитанции очереди. Стартовое и периодическое планирование
пересматривает до 50 сроковых квитанций за проход, не чаще раза в 30 секунд на
квитанцию, без вызова модели и без сброса попыток восстановления. Колбэки
очистки используют тот же путь допуска. Блокировка задачи не даёт параллельным
воркерам доставить принятую или отброшенную квитанцию повторно. Область
очередных сообщений показывает текущую причину ожидания. Паузы, согласования,
бюджеты, владение и авторизация внешнего чата продолжают действовать. Сообщение,
отправленное до завершения прогона, не даёт новых полномочий после остановки.

Исторические легаси-удержания прерывания для разговорных адаптеров больше не
блокируют новые сообщения и Resume. Автоматическая классификация использует
принадлежащую серверу идентичность адаптера, сохранённую атомарно при захвате
прогона, сохранённый вызов адаптера или политику продолжения — никогда текущие
настройки адаптера агента. Отсутствующие исторические доказательства адаптера
сохраняют автоматическое удержание; явное продолжение пользователя может снять
его после доказательства остановки предшественника. Терминальная строка с живым
процессом-предшественником, невысвобожденным lease окружения или
проваленной/ожидающей очисткой всё равно блокирует фактический допуск и Resume;
один лишь таймстамп высвобождения не доказывает успех очистки. Планирование
повтора может произойти до очистки, но не даёт полномочий исполнения. Восстанов
свёртывает их устаревший бухгалтерский запрет повтора, не меняя владение,
статус задачи и не пробуждая старую работу автоматически. Аудиторский след
остаётся читаемым. Нативные удержания целостности и владения, а также удержания
неразговорных адаптеров, продолжают действовать.

Серверная проекция остаётся доступной для диагностики. Обычные ожидания работы,
завершения и интеракций не добавляют бейджей и карточек в списки задач и ленты.
Заголовки активного транскрипта продолжают говорить «Работаю» во время
автоматического повтора и подтверждения исполнения; попытки, причины и решения
о восстановлении принадлежат логу прогона. Восстановление использует
существующий транскрипт и лог прогона, а не дополнительную форму выверки.
Отменённый прогон, который так и не стартовал, говорит «Не удалось запустить»
вместо намёка, что агент ответил.

### Стартап Codex и состояние провайдера

Paperclip доверяет выбранному сервером корню исполнения стартапа в изолированной
конфигурации Codex. Разрешите этот корень на хосте исполнения, включая ключ
доверия основного репозитория для git-worktree. Запускайте провайдера в том же
корне. Это не меняет права сэндбокса, авторизацию инструментов, доступ к секретам
и отдельную политику доверия Codex по хукам.

Codex сохраняет разговор модели. Paperclip возобновляется с
`excludeTurns: true`, читает лёгкое состояние треда и загружает постраничные
метаданные ходов или конкретные элементы хода только когда выверке исполнения
они нужны. Неподдерживаемая или неполная история — явная ошибка, а не
доказательство простаивающего исполнения.

Снимок использования корневого треда, отправленный при возобновлении,
принадлежит его заявленному завершённому ходу. Сохраните ограниченную локальную
диагностику и используйте кумулятивные итоги как базовую линию; не выдавайте
предупреждение и не списывайте историческое использование `last` на новый прогон.
Сохраняйте базовую линию между восстановлениями одного прогона и начинайте новую
дельту прицепления нового прогона. Остальные проверки устаревших событий и
полномочий сохраняются.

### Явное продолжение пользователя после сбоя исполнения

Удержание восстановления исполнения блокирует автоматический повтор. Новый
аутентифицированный комментарий пользователя или точечный Retry упавшего прогона
может авторизовать свежий нативный или легаси-ход разговора после подтверждения,
что исполнение предшественника остановлено. Это новый запрос, а не ещё одна
автоматическая попытка в том же инциденте. Старый счётчик попыток и неизвестные
исходы действий остаются неизменными. Известные доказательства
неконверсационного адаптера по-прежнему требуют своего исходного потока выверки,
даже если текущие настройки агента изменились. До-апгрейдные прогоны без
доказательств адаптера могут получить новый явный ход пользователя только после
доказательства остановки; их старый адаптер и исходы действий остаются
неизвестными и не получают права автоматического повтора.

Допуск валидирует автора, задачу и время сохранённого комментария против каждого
удерживаемого предшественника. Retry валидирует компанию, задачу и агента
выбранного упавшего прогона и сохраняет идентичность этого прогона через допуск
и загрузку истории. Дублирующиеся запросы Retry принимают того же преемника.
Комментарий агента, старый запрос из очереди или общий системный wake не могут
снять удержание. Задача-источник сохраняет назначенного исполнителя. Владение
процессами, активные контроллеры, lease очистки, пауза, согласование, бюджет и
обычные гейты исполнения продолжают действовать. Режим интеракции
«зависимость-заблокирована» остаётся ограничен своим контрактом
ответа/сортировки.

Снятие удержаний, аудиторская запись и новый прогон фиксируются вместе под
блокировкой задачи. Новый ход использует свежую сессию провайдера и сохраняет
последний запрос пользователя, историю задачи, завершённую работу и уведомление
о прерывании. Он не получает инструкции повторять старые вызовы инструментов.
Позднейшие сообщения не могут сбросить бюджет повторов старого инцидента или
создать ещё одну автоматическую замену для него.

Явное продолжение проверяет локальные идентичности процессов для локальных
прогонов. Удалённые прогоны вместо этого требуют квитанцию остановки провайдера
для каждого lease, с успешной очисткой и без активного владения. Это относится
и к по-ходовым, и к тёплым нативным раннерам. Квитанция остановки снимает только
устоявшегося владельца очистки для этой точной компании, прогона, провайдера и
ресурса сэндбокса, не меняя его чекпоинт и записанные исходы действий.
Независимые удалённые сэндбоксы имеют отдельные гейты очистки, включая случай,
когда один прогон владеет несколькими сэндбоксами. Успешные повторные попытки
ожидающей очистки сохраняют ту же квитанцию и пересматривают отложенные
сообщения пользователя; сбой доставки никогда не откатывает успешную очистку
провайдера. Проваленный чекпоинт не мешает уничтожению изолированного сэндбокса
терминального прогона; занятое владение всё равно мешает. Отсутствующие
квитанции и проваленная очистка сохраняют удержание. Старые провайдеры, не
возвращающие квитанцию, остаются поддерживаемыми, но не могут авторизовать
удалённое продолжение. Терминальный статус в базе или проверка PID не на том
хосте недостаточны. Ни одна историческая задача не пробуждается этим изменением
автоматически.

Стартап ждёт инициализации провайдерного плагина перед удалённым восстановлением
и очисткой lease. Заметка о блокировке задачи предлагает Retry, а отказной Retry
показывает фактическое удержание восстановления. Каждый явный Retry пользователя
может сделать одну попытку очистки в области своего упавшего прогона, даже
после исчерпания автоматической очистки. Если эта попытка провалилась, более
поздний Retry пользователя может попробовать снова после восстановления
провайдера. Проваленная очистка сохраняет удержание исполнения на месте. Retry
не сбрасывает автоматический лимит и не чистит lease чужой задачи. Перед
допуском нового разговора остановка провайдера всё равно должна быть
подтверждена.

### Явное действие восстановления

Paperclip открывает явное действие восстановления, когда система может
определить проблему, но не может безопасно завершить работу сама.

Примеры:

- автоматический повтор осиротевшей работы уже исчерпан
- граф зависимостей имеет невалидного/невызываемого владельца, ненаначенного
  блокера или невалидного участника ревью

Действие восстановления по умолчанию остаётся в области действия источника.
Эскалация осиротевшей задачи принадлежит доске и записывает причину,
доказательства, следующее действие, исходного и возвращаемого владельца,
`routingPolicy: board_escalation_no_takeover_v1`, политику побудки или монитора
в треде/детальной поверхности источника.

Доска владеет решением о восстановлении, а не исходным результатом. Автоматическое
восстановление обязано сохранить оба поля исполнителя источника. Только явное
решение оператора или применимая политика серьёзного сбоя может передать
результат.

Апгрейд может встретить уже активное принадлежащее агенту действие восстановления.
Paperclip сохраняет эту запись читаемой и разрешимой для совместимости, но
периодический реконсайл не ставит в очередь ещё один wake-захват из неё.

Создавайте привязанное к задаче действие восстановления, только когда отдельная
задача — правильный объект исполнения. В этой резервной форме задача-источник
остаётся видимой и блокируется на задаче восстановления, когда блокировка нужна
для корректности. Владелец восстановления обязан восстановить живой путь, вручную
закрыть задачу-источник, делегировать реальную последующую работу или записать,
почему сигнал — ложное срабатывание.

### Эскалация человеку

Эскалация человеку требуется, когда следующее безопасное действие зависит от
суждения доски, политики бюджета/согласования или информации, недоступной
плоскости управления.

Примеры:

- исходный владелец на паузе, удалён, ожидает согласования или заблокирован
  бюджетом
- задача принадлежит человеку, а не агенту
- прогон намеренно тих, но требует решения оператора перед отменой или
  продолжением

В этих случаях Paperclip должен оставить видимый след в задаче/комментариях,
а не молча повторять.

## 14. Что это не значит

Эти семантики не превращают V1 в систему автопереназначения.

Paperclip по-прежнему не:

- автоматически переназначает работу другому агенту
- выводит семантику зависимостей только из `parentId`
- трактует работу в руках человека как исполнение под heartbeat-менеджментом

Модель восстановления намеренно консервативна:

- сохранять владение
- использовать специфичный для причины лимит, когда плоскость управления потеряла
  непрерывность исполнения; намеренные ожидания без цели используют пять
  отпечатанных ремонтов диспозиции исходным владельцем
- открывать принадлежащее доске действие восстановления, когда лимит исходного
  владельца исчерпан или небезопасен
- эскалировать видимо, когда система не может безопасно продолжать

## 15. Практическая интерпретация

Для оператора доски предполагаемый смысл такой:

- `in_progress` за агентом должен означать «это живая работа или ясно показанная
  проблема»
- `todo` за агентом не должен оставаться назначенным навсегда после краха без
  оставшегося пути побудки
- родитель/подзадача объясняет структуру
- блокеры объясняют ожидание

Это и есть контракт исполнения, который Paperclip должен показывать операторам.

### Отмена во время нативного старта

Отмена записывает барьер подготовки, удерживая блокировку строки прогона. Выбор
нативного рантайма проверяет этот барьер, статус running и текущий lease
стартап-контроллера в той же транзакции, что создаёт нативного координатора.
Нативный исполнитель перепроверяет отмену и терминальный статус при захвате
координатора, до старта или прицепления провайдера.

Отменённый стартап может продолжиться от более нового аутентифицированного
сообщения пользователя после очистки. Сервер требует либо его явный барьер
«до выбора», либо незахваченного нативного координатора (ноль попыток и
поколений контроллера, без контроллера, lease и результата). Он также проверяет
противоречащие доказательства запуска/процесса и верифицирует локальную очистку
или точные квитанции удалённой остановки. Подготовщик должен был завершиться
или его lease стартапа должен истечь. Один отсутствующий PID сам по себе этого
не доказывает.

Существующий ограниченный воркер сохранённых сообщений перепроверяет это
доказательство после рестарта. Допуск атомарно закрывает незахваченный
координатор и допускает один свежий ход, сохраняя историю, неизвестные исходы
действий и счётчики попыток. Паузы, согласования, бюджеты, владение задачей и
терминальный статус задачи продолжают гейтить допуск. Автоматический повтор
провайдера отменённым стартапом не авторизуется.

### Доставка сообщений из очереди после остановки легаси-прогона

Легаси-действие Interrupt для сообщений из очереди принимает null `targetRunId`,
когда нет активного хода. Оно валидирует идентичность и ревизию очереди под
блокировкой задачи и записывает долговечное намерение доски отправить сохранённую
очередь. Прогон, остановившийся между чтением очереди и кликом, тоже
принимается. Сервер никогда не перенаправляет прерывание на посторонний активный
прогон. Намеренное прерывание не показывает глобальный тост отменённого/упавшего
прогона; элемент управления очереди сам даёт обратную связь о доставке.

Этот клик может авторизовать свежий разговор для сообщений, написанных до
остановки предыдущего прогона. Он сохраняет исходное содержимое и авторов
сообщений, доказательства остановки процессов/lease, владение задачей, паузы,
согласования и бюджетные проверки. Правки и сбросы очереди остаются
авторитетными до диспетчеризации. Диспетчеризация перепроверяет потреблённую
квитанцию очереди против оператора, задачи, агента, сообщения и прогона-
преемника; оператор не обязан быть автором сообщения. Повторные попытки доставки
не могут создать второго преемника после потребления очереди. Нативный
same-turn steer сохраняет свой контракт активной цели.

Легаси-финализация повторяет отложенный ввод после очистки адаптера и lease.
Планировщик также пересматривает ограниченными батчами осиротевшие очереди после
рестарта или позднего добавления. Оба используют обычный допуск; существующий
преемник из очереди владеет следующим ходом ещё до захвата блокировки исполнения
задачи. Удержание восстановления не блокирует недоставленное сообщение
пользователя в долговечной очереди. Сервер валидирует сохранённый комментарий и
его автора, даже если очередь началась с системного wake. Затем он может начать
свежий легаси-разговор после доказательства остановки старого процесса. Он
сохраняет неизвестные исходы действий и не повторяет комментарии, уже
доставленные упавшему прогону. Обычный Stop оператора всё равно требует нового
действия пользователя. Гейт преемника действует в области того же агента, поэтому
участие в ревью другого агента сохраняет свой независимый путь восстановления.

Явный Interrupt по сообщению из очереди также даёт одну повторную
попытку очистки в области остановленного прогона. Старые эфемерные lease, чья очистка
предшествует квитанциям остановки провайдера, перепроверяются через записанный
путь teardown провайдера. Сохранённые ресурсы и сэндбоксы, принадлежащие другому
lease, так не перепроверяются. Доставка всё равно требует проверенной квитанции
остановки провайдера. Периодические повторные попытки очереди не получают
дополнительных попыток очистки, и очередь показывает причину ожидания сервера,
пока очистка не разрешена.

Легаси-уведомление о восстановлении задачи показывает «Автоматическое
восстановление этой задачи остановлено.» в рамочном контейнере с Retry для
упавшего или истёкшего по таймауту прогона. Проваленный Retry показывает свою
ошибку в том же контейнере. Новые сообщения пользователя и сохранённые
недоставленные сообщения проходят обычный допуск независимо от исчерпания
автоматического восстановления.

### Идентичность оператора и права на ручную диспетчеризацию

Легаси-Interrupt по сообщению из очереди — новая инструкция от пользователя,
который его нажимает. Новый прогон использует исполнительскую идентичность этого
пользователя, включая случай, когда сообщения из очереди написал кто-то другой.
Тела сообщений и исторические авторы остаются неизменными. Страница задачи и
пайплайн-разговоры разрешают Interrupt после остановки целевого прогона и
отправляют текущую ревизию очереди.

Стартап валидирует потреблённую квитанцию очереди против нового прогона,
компании, агента, задачи, нажавшего пользователя и ID доставленных сообщений.
Автоматические попытки наследуют получившуюся исполнительскую идентичность через
обычную историю идентичности прогонов.

Запуск существующего агента требует `agent:wake`, которое есть у всех активных
невьюерных участников доски внутри своей компании. Обе конечные точки wake
используют это действие вместо `agents:create`. Точный Retry задачи также
проверяет `issue:comment` на задаче из сохранённого упавшего прогона и
верифицирует, что назначенный агент не менялся. Повторы внешнего чата сохраняют
свою дополнительную авторизацию разговора. Обычные запросы wake на доске также
сохраняют идентичность нажавшего пользователя, поэтому принятие
сообщения из очереди другого автора не может изменить его исполнительские полномочия. Если
такой wake сливается в более старый отложенный запрос, та же транзакция
обновляет исполнительского инициатора запроса на нажавшего пользователя. Запросы
ручного wake ждут собственный прогон и исполнительскую идентичность. Они не
сливаются в активный прогон агента — ни с задачей, ни без. Приватные разговоры
агентов сохраняют проверки wake и retry только-владельцем.

Эти действия не дают права нанимать агентов или менять их настройки. Каждое
действие во время исполнения всё равно проверяет полномочия агента и
ответственного пользователя. Отказанный retry возвращается до диспетчеризации;
он не создаёт нового упавшего прогона и не меняет состояние задачи.

### Владение при рестарте нативного контроллера

Контроллер сохраняет идентичность процесса новорождённого раннера до ожидания
старта провайдера. Резкий выход контроллера во время открытия сессии тогда
восстанавливается через те же проверки точной идентичности процесса, что и
активный ход.

И graceful, и hot рестарты отцепляют старый контроллер от нативных сессий. Если
выключение начинается во время открытия сессии провайдера, её eventual-публикация
учитывает ожидающее отцепление до диспетчеризации хода. После отцепления старый
финализатор исполнения не может приостановить или просигналить долговечный
раннер: следующий контроллер обязан восстановить его через аутентифицированные
проверки владения. Это сохраняет активную работу и сообщения из очереди, не
трактуя рестарт сервера как отмену пользователем.

До выхода любого из путей выключения простаивающие тёплые сессии закрываются
через свой обычный путь suspend-and-checkpoint. Удалённые сессии поэтому
оставляют проверенную резервную авторитетность следующему контроллеру, хотя их
последний прогон уже завершён. Занятые сессии используют адопцию активного
прогона, пока активны; если ход завершается во время выключения, его освобождение
чекпоинтит сессию перед возвратом, не оставляя нового простаивающего владельца.
Если чекпоинт провален, сохранённое состояние продолжает блокировать
непроверенное переиспользование.

### Непрерывность тёплого сэндбокса

Привязка общего воркспейса тёплого сэндбокса сохраняется независимо от
экспериментального UI изолированных воркспейсов. Обычные обновления воркспейса
остаются гейтованными; рантайм может привязать только валидированный общий
воркспейс в компании и проекте задачи. Последующие работы поэтому переиспользуют
тот же сэндбокс и сессию провайдера. Стейдженный пакет провайдера
переиспользуется только после полной проверки ожидаемых манифеста и хэшей
артефактов. Отсутствующий, изменённый или несовместимый пакет обязан быть
заменён и проверен до запуска.

Безопасная нативная замена может снять статус Blocked только с долговечной
квитанцией, что именно этот упавший прогон спроецировал эту точную версию
статуса. Явное переутверждение Blocked или изменение его блокеров двигает версию
статуса, даже если отображаемый статус не изменился. Добавление сообщения в очередь
комментария не меняет этой авторитетности. Более поздняя блокировка также
подавляет замену на гейтах запланированной, отложенной в очереди и финальной
диспетчеризации. Отложенная в очереди и финальная диспетчеризация нативной замены также
перечитывает готовность зависимостей, потому что новые зависимости не обязаны
менять отображаемый статус задачи. Старые заблокированные строки без квитанции
остаются удержанными; исторический бэкфилл статусов не выполняется.

### Ввод из очереди после нативного Stop

Run-only Stop завершает текущий ответ. Он не отбрасывает сообщения из очереди
пользователя и не требует инцидента восстановления. После освобождения владения
контроллером и появления проверенной записи остановки старого локального процесса
или удалённого окружения Paperclip отправляет сохранённый ввод через обычный
допуск задачи, один раз, с полномочиями исходного пользователя. Паузы, владение
задачей, бюджеты, согласования и удержания восстановления исполнения продолжают
действовать. Неподтверждённая очистка не начинает работу.

Активная сессия объявляет steer только когда её драйвер его поддерживает.
Транспорт, отклоняющий steer, не даёт этой способности. Управление сообщениями очереди
остаётся смонтированным, пока сервер не примет steer-запрос, поэтому
отклонённое действие последней строки сохраняет своё сообщение и видимую ошибку.

### Сохранение работы при передаче и доставка запрошенных файлов

Передача агента несёт преемнику авторизованную историю задачи прерванного
прогона, завершённые семантические действия и доступную сводку результата.
Преемник обязан осмотреть существующие файлы и сохранить завершённое содержимое
до правок. История источника всё ещё в области действия той же компании и задачи;
прежние результаты — недоверенные доказательства, а не инструкции и не новая
авторизация. Сохранённые комментарии задачи переезжают в квитанцию доставки
преемника той же транзакцией, что ставит её в очередь. Их исходные авторы
остаются нетронутыми. Обычная побудка комментарием бывшего исполнителя не должна
запускать ещё одно исполнение или переоткрывать завершённую задачу после
финиша преемника. Упоминания, доставки в чат и выделенные продолжения интеракций
сохраняют свои отдельные контракты доставки.

Запрошенный файл завершён, когда пользователь может его получить. Нативные
раннеры обязаны зарегистрировать запрошенные выходные файлы до отчёта Done и
сослаться на получившееся вложение в своём ответе. Обратная связь завершения
отклоняет ссылки только-на-воркспейс-файл и сфабрикованные или чужие квитанции
доставки. Текстовые ответы и доступные репозиторные рабочие продукты вложения
не требуют. Сбой публикации требует продолжения работы или конкретного блокера,
а не человеческого подтверждения, что задача завершена.

Для явного файлового вывода в текущем запросе пустой отчёт, ссылка
только-для-верификации или незарегистрированный URL не могут закрыть доставку.
Отчёт обязан сослаться на вложение, верифицированное долговечной квитанцией
публикации текущего прогона и совпадающее по задаче, имени файла, размеру и
SHA-256, либо на доступный рабочий продукт, зарегистрированный этим прогоном
с опубликованным URL. Вывод прежнего прогона не может заменить заново
запрошенный файл. Рестарт контроллера в том же прогоне сохраняет квитанцию;
замена может осмотреть и перерегистрировать сохранённые байты воркспейса без
участия пользователя в бухгалтерии. Последующие запросы без нового файла всё ещё могут
ссылаться на существующие загрузки. Прежние загрузки также могут сопровождать
валидный текущий вывод как контекст. Авторизованное переиспользование чат-
вложения снабжает проверенный клон квитанцией публикации текущего прогона; более
старые квитанции переиспользования обязаны дополнительно совпадать с нетронутым
привязанным к компании источником по имени, размеру и хэшу. Один локатор
`workspace_file` — не доказательство доставки: он не верифицирует файл и не
сохраняет его байты после очистки. Чтение или ревью существующего файла для
ответа инлайн не требуют загрузки этого входа. Неоднозначная проза остаётся
под контрактом завершения раннера; явная проверка сервером вывода намеренно
узкая.

Локальные и удалённые раннеры используют один контракт публикации вложений.
Удалённые файлы читаются через привязанный раннер окружения с конфайнментом
воркспейса, без симлинков и хардлинков, стабильной идентичностью файла, границей
10 МиБ и точными проверками размера и SHA-256 до хранения. Удалённые пути
никогда не открываются на контроллере.

Сбой асинхронного удалённого сигнала, включая уже удалённый оператором сэндбокс,
не должен ронять контроллер. Логирование этого сбоя тоже обязано быть
контейнированным. Отклонённый сигнал не доказывает остановку: существующие
мониторинги процесса и провайдера по-прежнему владеют подтверждением остановки
и доказательством очистки.

Обработка протокольного сбоя может начать транспортную очистку до того, как
владеющий рантайм её ждёт. Этот фоновый вызов немедленно наблюдает отклонение,
включая случай, когда удалённый сэндбокс уже исчез. Ожидаемое владельцем
закрытие всё равно получает исходный сбой; контейнирование никогда не
фабрикует успешное закрытие или право переиспользовать непроверенное исполнение.

### Назначенные соединения в нативных ACPX-сессиях

Нативные ACPX-сессии регистрируют назначенный MCP-шлюз Paperclip рядом с
задачным мостом инструментов. Вызовы шлюза сохраняют существующие гранты
соединений и согласования действий. Отсутствующие назначенные привязки и имена,
коллидирующие с задачным мостом, останавливают допуск. Апстрим-креды остаются
у шлюза; провайдеры получают его привязку доступа с той же областью действия. Квалифицированный
ACPX-сайдкар получает имя шлюза, URL и токен вместе через allowlist запуска;
посторонние секреты окружения остаются исключёнными. Это не ограничивает
произвольный сетевой доступ к публичному сервису вне шлюза.

### Используйте реальные запросы соединения (2026-09-14)

Когда пользователь просит подключить известный сервис, агент находит этот сервис
и использует `connection_request`, если нужна настройка. Агент не должен снова
спрашивать то же разрешение или копировать «Подключить / Не сейчас» в общий
вопрос. Общий вопрос не начинает настройку. Реальная карточка соединения держит
вместе идентичность пользователя, гранты доступа, решение и продолжение. Это
руководство не одобряет соединение и не обходит его обычное решение пользователя.

## Ответы, отправленные во время активного прогона

Подтверждение, подтверждение чекбоксов или ответ на вопрос — это новый ввод
разговора. Разрешение карточки записывает решение немедленно; оно не прерывает и не
перенаправляет (steer) агента, который делает работу. Его типизированная побудка продолжения
ждёт за активным исполнением задачи и появляется в очереди сообщений.

Очередь проецирует исходную разрешённую интеракцию как неизменяемый ответ.
Она сохраняет выбранные ответы и принятую ревизию документа; она не создаёт
редактируемый комментарий, который мог бы тихо изменить одобренное. Обычные
сообщения сохраняют существующее поведение правки, сброса и переупорядочивания.

- Обычное завершение прогона поднимает сохранённый ответ один раз. Стартовый
  скан также находит осиротевшие квитанции интеракций после высвобождения
  блокировки исполнения задачи.
- **Steer** явно доставляет сохранённый ответ в совместимый нативный ход.
  Подтверждение потребляет квитанцию, поэтому повтор не может создать вторую
  доставку. Он сохраняет исполнительскую идентичность существующего прогона.
- **Interrupt** останавливает легаси-ход и начинает продолжение с типизированным
  ответом. Нативные согласования планов, требующие свежей сессии, тоже
  используют Interrupt; steer не может превратить сессию планирования в сессию
  исполнения. Существующие гейты остановки процесса, очистки окружения,
  владения и восстановления продолжают действовать.
- Если провайдер заблокирован на исходном нативном запросе вопроса, ответ
  разрешает этот запрос инструментов напрямую. Он не должен ждать за
  заблокированным ходом.

Агент может завершить передачу ревью уже после того, как пользователь ответил
на его карточку. Разрешённая карточка того же прогона-источника или её
продолжение из очереди — валидный живой путь. Устаревшая передача от агента человеку не
может отменить прогон и осиротить ответ из очереди. Это не делает старую
разрешённую карточку путём ревью для более позднего прогона и не мешает явному
переназначению на доске.
