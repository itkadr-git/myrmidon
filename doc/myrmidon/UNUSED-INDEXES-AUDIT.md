# Реестр и классификация неиспользуемых индексов базы данных Myrmidon (DB-AUDIT)

Документ подготовлен в рамках задач **OPE-12580** и **OPE-13055** (подзадачи родительской задачи **OPE-12979**).
Регламентирует аудит индексов со значением `idx_scan = 0` (по данным `pg_stat_user_indexes`), обоснования их сохранения или удаления, статус контрольного замера и проверяемые исключения.

---

## 1. Контекст и динамика аудитов

Критерий `unused-indexes` в модуле `datastore-care` (DBC-4) проверяет долю и совокупный объём неиспользуемых индексов:
- Порог: **доля ≤ 20 %** и **объём ≤ 512 MiB**.
- В случае превышения порога доли критерий приёмки задачи допускает: **доля ≤ 20 % либо документированное обоснование каждого оставшегося индекса**.

### Динамика по релизам:
- **1.6.5**: 730 из ~1010 неиспользуемых (72 %, ~98 МБ).
- **1.6.6**: 692 из 1208 неиспользуемых (57.3 %, 602 MiB).
- **1.6.7**: 667 из 1208 неиспользуемых, 628 MiB.
- **Миграция 0477 (OPE-12580, PR #2836)**: удалены 4 крупнейших неиспользуемых индекса (~527 MiB):
  - `activity_log_company_responsible_user_created_idx` (293 MiB)
  - `secret_access_events_company_credential_owner_idx` (201 MiB)
  - `heartbeat_runs_company_ctx_taskkey_created_idx` (22 MiB)
  - `cost_events_company_biller_occurred_idx` (11 MiB)
- **1.6.8 (исходный замер 13.11.2026, коммит `4e84921b0d`, инстанс 1.6.7-rc.30)**:
  - Всего индексов в `pg_stat_user_indexes`: **1208**.
  - Неиспользуемых (`idx_scan = 0`): **658** (суммарный объём **410 MiB**).
  - По объёму критерий выполнен: **410 MiB ≤ 512 MiB** (норма).
  - По доле: 54.5 % > 20 %.

### Источник истины и границы утверждений
- Исходный аудит 13.11.2026 зафиксировал агрегатные показатели на бою (`1208` всего, `658` неиспользуемых, `410 MiB`), однако сырой дамп таблицы `pg_stat_user_indexes` со всеми 658 именами в репозитории отсутствует (выгрузка производилась в рамках операционного отчёта `6508d1cc-f141-4bb1-9f22-5a57832dfb16` в OPE-12979).
- В связи с этим репозиторий не содержит поимённого списка всех 658 строк выборки `idx_scan = 0`, и любое утверждение о полном 1:1 поимённом реестре именно неиспользуемых индексов замера является неподтверждённым.
- Настоящий документ фиксирует:
  1. Безопасное удаление подтверждённого балласта (3 индекса `secret_access_events`, миграция 0483);
  2. Проверяемые категории обоснованных исключений для подтверждённого набора индексов с конкретными примерами из схемы Drizzle (`packages/db/src/schema/`);
  3. Статус контрольного замера как невыполненного до выката релиза оператором ADM.

## 2. Безопасные неиспользуемые индексы к удалению (Миграция 0483, OPE-13055)

Индексы, по которым полный статический анализ кодовой базы (`server/src/`, `packages/`) подтвердил отсутствие каких-либо поисковых запросов (0 ссылок в проде и тестах), и удаление которых безопасно:
1. `secret_access_events_consumer_idx` (`company_id`, `consumer_type`, `consumer_id`)
2. `secret_access_events_run_idx` (`heartbeat_run_id`)
3. `secret_access_events_user_definition_created_idx` (`user_secret_definition_id`, `created_at`)

### Обоснование удаления:
Таблица `secret_access_events` является наиболее интенсивно пополняемой таблицей аудита (до 1.5–3.6 млн записей в сутки до фикса OPE-12890). Кодовые ссылки в проде и тестах обращаются к таблице исключительно:
- по окну `(company_id, created_at)` в attention feed (обслуживается индексом `secret_access_events_company_created_idx`);
- по `(secret_id, created_at)` при аудите конкретного секрета (обслуживается индексом `secret_access_events_secret_created_idx`);
- по `created_at` при регламентной очистке устаревших событий (retention).

Ни один запрос в кодовой базе не использует колонки `consumer_type/consumer_id`, `heartbeat_run_id` или `user_secret_definition_id` для выборки. Удаление этих трех индексов снимает паразитную нагрузку на дисковый ввод-вывод (write amplification) на наиболее горячей таблице системы.

## 3. Проверяемые категории исключений для подтверждённого набора индексов

Так как полный дамп неиспользуемых индексов с продакшена недоступен, проверяемые исключения классифицируются по функциональным категориям схемы с привязкой к конкретным DDL-определениям в кодовой базе (`packages/db/src/schema/`).

### 3.1. Индексы, зависимые от планов выполнения (EXPLAIN-кандидаты)
- **Индексы**: `heartbeat_runs_company_ctx_paperclip_issue_created_idx` и смежные expression-индексы на `context_snapshot`.
- **Обоснование**: В продакшене запросы к `heartbeat_runs` используют сложные выражения с `coalesce` по нескольким контекстным полям. Удаление таких индексов на основе `idx_scan = 0` без анализа `EXPLAIN (ANALYZE, BUFFERS)` на реальных объёмах данных грозит резкой деградацией производительности ключевых запросов планировщика.
- **Статус**: Анализ планов выполнения и принятие решения о целесообразности DROP переданы в родительскую задачу **OPE-12979**.

### 3.2. Первичные ключи (PRIMARY KEY)
- **Характер**: Суррогатные и составные первичные ключи (`*_pkey`), создаваемые декларациями `primaryKey()` в схеме Drizzle.
- **Обоснование**: Первичный ключ обеспечивает уникальность записей, физическую адресацию строк и реляционную целостность базы данных. Значение `idx_scan = 0` на первичных ключах таблиц-логов или промежуточных очередей закономерно при отсутствии точечных выборок по ID, но удаление PK технически недопустимо.

### 3.3. Ограничения уникальности (UNIQUE)
- **Характер**: Уникальные индексы и ограничения (`uniqueIndex()`, `unique()`), обеспечивающие бизнес-инварианты уникальности на уровне СУБД.
- **Обоснование**: Уникальный индекс валидирует данные при операциях `INSERT` и `UPDATE`. Отсутствие сканирований (`idx_scan = 0`) в окне статистики не означает невостребованность ограничения — его удаление приведёт к деградации контроля целостности данных и появлению дублей.
- **Подтверждённые примеры из схемы**:
  - `budget_incidents_policy_window_threshold_idx` (`packages/db/src/schema/budget_incidents.ts`, миграция 0034): частичный `uniqueIndex` (`WHERE status <> 'dismissed'`), защищающий единственность активного инцидента бюджета по политике и временному окну.
  - `environments_name_idx` (`packages/db/src/schema/environments.ts`, миграция 0105): `uniqueIndex`, защищающий уникальность имени окружения.
  - `environments_local_driver_idx` и `environments_managed_sandbox_idx` (`packages/db/src/schema/environments.ts`, миграция 0105): частичные `uniqueIndex`, реализующие инвариант синглтона локального драйвера и песочницы.
  - `agent_wakeup_requests_*_idempotency_uq` (миграции 0206, 0226, 0247, 0249, 0260, 0401): частичные индексы идемпотентности пробуждения агентов.

### 3.4. Покрытие внешних ключей (Foreign Key Covering)
- **Характер**: Индексы на внешних ключах (`reference()` в Drizzle).
- **Обоснование**: В PostgreSQL отсутствие индекса на внешнем ключе приводит к тому, что операции `UPDATE` или `DELETE` на родительской таблице вызывают полный последовательный скан (`Seq Scan`) и блокировку (`ShareRowExclusiveLock`) дочерней таблицы. Даже если прикладные `SELECT`-запросы не используют данный индекс (что даёт `idx_scan = 0`), его удаление создаёт угрозу взаимных блокировок и деградации транзакционной производительности.
- **Подтверждённые примеры из схемы**:
  - `adapter_auth_sessions_environment_idx` -> `environments(id)`
  - `agent_api_keys_company_agent_idx` -> `companies(id)`
  - `agent_castes_company_idx` -> `companies(id)`
  - `agent_config_revisions_agent_created_idx` -> `agents(id)`

### 3.5. Индексы регламентных процедур, очередей и retention
- **Характер**: Индексы по колонкам `created_at`, `status`, `scheduled_at`, используемые периодическими воркерами фоновой очистки и архивации.
- **Обоснование**: Периодичность выполнения регламентных задач (раз в сутки, раз в неделю или по расписанию) может превышать интервал сброса статистики `pg_stat_reset()`. В результате индекс фиксируется как `idx_scan = 0`, несмотря на его необходимость во время прогона задач обслуживания.

### 3.6. Опциональные расширения и неактивные плагины
- **Характер**: Индексы модулей дистрибутива Myrmidon, которые не активированы в базовой конфигурации инстанса (например, `chat_teams_file_transfers`, `cli_auth_challenges`, `plugin_database_namespaces`).
- **Обоснование**: Таблицы поставляются в составе стандартной схемы, но не наполняются данными в инстансах без подключения соответствующих модулей.

## 5. Методика контрольного замера после выката (для ADM / OPE-12979)

После вливания PR #3138 и применения миграции 0483 на боевой базе оператор ADM выполняет следующие контрольные запросы:

### SQL-запрос 1. Проверка фактического удаления целевых индексов
Ожидаемый результат: **0 строк** (все три индекса отсутствуют).
```sql
SELECT indexname, tablename
FROM pg_indexes
WHERE indexname IN (
  'secret_access_events_consumer_idx',
  'secret_access_events_run_idx',
  'secret_access_events_user_definition_created_idx'
);
```

### SQL-запрос 2. Контрольный замер общей доли и объёма неиспользуемых индексов
```sql
SELECT
  count(*) AS total_indexes,
  count(*) FILTER (WHERE idx_scan = 0) AS unused_indexes,
  round(100.0 * count(*) FILTER (WHERE idx_scan = 0) / count(*), 2) AS unused_share_pct,
  pg_size_pretty(sum(pg_relation_size(indexrelid)) FILTER (WHERE idx_scan = 0)) AS unused_bytes
FROM pg_stat_user_indexes;
```

**Ожидаемый результат (гипотеза)**:
- Общее число неиспользуемых индексов должно снизиться как минимум на 3 (с 658 до 655 относительно замера 13.11).
- Фактический вывод запросов сохраняется в родительской задаче **OPE-12979** для окончательной верификации снижения доли.
